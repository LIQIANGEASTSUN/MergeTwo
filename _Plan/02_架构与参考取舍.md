# 架构与参考取舍

建议采用 ProjectIdea 已固定的 Command／Operation 执行机制，在二合内实现普通 C# 规则，UGUI 表现消费结果。HomeHub 是骨架参考，旧 Lua 是业务证据，三合是局部经验来源。所有推荐仍是讨论稿，已确认的产品范围见 [09](09_决策与接续记录.md)。

原设计的 Entity、EntityView、两侧 Function、Command、AtomicOperation 及完整执行／生命周期说明，统一见 [02a 逻辑表现分离架构详解](02a_逻辑表现分离架构详解.md)。本页专门解释新二合采用哪些部分、增加哪些约束，不能把这里的适配选择反推为原架构的通用要求。

## 选择的是复用范围

这里先比较工程接入范围。建议采用 ProjectIdea 文档内部已固定的队列／Batch 语义；这仍是本次方案建议，用户可以决定改变。若要改变，应明确记录契约差异，不能继续把它称为未经修改的参考核心。

| 方案 | 优点 | 工作量与风险 | 建议 |
| --- | --- | --- | --- |
| 以现有 MergeCore 扩展二合模式 | 立即获得实体、系统和 Proxy | 表面工作中，实际需剥离三合地图、合成收集、HungUp、动画 ACK、Profile；可能影响宿主三合 | 不推荐作为本轮基线 |
| 二合独立模块，按规范移植最小核心 | 边界清楚，业务和资源可独立验收；不牵动现有玩法 | 中等；需要自己的规则、适配和小型表现实现 | **推荐** |
| 先从多个项目提取通用玩法框架，再实现二合 | 多玩法可统一维护核心 | 高；需要跨仓库版本、依赖及迁移验证，范围大于当前独立棋盘 | 等出现真实跨玩法复用任务再做 |

不恢复旧 Lua 框架。旧包的 AppServices、PanelManager、协议和脚本 GUID 不是宿主项目运行基础设施。

## 模块职责

| 模块 | 负责 | 写入权限 |
| --- | --- | --- |
| Host／Facade | 打开、隐藏、关闭、配置与 Profile 装配、资源就绪、系统时间输入、外部边界 | 应用生命周期；通过 Command 请求业务修改 |
| CommandRuntime | FIFO、重入、注册、Batch 执行和诊断 | 队列和运行时门禁 |
| Logic | 棋盘、物品、能力、生成、时间、撤销；消费意图 | Operation.Apply 内写自身状态 |
| ConfigAdapter | 旧 JSON → 已校验、只读配置 | 仅构建配置；不保存玩家数据 |
| ProfileAdapter | 加载稳定状态、发布已完成状态快照、请求现有 Profile 落盘 | 二合 Profile 的唯一接入写入口 |
| Graphic | View、输入命中、拖拽跟手、Tween、图标、表现冲突和资源池 | 仅表现状态 |
| ExternalAdapter | 后续宿主钱包、奖励、活动、广告等 | 只调用其权威 API，不让它们反向操纵 View |

这些是职责，不要求每行都有一个抽象基类、Manager 或单独程序集。规则简单时先用直接方法；不引入 ECA／BT／ECS。生成器的时间状态可用明确字段和状态转换表达，不必先写通用 FSM 编辑器。

## 执行主线

```mermaid
sequenceDiagram
    participant UI as 输入与应用入口
    participant RT as CommandRuntime
    participant C as 业务 Consumer
    participant B as OperationBatch
    participant S as Logic 状态
    participant P as ProfileAdapter
    participant G as Graphic
    UI->>RT: SubmitCommand(稳定目标与参数)
    RT->>C: FIFO 出队并解释
    C->>S: 只读校验与求解
    C->>B: 完整求解后一次登记业务操作
    RT->>B: End
    B->>S: 按序同步 Apply
    Note over B,S: 已登记操作全部 Apply 成功；完整性由收集约束保证
    RT->>P: 二合接入扩展：发布稳定快照
    RT->>G: Play(batch)
    G-->>RT: 同步消费结果
    RT-->>UI: 同步结果或重入入队结果
    Note over G: 动画可随后完成或取消
```

Profile 发布位置是本玩法新增接入工作，见下一节；图不能被理解为现成 CommandRuntime 已有该回调。

## 采用参考核心时应保留的语义

基础接口、FIFO、Batch、Consumer 的失败语义与 bool 含义以 [02a 第 5–6 节](02a_逻辑表现分离架构详解.md#6-atomicoperationbatch-与表现消费) 为准。这里保留对二合取舍最关键的三点：先全部收集／Apply，再表现；失败 Consumer 已登记的操作仍保留；Apply 没有自动回滚，Submit 的 bool 也不是业务成功收据。

原核心允许同类型多个 Consumer、同一批多个 Operation。**下面的“一个业务归属 Consumer、完整求解后一次登记”是二合新增的业务约束**，不是 AtomicOperation 的定义，也不要求其它玩法重写现有多 Operation 流程。

### 收集完整性是业务方的约束

仅有“一个 Consumer”还不够：若先登记扣费，再求落点时抛异常，参考 Runtime 会保留扣费操作并继续 End；该操作 Apply 成功也不能证明一次生成完整成功。

建议二合每个业务命令只有一个可写业务 Consumer：先完成正常校验、局部随机求解、ID 规划及结果构建，最后一次登记已完整构造的业务 Operation，随即返回；登记后不再执行可能失败的业务工作。求解过程不得修改活动状态、余额、ID 分配器或正式随机源。装配时检查这一归属，防止新增第二个消费者分拆经济副作用。

这样无需改变 A／H 的“Consumer 失败继续”契约，也不引入通用回滚框架。若未来确需多个可写消费者协作，必须另行设计收集完整性协议，不能直接放宽此约束。单个业务 Operation 在 Apply 中异常仍可能部分写入，按下面的故障出口关闭实例。

## 二合需要补的两项接入能力

### 完整逻辑结果的提交出口

在上述收集约束成立后，本地存档需要知道“全部必要 Apply 已成功”，不能等动画，也不能看 Submit 的 bool。建议在二合接入版本的 `End 成功 → Play 之前`增加一个明确提交观察点，发布本次成功的状态快照和业务结果。

这是相对规范基础参考实现的**显式接入扩展**，需在实施前确认并单独测试；不静默修改 Consumer 失败、FIFO、Apply 或 Player 算法，不修改 ProjectIdea／TileScape 原文件。纯表现、选择变化、最终资源回收等没有持久变化的请求不必发布新 Profile 快照。

快照发布不得 Submit 新业务、重新 Apply 或触发正常业务校验。提交观察点由 Runtime 接入层统一维护，不让各业务末尾分别登记“保存操作”；避免漏保存和误把未完整收集的 Batch 当成成功。

### 一致性故障收口

基本规则拒绝、表现缺图和状态执行故障分开处理。Apply 异常、提交后不变量检查失败或快照构建／发布失败时，二合宿主需要结构化故障通知，在处理下一条命令前 BeginShutdown 废弃待执行项；保留最后确认快照与故障信息，结束本次实例，按 03 的版本核对结果恢复。发布过程中报错时，不能盲信可能已经替换过的 Profile 当前引用。不能依靠解析日志文本或 bool 推断阶段。

磁盘保存失败属于独立阶段，不能据此回滚已发布状态或再次扣费；落盘策略见 03。A §11、§12.5 已说明一致性恢复服务不在基础 Runtime 内。本方案把它列为二合本地存档的接入工作；在故障发生点通知宿主，确保下一条命令执行前关闭，不等最外层 Submit 返回。Graphic 可恢复错误只刷新表现，不回退已完成逻辑。恢复后不自动重新提交失败请求。

## 对象和能力

两侧 Function 的职责、触发与生命周期以 [02a](02a_逻辑表现分离架构详解.md) 为准。本二合的 [10 Function 与 Effect 建模讨论](10_Function与Effect建模讨论.md) 推荐 Function 继续承载行为实现，Effect 记录可附加的规则影响，通过统一查询参与求解。该选择不改变 Command／Operation 主链，Q11 确认后再更新具体状态模型。

- `ItemEntity` 表达一个物品实例，配置 ID 决定种类／能力。普通物品与生成器可以共用实例模型，专用状态为显式可选数据。
- `BoardState` 与格子结构先作为领域容器；不强制每个格子都建完整 Entity＋Function 树。
- `ItemView` 与 `CellView` 只绑定已确定的逻辑身份与状态。View 的 GameObject 可以回收，业务实例不能由对象池决定寿命。
- 逻辑 Function 与 Graphic Function 分开；只有明确的组合需求才引入两套功能集合。优先让 DropRules、GeneratorRules、RemovalRules 的主链可直接阅读。
- 一个 Operation 可以同步修改多个共同维护不变量的字段；“原子操作”是职责单元，不是自动数据库事务，也不要求“一字段一操作”。

| 来源 | 采用／参考 | 改造或不搬用 |
