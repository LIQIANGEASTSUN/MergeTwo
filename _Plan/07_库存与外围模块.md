# 库存与外围模块边界

本页整理后续接入顺序与需要保留的边界，不把旧包全部功能加入首期。用户已确认先完成独立棋盘。仓库、图鉴、商店、BP 的规格主要来自旧代码与交接文档，仍须按模块讨论。

## 仓库和待领取队列

| 概念 | 建议含义 | 与棋盘的关系 |
| --- | --- | --- |
| 仓库 | 已存在物品实例的另一个容器 | 入仓／出仓保持 ItemInstanceId 与完整专用状态 |
| 待领取队列 | 外部奖励或购买产生的待领取条目 | 是否已分配实例身份要先定；不能与已落盘物品重复统计 |
| 棋盘退役集合 | 已消费物品的表现收尾数据 | 不属于库存，不可入仓 |

入仓在一次业务操作里同时释放格子、改变物品 Location 和修改仓位；出仓则反向执行。容量不足、物品被移除、状态不允许或落点不足时整体拒绝，不由 UI 先删格再尝试放仓库。

L 的 `TwoMergeNetBag.lua` 有暂停时间与取出时修正截止时间的实现，可作为“入仓暂停冷却”的证据，不能据此扩展成全部状态一律暂停。需确认生成器、气泡、开启中的宝箱分别能否入仓、如何计时；新模型用明确 TimerMode／剩余时间，避免反复入出仓累积误差。

待领取只在成功分配位置后移除相应条目；满盘时仍保留。可选合成气泡与衍生物没有落点时不自动变成待领取奖励，见 05。

## 宝箱、使用物和特殊工具

| 能力 | 可参考内容 | 新实现前必须明确 |
| --- | --- | --- |
| 使用物 | R 的使用后销毁并发资源，L UseFunction | 使用与生成互斥、货币权威、满余额／溢出策略 |
| 普通宝箱 | L NormalChestFunction、MergeTwoboxTemplate | 开启等待、固定／随机输出、使用次数、用过后能否合成 |
| 自选宝箱 | L SelectChestFunction、选择面板 | 弹窗关闭不消耗；提交时重验箱子身份、选项及空间 |
| 减 CD 工具 | L ReduceCDFunction | 减少哪个阶段、是否跨轮、无冷却目标时是否消费 |
| “剪刀” | L ShearsFunction 名字与调用链冲突 | 当前源码走目标 nextId 的合成升级，不是已验证的拆分能力；须重新定义实际工具需求 |
| 倍率 | L 倍率提高输出等级并增加费用 | 区分 OutputCount；链尾／资格不足的回退，旧 4× 不保证先降 2× |

工具的接受目标规则进入统一 DropRules，不让多个 Function 按不确定注册顺序抢同一次拖拽。普通使用物属于 M2，宝箱与其它工具可在 M3 或更后单独验收。

## 图鉴与查询

图鉴展示的链、产出来源属于配置查询；“曾经发现”属于持久事实；“目前持有最高等级”属于当前库存派生统计。三者分开，不能用历史图鉴代替生成器出售保护。

建议只在成功创建／获得结果提交后更新首次发现；选择物品和播放图鉴动画不解锁奖励。若未来有发现奖励，奖励已领取标志与发现标志分开定义，避免恢复 Profile 时重复发奖。

## 活动和经济宿主

独立棋盘最终应通过少量应用入口接入，例如 Open／Close／QueryState／SubmitIntent；活动配置传入 BoardDefinitionId 和棋盘实例键，不让活动直接写格子和物品。

| 外围 | 接入职责 | 开始前需要的业务定义 |
| --- | --- | --- |
| 活动生命周期 | 创建期次实例、开放／关闭入口、结束回收 | 跨期存档、过期待领取队列处理、补领奖策略 |
| 体力恢复 | 明确余额与下次恢复时间的权威 | 上限、恢复周期、溢出、暂停／离线、宿主时间来源 |
| 商店／广告／支付 | 完成经宿主确认的购买，再交付奖励 | 价格／库存权威、广告结果、重复回调、购买恢复 |
| BP／任务 | 消费已成功的业务结果，推进外围进度 | 积分归属、任务条件、领取边界；旧 BP 币不直接复用 |
| 引导 | 查询并限制输入，提交正常命令 | 引导存档、关闭恢复、跳过策略，不直接制造物品 |
| 音效／埋点 | 使用成功业务结果和表现节点 | 获取／消耗原因、失败原因；取消动画不重复上报业务结果 |

核心查询可以直接调用。跨模块的完成通知在提交后发送，携带稳定实例与结果信息；订阅者不得反向改当前正在 Apply 的状态。通知需要触发新业务时正常进入 FIFO，并遵守已定义的跨系统提交边界。

接入活动或外围服务时再建立真实需要的接口程序集与 Proxy。M1 只需要测试入口、测试经济和当前 Profile，不为未使用的支付、广告、BP 预建空实现。

## 实现顺序建议

1. **Step 1：在 M2 后确认库存规则。** 决定可入仓类型、计时、待领取的身份与领取顺序；补容器不变量和 Profile 版本。
2. **Step 2：实现仓库与领取。** 一次操作完成位置转换或奖励落盘，覆盖满盘、容量不足、重复领取和关闭恢复。
3. **Step 3：分模块补宝箱／图鉴。** 每个模块先写状态与规则，补实际配置样例，再接 UI。
4. **Step 4：讨论活动与正式经济。** 明确宿主注册、钱包、奖励、时间与存档的完整边界后，再接商店、BP、广告和引导。
