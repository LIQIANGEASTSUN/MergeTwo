# 二合、三合与 Effect 的外部实现调研

检索日期：2026-09-23。目标是为 Function／Effect／State 的选择提供可核验例子，不统计市场占有率。优先采用作者文章、官方说明和源码；没有找到足以证明主流商业二合统一采用某种内部类结构的公开证据。

本页区分 **二合／三合（Merge-2／Merge-3，生成新物品）** 与 **三消（Match-3，匹配清除与补位）**。三消的机关组合有参考价值，但它的回合、掉落和连锁流程不直接成为本次二合需求。

## 可以核验的实现路线

| 路线 | 实际例子 | 对本次的启发 |
| --- | --- | --- |
| 棋盘数据＋行为策略＋生成管道 | Merge2 Core SDK | 二合不必依赖 Unity 对象或先建立通用 Buff 引擎 |
| 邻接集合＋配置升级关系＋连续求解 | Triple Game | 三合的数量／邻接／升级求解与 Effect 建模是两个问题 |
| 棋盘对象＋独立机关层＋统一结算器 | unity-match3 | 土地锁、可移动炸弹、障碍层数可以有不同数据归属 |
| 配置定义＋运行实例＋规则影响 | Unity Buff 作者文章、Epic GAS | 支持动态效果与能力限制，但效果本身仍有状态 |
| 逻辑结果＋独立显示 | Catlike Coding | 分离表现与规则，与是否采用 Effect 没有冲突 |

这些是公开样本中存在的路线，不能据此声称每家商业游戏都按这五种之一实现。

## E01：真实二合的可观察规则

Merge Mansion 官方说明：蛛网物品可与相同物品合成；生成器有独立的产出冷却。它们说明“物品种类、附加限制、生成进度”需要分别表达，但页面没有公开内部 State／Effect／Function 类结构。[蛛网说明](https://support.metacoregames.com/hc/en/merge-mansion/articles/how-do-i-make-use-of-the-items-covered-in-cobwebs-87)、[生成器冷却](https://support.metacoregames.com/hc/en/merge-mansion/articles/why-cant-i-make-any-more-items-by-tapping-69)

对本项目的推论：限制应细分到具体动作；生产能力的次数与冷却不因增加锁效果而丢失。这是本方案的建模判断，不是对该商业游戏源码的描述。也不据其冷却说明覆盖 R 中已有的多轮规则。

## E02：真实三合的土地与物品关系

Merge Dragons 官方明确：死亡土地上的物品不能移动，但可以通过附近同类物品参与合成，土地随之治愈。因此“不能移动＝不能合成”不是普遍规则；土地条件与物品身份也应分别考虑。[官方说明](https://zyngasupport.helpshift.com/hc/en/82-merge-dragons/faq/13773-tip-merge-something-off-dead-land-to-insta-heal-it/?contact=1&p=all&sf101510810=1)

Gram Games 的 Ray Mazza 在 GDC 2019 有开发分享，公开会议信息强调发现、持续游玩和可广泛合成的设计支柱。本轮只核对了会议摘要，未观看完整演讲，也未从它推断内部代码结构。[GDC 会议信息](https://www.gdcvault.com/play/1026075/Design-Philosophies-and-Lessons-from)

## E03：Merge2 Core SDK，实际二合核心源码

[仓库：ArtemVetik/com.agava.merge2](https://github.com/ArtemVetik/com.agava.merge2)。本轮读取 Runtime 下 Board、Item、DefaultMergePolicy、CommandQueue、CooldownCommand、CommandFilter 与 asmdef。

可直接核验：Board 管位置与开放区域；Item 区分实例 Guid 和类型／等级；MergePolicy 校验并合成；点击链组合冷却等命令。程序集设置 `noEngineReferences: true`。[Board 源码](https://github.com/ArtemVetik/com.agava.merge2/blob/main/Runtime/Core/Board/Board.cs)、[MergePolicy](https://github.com/ArtemVetik/com.agava.merge2/blob/main/Runtime/Core/Input/MergePolicies/DefaultMergePolicy.cs)

关键差异：其 CommandQueue 捕获特定 CommandException 后逆序 Undo 已执行项，与本项目参考 Batch“不回滚”的契约不同；Board 还在逐次增删时通知更新。不能整包替换 HomeHub 核心。它的 Item.Next 使用同类型等级加一，也不能替代本项目明确的 nextId 配置关系。[CommandQueue](https://github.com/ArtemVetik/com.agava.merge2/blob/main/Runtime/Core/ClickCommands/CommandQueue.cs)

## E04：Triple Game，实际三合而非三消

[仓库：WilliCommer/triple-game](https://github.com/WilliCommer/triple-game)。作者定位为类似 Triple Town 的 JavaScript 游戏，提供独立引擎及多个显示入口。

源码中 Board.getCluster 用四邻 flood fill 求集合；setFigure 在数量至少为 3 时清理集合，按 figures.growto 升级并继续检查。本轮阅读了三个核心文件的相关链路，未运行游戏。[棋盘集合](https://github.com/WilliCommer/triple-game/blob/master/lib/board.js)、[合成求解](https://github.com/WilliCommer/triple-game/blob/master/lib/triple_game.js)、[配置关系](https://github.com/WilliCommer/triple-game/blob/master/lib/figures.js)

可以借鉴“邻接／数量规则与结果求解分开”。它不是 Merge Dragons 的公开源码，也不能把它的 ≥3 规则、计分或具体连锁直接套到其它三合产品；本次二合仍按两物合成设计。

## E05：三消机关可以使用多个独立数据层

[公开仓库：thefcan/unity-match3](https://github.com/thefcan/unity-match3)。本轮抽查 LockGrid、BombTimers、FrostingGrid、CascadeResolver，未验证 README 的测试数量或运行结果。

LockGrid 把锁绑定到格子；BombTimers 按可移动 Tile 的身份保存计数；FrostingGrid 保存不可移动障碍的层数；CascadeResolver 处理命中、解除和后续变化。这是按宿主语义分数据的例子，并没有强制所有机关都是同一个 Buff 子类。[LockGrid](https://github.com/thefcan/unity-match3/blob/main/Assets/Scripts/Core/LockGrid.cs)、[BombTimers](https://github.com/thefcan/unity-match3/blob/main/Assets/Scripts/Core/BombTimers.cs)、[FrostingGrid](https://github.com/thefcan/unity-match3/blob/main/Assets/Scripts/Core/FrostingGrid.cs)

可参考归属与统一结算思想；不复制其三消回合、重力、连锁规则，也不把公开示例当成商业项目质量背书。[结算器](https://github.com/thefcan/unity-match3/blob/main/Assets/Scripts/Core/CascadeResolver.cs)

## E06：作者博客中的状态效果模型

[Stray Pixels：A Framework for Status Effects in Unity](https://straypixels.net/statuseffects-framework/) 从实际效果例子出发，把可编辑定义与运行期实例分开，并指出效果需要自己的生命周期和状态。可借鉴数据拆分；文章中协程等待后直接修改宿主的方式不迁入本项目的 Operation 主链。

[Jonathan Yu：Buff System with Scriptable Objects for Unity](https://www.jonathanyu.xyz/2016/12/30/buff-system-with-scriptable-objects-for-unity/) 区分 ScriptableBuff 定义与 TimedBuff 实例，并分别处理时间延长、效果叠加和周期行为。适合理解“再次施加同类型效果”需要显式规则；其 GameObject／Update／LINQ 示例不作为本项目的实现模板。

两篇文章都有具体代码，但都不能证明二合必须采用 RPG 式 Buff。它们解决的是附加效果的数据和生命周期问题。

## E07：Epic 官方 Ability／Effect 边界

GAS 的 Gameplay Effect 有定义与运行时 Spec，支持多种持续方式和叠加策略；Ability 的执行可由标签条件限制，Effect 也有阻止 Ability 的组件。这说明“实现行为”与“影响行为的条件”可以协作，而不必删除能力对象。[Gameplay Effects](https://dev.epicgames.com/documentation/unreal-engine/gameplay-effects-for-the-gameplay-ability-system-in-unreal-engine)、[Using Gameplay Abilities](https://dev.epicgames.com/documentation/unreal-engine/using-gameplay-abilities-in-unreal-engine)、[Block Ability Tags Effect Component](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/GameplayAbilities/UBlockAbilityTagsGameplayEffectC-)

对二合建议仅取定义／实例、宿主归属、限制聚合和到期处理；不引入完整属性捕获、联网预测和复制系统。Function 是本项目用语，不等于 GAS GameplayAbility 的完整概念。

## E08：逻辑与显示分离独立于 Effect 选型

[Catlike Coding：Match 3](https://catlikecoding.com/unity/tutorials/prototypes/match-3/) 用 Match3Game 和 Match3Skin 区分规则与显示，并分别保存逻辑棋盘和显示对象。可以学习分离思路，但该教程逻辑仍使用 MonoBehaviour／Unity 类型，不是本项目 Core 无引擎依赖的直接实现。

## 实现顺序建议

1. **Step 1：先读官方规则例子。** 用 E01／E02 对齐“不能移动但能合成”“地块效果与物品效果”的差异，不把市场例子直接变成新需求。
2. **Step 2：对照两类合成源码。** E03 看二合策略与生成链；E04 看三合邻接求解，标出与当前两物合成不同的部分。
3. **Step 3：研究效果的组合边界。** E05–E07 分别看宿主、定义／实例、权限和叠加；形成 10 的最小字段与规则例子。
4. **Step 4：回到当前执行框架。** 依照 E08 的分离原则和 02 的实际契约，确认效果变化只进入 Operation，表现消费结果。
5. **Step 5：确定试验范围后再实施。** 在 09 记录 Q11 的选择，按 10 与 08 验证最小链路；不直接整包引入外部框架。
