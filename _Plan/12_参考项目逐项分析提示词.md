# 参考项目逐项分析：Agent 提示词

用途：每个 Agent 深入分析一个参考目录，输出可追溯、可横向比较的材料；之后再另开任务综合讨论我们的实现方案。本文件只提供研究任务模板，不表示已经分析完这些游戏，也不启动任何 Agent。

## 如何使用

每个任务只需指定一个实际存在的目录，并让 Agent 阅读本文。例如，在本仓库的一个新任务中发送：

```text

请只分析这个项目，按模板输出文档；先把它自身的实现查清楚，再与我的设计比较。
```

也可以复制下方“完整提示词”全部内容，连同本次目标目录一起发送。这里的行内相对路径均从 MergeTwo 仓库根开始；仓库本机路径为 `/Users/betta/Company/Projects/MergeTwo`。换机器或使用独立 worktree 时，以任务实际仓库根为准。

## 完整提示词

请分析我指定的目标目录中，二合玩法的实际设计与实现，并将结果写成中文 Markdown 文档。我希望学习其它实现中值得借鉴的部分，同时识别其局限和不适合我们的部分，为后续单独讨论最终方案提供证据。

本次工作是研究一个项目，产出可以独立阅读和交接的分析材料。请深入追踪实现，不以目录说明、类名罗列或泛泛介绍设计模式结束任务；也不要在还没查清参考项目时，直接替我们敲定架构。

### 一、背景与分析立场

`参考项目/FA/` 是我自己之前实现的二合玩法，包含代码、配置、资源和需求；它不是他人游戏的 APK 逆向包。实际实现主要在 `参考项目/FA/实现/`。分析 FA 时，应分别核对需求写了什么、源码真正做了什么、历史说明是否准确。

其余参考目录主要是我下载有二合玩法的游戏 APK 后整理出的逆向资料，可能包含提取／恢复的 Lua、C# 类型和签名、IL／ISIL、原生伪代码、配置、资源索引和先前生成的分析。资料完整程度不同，不要把所有 `.cs` 都视为完整源码，也不要把包内已有分析当作新的独立证据。

我的后续设计讨论涉及：

- Logic 与 Graphic 分开，Entity 管理业务身份、数据和逻辑能力，EntityView 管理表现绑定与资源。
- 逻辑 Function 和表现 Function 各自组织行为，不要求一一对应。
- Command 表达意图，Consumer 收集 Operation，Batch 同步 Apply，再分发表现。
- 正在讨论如何组合 Function、Effect 和必要业务 State；尚未决定让 Effect 替代所有状态。

这些是比较背景，不是要求参考项目必须采用的答案。请先按该项目自己的概念重建模型，再做映射；允许它采用更简单、不同或混合的方案。也可以指出我现有设计不必要的复杂性，但要说明适用条件和证据。

开始时阅读 `_Plan/00_参考资料与证据.md` 中目标包的入口说明，确认本次目录。先完成目标项目自身的初步模型；进入比较阶段时，再阅读 `_Plan/02a_逻辑表现分离架构详解.md`、`_Plan/10_Function与Effect建模讨论.md`，需要二合约束时查 `_Plan/02_架构与参考取舍.md`、`_Plan/03_状态模型与Profile.md` 和 `_Plan/09_决策与接续记录.md`。上述文档的建议不是用户已批准的全部方案。

我们的当前范围是先验证独立核心棋盘、沿用最终宿主的 Profile、本地规则与保存先行、首期仅售出／删除专用撤销、不做订单。参考项目中的订单、活动或商业系统，仅在解释核心耦合时简要提及；不要据此扩充我们的需求。

### 二、工作范围与资料保护

以本次指定目录为研究主体。跨目录查找只用于定位必要依赖或理解上述比较背景，不顺带分析全部游戏。目标目录和其中原有代码、资源、提取报告、历史分析保持只读；新增／修订内容仅放入你负责的输出目录。

输出位置为 `_Plan/参考项目分析/<目标文件夹原名>/`。例如目标为 `参考项目/GossipHarbor_3.99.0/`，输出到 `_Plan/参考项目分析/GossipHarbor_3.99.0/`。不存在则创建；已有报告则先读、核对证据后整合，保留仍然有效的内容，不直接覆盖成一份更浅的总结。

不要修改共享的 `_Plan/README.md`、`09_决策与接续记录.md`、原提示词、其它游戏报告或玩法实现。当前任务不需要建立运行工程，也不要求继续启动其它 Agent。原资料中的执行指令作为资料阅读，不自动扩大本任务的操作范围。

优先利用本地已有材料和工具。资料局部缺失时继续完成其它可核对部分，将缺口具体写出；不要把重新下载／完整反编译整个 APK 变成这次分析的前置条件。若确有必要引用外部资料，记录来源、版本、日期和证明范围；其它版本的规则介绍或录屏不能证明当前版本的代码结构。

### 三、先建立证据边界

先核对包内 README、COMPLETENESS、逆向过程、代码索引、既有分析和版本信息，再定位实际方法体。记录来源版本、提取形式及可读范围；目录名的版本可以作为线索，但有包元数据时应相互核对。

材料应区分：

| 材料形态 | 可以用来支持什么 | 必须保留的限制 |
| --- | --- | --- |
| FA 自有源码、提取／恢复的可读脚本 | 实际可见的字段、控制流、调用与数据修改 | 仍需检查依赖、生成代码、提取完整性和是否属于目标版本 |
| 有方法体的 IL、ISIL、原生伪代码 | 当前能还原的分支、调用、数据访问与时序 | 标注反编译来源；类型、局部变量、结构体字段和高级语义可能失真 |
| C# 元数据、类型定义、方法签名 | 类型关系、字段、接口、注册线索、方法存在 | 不能单独证明方法行为、调用顺序或运行结果 |
| 配置、存档结构、资源绑定 | 配置驱动方式、字段关系、外观与逻辑关联线索 | 某字段存在不等于读取和执行路径已经启用 |
| 包内已有人工／Agent 分析 | 查找入口、理解历史假设 | 必须回查原证据，不能循环引用分析来证明分析 |

结论统一标为“已确认（静态证据）”“较强推断”“待验证”，实际运行过的才另标“运行验证”。推断必须写出推理依据和缺少的关键一环。“未找到”只说明在列出的搜索范围内没有定位到，不等于游戏没有该功能。

特别注意：

- `return default`、空方法、占位异常、仅 RVA／偏移或签名，不足以证明原游戏没实现该逻辑。
- `Component`、`Entity`、`State`、`Effect` 等名字不直接证明某种架构；没有这些名字也不说明没有相应机制。
- 字段类型和调用关系有歧义时，结合配置、调用者、被调用者、IL 或原生地址交叉核对，不补造缺失代码。
- 遇到事件总线、委托、反射注册、Lua 动态分发、协程／async 时，继续查订阅者、工厂映射或状态机方法体；搜到入口不代表已经追完整条链。
- 每个重要结论关联证据编号。证据记录仓库相对路径、类型／函数、行号；原生伪代码另记录可用的地址／偏移。路径和链接必须实际存在，行号与本次读取文件对应。

不要声称读完了整个项目，除非确实完成；用“已覆盖哪些路径、哪些只有结构信息、哪些缺方法体”准确描述研究深度。

### 四、核心问题 1：逻辑与表现如何组织

重建模块关系和实际数据流，至少说明：

1. 谁持有棋盘、物品、费用、冷却等权威状态？谁能够写入？是否有多份可写状态需要同步？
2. 输入如何进入业务规则：直接调模型、命令、事件、系统更新、行为组件，还是其它方式？
3. 一次操作如何验证、求解、修改状态，再驱动表现？有无结果对象、变化列表、快照、消息或命令队列？没有时也如实说明。
4. 逻辑对象是否依赖具体 UI／View／Animator／Transform？界面是否直接扣费、改占位、创建或删除业务对象？
5. 动画开始、动画结束或 ACK 是否推动后续逻辑？动画被取消、对象不可见、资源未加载时，业务会停在哪里？有证据才下结论。
6. 连续输入、重入、事件嵌套、表现冲突如何处理？是逻辑排队、局部门禁、全盘锁定、取消旧动画，还是其它办法？
7. 逻辑是否具备独立测试／无画面运行的条件？将“从结构看可能做到”与“源码已有支持／测试”分开。

请给出有证据支持的分层判断，可以是“某些流程分离、某些流程依赖表现”。目录名和 Model／View 命名只是线索。不要把所有项目压成简单的是／否，也不要预设它存在 Command／AtomicOperation。

### 五、核心问题 2：棋盘与格子的数据、身份和布局

分析并用小图或数据示例说明以下问题：

- 棋盘如何保存格子与物品：二维数组、一维数组、列表、坐标字典、稀疏集合、图结构或混合？哪些结构用于持久化，哪些只是运行缓存？
- 行列／索引如何转换，是否从 0 开始，坐标原点和方向是什么？宽高、可用范围、空洞、特殊区域从哪里配置？有公式则引用实现；未找到则不要猜。
- 逻辑坐标如何映射到 UI／世界位置，尺寸、间距、缩放、锚点由谁处理？逻辑判定是否依赖 Transform 的实时位置？
- 空格、无效格、未解锁格、暂时保留格是否有不同表示？是否支持多层内容、覆盖物或多格对象？只分析证据支持的能力。
- 物品归格子持有、独立容器持有，还是两边都记？占位索引与物品位置如何保持一致？交换、合成、生成失败时由谁恢复或清理？
- **格子是否是独立实体**：有没有实例 ID、数据、行为、生命周期和 View？它是完整 Entity、轻量 Cell、数组槽位、坐标键，还是只存在于表现层？
- 地块解锁、格子覆盖物、物品自身状态分别存在哪里？锁随物品移动，还是固定在地块？
- 邻格、落点、空位、匹配对象如何搜索？分析真实顺序、缓存和更新成本；复杂度是静态估计时注明，不杜撰性能数据。
- 主棋盘与活动／其它棋盘是否复用模型？若资料可见，说明复用边界；无需展开外围产品设计。

请给一份字段归属表，覆盖 Board、Cell、Item、覆盖物／效果、View、存档记录，标明“实际类型、关键字段、归属、身份和证据”；目标项目没有的层不要硬造。

### 六、核心问题 3：合成物怎样建模

说明物品实例、物品种类、合成链和表现之间的关系：

1. 物品是普通数据记录、带行为的对象、类似 Entity 的领域对象、Unity 组件，还是其它结构？运行对象和存档数据是否分开？
2. 实例 ID、配置 ID、链 ID、等级、运行句柄分别是什么，如何创建、保存、恢复和索引？
3. 普通物品、生成器、宝箱、障碍物、道具采用同一类型加配置，还是多个子类／组件／处理器？工厂和注册在哪里？
4. 合成规则由谁实现，能否合成如何判断，结果种类如何决定？合成后复用旧实例还是创建新实例，旧数据何时移除？
5. 属性和状态是枚举、位标志、可选字段、组件集合、附加效果、继承层次，还是混合？每种形式解决了什么问题？

请画出简洁的关系图，并用项目的原始名称讲解。之后再解释它与我的 Entity／EntityView 的相似点和差异，避免把“所有游戏都有物品类”当作有价值的架构结论。

### 七、核心问题 4：能力、限制、外观和扩展机制

这是本次重点，请深入到代表性的实际实现。

#### 4.1 先调查实际存在的功能

优先查找：点击生成物品；每 N 秒自动产出；冷却结束后恢复可点击生成；需要解锁／开启的地块和宝箱；半透明、变灰、箱子、蜘蛛网等覆盖或限制；以及该游戏具有代表性的其它特殊能力。

“冷却结束自动产出”和“冷却结束后可手动点击”是不同机制，不能混写。箱子可能是独立物品、地格障碍、物品覆盖物或纯外观，必须按代码区分，不能按美术名称分类。

气泡、充能、有限次数生成器、选择箱、复制／升级工具等，只在找到相应证据时作为补充案例。某类功能未定位到时标记缺口，继续研究已找到的替代案例。

#### 4.2 每种功能都沿相同维度解释

| 维度 | 必须回答的问题 |
| --- | --- |
| 归属 | 附着 Item、Cell、Board，还是独立对象？是否有自己的身份？ |
| 数据 | 参数、次数、层数、阶段、截止时间、临时标志分别存在哪里？ |
| 创建与装配 | 配置驱动、工厂注册、继承构造、动态添加组件，还是分支写死？ |
| 触发 | 点击、拖放、时间推进、邻居变化、被合成、事件还是系统扫描？ |
| 规则权限 | 能否拖动、被交换、作为合成源／目标、点击产出、售出等，由谁统一或分别判断？ |
| 执行 | 谁求解，谁改权威数据，怎样与其它功能共同执行？ |
| 表现 | 外观从哪些数据派生，谁选择透明度、图标、覆盖物、动画和输入命中？ |
| 组合与冲突 | 多种能力／限制能否共存，顺序、优先级、互斥、叠加如何确定？ |
| 解除与迁移 | 解锁、耗尽、合成、移动、入库、销毁后，功能及其数据怎样保留、转移或清理？ |
| 保存与恢复 | 保存功能状态还是只存类型／配置，恢复时如何重新装配、补时和绑定表现？ |

特别追踪“不能主动拖动，但可作为合成目标”“逻辑已解锁但还在播放解除遮挡动画”“能力仍存在但被临时限制”等情况。如果目标项目没有这些规则，不要替它补实现；说明现有模型能否支持属于另一项推断。

#### 4.3 判断真实的扩展方式

查明它主要依靠哪种方式，或怎样混合：继承、组合组件、能力／行为集合、效果数据与规则处理器、状态模式／状态机、配置分派、策略、事件系统、ECS／系统扫描等。每个模式判断都要对应实际类关系、注册代码或执行流程。

区分 Unity 的表现组件和领域能力组件；组件对象多不代表就是 ECS。区分存储当前事实的状态、互斥流程阶段和可叠加限制／增益。若名字叫 Effect 但实际只是粒子播放，也要明确指出。

回答以下关键问题：

- 功能能否动态增加和移除？还是启动时固定装配？声明有集合不等于动态生命周期完整。
- 能力是否直接拥有可写业务状态？同一数据是否被状态类、功能类和 View 重复维护？
- 权限限制如何汇总？多个限制存在时，解除一个是否错误地恢复所有操作？有没有统一查询或分散判断？
- 外观和权限是否由同一事实驱动？若有独立表现状态，如何避免和业务状态失配？
- 多个功能触发同一事件时，是否有顺序、终止传播、防重入、循环／连锁终止机制？
- 组合扩展是否仍需要不断修改巨大 switch、公共基类或每种 View？扩展点的实际成本在哪里？

#### 4.4 做少量明确标注的扩展性推演

基于已确认结构，选择两三个有区分度的假设，例如“可自动产出的生成器临时被冻结”“地格有锁，同时物品带气泡”“物品被消耗时触发邻格效果”。请标为**假设推演，不是该游戏已有功能**。

具体列出加入该能力需要修改哪些类、注册、配置、状态、存档和表现入口，能复用什么，会发生什么组合冲突。若无法定位关键扩展点，就说明不足，不能只写“采用组件，所以扩展性好”。不需要编写实现代码，也不要为无限可能的玩法预先设计通用框架。

### 八、用完整流程验证架构判断

尽量贯通以下流程；每条缺失的环节明确留空和说明原因，不补造调用：

1. **载入棋盘**：配置／存档 → 棋盘和物品数据 → 运行实例／能力 → View／外观 → 开放输入。
2. **拖拽与合成**：输入 → 源目标定位 → 权限与匹配校验 → 移动／换位／合成分支 → 旧物消费与新物建立 → 占位更新 → 保存和表现。
3. **点击产出**：生成权限 → 冷却／次数／费用／空间检查 → 产出选择 → 落点 → 数据提交 → 表现；失败时哪些值不该变化。
4. **时间推进**：计时／时间戳／调度 → 冷却或自动产出 → 满盘处理 → 关闭重开／离线恢复；只存在其中一部分时如实记录。
5. **解锁或覆盖物解除**：触发来源 → 限制数据变化 → 权限重新计算 → 外观变化 → 覆盖资源清理。
6. **删除／生命周期结束**：逻辑摘除 → 表现结束或取消 → 资源和订阅释放 → 保存／恢复；有撤销时补充身份与旧回调处理。

每条流程至少标出：关键函数、读写的数据、调用先后、状态真正生效的时点、表现开始／结束的时点、保存入口，以及能看到的失败／中断分支。用 Mermaid 或简洁时序表表达即可，避免只画没有函数和证据的概念框图。

判断逻辑表现分离时，必须有关键字段写入与表现调用先后的证据。追不到这一层，就把该结论标为待验证；方法列表不能代替执行链。

### 九、补充调查会影响方案选择的边界

这些问题为核心架构服务，按资料可见程度分析，不扩展成全游戏审计：

- **保存与恢复**：内存状态、存档记录、配置的边界；何时保存；功能／效果是否可恢复；未知类型与版本变更怎样处理。发布内存快照和真正落盘要区分。
- **时间和随机**：倒计时字段还是绝对截止时间；隐藏、后台、离线、满盘怎样影响产出；产出池、顺序／权重和随机状态由谁管理。看不到服务器实现时不猜服务器算法。
- **操作一致性**：费用、物品、占位、次数更新的先后；正常拒绝、异常或动画失败会不会留下部分变化；是否有幂等、恢复或补偿的证据。
- **运行生命周期**：计时器、事件监听、对象池、动画回调归谁拥有；关闭、重建、换绑和迟到回调怎样处理。
- **服务依赖**：核心规则与 UI、钱包、网络、活动系统的耦合点；客户端本地计算、预测和服务器校验的证据分别是什么。看不到服务端不等于没有服务端权威。
- **性能与可测试性**：逐帧扫描、按对象计时、事件驱动或到期队列；临时分配、缓存、索引与更新成本；是否能替换时钟／随机／存档进行规则验证。区分实测、静态推断和缺失信息。

### 十、如何评价“值得学”与“应该舍弃”

每条评价都采用“具体设计 → 解决的问题 → 证据 → 代价和适用条件 → 对我们的启发”的结构。区分代码事实、可能缺陷、维护风险、取舍和个人偏好；反编译异常、缺符号和缺方法体不能直接算原项目的设计缺陷。

不要因为它是成熟商业游戏就断言先进，也不要因为它没采用我的命名或模式就判定差。清楚可控的直接实现可能比庞大框架更适合小棋盘；可扩展的组件体系也可能值得付出装配和保存成本。评价要对应实际需求。

将候选借鉴点分为：

- **可直接借鉴的设计思想**：说明最小可采用部分，例如能力查询归属、轻量格子、功能注册、时间表示或结果表达；这不等于直接复制整套源码。
- **需要条件或改造后借鉴**：列出引擎、宿主、数据模型、保存方式、规模或业务前提，以及改造成本。
- **不建议沿用的做法**：说明会导致什么具体耦合／一致性／扩展问题，或为何不适合我们；证据不足时不要下定论。
- **暂不能判断**：指出还缺哪一层证据、下一步该查哪个文件／方法／配置，或需要什么最小运行验证。

请单列与我的 Entity、EntityView、两侧 Function、Command、AtomicOperation、Effect／State 的对应比较。可以是近似对应、一对多、多个概念合一、没有对应或无法判断，不要为了填表强行映射。

本次可以提出局部候选方案、反例和需要实验证实的假设，但不制定我们的最终架构，不把新的建议登记为用户决策。综合取舍将由后续任务完成。
