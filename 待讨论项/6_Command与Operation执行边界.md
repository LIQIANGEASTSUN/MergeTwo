# 6. Command 与 Operation 执行边界

- 状态：**待讨论**
- 来源：前一轮架构讨论；_Plan 的 A02／A03、Q02。
- _Plan 回写：未授权。

## 讨论目标

确定一次业务请求如何调用 Function、检查附加限制、形成完整变化，再把结果交给 EntityView。这里讨论通用执行协议，不裁定具体生成算法。

第 2 项的最终模型可以采用不同组件组织方式，但需要明确同一份业务数据由谁、在什么阶段修改。

## 现有参考契约

依据 [_Plan/02a](../_Plan/02a_逻辑表现分离架构详解.md) 中对原架构的说明：

- Command 表示请求；CommandConsumer 解释请求并登记 Operation。
- Batch 收集完成后按序同步 Apply，随后分发表现。原契约支持多个 Consumer 与多个 Operation。
- Consumer 失败不会自动撤销已经登记的 Operation。
- Apply 中途异常可能留下部分修改；Abort 不回滚已写数据。
- Submit 的 bool 不能作为完整业务成功、动画结束或保存成功的收据。

这些是文档中的参考契约；本轮未重新读取外部宿主源码。

## 已提出但尚未确认的候选

[_Plan/02](../_Plan/02_架构与参考取舍.md)建议每条二合业务请求由一个可写业务 Consumer 完整求解，最后一次登记完整 Operation，再于 Apply 成功后、表现开始前发布结果与快照。

这可以减少“先登记扣费，后续求解失败”的部分收集问题，但不会使 Apply 自动具有事务回滚能力。若沿用它，还需要故障出口和完整成功通知。

需要比较保留原多 Operation 组合方式与按业务登记完整 Operation 的复杂度；不能把助手建议直接写成原框架限制。

## 用当前需求验证

“普通物品合成进二级锁目标”的候选执行顺序：

1. 请求带稳定身份与预期位置；执行时核对当前对象。
2. 查询 Tile 与 Item 的有效限制，由相关 Function 求解合成及解锁。
3. 形成完整变化：消费哪些物品、创建什么、占位变化、哪份锁发生变化、表现需要的前后信息。
4. 在约定的写入阶段提交；提交后才能通知可观察完整结果的外部模块。
5. EntityView 使用结果播放。动画结束或取消只处理表现生命周期。

具体锁归属由第 3 项决定。生成算法也使用同一执行边界，但由生成 Function 决定产物等业务内容。

## 尚待确定

1. 是否采用当前 _Plan 的 Command／Batch 主线，以及需要保留或调整哪些契约。
2. 一条业务请求由一个完整 Operation 还是多个有序 Operation 表达，怎样证明收集完整。
3. Function 与 Effect 如何参加查询、求解和写入，避免另开随时修改数据的事件链。
4. 正常拒绝、完整成功、部分执行故障、表现故障如何返回与处理。
5. 完整结果与表现数据保存哪些内容；旧实体被移除后，动画如何取得所需信息。
6. 空位、占位和权限查询如何共享；具体顺序、数量和落点策略允许项目自定义。
