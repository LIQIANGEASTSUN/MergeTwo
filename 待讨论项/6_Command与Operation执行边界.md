# 6. Command 与 Operation 执行边界

状态：**待讨论**。来源：前一轮讨论、_Plan 的 A02／A03／Q02、用户 2026-09-30 原则。回写规则见 [索引](README.md#回写管理)。

本篇确定请求怎样调用 Function、检查限制、求解与写入，再把结果交给 EntityView；不规定具体生成算法。Function／Effect 的方法＋bool 查询、参数准备与表现协议见 [_Plan/10](../_Plan/10_Function与Effect建模讨论.md)；本篇继续确定完整写入、成功及故障协议。

## 参考契约与候选

根据 [_Plan/02a](../_Plan/02a_逻辑表现分离架构详解.md) 的历史说明：

- Command 表达请求，CommandConsumer 解释并登记 Operation。
- Batch 收集后按序同步 Apply，再分发表现；支持多个 Consumer／Operation。
- Consumer 失败不会自动撤回已登记 Operation。
- Apply 异常可能留下部分写入，Abort 不回滚。
- Submit 的 bool 不代表完整业务成功、动画结束或保存成功。

本轮未重新读取外部宿主源码。按已确认的综合选型原则，上述机制均可保留、简化或重设，包括失败处理、回滚和返回语义；先明确需求再比较成本，采用不同设计时记录差异。

[_Plan/02](../_Plan/02_架构与参考取舍.md)的候选是：一个可写业务 Consumer 完整求解后，一次登记完整 Operation，Apply 成功、表现开始前发布结果与快照。它减少“先登记扣费、后续求解失败”的部分收集问题，仍不提供自动回滚，需要完整成功通知与故障出口。原多 Operation 组合和此候选均待比较，不能把业务建议写成原框架限制。

## 用当前需求验证

普通 A 合成进二级锁同类 B、产生 C 的候选顺序：

1. 请求携带稳定身份与预期位置，执行时核对当前对象。
2. 查询 Tile／EntityElement 限制，由相关 Function 求解合成与解锁。
3. 确定消费 A、B，创建 C，占位与锁变化，以及表现需要的前后信息。
4. 在约定阶段提交完整结果，随后通知外部模块。
5. EntityView 按结果播放；动画结束／取消的通用处理见 [第 8 项](8_时间推进与表现生命周期.md)。

锁的唯一进度归 Tile、元素运行锁 Effect 从 Tile 重建已由 D24／D25 确认；D28 已确认二级锁禁止作为源、条件允许作为目标，D29 当前不添加 TileEffect。实施接线见 [_Plan/04](../_Plan/04_棋盘交互与合成.md#tile-解锁与运行时锁-effect)。生成 Function 自定算法并使用相同执行边界。快照与实际落盘由 [第 7 项](7_数据持久化与Profile接入.md)讨论。

## 邻接解锁的响应阶段（候选）

用户先前提出：在发生合成的 Tile 发送 Command，由一级锁 Tile 上的 Effect 监听／注册响应并求解 Operation；或先生成 Operation，再由注册的逻辑响应。**D29 已决定当前不添加 TileEffect；保留“注册响应”的设计意图，由 Tile 的解锁 Function 承担相应规则。** 注册到哪个执行阶段、怎样收集变化仍按本篇比较；不因暂不添加 Effect 就自动确认某种命令协议。这里的“邻接”是一次合成影响其周围 Tile。

注册响应可以保留扩展性，但必须明确时点：收到“请求合成”的 Command 不代表合成已经成功；现有参考框架的 OperationConsumer 则在 Apply 后进入表现分发。不能让邻格在合成校验前解锁，也不能把关键解锁写入放进表现 Consumer／动画回调。若新增逻辑 Operation 响应阶段，须明确它在保存与表现前完成，以及新增变化的收集和故障语义。

### 推荐先采用：合成求解中收集邻格响应，同次执行

以下是助手建议，尚未定案；沿用一个完整业务结果的候选，不声称已具备事务回滚。

```text
Merge Command
→ 合成处理入口校验源／目标及 Effects，准备本次主合成
→ 构造只读 MergeContext（拟发生合成的位置、参与元素及必要配置数据）
→ TileSystem 按项目邻接规则取得候选 Tile
→ 调用各 Tile.FunctionTileUnlock.TryPrepareAdjacentMergeUnlock
   每个 Function 只读判断，返回局部解锁／首次创建计划
→ 合并为完整 Merge Operation（也可待第 6 项选择有序操作组）
→ 同步 Apply：合成、目标解锁、邻格揭示／创建、占位、运行锁效果同步
→ 完整成功后发布保存结果与表现
```

MergeContext 是本次求解中的局部业务输入，**不是已经提交的成功事件**。所有必需变化可准备好才进入执行；准备失败时不发布成功事件，不创建元素、不改变 Tile 进度。地图内容／配置不存在属于准备错误；普通非一级锁邻格只是不响应，并非整次合成故障。

建议入口的最小责任如下：

| 入口／数据 | 责任 |
| --- | --- |
| 主合成处理者 | 准备合成，建立 MergeContext，收齐需要随主合成完成的后果；仅一次提交 |
| TileSystem 邻格查询 | 输出去重的邻格；四／八邻由项目规则确定，按稳定坐标顺序遍历 |
| FunctionTileUnlock.TryPrepareAdjacentMergeUnlock | 检查自身阶段与邻接条件，取得地编内容，返回预期阶段／下一阶段及首次创建描述；不写活动对象 |
| 完整 Operation.Apply | 核对预期关联／阶段并执行已确定变化，完成 Element 锁效果同步后才对外发布 |
| Graphic 的 OperationConsumer | 读取完整结果中的旧／新外观与位置；只展示，不继续求解解锁 |

单次合成计划内按 Tile 去重，不能同时通过 Command 监听和 Operation 监听把同一变化登记两次。相邻响应不会递归发送相同“合成成功”：创建 B 不是 B 参与了一次合成。若以后有真正连锁规则，再定义有序工作队列和终止条件。相关规则判断可采用用户提出的注册方式，但响应者返回局部计划，由主处理者统一收集；不让每个响应者各自提前写入／保存。

### 为什么当前优先考虑解锁 Function 响应

用户已明确 Tile 具有解锁 Function，而且所有 Tile 具有相同功能；D29 已决定当前不添加 TileEffect，由该 Function 判断当前阶段是否响应。若后续需要“临时禁止这个 Tile 解锁”“改变所需邻接次数”等独立影响，再讨论 Tile Effect 扩展；这些只是举例，不新增本期需求。

若选择用户另一条路径——合成提交后发送新的邻接解锁 Command——则主合成和解锁成为两次业务，必须另定两次保存之间中断的恢复办法，不能仍宣称本次合成含全部邻接变化。若监听 Operation 只是为了获取计划，则应显式设置逻辑求解阶段，不能沿用当前 Graphic OperationConsumer 的时点。第 6 项最终需在这些方案中作出选择。
