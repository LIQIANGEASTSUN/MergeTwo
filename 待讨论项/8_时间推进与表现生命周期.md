# 8. 时间推进与表现生命周期

- 状态：**待讨论**
- 来源：前一轮时间与回调讨论；_Plan 的 Q06／Q07／Q10。
- _Plan 回写：未授权。

## 讨论范围

确定时间从哪里进入逻辑、谁拥有计时字段、何时产生业务变化，以及 EntityView 的关闭、取消和复用如何处理。生成轮次、具体产出间隔和离线产量算法由项目定义，不作为本轮通用架构问题。

依据第 5 项，生成器冷却字段归生成 Function。若采用气泡 Effect，其期限归气泡自身；是否存在期限由该变体定义。

## 候选职责划分

| 职责 | 候选拥有者 |
| --- | --- |
| 提供当前业务时间与应用前后台输入 | 宿主适配层 |
| 保存某项能力的计时依据 | 对应 Function |
| 保存附加影响的期限 | 对应 Effect（如果选用） |
| 决定到期后的业务结果 | 对应规则，沿第 6 项确认的执行入口提交 |
| 显示倒计时、安排飞行或揭示节奏 | EntityView／表现 Function |

共享时间输入不要求所有对象采用同一种算法。截止时间、累计进度、暂停剩余时间等表示应服务具体机制；本篇不先建立一个包办所有计时的 State 系统。

## 需要避免的时序歧义

动画结束可以通知表现资源释放。若业务解锁、扣费或生成必须等某段动画回调才发生，就会使关闭、取消或缺失 View 影响业务结果；是否存在明确需要等待的业务阶段，应由逻辑事实表达。

原 CommandRuntime 的重入提交会排队。因此，在 Consumer 里提交时间命令后立刻继续读取状态，不能假定该时间命令已执行。若采用“先处理必要时间变化，再处理玩家请求”，需在执行封装中明确顺序和失败处理。

物品持久 ID 不足以辨别旧 View 的回调。候选方案应考虑棋盘重建代际、每次 View 绑定，以及删除后恢复同一物品的情况；具体协议与第 6、9 项共同决定。

## 尚待确定

1. 时间服务接入哪个宿主入口；怎样处理单位、回拨和一次操作内的统一时间取样。
2. 由谁触发到期检查，如何让未显示或受限制对象按自身规则继续推进。
3. Function／Effect 如何声明到期结果，怎样进入业务执行主线。
4. 隐藏、关闭、重新打开时，选择、未完成窗口和表现资源怎样处理。
5. 取消与迟到回调如何检查身份和绑定，避免作用于复用后的对象。
6. 是否需要共享调度器，还是当前规模可用直接扫描；按实际机制决定实现复杂度。

确认记录：时间数据归具体能力／效果是候选职责整理；统一调度、时间表示和生命周期协议尚未确认。用户已确认的生成字段归属继续有效。
