# 1. Tile 的 Entity 与 EntityView

状态：**讨论中，部分已确认**。来源：用户 2026-09-29 第 1、3 点及 2026-09-30 后续回复。已确认独立格子 Entity／EntityView、命名规范、对象职责、外观配置、Tile／Element 各自存档与初始化顺序；Cell／Tile 用词及下列候选仍待讨论。本文沿用 Tile，文件名待术语确定后处理。D10–D14 的已确认范围已于 2026-09-30 写回 _Plan/02、03、04、06、08、09 及相关入口；未决内容继续保留。维护与回写见 [索引](README.md)。

## 已确认的对象与职责（2026-09-30）

逻辑层命名为 **EntityXXX**，对应表现层命名为 **EntityViewXXX**。原 Item Entity 改称 **EntityElement**，表现为 **EntityViewElement**。

| 对象 | 已确认职责 |
| --- | --- |
| TileSystem（暂名） | 替代本项目原 Board 对象，保存所有 EntityTile，提供位置与邻格查询，协调占位变化；初始化时遍历 Tile 存档，先创建全部格子 |
| ElementSystem | 初始化时遍历 Element 存档，创建全部 EntityElement，并按各自坐标建立与格子的占位关系 |
| EntityTile（暂名） | 表示一个格子，保存自身坐标与配置 ID；当前放置的 EntityElement 的 ID 仅在运行时保存 |
| EntityViewTile（暂名） | 显示地面、沙土等格子外观，播放格子表现 |
| EntityElement | 表示一件物品，保存物品身份、配置及自身功能数据；自己的存档记录所在格子坐标与自身配置 ID |
| EntityViewElement | 显示物品，处理拖拽表现和物品动画 |

“占位”就是某个格子当前放着哪件元素。原文“实际需要的格子数据”曾泛指解锁进度、待揭示内容等尚未定案的候选；这句话过于宽泛，现以表中明确字段取代。锁与揭示数据是否由格子持有，仍由下文及 [第 3 项](3_锁的归属与分阶段解锁.md)确定。

## 已确认的配置方向（2026-09-30）

- 为格子建立配置表，在编辑器中给每格指定配置 ID。
- 一条配置记录可以包含多项设置，目前用于 EntityViewTile 的图片、Prefab 等外观选择。
- **所有格子的功能相同，配置 ID 目前只区分外观。** 不根据外观 ID 装配不同的逻辑能力。
- 用户描述的一种沙土、另一种沙土、沙土上叠有物品均需表达；外观差异与解锁程度分别描述，同一阶段可使用不同资源。

同功能允许各格处于不同业务进度；具体阶段与锁归属尚未裁定。两种 View 可通过显示层级组合，沙土、蛛网、物品的遮挡顺序由表现配置表达，Transform 父子关系不决定逻辑归属。蛛网等覆盖物最终由哪一侧 View 管理，随第 3 项确定。

独立表现行为按需拆成表现 Function、不同图片共用 View 类型，仍为助手建议；本轮无需确定拆表或具体表现模块协议。用户曾提到的截图当前没有可读取附件，需求依据文字描述。

## Cell 与 Tile（待确认）

| 用词 | 本项目可采用的含义 | 对应命名 |
| --- | --- | --- |
| Cell | 强调网格中的一个位置或容纳单位 | CellSystem、EntityCell、EntityViewCell |
| Tile | 强调游戏中的一块地格，可有外观和交互 | TileSystem、EntityTile、EntityViewTile |

两者均能表达当前模型。助手建议选 Tile，与地面、沙土和格子表现的语境更贴近；这是本项目命名取舍，不是行业强制定义。最终选定一个词贯穿位置管理、逻辑和表现即可。参考项目原有 Cell／Board／Item 类名保留原样。

## 占位与存档的关系（已确认，2026-09-30）

Tile 与 Element **各自有自己的存档记录**：

| 数据 | 已确认保存内容 | 与运行数据的关系 |
| --- | --- | --- |
| Tile 存档 | 自身坐标、配置 ID；后续若 Tile 有业务状态，也保存该状态 | 不保存当前 ElementId |
| Element 存档 | 自身坐标、自身配置 ID | 用坐标恢复所在格子 |
| Tile 运行数据 | 当前 ElementId | 创建元素并放到格子上时建立，恢复时重建 |

“业务状态”表示后续确认的实际进度数据，不由此引入通用 State 架构。表中列出当前确认的基础字段；Function 自有数据的保存仍按第 5、7 项讨论，Element 是否另需持久身份尚未确定。

**已确认的初始化顺序：**

1. TileSystem 遍历全部 Tile 存档，创建所有 EntityTile；此时格子的运行 ElementId 为空。
2. 全部格子创建完成后，ElementSystem 遍历 Element 存档，创建各个 EntityElement，按其坐标找到对应格子，并填入该元素的运行 ID。
3. 完成后，格子上的 ElementId 与元素坐标对应；保存 Tile 时不写入 ElementId，下次恢复重新建立关系。

此前助手仅把格子坐标／配置描述为编辑器地图数据的说法由本轮结论修正：它们明确进入 Tile 自己的存档。编辑器负责初始配置，初始化依上述两类存档数据执行；新局如何产生初始存档另由第 7 项处理。

## 运行时关系与职责（原则已确认，具体接口待设计）

配置 ID 表示外观种类；EntityTile 保存的元素 ID 指向具体某一件 EntityElement。多格可使用同一外观配置，两件同种物品仍有各自身份。运行 EntityId 与持久身份是否相同、如何映射，由 [第 7 项](7_数据持久化与Profile接入.md)裁定。

用户本轮基本认同前一轮方案：TileSystem 管理格子、提供空间与占位操作；ElementSystem 管理元素，通过格子入口维护关联。移动与移除统一维护“格子上的元素 ID”与“元素自己的位置”的一致性，避免两个 System 各自维护可独立修改的占位集合。具体索引容器、API 名称与实现细节继续设计。具体合成结果、生成与解锁规则仍由相应规则入口处理，执行阶段见 [第 6 项](6_Command与Operation执行边界.md)。

例如 A 从 (1, 2) 移到 (1, 3)：源格的元素 ID 清空，目标格记入 A 的 ID，A 的坐标改为 (1, 3)。两个 EntityTile 与 A 的身份保持，表现层显示结果。

恢复时的结构校验、锁格原有元素恢复，以及完整关联后再启用依赖棋盘的行为，已随用户本轮认可记为 D14，统一见 [第 7 项](7_数据持久化与Profile接入.md#恢复边界已确认原则)。存档归属与先格子、后元素的顺序保持。

## “共用基础约定”的具体含义（助手解释，待确认）

原表述需要澄清为以下三件事：

1. **身份**：每个逻辑对象可以被准确定位，格子与元素分别是各自的对象；格子的具体身份方式可采用所属棋盘实例与坐标，是否另有运行 EntityId 由绑定方案决定，不要求持久 UUID。
2. **绑定**：EntityViewTile 绑定具体 EntityTile，EntityViewElement 绑定具体 EntityElement，分别读取各自需要的逻辑信息。
3. **创建与释放流程**：可以复用基础初始化、绑定、解绑与释放代码；格子与元素各有自己的创建、销毁时机。格子可持续存在，元素在移动时保留身份，合成消耗时结束自身生命周期。

这三项是基础机制复用的解释，具体公共基类、字段与方法尚未确认。建议全部有效格（包括普通空格）使用统一对象模型，View 与可视资源按需创建／回收；采用 Entity 不要求每格执行 Update。所有格子遵循同样的功能规则，普通格也无需因外观而增加逻辑 Function。

## 一级锁下面是否已有 EntityElement

用户文字允许“已有但隐藏”和“尚无物品”，需比较两种候选：

| 候选 | 一级锁的数据 | 揭示时 | 需要判断的代价 |
| --- | --- | --- | --- |
| 已有 EntityElement，显示被遮住 | 格子的元素 ID 指向完整 EntityElement | 保留身份，改变可见与操作限制 | 锁内 Function 是否运行、是否计入库存，必须有明确规则 |
| 格子持待揭示内容描述 | 保存将创建的物品种类及必要初始参数 | 揭示时创建 EntityElement，再建立占位关系 | 不应把待创建内容误计作完整活跃物品；创建时机必须稳定 |

没有活跃元素的格子仍可限制放置，不能只靠元素 ID 为空判断可用。[两阶段解锁样例](3_锁的归属与分阶段解锁.md#用户提供的玩法样例)由第 3 项维护。
