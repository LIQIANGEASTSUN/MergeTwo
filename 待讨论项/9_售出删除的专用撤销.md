# 9. 售出删除的专用撤销

- 状态：**待讨论**
- 来源：前一轮身份与恢复讨论；_Plan 的 D03、Q05。
- _Plan 回写：未授权。

## 已确认的范围

[_Plan/09](../_Plan/09_决策与接续记录.md)中的 D03 已确认首期只处理售出／删除专用撤销。通用 Undo／Redo 与确定性回放不在当前首期范围。

本篇讨论这个有限恢复流程需要怎样的对象与数据协议。具体项目的售价、保护门槛和生成算法不在这里统一规定。

## 与当前模型讨论的关系

如果 Tile 拥有自己的 Entity，恢复 Item 时不能顺带覆盖 Tile 在此期间已经变化的进度。若 Item 有 Function 自有字段或 Effect，恢复数据必须能带回对应内容，不能只保存物品配置 ID。

实例恢复与表现复用需分别处理。恢复同一持久 Item 身份，也需要重新绑定当前 EntityView，避免原删除动画的迟到回调误伤恢复后的物品。

## 现有候选与边界

[_Plan/03](../_Plan/03_状态模型与Profile.md)、[04](../_Plan/04_棋盘交互与合成.md)建议一条专用恢复凭据，记录原物品完整数据、原位置、移除原因与已结算金额。当前方案还讨论原格占用、选中其它物品导致失效，以及不能扣回售出收入时拒绝恢复。

这些是旧需求与候选实现的接续入口。本次没有新批准凭据是否跨关闭保存、冷却如何流逝或所有项目都采用同一失效策略。

## 尚待确定

1. 恢复凭据保存独立数据副本，还是保留一个退役逻辑对象；哪种更符合最终 Entity 生命周期。
2. Function 和 Effect 如何输出与恢复自身数据，避免每增加一种能力就遗漏恢复字段。
3. Item、Tile 与容器的关系如何恢复，原位置条件不满足时如何给出明确结果。
4. 售出结算与撤销扣回如何与第 6、7 项保持完整成功边界。
5. 凭据有效期、关闭行为和计时恢复规则如何由具体项目明确，是否需要很小的策略入口。
6. 恢复后如何使旧表现回调失效。
