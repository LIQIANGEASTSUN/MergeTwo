# 9. 撤销边界与不可撤销操作

状态：**讨论中**（2026-10-03）。D70 已确认：Operation 逆序撤销，遇到第一个不可撤销操作即停止；售卖明确不可撤销。该结论替代 D03 中售出可撤销的旧范围，正式边界见 [02b](../_Plan/02b_Command与Operation执行方案.md#undo-边界d70-已确认)。

原“售出删除的专用撤销”文档由本页替代。售卖恢复物品、扣回售出收入及其机会有效期不再作为本项目待确认方案；普通删除是否可撤销已单独询问。Operation／OperationBatch 仍不存档；新增 Operation 仍只能由 Command Consumer 产生。

## 1. 已确认边界

执行顺序：**A（可撤销）→ B（售卖，不可撤销）→ C（可撤销）**。

回退时先撤销 C，随后在 B 停止；B 的售卖结果保留，不能跳过 B 撤销 A。当前刚执行的就是 B 时，不能继续向前撤销。只允许回退不可撤销边界之后连续可撤销的部分。

这不等于所有 Operation 都有有效 Undo，也不等于完整 Replay／Redo 已交付。一次玩家请求回退多少操作、同一 Command 的多个 Operation 如何成组，仍待讨论。

## 2. 接口与执行建议（待确认）

- 每种操作明确撤销能力，建议用只读 CanUndo() 返回 bool；未提供正确逆向实现的操作默认不可撤销。UI 不能随意写共享 CanUndo 标记。Undo 的具体接口及失败表示仍待设计。
- 历史依据实际成功 Apply 的顺序，不能按动画完成顺序。不可撤销项必须保留为边界；若裁剪历史，也必须使边界之前的操作无法经此历史继续访问。
- 逆序检查当前操作，能撤销才执行并移动历史位置；不可撤销立即停止。撤销执行失败也不能假装成功后继续向前，原 Batch 不提供自动回滚。
- 如使用 CommandUndo 输入，仍由 Command Consumer 准备逆向步骤并产生本次执行 Operation。Undo 的执行包装不能被再次当作普通新历史加入后挡住下一次回退；历史位置和登记入口需要继续明确，不改变普通命令的返回协议。
- 内存中的历史不等于 Operation 存档。若运行历史引用原 Operation，其恢复数据必须在 Entity／View 释放后仍有效；不能调用已 Release 对象恢复业务。跨重启 Undo 尚未确认，不能直接序列化原 Operation。
- OperationRefreshTimeDisplay 等纯表现操作须明确分类。建议其业务 Undo 为空操作，完成后按当前逻辑刷新表现；不能因默认不可撤销，让每秒刷新无意中挡住业务 Undo。这一分类待结合最终接口确认。

## 3. 售卖 Operation

售卖不可撤销已确认，不创建售卖恢复凭据，也不设计扣回金币恢复已售物品的入口。

建议物品移除、释放占位和发放收益作为同一售卖 Operation 的完整职责，避免多个步骤只有一部分不可撤销、回退时留下半套售卖结果。写入前仍需完成正常条件校验，一条 Operation 不代表数据库事务或异常自动回滚。

原格空着、余额足够或旧 View 还存在，都不能让售卖临时变得可撤销。普通删除、合成消耗、气泡到期和系统清理分别确定撤销能力，不能仅凭最终都移除 Element 就认定一样。

## 4. 普通删除若允许撤销，需保留的设计

以下由原讨论迁入，**仅在该类删除确认可撤销时采用**：

| 方面 | 候选处理 |
| --- | --- |
| 完整记录 | 删除前捕获完整独立 Element 数据副本，含配置、坐标及 Function／独立 Effect 子记录；仅配置 ID 不够 |
| 复制 | 集中深复制生成 Profile 数据，避免各能力另写一套撤销 ExportState；可变 Position／子记录不与退役 View 数据共享 |
| 身份 | 建议恢复原 UniqueId，创建新的 InstanceId／Effect.RuntimeId，不递增或回退共享计数器；新 C# 对象不自动等于业务新物品 |
| Tile | 不覆盖无关物品，不用元素副本回退 Tile 独立进度；派生格锁按恢复后的 Tile 重建 |
| 落点 | 原格须空置且满足规则；不满足时拒绝还是找其它格待定。逆序回退通常先处理较晚的占位变化，不能直接套用旧专用按钮的永久失效规则 |
| 计时 | 原绝对期限自然流逝，还是冻结删除时剩余时长，尚待确认；使用命令时间，自动补产由项目算法决定 |
| 生命周期 | 按第 8 项释放旧退役 Entity；恢复新运行绑定，旧动画只清旧凭据所指对象 |
| 记录寿命 | 是否只在当前实例、保留多少步、Release 后是否保留，取决于本次历史设计；不预设只有一个专用恢复按钮 |
| 失败与重复 | 重验目标、历史位置和落点，成功不重复恢复；失败不挤掉其它物品、不越过该步骤继续回退 |

恢复资料建议仅为独立数据，不持旧 Entity／View／退役凭据；业务移除前捕获，Consumer 准备不通过生成 setter 偷写记录。纯运行窗口、订阅和派生锁不复制。生成器售出／删除保护门槛、是否统计仓库等仍由项目资格规则决定，不能把参考项目规则设为通用要求。

## 尚待讨论

1. 普通零价删除是否可撤销，或按具体删除行为决定；其它操作也需分别声明。
2. 一次 Undo 按一个 Operation、一个 Command／Batch，还是按请求连续回退；同一 Batch 后段可撤销而前段不可撤销时，是否允许部分回退。无论如何均不能跨越不可撤销项。
3. CanUndo／Undo 接口、运行历史数据与位置、成功 Apply 的登记点、Undo 自身避免入历史的方式；保持 Consumer 产生 Operation、不存档 Operation 的约束。
4. 纯表现操作与时间输入产生的业务操作分别怎样分类，避免公共刷新意外成为边界。
5. 对可恢复的操作确定完整副本、持久身份、计时、寿命及失败行为。原售卖恢复提问已撤回，不能将此前候选记为已确认。
