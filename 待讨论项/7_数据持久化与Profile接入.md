# 7. 数据持久化与 Profile 接入

状态：**讨论中，部分已确认**。来源：前一轮讨论、_Plan 的 D02／A04／Q08 及用户 2026-09-30 的存档补充。沿用宿主 Profile、本地先行，以及 Tile／Element 各自存档和初始化顺序已确认；结构校验、锁格原有元素恢复与完整关联后启用行为也已获基本认可；完整保存结构与协议待定。D13／D14 已回写 _Plan/03、08、09，维护与回写见 [索引](README.md)。

## 数据范围与恢复归属

生成字段归属已由 [第 5 项](5_生成Function的数据归属与扩展边界.md)确认。本篇处理这些数据怎样保存与恢复；序列化 DTO 不等于独立 State 行为层。

| 对象 | 已确认范围与待定持久数据 | 不应据此做出的预设 |
| --- | --- | --- |
| EntityTile（暂名，对象已确认） | 自己的存档保存坐标、配置 ID；以后若有业务状态，也保存状态，具体归属与结构待定 | ElementId 仅在运行时保存；不能先决定一级锁下面已有元素或待揭示内容归格子 |
| EntityElement | 自己的存档保存坐标、配置 ID 已确认；持久身份、其它容器、能力装配信息的保存协议待定 | 不能用配置 ID 或位置代替实例身份；本轮未要求将运行 ID 存盘 |
| Function | 自有次数、时间依据及其它必要进度 | 不要求每个字段成为 State／Effect |
| Effect 候选 | 类型与该实例必要参数；存在时保存期限、来源等 | 不预设每种效果都有独立 UUID、层数或多来源 |
| EntityView | 可从逻辑与配置重建的表现 | 不把动画句柄、资源对象或临时回调作为业务存档 |

[第 1 项](1_Tile的Entity与EntityView.md#占位与存档的关系已确认2026-09-30)统一维护已确认的初始化流程：TileSystem 先按 Tile 存档创建全部格子，再由 ElementSystem 按 Element 存档创建元素并重建占位。运行数据拥有者与存档记录位置可以不同；恢复需准确对应同一能力，不能依赖可能变化的集合下标。新增能力是否要改中央分支也需比较。

## 恢复边界（已确认原则）

- 恢复检查数据结构：Tile 坐标唯一、元素坐标对应已有 Tile、同一格最多一个元素、配置可解析。失败时保留原始数据并报告具体记录，不静默覆盖或丢弃元素；修复与迁移策略另定。
- 已保存于锁格中的元素仍应恢复到原格。初始化绑定按存档事实恢复，不用玩家操作时的“该格是否允许放入新物品”规则拦截；锁定期间的操作限制在恢复后继续生效。
- 创建时可恢复字段、构造 Function；依赖完整格子／元素集合的查询、计时结算和主动行为，等两轮创建与占位绑定结束后再启用。表现资源加载完成不负责触发首次生成或决定占位。
具体错误修复、API 与保存载体仍待设计，确认这些原则不等于批准完整快照／落盘方案。

## 快照与保存（候选）

两类存档记录应反映同一轮完整业务后的结果；可在宿主 Profile 中分别组织 Tile 与 Element 数据。是否同一文件、快照与落盘协议仍待讨论。

当前 _Plan 建议 Logic 持唯一活动数据，完整业务成功后构建独立快照发布给 Profile，后台只读取已发布内容。候选尚未确认，需避免 UI、Logic、Profile 共写活动对象。

业务写入成功、Profile 内存发布成功和磁盘落盘成功是三个时点。[_Plan/03](../_Plan/03_状态模型与Profile.md)的历史核对指出 SaveToLocal 返回 void，调用返回不能证明落盘；实施时仍需复核宿主接口。

“异常后从最后快照恢复”也有前提：发布已发生但结果不明时，先核对实际发布／持久化版本，不能盲目用旧快照覆盖新结果。执行成功边界见 [第 6 项](6_Command与Operation执行边界.md)。

## 尚待确定

1. Entity、Function 与 Effect 如何提供保存／恢复数据，新增能力是否需要修改中央分支。
2. 是否采用 Logic 自有数据＋完整成功后发布快照；如何避免可写对象同时被 UI、Logic、Profile 修改。
3. 新建与恢复是否分别进入不同流程，避免恢复时重复抽取产物、发奖励或重置期限。
4. 存档版本、配置变化、未知能力与缺失内容怎样处理，怎样保留足够诊断信息。
5. 如何观察关闭保存成功与失败；内存重建和冷启动磁盘恢复各怎样验证。
6. 与宿主钱包等外部权威数据一起变化时，如何确定结算和恢复边界；正式经济接入顺序见第 10 项。
