# 7. 数据持久化与 Profile 接入

- 状态：**待讨论**
- 来源：前一轮存档讨论；_Plan 的 D02、A04、Q08。
- _Plan 回写：未授权。

## 已明确的前提

[_Plan/09](../_Plan/09_决策与接续记录.md)中的 D02 已记录沿用宿主 Profile、本地规则与存档先行。生成次数、冷却归生成 Function 自有字段，是本次新确认的归属，见第 5 项。

字段属于 Function，与这些字段怎样保存是两个需要衔接的问题。序列化 DTO 可以承载 Function 的数据，但不因此增加独立 State 行为层。

## 本轮要解决的存档范围

| 对象 | 需要讨论的持久数据 | 不应据此做出的预设 |
| --- | --- | --- |
| Tile Entity 候选 | 坐标或稳定身份、配置、独立进度、占位或待揭示内容 | 不能先决定一级锁下面已经有 Item |
| Item Entity | 持久身份、种类、所在容器、能力装配信息 | 不能用配置 ID 或位置代替实例身份 |
| Function | 自有次数、时间依据及其它必要进度 | 不要求每个字段成为 State／Effect |
| Effect 候选 | 类型与该实例必要参数；存在时保存期限、来源等 | 不预设每种效果都有独立 UUID、层数或多来源 |
| EntityView | 可从逻辑与配置重建的表现 | 不把动画句柄、资源对象或临时回调作为业务存档 |

逻辑拥有者与存档记录位置可以不同。例如 Function 拥有运行字段，Profile 中使用对应的可序列化记录；恢复必须能准确回到同一能力，不能依赖可能变化的集合下标。

## 已提出的候选方案

当前 _Plan 建议 Logic 持有唯一活动数据；一次完整业务完成后，构造独立快照并发布给 Profile，后台保存只读取已发布内容。这个方案尚未确认为最终适配方式。

需要清楚区分三个时点：业务写入成功、Profile 内存快照发布成功、磁盘保存成功。根据 [_Plan/03](../_Plan/03_状态模型与Profile.md) 的历史核对，宿主 SaveToLocal 返回 void，不能仅凭调用返回证明已落盘；实际接口仍需在实施时复核。

前一轮助手说“异常后从最后快照恢复”需要限定：如果发布已经发生但结果不明，应先核对实际发布或持久化版本，不能盲目用旧快照覆盖新结果。

## 尚待确定

1. Entity、Function 与 Effect 如何提供保存／恢复数据，新增能力是否需要修改中央分支。
2. 是否采用 Logic 自有数据＋完整成功后发布快照；如何避免可写对象同时被 UI、Logic、Profile 修改。
3. 新建与恢复是否分别进入不同流程，避免恢复时重复抽取产物、发奖励或重置期限。
4. 存档版本、配置变化、未知能力与缺失内容怎样处理，怎样保留足够诊断信息。
5. 如何观察关闭保存成功与失败；内存重建和冷启动磁盘恢复各怎样验证。
6. 与宿主钱包等外部权威数据一起变化时，如何确定结算和恢复边界；正式经济接入顺序见第 10 项。
