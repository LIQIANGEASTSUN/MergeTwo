## 用户提出的问题

Function、Effect、State 必须有清楚的定义，避免重复表达同一件事。需要比较参考项目中的 Component、System、能力对象、字段和阶段，与本项目概念如何对应。

Travel Town 的 ECS 路径用 Component 保存数据，例如 LockComponent 中的锁定事实；这不要求另建一个名为 Effect 的系统。用户要求继续讨论：是否引入 Effect，是否需要独立 State，二者能否合并，以及是否会增加不必要的设计负担。

设计目标已经明确：可扩展、清晰简洁、容易理解。生成次数和冷却归生成 Function 内部字段，第 5 项已确认。

## 先消除 State 一词的歧义

此前助手把“当前数据”和“State 架构模块”混在一句话里，容易让人理解为要为生成次数、冷却再建一套 State 系统。后续按以下用法讨论。

| 用法 | 本轮如何表述 |
| --- | --- |
| 剩余次数、冷却截止时间等当前值 | Function 的字段或自有数据；需要保存不等于需要独立 State 对象 |
| 未开启／开启中／可领取等局部过程 | 所属 Function 或 Effect 的阶段字段；是否使用 enum 是局部实现选择 |
| 冰冻、沉默、气泡等可附加影响 | Effect 候选，或专用组件／Function；其装配方式尚待选择 |
| 通用 State 基类、StateManager、状态实例集合 | 独立架构选择；目前没有确认必须建立 |

引用参考类名中的 State 时保留原名，并说明它究竟是数据结构还是行为对象。不能因为原类叫 State 就要求本项目也建立同名层。

## 可讨论的定义

以下是助手根据用户修正后提出的候选定义。

- **Function**：实体具备的一项业务能力，包含行为及其专用字段。例如生成、合成、使用、受邻格事件影响。字段可以集中为该 Function 的数据记录以便保存，但不另立 State 层。
- **Effect**：附加在某个宿主上的玩法影响，拥有明确的附加、解除或结束规则，可以影响已有能力或增加触发后果。例如气泡、限时冻结、外部施加的冷却倍率。
- **局部阶段**：所属 Function／Effect 的字段。例如 Bubble 的解锁进度，或开启 Function 的当前阶段。无需自动升级为独立架构对象。
- **EntityView／表现 Function**：显示上述事实和结果。是否使用同名外观不决定逻辑是否为同一种 Effect。

Function 与 Effect 的业务区分，不直接决定它们是否使用不同基类。Effect 可以由专门处理器执行，也可能复用 Function 的装配基础；先比较实际生命周期、同类多份和解除规则，再决定代码继承关系。

## Buff 类比怎样使用

可把用户举出的冰冻、沉默、临时减少冷却、临时增加暴击或穿透，当作本项目讨论“附加玩法影响”的类比。这种类比不要求引入 MOBA／MMORPG 的整套属性、技能和同步框架。

例如，“基础暴击率为 10%”是属性值；“某来源增加 5% 暴击，期限结束后撤去”包含附加来源和生命周期，可作为 Effect／Buff 候选。生成器剩余次数与正常冷却属于生成能力自身；外部冻结或加速才是候选附加影响。

因此，可以讨论将原来表示附加限制的 State 合并为 Effect，并让各 Function 保留内部字段。无需为此再维护同一限制的 State 与 Effect 两份数据。这是候选简化方向，尚未确认独立 Effect 机制。

## 三种候选结构

| 结构 | 适合之处 | 需要承担的成本 |
| --- | --- | --- |
| Function＋内部字段，锁／气泡也作为专用能力组件 | 复用一套装配方式，类型较少 | 要明确能力与限制的查询、解除、同类多份规则，不能只按 FunctionType 去重后丢掉来源 |
| Function＋Effect，局部数据各自拥有；不建立通用 State 层 | 能力与附加影响的语义清楚，便于统一附加／移除与权限查询 | 需要一个足够小的 Effect 协议；避免再复制一套执行队列、存档和事件系统 |
| 统一 Component 数据＋共享规则处理器 | 组织方式接近 Travel Town 分析中的 ECS 路径 | 会改变当前 Function 的数据／行为组织方式，不能仅把类重命名就当成完成迁移 |

助手目前更倾向第二种作为讨论起点，第一种仍是有效候选。选型应通过“给生成器附加冻结后解除”和“给物品添加两种气泡变体”比较需要改哪些代码，再决定哪一种更简洁。
