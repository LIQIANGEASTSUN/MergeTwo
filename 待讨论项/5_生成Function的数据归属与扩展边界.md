## 已确认结论

1. **生成次数与冷却属于生成 Function 内部的属性字段。** 不应因此建立独立 State 组件、State 系统，或把这些字段改成 Effect。
2. 第一次、第二次及后续生成什么，属于生成 Function 的算法机制。每个项目可以自定义自己的生成需求。
3. 本轮先讨论 Tile、Function、Effect 和相关扩展边界。具体产出顺序、固定段是否计次或扣费等玩法算法退出当前讨论范围，不阻塞架构讨论。

用户原话包括：“应该算作 生成Function 内部的属性字段”“每一个项目可以自定义自己的生成需求”“不应该在我们的讨论范围内”。

## 对此前助手建议的处理

此前助手提出的以下内容均未被确认为产品规则，不再保留为要求用户回答的独立讨论项：

- 固定段先于普通轮次、扣标准费用但不占普通次数。
- 合成得到的新生成器统一重置固定段与轮次。
- 以裁定首次、第二次、第三次产出内容作为架构定稿的前置条件。

这些实现可在具体项目需要时选择；当前没有批准它们，也没有批准相反的固定规则。

## 对后续架构讨论的约束

以下是助手对上述已确认边界的应用说明，具体数据载体和扩展接口仍需讨论。

生成 Function 可以拥有自己的字段，也可以为保存而组织一个自有数据记录；序列化如何接入见第 7 项。保存或恢复这些字段不意味着引入独立 State 层。

当前用“生成 Function”表示职责，尚未确认类名必须是 GenerateFunction 或 GeneratorFunction。也未决定每实例一个策略对象、共享策略、接口或配置分派等具体实现。

若以后讨论外部冻结或加速，应在第 2 项区分：正常次数与冷却是生成能力内部数据；外部施加的限制或倍率是 Effect 候选。它们不应各自维护一份可独立写入的剩余次数。

具体空间不足策略、固定池或随机池、合成继承、主动／被动生成细则由对应项目定义。架构只需给这些算法清楚的数据、调用与结果边界，不提前替项目选择统一玩法。
