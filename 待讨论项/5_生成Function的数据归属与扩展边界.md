# 5. 生成 Function 的数据归属与扩展边界

状态：**已确认**，仅指下列“已确认结论”。来源：用户 2026-09-29 第 5 点。2026-09-30 已按用户要求回写为 D15，落实至 _Plan/01、03、05、08、09、10 及入口说明，见 [索引](README.md#回写管理)。

## 已确认结论

1. **生成次数与冷却属于生成 Function 内部属性字段**，不因此建立独立 State 组件／系统，也不把这些字段改成 Effect。
2. 首次、第二次和后续产出属于生成 Function 的算法机制，每个项目可以自定义生成需求。
3. 本轮先定 Tile、Function、Effect 及扩展边界；具体产出顺序、固定段计次／扣费退出当前讨论，不阻塞架构定稿。

用户原话：“应该算作 生成Function 内部的属性字段”“每一个项目可以自定义自己的生成需求”“不应该在我们的讨论范围内”。本篇于当日据此标记已确认。

## 退出讨论的助手旧建议

以下未被确认为产品规则，也不再作为必答题：

- 固定段先于普通轮次、扣标准费用但不占普通次数。
- 合成的新生成器统一重置固定段和轮次。
- 以裁定前三次产出内容作为架构前置条件。

具体项目可按需要选择；当前既未批准这些规则，也未批准其相反规则。

## 尚未确定的实现方式

以下是助手对已确认边界的应用说明，数据载体与扩展接口仍可讨论：

- Function 可持字段或自有数据记录；保存／恢复协议由 [第 7 项](7_数据持久化与Profile接入.md)维护，不因此增加 State 层。
- 尚未规定类名为 GenerateFunction 或 GeneratorFunction，也未决定实例策略、共享策略、接口或配置分派。
- 外部冻结／加速是 [Effect 候选](2_Function与Effect及State的职责边界.md)，应与正常次数／冷却分清，不能维护两份独立可写的剩余次数。
- 空间不足、固定池／随机池、合成继承和主动／被动细则由项目定义；架构提供清楚的数据、调用与结果边界。
