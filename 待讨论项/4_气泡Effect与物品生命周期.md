# 4. 气泡 Effect 与物品生命周期

- 状态：**讨论中**
- 来源：用户 2026-09-29 第 4 点。
- _Plan 回写：未授权。

## 用户的候选思路

气泡可作为 Effect，共用“气泡包裹物品”的表现，并具有多种行为变体：

| 变体 | 解锁方式 | 到期行为 |
| --- | --- | --- |
| 条件解锁气泡 | 点击展示付费／广告等条件，满足后解锁物品 | 用户未规定必须有期限 |
| 带期限的条件解锁气泡 | 同上，另有倒计时 | 到期仍未解锁时销毁该物品 |
| 其它气泡 | 后续按实际需求增加 | 按对应规则定义 |

这是用户提出并要求继续讨论的方向，尚未确认统一使用 Effect，也未确认全部变体的实现方式。

## 与旧方案的差异

[_Plan/05](../_Plan/05_生成器与时间.md)目前讨论的是到期替换成指定物品，并涉及选择保护。用户最新举例包含到期销毁物品。后续设计需要能表达相应变体，不能将旧的替换行为或选择保护设为所有气泡的强制规则。

表现可以复用；不同解锁条件和到期后果是否属于同一 Effect 类型的配置，或属于不同 Effect 实现，需要根据差异规模比较。不要仅因外观相同就把所有业务分支塞进一个巨大的条件判断。

## Effect 候选要承担的职责

若选 Effect，可让它记录适用的解锁条件、可选期限和结束原因。是否拥有独立实例 ID、来源、层数，按第 2 项的实际组合需求决定。

解锁满足条件后，逻辑移除气泡影响，并保留或创建可操作的物品；EntityView 展示气泡解除。到期分支按该变体执行销毁、替换或其它明确结果。显示倒计时不决定业务期限。

付费／广告窗口只发起请求和显示进度；返回时必须重新检查目标身份、气泡是否仍存在、是否已到期及是否已处理。这里讨论回调协议，不接入真实支付或广告服务。

## 气泡里的物品是否已经存在

| 候选 | 表达与优点 | 需要确定 |
| --- | --- | --- |
| 原 Item 已存在，气泡附着在它上面 | 解除后保留同一物品身份与 Function 数据；适合对现有物品施加影响 | 包裹期间哪些能力暂停、哪些字段仍推进 |
| 包装对象持待生成内容 | 解锁时才创建 Item；适合尚未形成完整实例的奖励 | 谁是 Effect 宿主；是否真的应使用 Effect 而非独立容器／物品 |

不能只保存物品种类却承诺保留原生成器的完整进度。也不能为了表现一个气泡，在一物一格模型里暗放两件可查询、可计数的活跃物品。

## 尚待确定

1. 是否把气泡作为 Effect，以及两个已描述变体如何复用逻辑与表现。
2. 气泡宿主是谁，内部 Item 是否已存在，解除后身份是否保留。
3. 期限、解锁条件与结束行为哪些可配置，哪些应由独立实现承担。
4. 与 Tile 锁等其它影响同时存在时，移除气泡后如何重新计算权限。
5. 解锁回调、到期、物品移除和界面关闭同时出现时，如何保证同一结果只处理一次。

确认记录：气泡作为 Effect 是用户候选思路；最终模型未确认。
