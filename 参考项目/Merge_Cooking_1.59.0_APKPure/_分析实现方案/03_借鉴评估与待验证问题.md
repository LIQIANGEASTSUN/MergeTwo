# 哪些做法值得借鉴，哪些需要重新处理

**Merge Cooking 1.59.0｜2026-09-25。** 版本来自目录名，尚未核对原包。本篇在 [架构](01_架构与数据模型.md) 和 [流程](02_功能扩展与执行流程.md) 的基础上比较设计。源码行为为**已确认（静态证据）**；对适用性和风险的评价属于**较强推断**；材料缺口标为**待验证**。没有运行验证。

我的判断是：它对位置、物品、生成次数和保存阶段的区分值得保留；界面参与业务修改、分步提交和回收后的身份问题，需要结合我们的目标重新处理。下面讨论的是候选取舍，不是在此敲定最终架构。

## 1. 比较时采用什么前提

我们的当前范围是先验证独立核心棋盘，使用宿主已有的 Profile 存档设施，先做本地规则与保存；首期只支持售出／删除专用撤销，不做订单。参考游戏的其它系统只用于理解依赖，不扩大我们的需求。[C01](04_证据索引.md#c01)

原设计希望把操作分成几个阶段：Command 表达意图，Consumer 收集要做的修改，Batch 依次调用 Operation.Apply 完成数据变更，之后交给表现层。它允许多个操作互相依赖，但**不会自动撤回已经执行的修改，也不会默认生成撤销记录**。因此，采用 Batch 以后，仍要规定失败时如何保持数据一致。[C01](04_证据索引.md#c01)

Function、Effect、State 的具体分法还在讨论。用户没有批准删除所有 State，本篇也不会把“全部改成效果”当作既定方向。

## 2. 和我们的设计相比，真正的差别在哪里

### 2.1 都有物品和画面，差别在写入权限

参考项目的物品记录与行为对象，近似承担我们 Entity 的一部分职责；物品画面则近似 EntityView。但参考项目的行为直接引用 Unity 格子，画面又能修改同一份物品记录。我们的设计希望把业务修改与画面绑定分开，所以两者不能只按类名一一对应。[E02](04_证据索引.md#e02)–[E04](04_证据索引.md#e04)/[E09](04_证据索引.md#e09)/[E29](04_证据索引.md#e29)

格子也不必强行对应完整 Entity。它的存档只是位置和解锁属性，运行对象才有输入和画面职责。我们是否给每格建立完整实体，应取决于它是否有独立业务行为。[E05](04_证据索引.md#e05)–[E08](04_证据索引.md#e08)

### 2.2 都会执行一串步骤，差别在何时允许改数据

参考项目主要由点击、拖放和计时函数直接推进，检查条件与修改数据交错。例如选产物时就可能改变队列，画面绑定又夹在改格过程中。[E11](04_证据索引.md#e11)/[E15](04_证据索引.md#e15)/[E27](04_证据索引.md#e27)

我方 Command／Operation 机制的价值，应体现在先确认要做什么，再在明确阶段改数据。它不是多加几个接口就自动获得事务性：即使前一个 Apply 成功、后一个失败，前面的修改也不会因此自行恢复。这个失败边界仍需针对二合规则设计。[C01](04_证据索引.md#c01)

### 2.3 都有能力和状态，差别在能否独立组合

参考项目通过能力对象复用生成等行为，这与逻辑 Function 的用途相近；但能力会直接扣费、搜格和调动画。表现侧没有看到与之对称的独立 Function 控制器，很多逻辑集中在物品画面方法中。[E04](04_证据索引.md#e04)/[E15](04_证据索引.md#e15)/[E28](04_证据索引.md#e28)

它用一个 GoodsState 值同时表示气泡、锁和生产阶段，难以同时表达多种独立物品限制；系列增益另有多来源容器。对我们而言，值得讨论的是哪些限制要独立组合、哪些阶段本就互斥，而不是把 State 这个名字全部消除。[E13](04_证据索引.md#e13)/[E33](04_证据索引.md#e33)

完整的 Entity、Function、Command 等名称对应放在 [文末对照表](#concept-reference)，需要映射到接口时再查。

## 3. 可以直接借鉴的思想

这里的“直接”指采用最小设计思想，不是复制参考源码。

**把位置限制与物品限制分开。** 解锁地块是改变某个位置，气泡等限制则属于某一件物品。分开后，移动物品不会顺便搬走地块锁。我们可以先用轻量位置数据表达格子，但要避免模型和界面缓存各自维护一份可独立修改的锁事实。[E05](04_证据索引.md#e05)/[E13](04_证据索引.md#e13)/[E32](04_证据索引.md#e32)

**把恢复次数与生成物品分开。** 先补充可用次数，再决定何时消耗次数出货，能够清楚解释满盘和离线补量。不过，达到容量上限后是否继续计时、放入背包是否暂停，仍须明确。先定这些规则，比先选 Function 或 State 更有帮助。[E16](04_证据索引.md#e16)/[E17](04_证据索引.md#e17)

**保存业务记录，重新创建运行能力。** 这样不需要把 Unity 对象、委托或动画状态塞进存档。我们可让 Profile 保存事实，恢复后装配能力并补时，同时约束初始化时的外围通知和配置兼容。[E02](04_证据索引.md#e02)–[E05](04_证据索引.md#e05)

**有位置再消费待掉落内容。** AutoDrop 先找空格，再移除待掉落项，所以满盘时能保留已经确定的产物。这个顺序只在该路径得到确认；借鉴时应让队列移除与占位建立共同成功，不能误以为所有生成分支已经如此。[E18](04_证据索引.md#e18)

**确有多个来源时，保留各自来源。** 系列增益保留活动来源，移除一个不会直接抹去其它记录。它采用最长剩余时间，不是数值相加。我们若有相同需求可保留来源和时长；单来源阶段无需为此预建完整效果框架。[E33](04_证据索引.md#e33)

## 4. 有价值，但需要改造的做法

**能力组合和类型工厂。** 它们可以减少不同生成器之间的重复代码；要用于独立核心，需要移除对具体格子画面、钱包单例等的直接依赖，并明确创建、触发、移除和释放的责任。同一枚举键只存一个能力，也不能直接用来容纳多份同类效果。[E03](04_证据索引.md#e03)/[E04](04_证据索引.md#e04)

**小棋盘的直接扫描。** 对默认 63 格，扫描容易读懂，也方便确认落点顺序。可以先采用类似规模的简单算法，再测分配和耗时；但“靠近盘上同种物品”的搜索偏好需要确认是否符合我们玩法，画面吸附也应与逻辑选位分开。[E08](04_证据索引.md#e08)

**多格物品的主格与从格关系。** 一份物品身份覆盖多个位置，能避免重复保存物品。但最终落点必须检查完整形状，移动、删除、恢复都要维护关系；参考项目还限制了这类物品的拖动。只有我们确实需要多格物品时，才值得引入。[E07](04_证据索引.md#e07)/[E10](04_证据索引.md#e10)/[E11](04_证据索引.md#e11)

**数据先成立，随后播放飞行。** 这使正常生成不用等待动画结束。参考实现的画面绑定仍嵌在数据更新中，我们要进一步拆开，并保存动画需要的起点和终点，避免表现后来只能读到最终状态。[E09](04_证据索引.md#e09)/[E15](04_证据索引.md#e15)/[E17](04_证据索引.md#e17)

**保留少量互斥阶段。** 宝箱“未开启、开启中、可领取”等顺序适合明确表达。可以把可独立叠加的限制分出去，同时保留有业务意义的阶段；否则阶段顺序可能隐含在多个效果的组合里，反而更难读。[E13](04_证据索引.md#e13)/[E20](04_证据索引.md#e20)

**把保存分为多个阶段。** 标记待保存、生成存档内容、请求写盘可以减少频繁操作的写盘成本。我们应对齐已有 Profile 的线程、快照和后台行为，分别验收业务完成与持久化完成，不另搬一套 PlayerPrefs／MMKV 设施。[E23](04_证据索引.md#e23)/[E24](04_证据索引.md#e24)/[C01](04_证据索引.md#c01)

## 5. 不建议按原样沿用的做法

以下评价针对我们的独立核心目标，不代表参考游戏已经出现相应线上故障。

- **由画面修改业务，或由动画完成决定补次数。** 资源和动画状态因此进入规则的必要路径。建议由明确的数据执行阶段推进事实，让画面读取结果；特定转换器分支是否在线启用仍待验证。[E09](04_证据索引.md#e09)/[E19](04_证据索引.md#e19)
- **先消费产出队列，再确认最终位置。** 晚拒绝可能已经改变后续产出顺序。可以把预览候选与真正消费分开，或提供明确补偿；该风险是否由真实配置触发尚未确认。[E15](04_证据索引.md#e15)/[E27](04_证据索引.md#e27)
- **分别改费用和格子，其间调用界面及同步事件。** 中途失败可能留下部分结果。我们应明确哪些字段必须共同保持一致，以及异常后的处理办法；Batch 本身不代替这些规则。[E09](04_证据索引.md#e09)/[E11](04_证据索引.md#e11)/[E15](04_证据索引.md#e15)/[E34](04_证据索引.md#e34)
- **把独立限制和生产阶段放进一个单值状态。** 同一物品无法同时通过该值表达 Bubble 和 Lock。应按实际需要拆分限制，保留必要阶段，避免反过来把所有事实都包装成效果。[E13](04_证据索引.md#e13)
- **清理责任分散，旧回调只检查物品种类。** 事件注册与注销不对称已经可见，是否导致复用故障仍是推断。需要明确谁清理事件、定时和动画，并让迟到回调核对它处理的仍是原实例或原次绑定。[E19](04_证据索引.md#e19)/[E29](04_证据索引.md#e29)/[E30](04_证据索引.md#e30)
- **让底层规则直接联动所有外围服务。** 钱包、任务、统计和界面调用会增加独立测试的依赖。我们首期只接必要的宿主服务，其余不因参考项目存在而加入需求。[E04](04_证据索引.md#e04)/[E15](04_证据索引.md#e15)/[E36](04_证据索引.md#e36)

## 6. 用三个假设检查它的扩展成本

**以下都是假设推演，不是该游戏已经具备的功能，也不是我方已批准需求。** 它们用于回答：新增一个规则，究竟只改配置，还是会触及多处代码？

### H1. 冻结自动生成器，但仍允许移动

假设要求冻结期间不出货，解冻后保留原来的库存。不能只把 GoodsState 改成 Frozen，因为这样就无法从同一个状态值知道原先是自动就绪还是冷却中。[E13](04_证据索引.md#e13)/[E17](04_证据索引.md#e17)

首先要决定“暂停充能”还是“只禁止出货”。前者需要记录冻结时段或调整冷却起点；后者可以继续计时。只保存一个冻结布尔值，不足以正确处理离线恢复。

改动会落在这些位置：

- **数据和保存**：在 GameGoodsVo 中增加冻结时限或限制记录，多来源时另存来源；同时补本地和网络字段，不能假设它们自动同步。按系列作用的 Buff 也不能直接代表一件物品的冻结。[E25](04_证据索引.md#e25)/[E33](04_证据索引.md#e33)
- **能力和入口**：被动更新、被动执行、手动领取，以及混合生成器的主动能力都要遵守同一规则。只拦自动更新会被手动领取绕过；也不能借“禁止拖动”误伤允许移动的要求。
- **装配和画面**：若只限制既有能力，无需增加物品类型；若加专门处理器，仍需接入构造和释放。画面增加冻结覆盖层，同时保留冷却／就绪信息，并明确与气泡等的显示顺序。
- **迁移和结束**：移动保留冻结；合成是否继承、用尽或售出是否移除、撤销是否恢复，都需规定。当前合成只转移指定字段，新字段不会自然保留。

**较强推断**：这个例子的收益来自限制和生产阶段独立，而非一定要建立大型效果系统。最小验证应覆盖冻结中点击、满盘、移动、跨离线和解冻。

### H2. 地块锁住，里面的气泡仍按真实经过时间到期

位置解锁和物品气泡本来分开存，因此数据结构可以容纳两者。但当前格子锁会阻止能力更新，恢复时的锁判断也先于气泡处理；“可以同时保存”并不表示“两者已经独立计时”。实际配置是否出现该组合仍待验证。[E05](04_证据索引.md#e05)/[E13](04_证据索引.md#e13)/[E21](04_证据索引.md#e21)/[E32](04_证据索引.md#e32)

要实现这个假设，需要先选择明确的时间基准，兼容旧 BubbleGoodsOpt 分支，不能把累计游戏时长与绝对时间混用。然后调整 `Grid.OnUpdateTime` 的锁过滤，或让气泡到期独立于可操作格子的扫描。

解除也应各管各的：解地块不能顺便把气泡改成 Normal，气泡到期不能自动解地块。还要规定锁内到期能否换物、发钱包奖励或清空，并让这些动作在画面隐藏时仍可完成。

存档继续保存位置解锁、气泡分支和开始时间即可，不必新增第二件物品身份。画面上则要核对云层与气泡的层级和回收关系；缺 Prefab，不能认定当前资源已经支持这种叠放。

**较强推断**：主要成本在计时和解除路径的分离，而不只是增加一个效果字段。

### H3. 物品被合成消耗时，影响一次邻格

参考项目已经在合成成功后处理邻格覆盖，但那是专门分支，没有通用的“物品被消耗”事件。普通移动、入背包也会清源格，不能看到 `ChangeGameGoodsVo(null)` 就一律触发消耗效果。[E10](04_证据索引.md#e10)–[E12](04_证据索引.md#e12)/[E22](04_证据索引.md#e22)

新增时，首先要明确触发原因：普通合成、AwaitRemove、器具投入、真正删除如何区分；售出入口缺文件，目前无法证明能覆盖全部消耗路径。触发记录需知道原物品实例、所在格子以及效果次数。

随后要在旧物被替换前保存邻域和触发信息，避免清格后再找不到原位置，或者把刚生成的新物误当旧物。若效果还能引起其它消耗，还要规定执行顺序、同一事件是否只执行一次，以及连锁怎样结束；当前的能力遍历和同步事件没有给出通用保障。

表现可以使用事先保存的旧位置和最终影响结果，不能等粒子碰到邻格才决定规则是否生效。存档保存最终业务状态，定义与次数放在记录或配置里；网络字段、合成继承和删除撤销也需同步处理。是否要跨崩溃补执行是额外要求，不能默认已有。

**较强推断**：这里涉及多处“消耗”语义和整体执行顺序，单加一个 Attribute 无法自动完成接线。

## 7. 哪些问题还需要补证

下表均为**待验证**。它列出最小需要的材料或实验，不要求重新提取整个游戏。

| 要回答的问题 | 最小补证方式 |
| --- | --- |
| 特定转换器是否真的等动画，取消后如何恢复？ | 补 AB 分支和一个 type 3 配置；记录开始、取消、重进时的次数及实例编号。[E19](04_证据索引.md#e19) |
| 最终找不到位置时，产出队列是否已改变？ | 用实际允许的多格产物等配置，比较失败前后的队列、次数、余额和格子。[E15](04_证据索引.md#e15)/[E27](04_证据索引.md#e27) |
| 格子回收再使用，事件会不会重复触发？ | 补池实现，执行“初始化—回收—再初始化”，统计 203024/203030 的回调次数。[E30](04_证据索引.md#e30) |
| 旧动画会不会影响同种新物品？ | 同格换成同 goodsID、不同 UUID 的物品，再完成旧动画；检查数据、层级和回收状态。[E19](04_证据索引.md#e19)/[E29](04_证据索引.md#e29) |
| 售出和撤销怎样恢复物品与资金？ | 补两种 GameGoodsInfoView 的售出／撤销方法，核对编号、返扣款、位置冲突和重复点击。[E31](04_证据索引.md#e31)/[E36](04_证据索引.md#e36) |
| 玩家升级后，现存格何时真正可操作？ | 补升级到格子刷新的入口，对照模型解锁、mIsLock 和云层动画时点。[E32](04_证据索引.md#e32) |
| 云恢复是否保留产出顺序与实例？ | 对比本地、发送、接收记录及服务端保存入口，检查字段、冲突和迁移。[E25](04_证据索引.md#e25) |
| 后台、背包、锁地期间怎样计时？ | 补时间服务实现和一个存档样本，记录前后台、时间回退与补量上限。[E21](04_证据索引.md#e21)/[E26](04_证据索引.md#e26) |
| 遮挡只是视觉，还是也拦点击？ | 补普通、Lock、Covered、Bubble 的 Prefab／资源，检查层级、材质和射线设置。[E28](04_证据索引.md#e28) |
| 这份恢复代码是否确属 1.59.0？ | 提供原包版本元数据、DLL 哈希或提取清单。[E01](04_证据索引.md#e01) |
