# 数据、格子和物品是怎样组织的

**Merge Cooking 1.59.0｜2026-09-25。** 版本来自目录名，尚未核对原包。本篇只解释参考项目自身的结构；默认实现结论为**已确认（静态证据）**，推断和缺口另行标注。没有运行验证。

## 1. 一件物品分成三部分，但它们还没有完全独立

这个项目用三种对象共同表示一件物品：

| 部分 | 负责什么 | 代码对应 |
| --- | --- | --- |
| 物品记录 | 记住它是什么、当前状态、剩余次数、计时和待产出内容 | GameGoodsVo，后文简称“记录” |
| 物品行为 | 执行点击产出、冷却等规则，并保存它所在格子的引用 | GameGoodsBase 及其 Attribute 能力 |
| 物品画面 | 显示图标、覆盖物和动画，响应部分输入 | GameLevelItem，即物品 View |

关键在于：**行为对象和画面通常引用同一份记录，而不是各自保存一份副本。** 所以界面代码修改状态时，改的就是规则随后读取的状态。这减少了数据复制，却让“谁可以修改业务”变得不够集中。[E04](04_证据索引.md#e04)/[E09](04_证据索引.md#e09)

棋盘和格子也参与执行。棋盘界面负责创建格子、搜索空位、定时更新；格子负责拖放、绑定物品和发起保存。下图保留主要关系，省略钱包、图鉴等外围依赖。

```mermaid
flowchart TD
  M[棋盘模型：位置与物品记录] --> D[物品记录：种类、身份、状态、次数]
  B[物品行为：组合生成等能力] -->|读取和修改| D
  I[物品画面：图标与动画] -->|显示，也可能修改| D
  V[棋盘界面：建格、搜格、定时更新] --> G[格子对象：输入、绑定、提交]
  G --> B
  G --> I
  B -->|经所在格子调用界面| G
  G -->|更新地图并标记待保存| M
```

这是一种职责有所划分、执行仍互相依赖的结构。能力对象是普通 C# 类，但它会直接调用 Unity 格子和画面；单凭“有能力组件”不能认定它已具备独立运行的规则核心。[E04](04_证据索引.md#e04)/[E06](04_证据索引.md#e06)/[E09](04_证据索引.md#e09)/[E26](04_证据索引.md#e26)

## 2. 谁保存数据，谁可以改数据

棋盘模型保存两张主要表：一张记录“哪个位置放着哪个物品”，另一张记录“哪个位置已经解锁”。运行时，棋盘界面还有一张表，用位置编号找到实际的格子对象。[E05](04_证据索引.md#e05)/[E06](04_证据索引.md#e06)

因此，需要保持一致的不只是物品记录本身，还包括这些关系：模型里的位置、格子当前持有的物品、物品记住的所在格子、画面当前绑定的物品。移动或交换要一起更新这些关系；拥有数量、生成器编号等附带记录也要同步。[E09](04_证据索引.md#e09)/[E11](04_证据索引.md#e11)

一个容易误解的细节是：`GetGameLevelMap()` 默认虽然返回一张新字典，但字典里的物品记录仍是原对象。改返回值中的某个物品，也会改原记录。它不能直接作为撤销或后台保存所需的独立快照。[E05](04_证据索引.md#e05)

某些看似查询或刷新的接口也会写数据。例如，查询免冷却时长可能更新标志，重载时查询地块是否解锁可能顺便补写解锁，而界面的 `UpdateItemState` 直接改物品状态。**较强推断**：要限制业务写入时点，需要梳理这些实际调用，不能只根据方法名划分读写。[E02](04_证据索引.md#e02)/[E09](04_证据索引.md#e09)/[E32](04_证据索引.md#e32)

完整字段归属放在文末，理解结构时可暂不逐项阅读。

## 3. 棋盘如何表示位置和空间

### 3.1 默认是九行七列，用位置编号查找

行和列都从 1 开始，格子编号为 `行 × 10 + 列`。例如，11 是第一行第一列，23 是第二行第三列；它不是连续的 0～62 下标。[E06](04_证据索引.md#e06)/[E08](04_证据索引.md#e08)

```text
说明性示例，使用代码中的默认布局：
        第1列 第2列 第3列 … 第7列
第1行     11    12    13  …   17
第2行     21    22    23  …   27
 …
第9行     91    92    93  …   97
```

画面上列向右增加，行向下增加。格子间距默认横竖都是 86，物品尺寸初始值为 85；局部位置计算为：

```text
x = (列 - 1) × GridWidth  + InitialPositionX
y = -(行 - 1) × GridHeight + InitialPositionY
```

两个初始位置属性默认返回 0，但这里的原点属于棋盘父节点，不一定是屏幕左上角。最终位置还受屏幕适配、锚点和资源影响，缺少 Prefab，实际显示效果待验证。`GridId` 表示位置，另一个 `GridIndex` 主要用于底色交错。[E06](04_证据索引.md#e06)

规则搜索主要使用编号，拖放选目标却会读物品当前的画面位置：把拖动中的位置换算到棋盘坐标，再找距离最近的格子；也有射线检测分支。默认吸附半径约为格宽的 0.75 倍，同距离倾向较小编号。这意味着拖放目标的确定仍依赖画面位置。[E10](04_证据索引.md#e10)

### 3.2 “看起来空着”不一定能够放物品

| 情况 | 数据如何表示 | 是否可当作空位 |
| --- | --- | --- |
| 有效空格 | 格子存在，物品记录为空或物品编号无效 | 还要检查是否解锁、是否被多格物品占用 |
| 无效位置 | 运行格子表中找不到该编号 | 不可使用 |
| 未解锁地块 | 位置解锁记录不满足 | 不可使用，即使没有物品 |
| 多格物品的其它占用格 | 指向保存物品记录的主格 | 已被占用，只是这里不重复保存物品 |
| 被箱壳等覆盖的物品 | 物品记录仍在，状态为覆盖中 | 不是空格 |
| 可堆叠数量 | 数量保存在单个物品内 | 不等于一格中保存多个独立物品层 |

以上区别见 [E05](04_证据索引.md#e05)/[E07](04_证据索引.md#e07)/[E08](04_证据索引.md#e08)/[E13](04_证据索引.md#e13)。多格物品只在主格保存一个物品身份，其它格保存“归哪个主格占用”的关系。形状配置记录相对行列偏移，实际位置按 `主格编号 + 行偏移×10 + 列偏移` 计算；宽高由偏移范围确定。加载时重建这些关系，换物时先清除旧关系。[E07](04_证据索引.md#e07)

目前拖拽入口禁止拖动带形状配置的物品，普通交换也拒绝任一方为多格物品。因此，代码支持多格占位，不等于支持多格物品自由移动。[E10](04_证据索引.md#e10)/[E11](04_证据索引.md#e11)

**格子在数据层与运行时有不同职责。** 持久数据层更接近“一个位置和它的解锁属性”；运行时却是带输入、物品协调和画面的 Unity 对象。没有找到独立 Cell 实例编号，以及与它分开的 CellView 模型。[E05](04_证据索引.md#e05)–[E07](04_证据索引.md#e07)

### 3.3 找空位并不只有一种规则

普通“附近空位”会先扫描全盘。传入产物种类时，它可能优先把搜索中心改到盘上第一个同种、可匹配物品附近，再选择距离最小的位置。先比横竖距离之和，再比横竖距离的较大值；仍相同时保留先遍历到的位置。[E08](04_证据索引.md#e08)

被动自动产出用另一套规则：依次查**上、下、左、右、左上、右上、左下、右下**，找到第一个空位就停止。所以邻格满了，即使远处有空格，也可能暂时不自动出货。[E08](04_证据索引.md#e08)/[E17](04_证据索引.md#e17)

另外，检查空位数量按从上到下、从左到右遍历，够数就停；“最低空位”则先选较下方的行，再选较左的列。提示可合成对象只检查同种和部分限制，真正合成还要检查下一等级配置。[E03](04_证据索引.md#e03)/[E08](04_证据索引.md#e08)

**较强推断**：默认只有 63 格，直接扫描容易理解和维护。单次全盘搜索大致随格子数增长；带形状检查还要乘以形状面积，排序最低格则多一次排序开销。源码中有临时列表分配，但没有设备耗时或内存实测，不能据此断言性能好坏。[E08](04_证据索引.md#e08)

## 4. 移动、合成之后，物品还是原来那一件吗

需要区分三种身份：

| 身份 | 表示什么 | 移动或合成时怎样变化 |
| --- | --- | --- |
| 种类编号 goodsID | 它是哪种物品 | 移动不变，升级合成后改变 |
| 实例编号 UUID | 它是具体哪一件物品 | 移动保留；普通合成创建新的编号 |
| 位置编号 gridID | 它现在在哪个格子 | 移动改变；不是物品自己的永久身份 |

合成链和等级另由配置中的 `series/level` 表示。加载存档会保留已有 UUID，缺失时补齐；编号生成使用种类编号、对象哈希及冲突处理，格式字符串未可靠恢复，跨设备唯一性待验证。也未找到把所有 UUID 统一解析为运行实体的通用管理器。[E02](04_证据索引.md#e02)/[E03](04_证据索引.md#e03)

普通合成会建立一份新记录，转移代码明确列出的生成次数、额外次数和待掉落列表，不会自动复制旧物品的全部状态。实际主入口是格子的 `EndDragToTargetGrid`，不是物品基类的 `Merge` 辅助方法。移动和交换则保留旧记录与行为对象，只改变所在格子。[E04](04_证据索引.md#e04)/[E11](04_证据索引.md#e11)

画面还具有另一层身份：池中的同一个画面对象可以先显示物品 A，回收后再显示物品 B。`InitGoodsVo` 会回收旧画面并绑定新记录，之后更新格数据；`ChangeGridGameGoods` 则可保留原画面用于移动。旧动画如何与新绑定隔离，是回收问题的关键，详见 [删除与回收流程](02_功能扩展与执行流程.md#lifecycle)。[E09](04_证据索引.md#e09)/[E29](04_证据索引.md#e29)

物品类型的差异也不全靠一种机制：工厂按配置选择子类，子类组合生成等能力；一些工具仍是普通物品，由拖拽分支单独处理。[E03](04_证据索引.md#e03)/[E04](04_证据索引.md#e04)/[E11](04_证据索引.md#e11)

## 5. 数据与画面究竟分离到什么程度

**常规结果通常先于动画生效。** 普通合成的目标物品和源格先更新，普通生成也先把产物放进数据中的目标格，再播飞行动画。不过，合成成功后的其它影响仍会穿插执行，例如动画开始后才处理邻格覆盖和额外掉落。[E11](04_证据索引.md#e11)/[E12](04_证据索引.md#e12)/[E15](04_证据索引.md#e15)

**界面仍参与业务修改。** 物品画面可以写状态；特定 Inn 转换器把补充次数放在进度动画完成回调里。这个分支可能受资源缺失或动画取消影响，但 AB 实验是否让当前玩家使用它，还没有证据。[E09](04_证据索引.md#e09)/[E19](04_证据索引.md#e19)

连续操作主要靠“正在拖动”“正在播动画”“引导中”等标志允许或拦截，并配合停止动画、复位位置。能力依次调用，事件立即执行监听函数；事件处理还可能再次进入其它规则，也就是同步重入。已查主链没有统一排队和集中应用修改的协议。[E04](04_证据索引.md#e04)/[E10](04_证据索引.md#e10)/[E28](04_证据索引.md#e28)/[E34](04_证据索引.md#e34)

**较强推断**：若我们要提取一个可脱离界面测试的核心，需要明确改数据的入口，并替换它直接依赖的界面、时钟、钱包、随机和保存服务。只把物品类改名为 Entity 不会解决这些依赖。执行顺序的完整证据见 [02](02_功能扩展与执行流程.md)。

## 6. 保存之后，数据到了哪里

### 6.1 修改记录、准备保存、写入磁盘是不同阶段

代码里调用“保存格子”，主要效果是更新内存地图，并标记模型需要保存。之后定时任务才把记录转换成 JSON；真正让保存设施写入磁盘，还要经过另一个入口。[E23](04_证据索引.md#e23)/[E24](04_证据索引.md#e24)

| 阶段 | 做了什么 | 关键方法 |
| --- | --- | --- |
| 更新内存 | 将格子对应的物品记录替换或清空 | SaveGridData → ChangeMapById → ChangeGameLevelMap |
| 标记待保存 | 把 SaveData 设为 true | SaveLevelMapData |
| 生成保存内容 | 将当前地图序列化，并调用 PlayerPrefs.SetString 更新缓存 | SaveDirtyModels → SaveDataToDB／SaveItem |
| 请求写盘 | 处理待保存模型，再调用 PlayerPrefs.Save 和 MMKVSave.Save | SaveToDisk／SaveToDiskForce |

一个容易被方法名误导的细节：`SaveGameMapToDisk` 给下一层传入 `bforce=true`，但那层仍然只是设置待保存标志，IL 也确认了这一点。[E23](04_证据索引.md#e23)

待保存模型约每秒处理一次。写盘入口有频率限制：暂不允许写盘时先记下请求，达到 60 秒且还有待写请求才强制执行；进入后台另有强制入口。因而“某格调用了保存”不代表该时刻已经完成磁盘写入。[E24](04_证据索引.md#e24)

### 6.2 恢复的是记录，运行能力需要重建

物品行为对象和动画不直接存入记录。恢复时读出次数、时间、待产物等字段，再按类型重新创建能力；初始化和后续更新还可能补算冷却。因此恢复过程会执行规则，而非单纯重现画面。[E03](04_证据索引.md#e03)/[E05](04_证据索引.md#e05)/[E16](04_证据索引.md#e16)

代码有无存档时用配置初始化、缺 UUID 时补齐、部分配置适配，以及 JSON 解析异常处理。未知类型可退回普通物品，缺配置也有保留或返回空的分支；网络列表按字段数量兼容读取。这些是具体容错，不能直接视为完整的版本迁移制度。[E03](04_证据索引.md#e03)/[E05](04_证据索引.md#e05)/[E25](04_证据索引.md#e25)

本地保存与网络发送也不是同一份字段清单：网络列表未同样包含部分产出队列和序列字段。**待验证**：服务器可能另行处理，缺少服务端实现及真实存档，无法判断跨端恢复是否保持相同产出顺序。[E25](04_证据索引.md#e25)/[E36](04_证据索引.md#e36)

此外，当前记录是共享可写对象，字典副本也是浅复制；保存入口没有冻结独立快照，也未见地图、费用中途失败后的整体回滚保证。[E05](04_证据索引.md#e05)/[E23](04_证据索引.md#e23)

### 6.3 时间和随机也会影响恢复结果

主冷却时间经过两层时间工具，最终读取 `ServerManager.ServerTimeV3`。最内层实现缺失，所以校时方式和可信度待验证。具体的补次数、自动出货、气泡计时差异见 [时间流程](02_功能扩展与执行流程.md#time-flow)。[E26](04_证据索引.md#e26)

普通产出并非每点击一次就完全独立抽签。它维护剩余序列候选和当前产物列表：选定序列、把固定及按权重次数展开的产物随机排列，再逐项取出；另有优先产物分支。已排好但尚未用完的列表可以随本地记录保存。[E27](04_证据索引.md#e27)

选序列使用 Unity 随机，插入辅助函数还会取得随机种子后新建 Random。没有发现一个统一、可保存和替换的随机状态接口。因此，保存待产物列表并不等于能凭一个种子重放所有历史操作。[E25](04_证据索引.md#e25)/[E27](04_证据索引.md#e27)

## 7. 其它棋盘是否复用同一个核心

材料中还有 Independent 和 MiniMerge 两套活动棋盘，各有自己的界面、格子和物品类型。能看到相似组织方式，但不能说所有活动都直接复用主棋盘核心；本次未深入调查活动规则。[E35](04_证据索引.md#e35)

主盘规则还直接依赖钱包、图鉴、任务统计、引导、AB 实验、资源池等服务。扣费甚至会同步通知多个外围系统。这些调用需要在独立核心设计中另作边界划分，不能因参考游戏有它们就扩充我们的需求。[E15](04_证据索引.md#e15)/[E36](04_证据索引.md#e36)
