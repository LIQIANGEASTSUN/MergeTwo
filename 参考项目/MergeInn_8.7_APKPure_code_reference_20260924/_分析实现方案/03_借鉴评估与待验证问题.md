# 03｜设计比较、借鉴取舍与待验证问题

**最值得借鉴的是物品身份、轻量格子、按操作区分权限，以及明确的类型专用规则。最需要调整的是状态写入、动画和保存之间的关系。** 这些评价来自已还原的实现，不以“有没有某种框架”判断设计好坏。

## 1. 与我们当前目标的关系

我们已经确认：先验证独立核心棋盘，沿用宿主 Profile，本地规则与保存先行，首期仅售出／删除专用撤销，不做订单。Entity／EntityView、两侧 Function、Command／Operation 与快照是现有讨论背景，但二合接入方案仍有候选项尚未批准，也没有决定让 Effect 替代所有 State。

比较依据是本仓库《逻辑表现分离架构详解》《Function 与 Effect 建模讨论》和 2026-09-25 的《决策与接续记录》；本次没有重新审计其引用的外部 HomeHub 工程。下列建议均为候选取舍，不新增正式需求或决策。静态可见的风险没有经过运行复现，资料缺体和反编译错误也不算原项目设计缺陷。

## 2. 可以直接借鉴的思想

- **区分物品、配置和显示对象。** 持久 ID 回答“哪件物品”，合成链与等级回答“哪种物品”，池对象承载画面。保留这个分工，才能可靠描述移动、合成、加载和撤销；具体 ID 分配及过期回调识别还需由我们自行保证。
- **格子保持轻量。** 一格一物、坐标和少量标志足以表达已见关系。我们可采用简单 Cell 并另绑 CellView；只有出现复杂地块身份、多层占位等实际需求时，才考虑更完整的实体结构。Merge Inn 的 Cell 混有界面职责，不适合整体照搬。
- **按操作判断权限。** 锁定物不能主动拖出，却可能接收普通合成，也可能拒绝喂料。这要求分别判断拖动、合成源、合成目标、生产等意图。多个限制并存时，统一汇总查询有价值，一个 CanOperate 无法表达全部差别。
- **保留必要业务状态与迁移规则。** 轮次、轮内次数、填充需求和开启阶段各有用途，不必全部改成临时 Effect。合成后额外补一轮、返还已投材料等规则也不能由“继承父类数据”自动推导，必须明确按类型处理。具体数值规则是否采用，属于玩法选择。
- **区分恢复可用与自动产出。** 点击生成器就绪后仍等玩家操作，自动生成器才继续生产。可共享产物和容量规则，再区分点击、时间两种触发；业务触发不必照搬动画回调。

## 3. 需要条件或改造后采用的做法

| 原做法及适用条件 | 代价或边界 | 对我们的建议 |
| --- | --- | --- |
| 按类型选对象、绑定回调，适合少量固定类型 | 新类型常牵动枚举、池、工厂和 AddItem；玩法与预制体绑定紧 | 先用明确工厂和少量规则，实际出现重复后再抽 Function；配置装配与显示资源分开。 |
| 每件物品按 ID 单独计时、保存功能状态 | 依赖 Unity 协程与分散存储；离线补算、满盘重试尚不明确 | 先定义时间规则，让业务计时不依赖画面存活；是否存截止时间由玩法决定。 |
| 同帧合并保存请求以减少写入 | 不能保证一次业务的物品、费用、次数一起保存 | 先形成完整、稳定的数据，再由宿主合并磁盘写入；数据完成与落盘成功分别跟踪。 |
| 载入时修复重叠或类型变化 | 会改位置、清专用状态，某些异常分支还移除棋盘记录；补偿去向未知 | 校验关系、保留修复前记录及原因，对无法恢复的物品给出明确处置。 |
| 只暂存一件售出物，撤销成本小 | 原格占用会阻止恢复；费用重新查询，计时与失效规则尚不完整 | 符合首期范围；保存固定的数据副本、原位、金额与版本，明确定时状态怎样恢复，暂不建通用历史。 |
| 线性找空格，无需复杂缓存 | 周边查格重复全盘扫描；是否够快取决于规模和频率 | 先明确搜索顺序与落点语义；必要时直接按坐标取格，进一步优化由实测决定。 |

## 4. 不适合我们当前目标的实现方式

**让动画完成决定创建与扣次。** 这种方式便于同步演出节拍，却让取消、隐藏和迟到回调参与决定业务是否发生。独立核心更适合由逻辑调度决定产出时点，再交给画面展示；动画回调仍可用于释放表现资源。

**让一个物品对象同时写规则、图标、计时和存储。** 对 Unity 内的小项目很直接，但会将纯规则测试、对象复用、广告订阅和资源加载联系在一起。我们的目标需要提取业务数据与规则，让 View 处理显示和绑定。

**逐步修改后，用局部返回值代表整体成功。** Place 返回失败时占位可能已经变化，TryToPutBack 又只恢复画面；UndoManager.Restore 返回 Cell 也不代表已恢复。应明确成功、正常拒绝和部分执行失败，先算好整组变化，再在受控阶段修改。Command／AtomicOperation 的名称本身不提供回滚；现有参考契约也允许多个 Operation，Apply 失败不会自动撤销已执行部分。

**把无返回值的生产回调当作创建成功。** 产物、费用、次数和预设索引分阶段变化，自动回调还存在未绑定生产函数却继续扣次的分支。我们应返回明确的创建结果，约定失败阶段，保证正常拒绝不推进费用、次数或随机状态；异常如何处理则另设故障出口。

**每增加一个限制，就在多个入口各补一次判断。** 这样容易漏掉已启动的自动回调、恢复、交换或类型特例。确有多限制组合时，应统一按操作查询权限；这不要求把次数、生命周期和开启阶段都改成 Effect。

这些取舍针对独立核心与宿主保存目标。对类型固定、只在 Unity 运行的小棋盘，直接操作对象可能更省初期成本。

## 5. 与我方概念的对应

“接近”表示职责相似，不表示 Merge Inn 已采用同一架构。

| 我方概念 | Merge Inn 中接近的部分 | 关键区别 |
| --- | --- | --- |
| Entity：业务身份、数据和逻辑 | Item，加上 GameState 的管理职责 | Item 同时持有图片、动画和协程。 |
| EntityView：绑定并显示业务对象 | Item／Cell 中的显示字段和方法 | 没有已定位的独立对应层。 |
| 逻辑 Function：组织业务能力 | 各容器子类、GameState.Merge 等 | 靠继承与直接调用，没有同等的 FunctionController。 |
| 表现 Function：组织画面行为 | AnimatePlacing、DestroyWithAnim、特效组件 | 与业务在同一对象内交织，也不与逻辑能力一一配对。 |
| Command：表达操作意图 | 点击、Select、TryMerge 的参数 | 已读流程未形成独立请求对象和统一队列。 |
| Consumer：解释请求并收集修改 | FieldInteraction、TryMerge 的判断部分 | 边判断边写入，没有先形成完整计划。 |
| AtomicOperation／Batch：组织状态修改 | MergeTwoItems、Place、Swap 等操作过程 | 没有同等变化批次与统一 Apply→Play 调度；我方方案也需明确失败后的行为。 |
| Effect：附加限制或效果 | 锁、包裹、气泡的部分语义 | 实际采用标志、包装物和计时等不同形式；EnergyEffect 是画面提示。 |
| State：当前事实和流程阶段 | ChargeData、填充需求、openInProgress、isAlive | 次数、阶段和生命周期仍须有明确数据归属。 |
| ProfileAdapter：连接宿主存档 | GameStateSave、ContainerDataStorage、ProfileStorage 调用 | 写入入口分散，未证明存在完整稳定的快照出口。 |

**执行机制与对象复杂度可以分开选择。** 使用命令和明确操作结果，不要求每个 Cell 都成为带完整 Function 树的 Entity；轻量格子也可以配合严格的写入、保存边界。

## 6. 三个扩展假设

以下均为假设推演，用于检验现有结构，不是 Merge Inn 已有功能，也不新增我们的正式需求。

### 自动生成器临时被冻结

容量、产物选择、找格与动画可复用。需要新增可保存的冻结数据，在 AddItem 恢复，并覆盖点击、冷却到期、StartAutoSpawn 和已启动动画回调的权限检查；画面也需读取同一事实。一个标志不必新增 ItemType，但当前未见可直接注册的通用效果宿主。

最容易漏的是冻结前启动的动画：其回调没有锁、泡或新冻结条件的重新校验，SafeKill 的完成语义又未知。解除后补产、继续冷却还是重新计时，应先定规则；仅增加 Freeze 子类不能自动保证所有入口一致。

### 地块锁与物品气泡同时存在

坐标、占位和气泡可以复用，但 Item.isLocked 会随物品归属，不能代替留在位置上的地块锁。需要补 Cell 的持久数据、配置、创建恢复与显示；移动、交换、合成、点击、自动生成和两种找空位方法都要考虑地块限制。

若地块锁不占物品槽，空格也不一定允许放置。移除气泡不能清地块锁，交换只移动物品状态；先定数据归属，再选择 Effect 或少量 CellState。

### 物品消耗时影响邻格

可复用 RemoveItem 与四邻搜索，但必须区分合成消耗、售出、气泡消失、关闭棋盘等原因，新增本次操作标识，并明确触发数据的保存、迁移与移除。邻格显示应跟随求解结果更新。

若直接在 onDestroy 中递归改邻格，就会与“先建结果、再消耗旧物、再拆包”的顺序交错，甚至继续触发删除。已读流程未见通用循环终止或同次去重协议。少量确定规则可在一次交互内求解；确有连锁后，再考虑局部队列与终止约束。

## 7. 仍待验证的问题

下列验证方式均为建议，尚未执行。优先补齐时间规则、取消行为和持久化边界，它们最影响核心架构判断；已经确认的“按当前格放回”“原格被占不撤销”等，不再作为未知规则重复提问。

| 未知问题 | 缺失环节与最小验证方式 |
| --- | --- |
| 坐标怎样对应画面，洞格怎样创建？ | 需要完整 LevelLayout、建格和尺寸计算，以及一份配置；用 2×3 带洞布局记录坐标、数组位置、屏幕中心，确认方向和洞是否建对象。 |
| 冷却、满盘、后台与离线怎样推进？ | AddCharges、RestoreTimer、启动计时和自动调度缺关键体；测试在线多轮补充、满盘腾格、暂停重开，记录时间、轮次、容量、产物 ID。 |
| 取消自动动画是否触发业务，旧回调能否影响新物？ | 缺 SafeKill 实现与完整调度；在动画中隐藏、合成或回池复用，核对回调次数、创建与扣次归属，并覆盖生产回调为空的分支。 |
| 退出时物品、费用与功能状态是否一起保存？ | 缺 DataStorage、ProfileStorage、InventorySave 和退出刷新实现；在各写入时点终止进程，冷启动核对产物、费用、次数、预设索引、填充与气泡时间。 |
| 异常移动和加载能否恢复一致？ | 可见移动链不回滚，加载部分分支会移除记录；需查外围异常处理和记录移除后的去向。构造缺失 ID、重叠且满盘、无效坐标、配置类型变更，核对占位、保存、补偿与后续输入。 |
| 通知会不会触发嵌套操作或暴露中间状态？ | 缺 itemAdded、合成通知的完整订阅者与外围控制；在通知中记录活跃列表、占位、存档，再尝试下一操作，确认是否排队或重入。 |
| 创建失败会推进多少序列或随机状态？ | 预设索引提前推进已知，补偿与随机源未知；固定初始状态并制造创建失败，比较索引、随机状态和产物，同时验证空数组、非法权重的配置检查。 |
| 宝箱与喂料容器中断后怎样恢复？ | 缺完整开启计时、Restore、末次领取、填充与冷却辅助方法；测试开启中合成、喂满销毁、返还材料、售出撤销和重开，核对阶段、材料、ID 与费用。 |
| 哪些限制组合实际可达，选择是否暂停气泡？ | 需要实际配置、BubblePaused／Unpaused 调用者和移除订阅链；测试锁目标合成、锁目标喂料、拆包、带泡移动交换、选中时到期及付费移除。 |
| 迟到图标会不会覆盖已复用的物品？ | 缺 RemoteSprite 加载器的取消与身份约定；让旧图在对象回池并复用后完成，核对图片、当前 ID 和配置。 |
| 撤销在金币不足、时间跨越或关闭后如何处理？ | 原格占用会直接返回已确认；还缺 CoinsSystem、撤销失效入口、候选 ID 生成和各类 Restore。测试花完收入、跨过冷却、重复撤销、关闭重开与池复用，核对旧 ID、金额和计时。 |
| 多棋盘和外部服务怎样隔离？ | 缺完整存储键、实例管理与通信入口；切换普通／季节棋盘，核对保存键和回调归属，并列出独立核心必须替换的服务。没有服务器资料时不推定其权威算法。 |
