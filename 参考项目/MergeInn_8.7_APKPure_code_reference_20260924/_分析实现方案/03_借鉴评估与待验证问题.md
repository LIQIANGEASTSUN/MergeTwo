# Merge Inn 8.7｜哪些值得借鉴，哪些还不能判断

**最值得借鉴的是清楚的物品身份、简单的单格模型，以及按具体操作区分限制。最需要改造的是业务对画面对象的依赖、一次操作分散修改数据的方式，以及动画取消与保存的处理。** 以下评价以 [01 的模型](01_架构与数据模型.md)和 [02 的流程](02_功能扩展与执行流程.md)为依据，不另行推定游戏行为。

## 1. 先明确我们的目标

我们当前已确认的范围是：先验证独立核心棋盘，沿用宿主 Profile，本地规则与保存先行，首期只做售出／删除专用撤销，不做订单。逻辑与表现两侧的 Function、Command／Operation 接入，以及完整快照的组织方式，仍有候选方案尚未批准；也没有决定用 Effect 替代所有 State。[P01](04_证据索引.md#p01)

所以，“可借鉴”指可以采用某个设计思想，不表示直接复制逆向源码。下面的建议都是候选取舍；提到的风险属于有条件的静态推断，尚未运行复现。缺方法体或反编译错误属于资料限制，不算原项目的设计缺陷。

## 2. 可以直接借鉴的设计思想

**把物品身份与配置、显示对象分开。** Merge Inn 用 ID 区分玩家拥有的每个物品，用合成链和等级描述种类，Unity 池对象则可以复用。这样移动、加载和显示对象替换时仍有追踪依据。我们可以保留这三者的分工，但它的 ID 生成和旧回调识别并未完整证明，不能照搬其具体保障方式。[E05](04_证据索引.md#e05) [E06](04_证据索引.md#e06)

**格子可以保持简单。** 一格一个物品，加上坐标和少量标志，已经能表达已见棋盘关系。我们可以采用轻量 Cell，再单独绑定 CellView；没有必要仅为了统一形式，就让每格都拥有完整 Entity 和 Function 体系。适用前提是暂时没有复杂地块身份或多层占位需求；Merge Inn 的 Cell 本身仍混有界面职责，不能整体照搬。[E01](04_证据索引.md#e01) [E04](04_证据索引.md#e04)

**按具体操作判断权限。** 锁定物不能主动拖出，却可成为合法合成目标。这说明一个笼统的 CanOperate 不足以表达规则。我们应分别问“能否拖动”“能否接收合成”“能否生产”；多限制并存时再统一汇总这些查询，避免继承它当前分散检查的维护成本。[E09](04_证据索引.md#e09)

**保留生成器真正需要的业务状态。** charges 和 capacity 分别处理轮次与轮内产出数，解决了“还能进行几轮、这一轮还剩多少”的不同问题。我们应保留必要的 State／Data，不必将所有次数都解释成临时 Effect；代价是合成、换类型和存档时需要明确迁移规则。[E14](04_证据索引.md#e14)

**区分“恢复可用”与“自动生产”。** 基类冷却结束只是提示可以使用，自动子类才继续生产。我们可以共用生成规则，再分开点击与时间触发方式；至于自动生产当前依赖动画回调的做法，需要另行改造。[E16](04_证据索引.md#e16) [E17](04_证据索引.md#e17)

## 3. 有条件、经过改造后可借鉴的部分

| 原做法解决了什么 | 适用条件与代价 | 对我们的建议 |
| --- | --- | --- |
| 按配置类型选对象、绑定回调，能快速建立不同物品。 | 固定少量类型时直接；新增类型往往要改枚举、池、工厂和 AddItem 分支。 | 先采用明确工厂和少量规则，出现实际重复后再抽 Function；配置装配与显示预制体分开。[E06](04_证据索引.md#e06) [E13](04_证据索引.md#e13) |
| 每个物品单独计时、按 ID 存状态，便于独立恢复。 | 当前依赖 Unity 协程；补时方法缺失，满盘与离线语义还不清楚。 | 先定义时间规则，让业务时间不依赖画面对象存活；是否保存截止时间由规则决定。[E14](04_证据索引.md#e14) [E16](04_证据索引.md#e16) |
| 同帧合并保存请求，减少频繁存储。 | 它不能保证每次业务完整保存；次数、序列进度、气泡计时还分散在不同键。 | 先提供完整稳定的数据，再由宿主合并磁盘写入；“数据完成”与“已经落盘”分别处理。[E24](04_证据索引.md#e24) |
| 加载时重建对象并修复重复占位，能兼容部分异常存档。 | 自动换位置会改变玩家状态；缺配置或无空格时还需要明确策略。 | 加载时检查数据关系，保留原始记录并说明修复原因；不静默丢弃无法恢复的物品。[E07](04_证据索引.md#e07) |
| 暂存一份售出的旧物，可以用较小成本实现撤销。 | 当前保留场景引用；还要处理费用、计时和原格被占等问题。 | 符合我们首期的专用撤销范围；可保存固定副本、原位、金额与版本，暂不建立通用回滚框架。[E27](04_证据索引.md#e27) |
| 线性扫描空格，让搜索顺序直观且无需维护复杂缓存。 | 是否够快取决于规模和频率；八邻查找又会多次扫描全盘。 | 先确定顺序和玩法语义；必要时改为直接坐标读取，是否继续优化用实测决定。[E03](04_证据索引.md#e03) |

## 4. 不建议在当前目标下沿用的做法

**把创建产物和扣次数放进动画完成回调。** 原做法容易让演出节拍与产出同步，但会使取消、隐藏或迟到的回调影响业务时点。我们的独立核心更适合由明确的逻辑调度决定何时生产，再交给画面展示。这不代表禁止所有动画回调，只是业务完成不宜依靠它兜底。[E17](04_证据索引.md#e17) [E18](04_证据索引.md#e18)

**让同一个物品对象同时负责规则、图片、计时和存储。** 这样可以减少对象和跨层连接，但纯规则测试、对象复用、广告订阅和图片加载会相互牵连。若目标是独立核心，应提取数据和规则，把显示交给专用 View。[E01](04_证据索引.md#e01) [E13](04_证据索引.md#e13) [E23](04_证据索引.md#e23)

**在多个方法里逐步修改，再用局部返回值代表整次操作。** Place 可能已经改了占位，却因存档更新失败返回 false；生产也把产物、费用和次数分开写。建议先算出整组变化，再在受控阶段执行，并明确失败后怎样处理。即使使用 AtomicOperation，名称也不会自动提供回滚能力。[E04](04_证据索引.md#e04) [E12](04_证据索引.md#e12) [E24](04_证据索引.md#e24)

**把生产回调正常返回当成创建成功。** Action 接口很简单，却没有成功或失败结果；预设产物进度还可能早于创建推进。我们应明确返回本次创建结果与失败阶段，并保证正常拒绝不会推进费用、次数或随机状态。[E13](04_证据索引.md#e13) [E15](04_证据索引.md#e15)

**新增一个限制，就在多个入口分别补判断。** 初期修改很快，之后容易漏掉交换、恢复或已经启动的自动产出回调。若确有多种限制需要组合，统一按操作查询权限有实际价值；这仍不意味着所有业务阶段都必须改成 Effect。[E09](04_证据索引.md#e09) [E13](04_证据索引.md#e13) [E16](04_证据索引.md#e16) [E17](04_证据索引.md#e17)

以上取舍来自我们的目标。对类型固定、只在 Unity 中运行的小项目，直接操作对象可能更省初期成本；缺少某种框架本身不是负面证据。

## 5. 与我们的概念怎样对应

下表先用一句话说明我方概念，再映射到实际代码。“接近”只表示职责相似，不表示项目已经采用同一套架构。我方定义来自现有设计文档，本次没有重新审计它们引用的外部 HomeHub 工程。[P01](04_证据索引.md#p01)

| 我方概念及含义 | Merge Inn 中最接近的部分 | 关键区别 |
| --- | --- | --- |
| Entity：一个业务对象的身份、数据与逻辑 | Item，连同 GameState 的部分管理职责 | Item 还持有图片、动画和协程，多个职责合在一起。[E01](04_证据索引.md#e01) [E05](04_证据索引.md#e05) |
| EntityView：绑定并显示业务对象 | Item 的显示字段、Cell 的显示对象 | 已读部分没有独立对应层，但显示职责存在。[E01](04_证据索引.md#e01) [E26](04_证据索引.md#e26) |
| 逻辑 Function：组织某项业务能力 | 各容器子类的方法、GameState.Merge 等 | 通过继承和直接调用组织，没有同等 FunctionController。[E06](04_证据索引.md#e06) [E13](04_证据索引.md#e13) [E22](04_证据索引.md#e22) |
| 表现 Function：组织动画和画面行为 | AnimatePlacing、DestroyWithAnim、特效组件 | 多种职责分布在同一物品对象，不与逻辑能力一一配对。[E11](04_证据索引.md#e11) [E25](04_证据索引.md#e25) |
| Command：表达一次操作意图 | 点击事件、Select 或 TryMerge 的参数 | 主流程直接调用方法，未看到独立请求对象和统一队列。[E08](04_证据索引.md#e08) |
| Consumer：解释请求、收集要做的修改 | FieldInteraction、TryMerge 的判断部分 | 当前边判断边修改，没有先形成完整计划。[E09](04_证据索引.md#e09) [E13](04_证据索引.md#e13) |
| AtomicOperation／Batch：记录并组织状态修改 | MergeTwoItems、Place、Swap 的修改过程 | bool 或物品引用只是局部结果，没有同等变化批次与统一 Apply→Play 调度；我方方案也不会自动回滚。[E11](04_证据索引.md#e11) [E12](04_证据索引.md#e12) [P01](04_证据索引.md#p01) |
| Effect：正在讨论的附加限制或效果 | 锁、包裹、气泡的部分语义 | 对应布尔值、包装物和计时字段等不同表示；EnergyEffect 是画面效果。[E19](04_证据索引.md#e19) [E23](04_证据索引.md#e23) |
| State：必要的当前事实和流程阶段 | ChargeData、openInProgress、rechargeTime、isAlive | 存在次数、阶段与生命周期状态，不能都当成可移除效果。[E14](04_证据索引.md#e14) [E21](04_证据索引.md#e21) |
| ProfileAdapter：与宿主存档连接的边界 | GameStateSave、ContainerDataStorage 和 ProfileStorage 调用 | 有多个可写入口，没有已证明的完整稳定快照出口。[E24](04_证据索引.md#e24) [P01](04_证据索引.md#p01) |

这里还有一个可避免的复杂度：是否使用命令和操作结果，与是否把每格都建成完整 Entity，是两个独立选择。可以让 Cell 很简单，同时把执行和保存的时点定义清楚。[E03](04_证据索引.md#e03) [E04](04_证据索引.md#e04) [E17](04_证据索引.md#e17) [E24](04_证据索引.md#e24)

## 6. 如果增加功能，实际需要改哪里

**下面三个例子都是假设推演，不是 Merge Inn 已有功能，也不新增我们的正式需求。** 目的在于检验已见结构怎样扩展。

### 假设 A：自动生成器临时被冻结

容量、产物选择、找空位和动画都能复用。新增的冻结状态需要可保存、可恢复，不能只禁用画面对象。沿现有结构，至少要修改 ItemData／ItemDataSave 或专用存储、AddItem 恢复，以及 ItemContainer.Select、冷却结束、StartAutoSpawn 和动画完成回调的检查；显示也要读取这个状态。一个标志不必新增 ItemType，但目前没有可直接注册的通用效果宿主。[E06](04_证据索引.md#e06) [E13](04_证据索引.md#e13) [E16](04_证据索引.md#e16) [E17](04_证据索引.md#e17)

**最容易漏掉的是冻结前已经启动的动画。** 它的完成回调只检查当前容量和空位，不会自动知道新加了冻结条件；SafeKill 是否仍触发完成也未知。解除冻结后要补产、继续冷却还是重新计时，需要先定规则。仅增加一个 Freeze 子类不能保证所有入口一致，可用这个最小例子检验统一权限查询是否值得做。[E18](04_证据索引.md#e18)

### 假设 B：格子有地块锁，物品同时带气泡

坐标、占位关系和气泡表示可以复用，物品上的 isLocked 却不能充当地块锁：否则锁会跟着物品走。沿原结构需要新增 Cell 的持久数据、配置、创建恢复和显示；移动、交换、合成、两种找空位方法、点击与自动生成落点也要检查它。如果地块锁不占物品槽，“格子没有 Item 就可放入”的规则还需修改。[E02](04_证据索引.md#e02) [E03](04_证据索引.md#e03) [E04](04_证据索引.md#e04) [E09](04_证据索引.md#e09) [E23](04_证据索引.md#e23)

**首先要解决的是归属。** 移除气泡不能顺带清掉地块锁，交换只能移动物品状态；存档也不能只凭物品列表还原地块限制。先确定谁保存、谁修改这些事实，再选择 Effect 或少量 CellState。[E24](04_证据索引.md#e24) [P01](04_证据索引.md#p01)

### 假设 C：物品被消耗时影响邻格

可以复用 RemoveItem 入口和四邻查找思路，但合成消耗、售出、气泡消失和关闭棋盘不能都算同一种玩法事件。需要新增消耗原因与本次操作标识，保存相关数据，并明确按类型迁移或移除的规则；邻格显示应根据修改结果更新。[E20](04_证据索引.md#e20) [E25](04_证据索引.md#e25) [E27](04_证据索引.md#e27)

**主要冲突是嵌套触发。** 若在 RemoveItem 或 onDestroy 中递归修改邻格，会与“先创建结果、再消耗旧物、再拆邻包”的合成顺序相互影响，还可能继续触发删除。已读代码未见通用的循环终止或同次去重协议。少量确定规则可以在一次交互里明确求解；确有连锁再考虑局部队列，不必提前建立通用反应引擎。[E11](04_证据索引.md#e11) [E20](04_证据索引.md#e20) [P01](04_证据索引.md#p01)

## 7. 暂不能判断：下一步怎样补证

以下是具体缺口。每项都给出下一处代码和最小验证方式；**所有运行用例均是建议，尚未执行。** 若只能优先补三项，选择 V02、V03、V04，它们分别决定时间规则、取消安全和存档一致性。

### 优先级高：会影响核心架构判断

<a id="v01"></a>

**V01｜逻辑格子怎样对应屏幕，洞格怎样创建？** 配置索引已知，UI 原点、缩放和洞格构造仍未知。[E02](04_证据索引.md#e02)

补查 LevelLayout、GameBoardConstructor.LoadLevel、CalculateFieldSize 完整体及一份 FieldData 配置。用 2×3 带洞布局记录格坐标、数组位置和屏幕中心，核对 y 方向及洞是否有对象。

<a id="v02"></a>

**V02｜冷却、满盘和离线分别怎样推进生产？** 在线到期的部分流程已知，但补时和自动重试策略缺失。[E16](04_证据索引.md#e16) [E17](04_证据索引.md#e17)

补查 RestoreTimer、StartCapacityTimer、TimerManager、Spawn(Cell,bool)。分别测试在线到期、满盘后腾格、暂停和重开；记录时间、轮次、轮内次数和产物 ID，不能只看动画。

<a id="v03"></a>

**V03｜取消自动动画，还会不会创建产物？** SafeKill 的具体语义决定完成回调是否继续执行。[E18](04_证据索引.md#e18)

补查 ExtensionMethods.SafeKill、动画句柄的赋值和全部取消入口。在自动动画中隐藏、合成或回池复用对象，记录旧、新物品 ID 各自产出与扣次，检查是否重复回调。

<a id="v04"></a>

**V04｜生产后突然退出，各项数据是否一起保存？** 主物品与次数、序列进度、气泡时间分开存，真实持久化边界未知。[E24](04_证据索引.md#e24)

补查 DataStorage.SetObject、ProfileStorage、InventorySave 和退出刷新。在生产后的不同保存时点终止进程，冷启动核对产物、费用、次数、预设序列进度和气泡时间。

<a id="v05"></a>

**V05｜移动已经改占位，随后返回失败，外层会修复吗？** Place 中可见这个顺序，但整个拖动恢复流程未查全。[E12](04_证据索引.md#e12)

补查 TryToPutBack、完整拖动状态机和异常处理。构造缺失物品存档 ID 的情况，观察失败后原格、目标格、物品记录、费用与后续输入是否一致。

<a id="v06"></a>

**V06｜事件订阅者会不会读到“新旧物同时存在”的中间状态？** itemAdded 早于旧物删除，但缺全部订阅者与外层限制。[E06](04_证据索引.md#e06) [E11](04_证据索引.md#e11)

补查 itemAdded、合成通知的所有订阅者及输入控制。在通知中记录活跃列表、格子和存档，并尝试提交下一操作，核对是否会嵌套执行或由外层排队。

### 优先级中：影响具体规则与生命周期

<a id="v07"></a>

**V07｜产物序列和随机状态会在失败后前进吗？** 预设进度先于创建更新，但随机源与完整拒绝处理未知。[E15](04_证据索引.md#e15)

补查随机调用符号、预设进度的保存方法和权重配置。固定初始状态重复生产，并制造创建回调失败，比较序列进度与随机状态，不只比较产物分布。

<a id="v08"></a>

**V08｜宝箱开启中断、最后一次领取和重开怎样恢复？** 已知开启入口与结束处理，完整计时和耗尽流程缺失。[E21](04_证据索引.md#e21)

补查 StartOpenTimer、其 MoveNext、Restore、SetupFiniteContainer 回调和配置。测试开启中合成、售出撤销、重开以及最后一次领取，核对阶段、旧 ID、掉落和费用。

<a id="v09"></a>

**V09｜锁、包裹、气泡的哪些组合真正会出现？** 数据能表示不等于配置和输入允许到达；选中气泡是否暂停也未知。[E09](04_证据索引.md#e09) [E19](04_证据索引.md#e19) [E23](04_证据索引.md#e23)

补查初始配置、BubblePaused／Unpaused 调用者和移除订阅者。测试锁目标合成、四邻拆包、气泡移动或交换、选中时到期，分别记录规则限制与画面变化。

<a id="v10"></a>

**V10｜旧图片加载完，会不会覆盖复用后的新物品？** 可见回调保留对象引用，加载器的取消与身份检查缺失。[E26](04_证据索引.md#e26)

补查 RemoteSprite 加载器及完成回调约定。延迟图片到对象回池并复用之后再完成，检查图片是否匹配当前物品 ID 和配置。

<a id="v11"></a>

**V11｜撤销时原格被占、金币不足或时间跨越会怎样？** 原 ID 可恢复，但占位、费用、时间和 ID 保留边界还不完整。[E27](04_证据索引.md#e27)

补查 UndoManager 的调用与失效入口、GetUnicID 候选生成器及各类 Restore。售出后分别占用原格、花完金币、跨过冷却或复用同池对象，再撤销核对原 ID、新对象绑定和状态。

<a id="v12"></a>

**V12｜不同棋盘是否隔离，哪些服务会阻断独立核心？** 普通和季节棋盘复用入口，但存档、回调和服务端边界未知。[E28](04_证据索引.md#e28)

补查 storageKey、实例管理与通信入口。在两类棋盘之间切换，记录保存键与回调归属，确认核心依赖哪些服务；没有服务端资料时不猜测其算法。
