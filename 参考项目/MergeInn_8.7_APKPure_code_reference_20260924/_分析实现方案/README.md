# Merge Inn 8.7｜实现分析导读

这组报告回答三个问题：Merge Inn 的二合玩法怎样运行，哪些实现值得参考，以及它与我们的设计有什么差别。**先读本页了解结论，再按问题查正文；证据索引用于核查，不需要从头读。**

## 先理解三个关键区别

**第一，物品对象同时负责规则和画面。** `Item` 既记住物品身份、所在格子和限制状态，也控制图片、动画和计时。棋盘操作通过这些 Unity 对象直接执行，并没有在已读主流程中形成独立的纯逻辑层。[E01](04_证据索引.md#e01) [E08](04_证据索引.md#e08)

**第二，不同操作对动画的依赖不同。** 普通合成会先建立结果物品、删除旧物品的业务记录，不必等旧物消失动画播完；自动生成器则在动画完成回调里创建产物、扣除次数。因此，不能仅凭“合成不等动画”就认为整个项目都实现了逻辑与表现分离。[E11](04_证据索引.md#e11) [E17](04_证据索引.md#e17)

**第三，包裹、锁定和气泡是三种不同实现。** 包裹物（`boxed`）占一个格子，拆开时会被一个仍然锁定的新物品替换；锁定（`locked`）限制物品操作，但满足条件时仍可作为合成目标；气泡（`bubble`）是物品上的标志，另带图片和倒计时。它们并不由一套通用效果系统统一管理。[E09](04_证据索引.md#e09) [E19](04_证据索引.md#e19) [E23](04_证据索引.md#e23)

以上均为**已确认（静态证据）**，来自可读代码和原生伪代码，尚未运行游戏验证。正文中的“较强推断”会说明依据与缺口；“待验证”表示现有材料还不足以下结论。

## 文中几个常用词

| 用词 | 本报告中的意思 |
| --- | --- |
| 业务状态／生效 | 棋盘真正记录了什么，例如物品已占格、旧物已删除、次数已扣除；画面可能仍在播放动画。 |
| 占位 | “格子里放着哪个物品”与“物品在哪个格子”的对应关系。 |
| 容器 | 源码对一类生成器的称呼；文中会区分点击生成器、自动生成器和宝箱。 |
| 回调 | 交给另一个对象执行的函数。例如动画完成后，再调用创建产物的函数。 |
| 对象池／回池 | 用过的 Unity 对象被收回，之后可以承载另一个物品；因此对象引用不等于物品的持久 ID。 |
| 快照／回滚 | 快照是某一时刻完整且固定的数据副本；回滚是操作失败后撤销已经发生的修改。发起保存请求不自动提供这两种能力。 |

## 这次分析覆盖到哪里

原资料共 123 个文件：68 个带 ARM32 注释的 C# 文件，以及 55 个原生伪代码文件。部分方法只有签名或开头，包内也没有实际配置与美术资源。材料说明见 [04 阅读范围](04_证据索引.md#scope)。

已追踪装载、格子与物品身份、创建、拖放合成、生成与计时、锁与包裹、气泡、删除回池、撤销和保存的主要流程。宝箱只确认了开启入口与结束处理，充能容器主要确认了喂料路径；其它道具和外围系统没有逐方法审计。

最影响后续判断的缺口是离线补时、动画取消和存档一致性，具体补证方案见 [03 待验证问题](03_借鉴评估与待验证问题.md#validation)。本次仍只做静态分析，不将候选建议登记为我们的正式决策。
