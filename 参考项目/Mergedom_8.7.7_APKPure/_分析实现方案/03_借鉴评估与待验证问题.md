# Mergedom：哪些值得借鉴，哪些还需要验证

2026-09-25 · 基于目录标记 8.7.7 的静态分析，包版本未独立核实。

## 1. 我们要借鉴的是哪些问题的解法

比较基线为 [02a 原架构详解](../../../_Plan/02a_逻辑表现分离架构详解.md)、[10 Function／Effect 讨论](../../../_Plan/10_Function与Effect建模讨论.md)；二合适配与确认范围按 [02](../../../_Plan/02_架构与参考取舍.md)、[03](../../../_Plan/03_状态模型与Profile.md)、[09](../../../_Plan/09_决策与接续记录.md) 区分。[E30](04_证据索引.md#e30)

我们的已确认范围是独立核心棋盘，接入最终宿主的 Profile 数据，本地规则和保存先行，首期只做售出／删除专用撤销，不做订单。执行与保存边界（Q02）、能力和效果如何组合（Q11）仍未定案。

因此，下面关注的是：它怎样分开格子与物品、怎样组织生成器、怎样安排数据修改和动画，以及这些做法接入我们的目标要付出什么代价。**可借鉴是候选建议，不表示用户已经批准；待验证也不表示发现了已复现的缺陷。**

## 2. 与我们讨论的架构，主要差在哪里

我们讨论的方案希望让业务对象管理身份和规则，让显示对象管理画面；一次操作先确定并应用数据变化，再通知显示。Mergedom 把更多职责放在同一个场景对象中，合成中途还会等待异步任务。因此，能借鉴它怎样拆分产出能力，但不能直接把其执行顺序当成我们的提交顺序。

下表是术语对照，供对照设计文档时查阅。“Apply”指真正修改业务数据的阶段；“Batch”指一组改动，它本身并不自动保证出错后回滚。

| 我方概念 | Mergedom 近似对应与关键差异 | 证据 |
| --- | --- | --- |
| Entity | BaseItem 合并业务数据、能力宿主和 Unity 资源；Slot 也含业务与显示行为。未见独立业务实例 ID | E01、E02、E23 |
| EntityView | Visual／Animator／Timer、Slot 的 Collider／Lock 分散承担；没有独立 View 绑定与寿命协议 | E01、E06 |
| 逻辑 Function | ItemProducer 列表接近专门能力集合，直接拥有容量／时间；普通合成规则仍在基类／Merger | E10–E16 |
| 表现 Function | Timer、Animator、BubbleComponent 与业务混合，未见独立有序 FunctionController 或与 Producer 一一对应 | E01、E19 |
| Command（操作意图） | 输入直达 Mover／Slot／Item，时间由协程触发，SignalBus 传通知；未证明按先后排队或统一重验 | E06、E11、E15、E21 |
| CommandConsumer | 规则分布在 InteractWithBoardSlot、CanMergeWith、TryProduce 及子类，未形成只读收集阶段 | E07、E12 |
| AtomicOperation／Batch | Merge 跨 async，Produce 直接修改＋回调，与同步 Apply 后表现不同；我方基础 Batch 也不自动回滚 | E08、E13 |
| Effect | 格锁／物锁是布尔值，气泡是专门 Item＋组件；EffectsManager 仅有 VFX 证据 | E17、E19 |
| State／Data（当前状态） | 次数、充能、时间、锁、IsPicked、交互开关分散存储；不能据此主张 Effect 替代全部业务状态 | E01、E15、E19 |
| Profile／保存记录 | 采集、复制、转保存格式、标记待保存、序列化；缺少所有数据修改成功后的统一保存入口 | E20–E22 |
| 运行与持久身份 | 普通合成复用源对象，存档按槽位重建、能力按下标；不同于我方候选的新合成身份＋资源复用 | E09、E10、E22 |

## 3. 可直接借鉴的设计思想

这里借鉴的是最小设计思想，不是复制逆向实现。

1. **让地块状态与物品状态各有归属。** 这样能解释“锁住的是这个位置，还是里面的物品”。我们可以保留轻量格子与独立物品，无须给每格建完整实体体系。但本项目的底层交换会连格锁一起交换，不能照搬其全部行为。[E01](04_证据索引.md#e01)、[E04](04_证据索引.md#e04)、[E17](04_证据索引.md#e17)
2. **把配置、当前状态和保存记录分开。** ItemProducerData 规定规则，ItemProducer 保存剩余次数与时间，另有保存记录。这能避免把可变状态写进共享配置；我方可先采用专门数据，再按真实需求决定是否装配多个 Function。按列表顺序恢复的部分需另改。[E10](04_证据索引.md#e10)、[E15](04_证据索引.md#e15)、[E20](04_证据索引.md#e20)
3. **冷却恢复次数，自动能力负责尝试产出。** 这使点击和时间触发能够复用同一生成规则。满盘重试、储备次数、离线补次数与离线补物品仍应分别定义。[E15](04_证据索引.md#e15)、[E16](04_证据索引.md#e16)
4. **有位置以后再选产物。** 正常满盘不会推进本次顺序掉落。我们可据此把空间、产物、费用和随机结果一起规划，再成功应用；但落点搜索也用随机，异常后自动退回的保证不能照推。[E12](04_证据索引.md#e12)、[E25](04_证据索引.md#e25)
5. **合成提示用按种类和等级分组的缓存。** 不必反复两两比较所有物品。它只是可重建的提示数据，棋盘内容仍是依据；小棋盘可先整盘重建，测量后再决定是否增量更新。[E28](04_证据索引.md#e28)
6. **保存截止时间，而非每秒减少的数字。** 读档时可以补算冷却进度，但要同时处理时钟回拨、时间格式、有效间隔和次数上限。[E15](04_证据索引.md#e15)

## 4. 需要条件或改造后借鉴

**多能力组合需要稳定的保存标识。** 它能让同一物品拥有多种产出方式，但配置顺序一变，旧状态就可能对应错能力；共用副计时器也限制显示数量。若采用，应补冲突、异常与保存规则，不默认一次点击的多份能力必然一起成功。[E10](04_证据索引.md#e10)、[E11](04_证据索引.md#e11)

**格子与物品互相引用，需要一起更新。** 好处是两个方向都查得快，代价是删除和换位时容易只改一边。我方可在同一次 Apply 中维护两边，并检查“一格至多一物、物品与格子互相指向”等约束。[E04](04_证据索引.md#e04)

**对象池可复用显示资源，业务身份应另外管理。** 池减少创建开销，但必须处理计时、订阅、动画取消和旧回调。可用“每次绑定都有不同编号”的办法识别过期回调；这就是文中所说的绑定代际。没有显示对象时业务是否仍存活，也需明确约定。[E23](04_证据索引.md#e23)

**快照与文件保存可以分开，但保存时点要统一。** 事件和周期保存容易接入现有 GameData，却不保证每个通知到达时业务已全部改完。我们可以借鉴先复制记录、再交给宿主写入的分工，何时生成完整快照及怎样确认落盘，继续按 Q02／Q08 讨论。[E21](04_证据索引.md#e21)

**售出时暂停冷却，是一种可选产品规则。** 本项目撤销后顺延结束时间，保留售出前剩余时长。只有选择“撤销期间不计时”才适用；金额、身份、原格冲突还需另定，Q05 尚未确认这一选择。[E24](04_证据索引.md#e24)

## 5. 不建议沿用的具体做法

以下取舍针对我们的独立规则与 Profile 目标，**执行顺序有静态证据，运行事故尚未复现**。

* **让动画等待打断一次业务修改。** 合成先等待再改格子，产出先占格和启动动画再处理次数、费用；暂停或外部服务异常时，就要额外协调只完成一半的状态。我们的候选设计应先明确整次修改的完成点。[E08](04_证据索引.md#e08)、[E09](04_证据索引.md#e09)、[E13](04_证据索引.md#e13)、[E14](04_证据索引.md#e14)
* **由旧动画直接恢复交互。** 移动完成函数把格子设为可交互，还读取 Mover 当前的 pickedItem。若期间已换成另一次操作，必须靠外部保护避免影响新对象；相关取消实现目前缺失。[E06](04_证据索引.md#e06)
* **仅靠列表位置关联保存状态。** 插入或重排能力会改变对应关系。配置需要持续演进时，应有稳定标识或明确迁移，而本包迁移机制未知。[E10](04_证据索引.md#e10)、[E20](04_证据索引.md#e20)
* **新增字段时分别维护多份保存列表。** 采集端有字段，不代表转换和恢复端也有；气泡的三字段缺口就是具体检查样例。我们应验证完整的保存后再读取过程，实际游戏后果仍待验证。[E22](04_证据索引.md#e22)
* **遇到未知配置就清空记录。** 这能避免构造无效物品，但不适合我们希望诊断配置缺失、保留可恢复数据的方向。这是取舍差异，不直接判定原项目错误。[E03](04_证据索引.md#e03)

本项目也说明少量布尔状态和专门 Producer 足以表达一些机制。是否需要 Effect 实例 ID、多来源叠加或完整能力生命周期，应由组合样例证明；不必给每个领域方法包装 Function。

## 6. 扩展性推演：假设，不是本游戏已实现的功能

### 假设 A：自动生成器暂时被冻结

可复用 ItemProducer 的容量／截止时间与 Auto 的触发，但仅把 TapItemProducer.CanProduce=false 不足以停止 Auto；只把 Slot.IsInteractable=false 也未必阻止自动对象寻找其它落点，因为 TryProduce 的交互限制主要检查目标落点。[E12](04_证据索引.md#e12)、[E16](04_证据索引.md#e16)

需要为 BaseItem／Producer 加冻结数据，在 TryProduce、Auto 重试／到期入口检查；选择暂停 EndDate 或自然计时，解冻时保留其它交互限制；补 BoardSlotData、采集、Clone、DataObjectBoard 双向转换和恢复；新增显示并在 Reset 清理。若还禁拖／禁目标合成，需改 ItemMover／CanMergeWith。此例可检验我方统一权限查询与时间规则，成本跨能力、输入、存档、显示。

### 假设 B：同一格有地块锁，里面的物品又是气泡

可复用两者现有字段，但格锁 SetLock 会隐藏整个 Item；BubbleComponent 的 Timer 是否仍执行，取决于外部 Timer 服务的调度，不能假设 GameObject 隐藏就暂停。解除格锁后气泡应继续原期限还是重设期限，需要产品规则；本项目气泡转换直接换 Slot.Item，又需确认是否允许在锁格里转换。[E17](04_证据索引.md#e17)、[E19](04_证据索引.md#e19)

需审核 BoardController.Create／解锁 helper、BubbleItem.Init、BubbleComponent 转换、Slot.SetLock 和输入权限；补气泡存档往返，Reset 清 Timer 与可视绑定。分开存储提供表达基础，组合行为仍需验证，可用于讨论我方 CellEffect／ItemEffect 的归属。

### 假设 C：物品被消耗时触发邻格变化

可复用 PostMergeSignal 的旧等级／物品／目标格信息和四邻查询；但仅监听 PostMerge 会漏掉出售、生成器耗尽、气泡替换等其他移除原因。若直接在信号订阅中改邻格并继续触发信号，执行顺序、重复处理和结束条件必须另建约定。[E08](04_证据索引.md#e08)、[E17](04_证据索引.md#e17)、[E29](04_证据索引.md#e29)

需明确“消费原因＋来源实例＋位置＋本次关联”事件数据，审核 Merger、Producer.Dispose、气泡转换及外部出售入口，定义去重／顺序／传播终止；新增状态进入采集和紧凑存档，动画展示结果。缺售出入口仍不能证明覆盖所有消费；该推演不构成首版引入通用连锁引擎的建议。

## 7. 待验证问题与最小补证

以下均为**待验证**，按影响优先级排列；最小补证是交接方案，未执行。

### V01 气泡保存并重开后，内容还完整吗？

**为什么要查：** 气泡三字段采集／Clone／Init 均使用，DataObjectBoard 紧凑转换没有（E19–E22）。

**还缺的材料：** 对应版本真实 JSON、序列化回调注册／存储服务；包版本证明。

**怎样验证：** 一颗未到期气泡保存→清进程内状态→从磁盘恢复；逐层比对内容 ID、等级、SpawnTime。既测 DTO 往返也测实机，不把同进程 Clone 当落盘。

### V02 合成到一半暂停或退出，会保存什么？

**为什么要查：** 合成在异步等待前后分阶段修改格子内容和交互状态（E08、E21）。

**还缺的材料：** 动画服务、异步异常路径、暂停事件注册和周期保存精确时机。

**怎样验证：** 在首次等待、清两格、OnMerged 等待、PostMerge 后分别暂停／退出；恢复后每格单占、无重复与损失；记录内存、快照和磁盘三个阶段。

### V03 旧动画会不会影响下一次操作？

**为什么要查：** 移动完成函数修改当时记住的格子，却读取当前 pickedItem；本段未检查是否还是同一次绑定（E06、E23）。

**还缺的材料：** ItemAnimator／动画注册表、取消委托协议、所有池调用者。

**怎样验证：** A 动画未结束时开始 B 操作，或回池再复用 A；旧完成／取消回调不得影响新物、错误发信号或开放他人交互限制。

### V04 合成中被消耗的目标物品，最终由谁回收？

**为什么要查：** 普通合成摘除 secondItem 占位，最终回池拥有者未定位（E08、E09）。

**还缺的材料：** PreMerge 动画消费者、ItemRemoved 订阅者与池间接调用映射。

**怎样验证：** 跟踪 secondItem 的 active、Slot 回指、Producer、池列表；成功／取消／异常各释放一次，不提前复用。

### V05 产出、扣次数、扣费和保存能否保持一致？

**为什么要查：** Producer 先占位／发信号，再扣容量并请求费用（E13、E14、E21）。

**还缺的材料：** IGameManager 钱包方法、产出信号订阅顺序、失败行为。

**怎样验证：** 注入费用拒绝／动画派发异常；检查占位、次数、费用和保存是否一致；普通满盘验证不扣费、不推进掉落游标。

### V06 真正开启宝箱的入口在哪里？

**为什么要查：** Chest 有开箱条件提示、Board 追踪 openingChest，但点击方法本身未调用 StartRecharging（E18）。

**还缺的材料：** 开箱 UI／Command／Popup 入口和相关服务。

**怎样验证：** 两只空容量可充能宝箱依次请求开启；确定谁拦截第二次、首次何时写时间、何时保存；不以提示文案代替规则证明。

### V07 离线回来到底补次数，还是补物品？

**为什么要查：** 开始／结束时间和离线容量补算可见，Auto 恢复后可产出（E15、E16）。

**还缺的材料：** 实际配置间隔／上限、时间 API 符号、重试常数及后台生命周期。

**怎样验证：** 离线小于／跨多个间隔、满盘、正好上限、回拨；区分恢复容量数和实放物品数，不断言逐时段补产。

### V08 拖着气泡到期时，会发生什么？

**为什么要查：** Bubble 转换调用 WhilePicked，拖动钩子写 IsPicked（E19）。

**还缺的材料：** WhilePicked.MoveNext、Timer 实现、选择／拖起全部调用者。

**怎样验证：** 到期时仅选中、正在拖、刚放下、对象被隐藏／回池分别观察；确认等待能取消且不写新绑定。

### V09 改变能力配置顺序后，旧状态会不会对应错？

**为什么要查：** 配置按 Producer 下标恢复，后续能力共用副 Timer（E10）。

**还缺的材料：** 真实多能力配置与版本迁移约定。

**怎样验证：** 保存两个不同能力状态后交换配置顺序；再测三个能力的 UI 与恢复；据结果决定是否需要稳定能力键。

### V10 格子和物品的双向位置关系始终一致吗？

**为什么要查：** Slot 双向引用由多处维护，Swap 还交换格锁，GetFirstEmpty 不查格锁（E04、E05）。

**还缺的材料：** 所有外部调用者与地图配置。

**怎样验证：** 逐入口检查锁格＋空格、移动／交换／删除；底层 helper 的前置条件是否真实成立。

### V11 售出撤销的完整规则是什么？

**为什么要查：** 有 OnSell／OnUndoSell 暂停钩子（E24）。

**还缺的材料：** 售出管理者、金额／撤销凭据、原格冲突处理和跨关闭协议。

**怎样验证：** 出售后换选、花费收入、原格占用、关闭重开、撤销两次；区分钩子存在与完整可撤销业务。

### V12 这些材料能否确认来自同一个版本？

**为什么要查：** 只有目录名版本、元数据和原生文本（E00、E27）。

**还缺的材料：** APK versionName／versionCode、构建哈希、符号／metadata 匹配和资源。

**怎样验证：** 获取最小清单与对应缺失类即可；不必以重新完整逆向为报告交付前提。
