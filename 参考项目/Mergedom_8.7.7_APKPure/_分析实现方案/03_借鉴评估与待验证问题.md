# Mergedom：哪些值得借鉴，哪些还需要验证

复核日期：2026-09-26 · Mergedom（目录标记 8.7.7）与我方设计的比较。

## 1. 我们要借鉴的是哪些问题的解法

比较基线为 [02a 原架构详解](/Users/betta/Company/Projects/MergeTwo/_Plan/02a_逻辑表现分离架构详解.md)、[10 Function／Effect 讨论](/Users/betta/Company/Projects/MergeTwo/_Plan/10_Function与Effect建模讨论.md)；二合适配与确认范围按 [02](/Users/betta/Company/Projects/MergeTwo/_Plan/02_架构与参考取舍.md)、[03](/Users/betta/Company/Projects/MergeTwo/_Plan/03_状态模型与Profile.md)、[09](/Users/betta/Company/Projects/MergeTwo/_Plan/09_决策与接续记录.md) 区分。

我们的已确认范围是独立核心棋盘，接入最终宿主的 Profile 数据，本地规则和保存先行，首期只做售出／删除专用撤销，不做订单。执行与保存边界（Q02）、能力和效果如何组合（Q11）仍未定案。

因此，下面关注的是：它怎样分开格子与物品、怎样组织生成器、怎样安排数据修改和动画，以及这些做法接入我们的目标要付出什么代价。**可借鉴是候选建议，不表示用户已经批准；待验证也不表示发现了已复现的缺陷。**

## 2. 与我们讨论的架构，主要差在哪里

我们讨论的方案希望让业务对象管理身份和规则，让显示对象管理画面；一次操作先确定并应用数据变化，再通知显示。Mergedom 把更多职责放在同一个场景对象中，合成中途还会等待异步任务。因此，能借鉴它怎样拆分产出能力，但不能直接把其执行顺序当成我们的提交顺序。

下表对应我方设计中的主要概念。“Apply”指真正修改业务数据的阶段；“Batch”指一组改动，它本身并不自动保证出错后回滚。

| 我方概念 | Mergedom 近似对应与关键差异 |
| --- | --- |
| Entity | BaseItem 合并业务数据、能力宿主和 Unity 资源；Slot 也含业务与显示行为。未见独立业务实例 ID |
| EntityView | Visual／Animator／Timer、Slot 的 Collider／Lock 分散承担；未见独立 View 绑定与寿命协议 |
| 逻辑 Function | ItemProducer 列表接近专门能力集合，直接拥有容量／时间；普通合成规则仍在基类／Merger |
| 表现 Function | Timer、Animator、BubbleComponent 与业务混合，未见独立有序 FunctionController 或与 Producer 一一对应 |
| Command（操作意图） | 输入直达 Mover／Slot／Item，时间由协程触发，SignalBus 传通知；未证明按先后排队或统一重验 |
| CommandConsumer | 规则分布在 InteractWithBoardSlot、CanMergeWith、TryProduce 及子类，未形成只读收集阶段 |
| AtomicOperation／Batch | Merge 跨 async，Produce 直接修改＋回调，与同步 Apply 后表现不同；我方基础 Batch 也不自动回滚 |
| Effect | 格锁／物锁是布尔值，气泡是专门 Item＋组件；EffectsManager 仅有 VFX 证据 |
| State／Data（当前状态） | 次数、充能、时间、锁、IsPicked、交互开关分散存储；不能据此主张 Effect 替代全部业务状态 |
| Profile／保存记录 | 采集、复制、转保存格式、标记待保存、序列化；未定位所有数据修改成功后的统一保存入口 |
| 运行与持久身份 | 普通合成复用源对象，存档按槽位重建、能力按下标；不同于我方候选的新合成身份＋资源复用 |

## 3. 哪些值得借鉴，哪些需要改造

以下均为**候选建议，不是已经批准的方案**。可直接借鉴的是拆分问题的思路；本项目的代码依赖 Unity 和现有服务，不能原样作为我们的独立规则实现。

| 主题 | 取舍与落到我方的要求 |
| --- | --- |
| 格子与物品的归属 | **借鉴分开保存状态。** 轻量格子与独立物品已经能表达“锁位置”或“锁物品”，不必给每格建立完整实体树；交换时是否移动格锁应由我方规则明确，不能照搬 Swap |
| 配置、能力与保存 | **借鉴三者分开，改造关联方式。** 共享配置保持只读，能力保存自己的次数和时间。若采用多份 Function，应以稳定键或明确迁移恢复状态，补充顺序、冲突、异常及显示数量约束；不默认多份能力一起成功 |
| 冷却与自动产出 | **借鉴先恢复次数、再尝试产出。** 保存截止时间，同时定义时钟回拨、格式、有效间隔与上限。补次数和补放物品、储备次数和满盘重试分别处理；尤其要明确剩余轮数怎样限制补算，不能照搬分别截断两个计数的算法 |
| 空间、费用与随机 | **借鉴有位置后才选择产物。** 进一步把落点、产物、费用和随机结果一起规划并应用；本项目的异常退回尚未证明。附近候选有重复，若我方需要均匀或固定落点，应另定搜索规则 |
| 合成提示 | **借鉴按种类与等级分组的可重建缓存。** 棋盘占位仍是依据，小棋盘先整盘重建，实际测量后再决定增量更新 |
| 双向位置关系 | **保留查询便利，集中维护。** 同一次 Apply 更新格子和物品两边，检查一格至多一物、引用相互一致；清空一边不能视为移除已经完成 |
| 合成、产出与表现 | **不沿用业务修改和动画等待交错的顺序。** 明确整次数据修改完成点，再通知显示。普通 OnMerged 本身虽不挂起，合成前段仍有等待；我方 Batch 同步 Apply 也不等于自动回滚，必须单独处理收集失败和写入异常 |
| 对象池与迟到回调 | **复用显示资源，另管业务身份。** 停止计时、订阅与动画；每次绑定使用不同编号，回调只作用于对应绑定。不能让旧完成函数直接开放新操作的交互；业务对象在无 View 时是否继续存活也要明确 |
| 快照与文件保存 | **借鉴先复制再交给宿主，改造保存时点。** 统一在完整业务修改成功后生成快照，区分快照发布和文件写入成功；覆盖保存开关、暂停时立即保存、空盘和暂停。具体契约仍按 Q02／Q08 讨论 |
| 新状态的保存 | **不采用分散维护字段却缺少整链检查的做法。** 气泡三字段缺口说明新增状态必须贯通采集、复制、格式转换和恢复，并验证保存后重新读取；实际游戏是否丢失仍待验证 |
| 售出与撤销 | **有条件借鉴暂停冷却。** 顺延截止时间适用于“售出期间不计时”；若选择自然流逝就不能沿用。金额、身份、原格冲突和跨关闭规则仍按 Q05 确定 |
| 未知配置 | **不直接沿用清空记录。** 原处理能避免构造无效物品，我方若希望诊断配置缺失并保留可恢复数据，应选择另一种容错策略；这属于目标差异，并非直接认定原项目错误 |
| Function／Effect 的规模 | **按组合需求增加抽象。** 少量布尔状态和专门 Producer 已能实现现有机制；Effect 实例 ID、多来源叠加和完整生命周期应由具体样例证明，不给每个领域方法包装 Function，也不让 Effect 替代所有业务状态 |

## 4. 扩展性推演：假设，不是本游戏已实现的功能

### 假设 A：自动生成器暂时被冻结

可复用 ItemProducer 的容量／截止时间与 Auto 的触发，但仅把 TapItemProducer.CanProduce=false 不足以停止 Auto；只把 Slot.IsInteractable=false 也未必阻止自动对象寻找其它落点，因为 TryProduce 的交互限制主要检查目标落点。

需要为 BaseItem／Producer 加冻结数据，在 TryProduce、Auto 重试／到期入口检查；选择暂停 EndDate 或自然计时，解冻时保留其它交互限制；补 BoardSlotData、采集、Clone、DataObjectBoard 双向转换和恢复；新增显示并在 Reset 清理。若还禁拖／禁目标合成，需改 ItemMover／CanMergeWith。此例可检验我方统一权限查询与时间规则，成本跨能力、输入、存档、显示。

### 假设 B：同一格有地块锁，里面的物品又是气泡

可复用两者现有字段，但格锁 SetLock 会隐藏整个 Item；BubbleComponent 的 Timer 是否仍执行，取决于外部 Timer 服务的调度，不能假设 GameObject 隐藏就暂停。解除格锁后气泡应继续原期限还是重设期限，需要产品规则；本项目气泡转换直接换 Slot.Item，又需确认是否允许在锁格里转换。

需审核 BoardController.Create／解锁 helper、BubbleItem.Init、BubbleComponent 转换、Slot.SetLock 和输入权限；补气泡存档往返，Reset 清 Timer 与可视绑定。分开存储提供表达基础，组合行为仍需验证，可用于讨论我方 CellEffect／ItemEffect 的归属。

### 假设 C：物品被消耗时触发邻格变化

可复用 PostMergeSignal 的旧等级／物品／目标格信息和四邻查询；但仅监听 PostMerge 不能覆盖出售、生成器耗尽、气泡替换等其他移除原因。若直接在信号订阅中改邻格并继续触发信号，执行顺序、重复处理和结束条件必须另建约定。

需明确“消费原因＋来源实例＋位置＋本次关联”事件数据，审核 Merger、Producer.Dispose、气泡转换及外部出售入口，定义去重／顺序／传播终止；新增状态进入采集和紧凑存档，动画展示结果。缺售出入口仍不能证明覆盖所有消费；该推演不构成首版引入通用连锁引擎的建议。

## 5. 待验证问题

以下均为**待验证**，按当前影响排序。列出的检查用于补齐静态分析边界，本轮没有执行。

### 5.1 气泡保存并重开后，内容还完整吗？

气泡三字段采集／Clone／Init 均使用，DataObjectBoard 紧凑转换没有。仍缺对应版本真实 JSON、序列化回调注册／存储服务；包版本证明。

**验证办法：** 一颗未到期气泡保存→清进程内状态→从磁盘恢复；逐层比对内容 ID、等级、SpawnTime。既测 DTO 往返也测实机，不把同进程 Clone 当落盘。

### 5.2 合成到一半暂停或退出，会保存什么？

合成在异步等待前后分阶段修改格子内容和交互状态。 还缺动画服务、异步异常路径、暂停事件注册和周期保存精确时机。

**验证办法：** 在首次等待期间暂停／退出；在清格后、升级后、PostMerge 后记录快照或注入中断，区分实际可暂停的异步点和同一调用内的观察点。普通 OnMerged 无额外等待；只有确认会挂起的特殊覆写才另测该等待段。检查恢复后每格单占、无重复或损失，并分清内存、快照和磁盘记录。

### 5.3 旧动画会不会影响下一次操作？

移动完成函数修改当时记住的格子，却读取当前 pickedItem；本段未检查是否还是同一次绑定。产出落点何时重新开放也未贯通。 还缺ItemAnimator／动画注册表、取消委托协议、所有池调用者。

**验证办法：** A 动画未结束时开始 B 操作，或回池再复用 A；旧完成／取消回调不得影响新物、错误发信号或开放他人交互限制；产出结束及取消都需核对落点最终是否可交互。

### 5.4 合成中被消耗的目标物品，最终由谁回收？

普通合成摘除 secondItem 占位，最终回池拥有者未定位。 还缺PreMerge 动画消费者、ItemRemoved 订阅者与池间接调用映射。

**验证办法：** 跟踪 secondItem 的 active、Slot 回指、Producer、池列表；成功／取消／异常各释放一次，不提前复用。

### 5.5 产出、扣次数、扣费和保存能否保持一致？

Producer 先占位／发信号，再扣容量并请求费用。 还缺IGameManager 钱包方法、产出信号订阅顺序、失败行为。

**验证办法：** 注入费用拒绝／动画派发异常；检查占位、次数、费用和保存是否一致；普通满盘验证不扣费、不推进掉落游标。另测保存开关关闭、暂停时立即保存及移除最后一物后的重开结果，核对空盘是否真正落盘。

### 5.6 真正开启宝箱的入口在哪里？

Chest 有开箱条件提示、Board 追踪 openingChest，但点击方法本身未调用 StartRecharging。 还缺开箱 UI／Command／Popup 入口和相关服务。

**验证办法：** 两只空容量可充能宝箱依次请求开启；确定谁拦截第二次、首次何时写时间、何时保存；不以提示文案代替规则证明。

### 5.7 离线回来到底补次数，还是补物品？

开始／结束时间和离线补次数可见，Auto 可在同一调用链连续产出。补次数使用未按剩余轮数截断的 n，轮数计数另行封顶。 还缺实际配置间隔／上限、时间 API 符号、重试常数及后台生命周期。

**验证办法：** 离线小于／跨多个间隔、只剩最后一轮但离线跨多轮、满盘、正好上限和回拨；再测仍有储备次数时使用加速。分别记录补出的次数、轮数计数和实际放出的物品，判断真实配置是否触发多补或覆盖储备次数。

### 5.8 拖着气泡到期时，会发生什么？

Bubble 转换调用 WhilePicked，拖动钩子写 IsPicked。 还缺WhilePicked.MoveNext、Timer 实现、选择／拖起全部调用者。

**验证办法：** 到期时仅选中、正在拖、刚放下、对象被隐藏／回池分别观察；确认等待能取消且不写新绑定。

### 5.9 改变能力配置顺序后，旧状态会不会对应错？

配置按 Producer 下标恢复，后续能力共用副 Timer。 还缺真实多能力配置与版本迁移约定。

**验证办法：** 保存两个不同能力状态后交换配置顺序；再测三个能力的 UI 与恢复；据结果决定是否需要稳定能力键。

### 5.10 格子和物品的双向位置关系始终一致吗？

Slot 双向引用由多处维护，Swap 还交换格锁，GetFirstEmpty 不查格锁；附近搜索含斜角和重复候选。 还缺所有外部调用者与地图配置。

**验证办法：** 逐入口检查锁格＋空格、移动／交换／删除，确认底层方法的前置条件成立；用边角、仅斜角有空位和多个空位的布局检查实际落点范围，概率测试单独统计不同格而非候选列表下标。

### 5.11 售出撤销的完整规则是什么？

有 OnSell／OnUndoSell 暂停钩子。 还缺售出管理者、金额／撤销凭据、原格冲突处理和跨关闭协议。

**验证办法：** 出售后换选、花费收入、原格占用、关闭重开、撤销两次；区分钩子存在与完整可撤销业务。

### 5.12 这些材料能否确认来自同一个版本？

只有目录名版本、元数据和原生文本。 还缺APK versionName／versionCode、构建哈希、符号／metadata 匹配和资源。

**验证办法：** 核对最小构建清单及缺失类是否与当前方法体匹配；补少量真实配置、保存文本和资源即可针对性验证，无需先重新完整逆向。
