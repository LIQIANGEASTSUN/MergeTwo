# Mergedom 8.7.7：这套二合玩法是怎样实现的

本报告先解释 Mergedom 自己怎样保存棋盘、处理合成和生成物品，再讨论哪些做法适合我们的设计。分析日期：2026-09-25；8.7.7 是目录标记，版本尚未独立核实。

## 先看三个核心结论

**第一，屏幕上的物品对象也在保存游戏规则所需的数据。** 一个物品对象既记着等级、锁定状态和所在格子，也持有图片、动画和计时显示的引用。因此，虽然移动、合成另有专门的类负责，规则仍依赖 Unity 场景对象。[对象与字段证据 E01](04_证据索引.md#e01)

**第二，普通合成会保留拖入的那个对象，并且不是一次性完成所有修改。** 例如把二级物品 A 拖到二级物品 B 上：代码先启动表现并等待，之后让 A 占据 B 的格子，再把 A 升到三级。B 离开该格，但它最终何时回到对象池，现有材料还没有查清。这是说明实现顺序的例子，不是实机测试。[合成证据 E08](04_证据索引.md#e08)、[升级证据 E09](04_证据索引.md#e09)

**第三，生成器把“恢复可生成次数”和“真的放出物品”分开处理。** 文中把一份产出能力称为 Producer：它保存可用次数和冷却时间，同一物品可以配置多份。冷却结束先补充次数，自动生成器再额外尝试生成。这种拆分值得借鉴；能力保存按列表顺序对应、业务修改与动画交错，则需要谨慎取舍。[能力装配 E10](04_证据索引.md#e10)、[冷却 E15](04_证据索引.md#e15)、[自动产出 E16](04_证据索引.md#e16)

另一个优先核查的问题是气泡存档：采集和恢复代码使用气泡内容、等级、时间三个字段，但中间的紧凑保存格式没有对应转换。**这能确认一个转换缺口，还不能确认游戏中已经发生数据丢失。** [存档证据 E22](04_证据索引.md#e22)

## 材料与可信程度

材料共 **219 个文件：75 个 C# 元数据、90 个 ARM64 反汇编、54 个 Ghidra 伪 C**。C# 方法体为空，行为依据原生实现；缺配置资产、包元数据和可运行工程，完整材料边界见 [E00](04_证据索引.md#e00)。

全文区分三种结论：**已确认（静态证据）**表示代码材料直接支持；**较强推断**表示有依据，但缺少关键环节；**待验证**表示还需要实现或运行结果才能判断。静态分析就是阅读代码、没有运行游戏；本轮也没有执行 Unity 或存档往返测试。“未找到”仅限本包材料，不等于完整游戏不存在该功能。
