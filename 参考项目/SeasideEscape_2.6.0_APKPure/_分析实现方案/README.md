# Seaside Escape 2.6.0：它怎样实现二合棋盘

这份分析想回答两个问题：**这款游戏实际上怎样工作？其中哪些做法适合我们的棋盘？**

最值得先记住的是：它把格子设计得很轻，把身份和能力主要放在物品上；但逻辑与动画的分工并不一致——普通合成先完成物品替换，剪刀拆分却要等动画回调才真正修改棋盘。

以下结论来自恢复 Lua 的静态阅读，没有运行游戏。本文先讲含义，具体方法、行号和缺失证据放在后面的专题与索引中。

## 先用几个场景理解这个项目

### 1. 格子记录“谁在这里”，物品记录“我是谁、能做什么”

主棋盘是 7 列、9 行的二维表。格子主要保存物品 ID；另一份物品索引根据 ID 找到真正的物品对象。物品对象保存种类、位置和能力，例如能否生成、剩余次数、吞入了多少材料。

因此，这里的格子不是和物品同样完整的业务对象。移动物品主要是调整格位占用和物品位置；正常入库也保留原物品的身份。**可借鉴之处是职责简单；需要自己保证的是两份位置记录始终一致。** [已确认（静态证据）：E02–E06、E28](04_证据索引.md#e02)

### 2. 普通合成与剪刀拆分，对动画的依赖不同

普通合成先删除两个旧物，创建结果物并放到目标格，再通知画面播放合成动画。所以即使旧图标还在靠拢，新物品已经存在于逻辑棋盘中。不过，邻格震动和额外产出还会在通知画面后继续处理，不能把整次连带变化都说成已经统一完成。[已确认（静态证据）：E11–E13](04_证据索引.md#e11)

剪刀拆分的顺序不同：先播放动画，到了 0.5 秒的回调，才调用真正的拆分函数。批量吞入材料也要等图标飞到目标后，才逐个消费材料。因此，**不能直接拿掉画面，就认为所有核心玩法仍能正常执行。** 取消动画后是否会卡住，还需要检查缺失的统一取消逻辑，尚未运行验证。[已确认（静态证据）：E23–E25](04_证据索引.md#e23)

### 3. 蛛网和纸箱保存的是“打开后生成什么”

被蛛网包住的物品，并不是一个正常物品对象上再盖一个独立效果。当前对象本身就是“蛛网物品”，内部保存打开后的物品代码。解除时，旧对象被替换为新对象，新对象获得新的 ID。

这适合“拆掉外壳，得到一件新物品”的玩法。如果我们的需求是“给已有生成器临时冻结，解冻后保留原来的次数和冷却”，就不能直接照搬这种做法。地格锁又是另一件事：活动中的云锁留在棋盘坐标上，不随物品移动。[已确认（静态证据）：E07、E18–E19、E33](04_证据索引.md#e07)

### 4. 点击生成，涉及多次依次发生的修改

可见的主要顺序是：

```text
检查能否生成
  → 减少生成器次数、选出产物
  → 创建产物并占格
  → 通知画面播放产出动画
  → 扣能量
  → 处理生成器耗尽或变形
```

这里“通知画面”发生在扣能量之前。**较强推断：**如果同步执行的画面监听中途抛错，后续步骤可能没执行，而前面的次数和产物已改变。这是从调用顺序推导出的风险，不是已经复现的游戏漏洞。这个例子能帮助我们明确：如果采用统一 Apply，应该把哪些相关修改放进同一次完整执行。[已确认顺序及推断依据：E15–E17、E21、E36](04_证据索引.md#e15)

### 5. “冷却好了”与“自动生成了”是两个动作

每秒更新负责按时间恢复可用次数；另一条更新路径才尝试自动生成物品。恢复次数时，不一定有空间放产物；有些自动生成器只检查周围八格，有些可以找全盘空位。

因此，源码能证明“保存时间起点后，可按时间差恢复次数”，但不能据此推出“离线多久，就按周期补出多少物品”。完整的后台和离线调度没有保留。[已确认（静态证据）及待验证边界：E14、E16、E29、E42](04_证据索引.md#e14)

## 阅读正文前，先认识这些名称

| 名称 | 在本文中怎么理解 |
| --- | --- |
| Model／逻辑对象 | 保存规则所依据的数据，并执行业务。这里的 Model 并非全部脱离 UI。 |
| View／表现对象 | 绑定逻辑对象，处理图标、动画与部分输入。它不是物品的持久身份。 |
| ItemModel | 一件具体物品的运行对象。两件同种物品可以有相同种类，但 ID 不同。 |
| ItemManager／Layer | 前者根据 ID 找物品，后者记录物品占哪个格。 |
| 组件／能力 | 附在物品上的行为对象，例如生成能力 ItemSpread；此处不是指 Unity 的画面组件。 |
| code／Type | code 是保存和创建物品用的代码，可含包装前缀；Type 是解析得到的配置种类。 |
| 替换／Replace | 移除旧业务物品，再创建新物品；不只是更换图片。 |
| 事件／回调 | 事件通知订阅者；回调是约定在某个时点执行的函数。它们可能修改业务，并非天然只负责显示。 |
| 存档缓存／落盘 | 前者是内存中待保存的数据，后者是实际写入数据库；两者不在同一时点完成。 |

证据标签也有固定含义：**已确认（静态证据）**是源码直接可见；**较强推断**是根据源码推导、但还缺验证；**待验证**是缺配置、调用链或运行证据。E 编号只是检索入口，不需要记住。

## 对我们最有用的取舍

可以先学它的**轻量格子、独立物品身份、配置式合成关系、能力专用数据和明确落点顺序**。这些思想并不要求我们采用完整商业系统，也不要求每个概念都增加一层框架。

对“动画可以取消，但逻辑结果必须完整成立”的目标，应重点审视它的拆分、批量吞噬和产出中途通知画面的做法。这里有具体时序可以作为设计检验用例，而不只是抽象地讨论“分层是否纯粹”。采用条件和三个扩展推演见 [03](03_借鉴评估与待验证问题.md)。
