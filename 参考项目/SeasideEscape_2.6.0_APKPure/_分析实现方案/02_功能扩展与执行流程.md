# 02 · Seaside Escape 2.6.0：功能与执行流程

复核日期：2026-09-26。目标为 `参考项目/SeasideEscape_2.6.0_APKPure/`，本文位于其 `_分析实现方案/`。以下为恢复 Lua 可见的静态行为；配置启用情况、异常是否实际发生及缺失的外部调用，分别注明边界，没有运行验证。

## 1. 输入与操作权限

主盘画面保存选中坐标，按下时查教程限制、禁用格和 View 的 `cantClick`；拖动时检查能否移动，再更新图标 Transform。松手时再次检查物品当前所在格是否仍指向同一对象，并重新查询移动权限，然后才请求入库或拖放。

松手目标还有一个辅助规则：如果最近 0.15 秒记录过可合成物，且其横纵坐标距落点都不超过一格，就沿用这个目标；这不是全盘寻找最近对象。教程或禁用目标会被转成无效坐标。输入取消则通知图标回逻辑位置，不修改占位。

再次点击已选中的物品，通常进入 TapItem；但订单、开启按钮、选择箱、待选择物品有优先分支，等级障碍首次点击也可触发 Tap。TapItem 本身只是把 OnTap 派发给全部组件，没有统一事务或完整权限验证。

| 操作 | 主要判断位置与规则 |
| --- | --- |
| 拖动／换位 | Item.CanMove 否决配置 `Fixed==1`、任何组件 `canMove=false` 和临时 `m_bLocked`；换位还查目标能否移动 |
| 合成 | 棋盘检查箱子当前使用状态、种类、合成结果、蛛网／冰、万能物和剪刀例外；并不统一调用两物的 CanMove |
| 拆分 | 检查棋盘是否满、剪刀次数和目标 CanSplit；开始确认前再取目标前一级种类 |
| 手动／自动生成 | 生成组件检查阶段、次数、吞噬、空间等；手动另查费用，自动入口另查临时锁 |
| 售出 | CanItemSell 检查有无售价和功能开关；SellItem 执行体没有重做全部判断 |
| 正常入库 | 先查可移动；拒绝有期限的变形物、气泡、冰、未清空活动 Token、正在开启箱子及部分初始化／活动类型 |

**权限是分散的。** 输入层做过检查，不代表直接调用模型方法仍会得到相同保护。例如 DragItem 执行体验证坐标与源对象，却不重新检查源 CanMove；激活也没有统一服从 `m_bLocked`。多个组件对移动的独立否决可以共存，但临时布尔锁没有持有者，清除一个来源的锁可能覆盖另一个来源。[输入处理](../code/Lua/decompiled/Board/View/BaseSceneBoardView.lua#L793)、[移动权限](../code/Lua/decompiled/Board/Model/Item/ItemModel.lua#L220)

## 2. 拖放、换位与普通合成

### 拖放的分支顺序

DragItem 先验证目标坐标和源对象当前占位，随后依次处理：

1. 目标为空或仍是自己：清源格、写目标格、更新物品位置。
2. 源是剪刀而目标不是剪刀：进入拆分分支；不能拆就提示并结束。
3. 能合成：执行普通合成或条件确认分支。
4. 目标能吞入来源：调用 Swallow。
5. 以上均不成立：目标可移动才尝试换位。开关决定直接交换，或把目标放到附近空位；找不到时以源格作退路。

**两个剪刀是例外：**CanItemSplit 此时只返回 false，不返回拆分组件，后续仍可合并剪刀次数；合并总次数不能超过 9999。早期历史分析把“源有剪刀”一律描述为停止于拆分，范围过宽。

正常物品可以合进蛛网／冰包装，判断会读取内层种类；双方都是这两类包装时拒绝。合成结果主要来自物品或组件的 GetMergedType；万能物还检查两侧 CanMergeByJoker。箱子的 `IsChestUsedOnce` 实际判断是“存在开启时长，且**当前剩余次数不等于最大次数**”，并非保存了一个永久的“曾使用过”标志。

确认窗与执行方法中的 `CheckItemStillInPosition` 只确认“物品当前声明的位置仍持有该对象”，**不比较操作开始时的原始位置，也不完整重跑合成条件**。合成确认窗本身还有测试／自动运行条件，不能把代码存在理解成正式版本每次都会弹出；剪刀的确认流程则有明确直接调用。[拖放与确认分支](../code/Lua/decompiled/Board/Model/Board/BaseSceneBoardModel.lua#L803)

### 普通合成怎样写数据

```text
移除来源：清格 → OnRemoved → 删除 Item 记录
  → 计算结果种类与成本
  → 移除目标，创建结果物
  → 保存新物属性，写目标占位
  → 发布 MergeItem，创建结果 View、安排旧 View 退场
  → 检查两旧位置的四邻，触发 OnShock
  → 尝试额外冰／气泡和合成奖励
  → 更新订单并发布全局 ItemMerged
```

新物品在 MergeItem 之前已占格，0.1 秒的合成回调只是处理旧画面；冰的演出可额外延迟 0.5 秒，不推迟核心新物建立。旧 View 缺失时，合成表现有提前返回分支，不会自动撤销已经写入的业务结果。

但是 **MergeItem 不是整个过程的首次通知**。保存物品属性会发布 ItemPropertyChanged；创建新物时该事件甚至早于写入格位。ReplaceItem 也会发布 ItemReplaced。因此只能说“核心替换早于专用合成动画”，不能说“先完成全部业务，才发生任何外部回调”。[保存与创建顺序](../code/Lua/decompiled/Board/Model/Board/BaseBoardModel.lua#L211)

四邻处理按右、下、左、上方向，交替查询目标旧位置和来源旧位置的邻居，没有统一去重集合。同一个格子可能被访问两次；每次读取的是当时的新状态，不是操作前快照。额外冰、气泡和奖励受功能开关、概率、空位、订单和活动条件影响，实际配置数值未保留。[合成与邻格处理](../code/Lua/decompiled/Board/Model/Board/BaseSceneBoardModel.lua#L909)

## 3. 生成器、开启箱与点击产出

### 状态和数据

生成能力 ItemSpread 附在物品上，没有独立 ID。配置决定自动模式、初始化／开启时长、单轮次数、储备周期、恢复时长、费用、产物规则和变形阈值；运行状态保存于宿主 Item 行。

| 阶段 | 进入和含义 |
| --- | --- |
| Initializing | 有初始化时长时优先进入，等待首次准备完成 |
| Closed | 无初始化时长但有开启时长，等待 OnOpen |
| Opening | OnOpen 开始开启计时 |
| Opened | 已开启，是否能生成仍取决于次数、空间、吞噬和费用 |
| OpenFinish | 恢复值为负等非循环配置耗尽后的结束阶段 |

初始化和开启完成都会进入 Opened；没有初始化或开启时长的物品，创建时就进入 Opened。组件持久化阶段、计时起点、可用次数、储备次数、累计产出、列表剩余项，以及部分箱子的额外运行数据。恢复按配置重装再读回；特定箱子的开启时长配置变化还可重置正在进行的计时，不能假定所有存档起点永远原样保留。

可开启宝箱是这个能力的一种配置，纸箱则是另一种包装物。画面会依据 Closed 和“盘上是否已有 Opening”显示叹号，但缺少开启按钮实现，无法证明全局只能同时开一个箱子。OnOpen 本身也没有完整阶段前置检查。[生成阶段及恢复](../code/Lua/decompiled/Board/Model/Item/ItemSpread.lua#L13)

### 一次普通手动产出的顺序

| 顺序 | 实际修改与边界 |
| --- | --- |
| 1 | OnTap 处理工具箱收集等专用分支，再检查 OpenFinish、点击锁及 NoCDTrain 限制；部分测试分支一次尝试多次 |
| 2 | `_TrySpread` 检查吞噬进度、普通产物的满盘、Closed／Opening／Initializing、可用次数和手动能量余额 |
| 3 | 普通 GenerateItemCode 路径增加累计产出、减少次数，推进冷却；选择产物、推进列表或序列，通知阶段变化并保存生成器 |
| 4 | 手动产出在选好产物后查找落点：先同链贴近，失败再转方环 |
| 5 | 有 code 时调用 SpreadItem：创建物品、保存属性、占格、通知产出表现；特殊原始 code 可另建只供飞行动画使用的临时物 |
| 6 | 手动有能量费用时，按实际等级跨度修正消耗，再调用钱包 Consume；没有使用其失败返回值 |
| 7 | 检查变形阈值、耗尽删除、OpenFinish 或重新喂料；结束／变形后可能返回 false |

由此可确认：产物、次数、随机选择与费用不是统一提交；`GenerateItemCode` 不是纯查询，`false` 也不等于“什么都没发生”。普通前置满盘会在选产物前拒绝；不能把它与“选产物之后因异常或重入未完成”混写。

费用与结果之间还可能经过同步监听、订单状态更新、活动和评分处理。正常的“缺 View 提前返回”和“表现监听抛异常”是两种情况：前者可继续后续业务，后者可能打断它。**较强推断：**中途异常可能留下次数／产物已改、费用未扣或后续变形未做的部分结果；没有复现线上故障。[产出及扣费顺序](../code/Lua/decompiled/Board/Model/Item/ItemSpread.lua#L1187)

### 不能忽略的生成例外

此前把 GenerateItemCode 概括为“一定先扣次数并保存”不够准确。可见例外包括：

- 幸运产出可提前返回，绕过普通累计次数、剩余次数及保存段。
- 加速状态下普通路径不减少剩余次数；额外工具产出可回补本次次数和累计产出。
- 气球产出有专门早返路径，按自身结束条件设置次数，不走普通末尾保存段。
- NotItem 可调用 ItemBattery.OnSpread，不返回棋盘物品 code，空间检查也有豁免；不能据“无产物对象”断言没有业务效果。
- 工具箱直接收集、Sunshine 奖励、教程强制产物、补偿、活动和特殊箱子都有旁路，不能把普通流程推广为全项目所有产出。

这些是分支事实；真实启用组合、概率和产品语义仍受缺失配置约束。[选择与计数分支](../code/Lua/decompiled/Board/Model/Item/ItemSpread.lua#L438)

### 随机和顺序由谁保存

List 模式从列表头取出项目，保存宿主剩余列表。普通权重模式直接使用权重抽选；RandomSequnce 通常把整数权重展开并洗牌，保存剩余顺序，序列消耗完或配置权重变化时重建。

普通预定序列按 **Type 共享**，并非每个生成器独立。能量箱另有按实例 ID 保存的序列；幸运和其它专用分支又可能使用独立模型。`FindNextGenerateItemCode` 虽不移除首项，但可能创建并保存新序列，也不能一概视为纯预览。全局随机种子和完整随机状态恢复未定位到，不承诺确定性回放。[固定序列](../code/Lua/decompiled/Board/Model/Board/ItemFixedSpreadModel.lua#L4)

## 4. 冷却、自动产出与离线

GameModel 根据 `DeviceInfo.GetCpuTime()` 加服务端偏移更新当前时间，存在强网络／后台相关的特殊冻结或校正分支；GetServerTime 读取这个缓存。缺少顶层调度与桥接，不能把它直接当成已确认始终推进的 UTC 时钟。

主场景棋盘只有在当前游戏模式匹配时才推进物品；库存不在常规棋盘扫描中，但全体物品 Refresh 是另一条入口。时间相关行为因此不能只按“对象还在 ItemManager”推断。

生成器有两条不同更新：

```text
每秒更新：设置计时起点 → 按经过时间判断开启／恢复 → 保存次数
每帧更新：自动配置＋次数非零＋未临时锁定＋非 HuntExtraSpread 排除 → 尝试产出
```

`m_auto>=1` 表示自动，`==2` 使用全盘落点，其余自动路径只查八邻。自动尝试没有普通手动能量检查和扣费，普通失败不发手动失败提示。次数有余时可连续多个 Update 尝试，没有统一的“每颗固定 N 秒”入口限制。

落点与选产物的顺序也不同：全盘自动与手动一样，先选产物，再查同链贴近或方环空位；邻格自动先找到八邻空位，才调用会修改次数和序列的 GenerateItemCode。早期历史分析将两者都概括为“先选产物再找位置”，需要收窄。

两级次数也不是每秒加一：储备最大值是单轮次数乘子周期数；短恢复补齐本轮缺口并减少储备。储备耗尽时可从原起点继续推进长恢复；长恢复完成补满两级。带吞噬且两级容量不同的组合有专门分支，不能套用普通恢复。起点为负且需要计时时，使用当前时间启动，并在这次调用先返回。

**较强推断：**已有持久计时起点的生成器，重新推进时可以按差值恢复到就绪。**待验证：**隐藏、后台、进程重启及取出库存的实际补时顺序；也没有证据证明按离线时长累计补出完整产量。满盘一般阻止尝试产出，不等于取消已有冷却计时。[时钟入口](../code/Lua/decompiled/Model/GameModel.lua#L20)、[恢复次数](../code/Lua/decompiled/Board/Model/Item/ItemSpread.lua#L182)

## 5. 纸箱、蛛网、等级障碍和灰物

这些功能由占格的包装 Item 表达，内层保存 code。四类组件均声明 `canMove=false`，但售出、目标合成等由其它规则决定。

| 包装 | 触发与实际变化 | 保存和组合边界 |
| --- | --- | --- |
| PaperBox | 邻近合成的 OnShock 触发 ReplaceItem，再发布 CollapseItem | 主盘／Hunt 可带 Sticker；没有完整内层对象 |
| Cobweb | 普通物可合进内层同种类并直接得到升级结果；也可按条件付费破网 | 破网价格依赖功能开放、内层种类和评分，可能取不到；缺 UI 前置条件，不能认为任意直接调用都有效 |
| MapBlocker | 监听等级和教程；达到等级后摇动、倒计数或点击解除 | 倒计数从 5 减到小于 0 才解除，不应写成精确 5 秒；解除后移除相关监听；恢复工厂可按当前等级直接去壳，临时倒计数不存档 |
| Gray | OnShock 替换物品；非 Freefall 分支继续调用 ShockNearby | 主盘未定位该方法；只可确认活动上下文的扩散能力，不能推出主盘已配置 |

蛛网清楚地体现“不能作为主动拖动源，却能作为合成目标”：目标合成先于换位权限检查。[包装解除](../code/Lua/decompiled/Board/Model/Item/ItemPaperBox.lua#L1)、[蛛网限制](../code/Lua/decompiled/Board/Model/Item/ItemCobweb.lua#L1)冰没有组件级不可拖声明，不能把同一结论推广给冰。

外壳解除通常先建立新物及其权限，再处理旧外壳动画。Collapse 先加新 View，旧壳约 1.2 秒后移除；付费破网使用 BubbleBreak 表现。新物能被逻辑查询，并不证明动画任意时点都能被实际点击，命中和遮挡还依赖资源与输入桥接。

蛛网图标来自内层 code，主盘默认颜色为 `(0.63,0.533,0.467)`；这是颜色，不是已确认透明度。活动还可覆盖该颜色，Freefall 使用白色。专用罩层、灰物材质和精确透明参数缺失。

Sticker 从坐标奖励配置及 BoxTypeMap 取奖励，与纸箱都响应 OnShock，顺序没有业务保证。它以 `m_hasAcquired` 防重复领取，纸箱解除时还传入新物引用；奖励不是独立持久 Cell 实体。嵌套包装继续按 code 解析，不会自动继承已解除外层的能力状态。

## 6. 气泡与限时冰

二者都是包装组件，不是给一个仍活跃的生成器附加冻结。它们本身没有 `canMove=false`，实际移动性仍受 Fixed 配置影响；正常库存明确拒绝二者。

### 气泡

气泡按内层配置取得价格，再由价格配置决定期限；60 秒只是兜底。主盘气泡还附加 ItemToken。保存的是 `bubbleStartTimer`，恢复时重新算期限；`m_lockBreak` 只阻止到期分支，不暂停时间比例，也不保存。目录中只找到 SetLockBreak 定义，不能确认选中保护机制。

普通破泡可以受免费次数和教程价格影响，并非每次都扣钻石。主要顺序是检查／消费、替换内层物、减气泡计数、发布破泡事件、显式 Destroy。到期先按 BubbleBroken 权重选结果，**还会经过每日上限转换**：特定结果达到上限后，可由钻石类改成能量类、能量类改成金币类；不能只写成一次独立随机抽取。主动删除则取 BubbleDelete 配置。

Hunt、CloudsDash、HuntMap 不走普通每秒到期转换，破泡走奖励发放后移除的专用分支。因此“气泡一定原地替换为内物”仅适用于普通路径。[气泡期限和转换](../code/Lua/decompiled/Board/Model/Item/ItemBubble.lua#L43)

画面显示内层图片及气泡动画；普通破泡／到期时，新物已存在，旧壳继续淡出。精确材质和点击遮挡待验证。

### 冰

开始时间和期限来自活动，工厂拿不到计时时直接创建 Coin01。普通冰到期或主动处理会换金币；临时冰取活动转换结果，结果不存在则删除。活动状态变化也可直接移除临时冰。

冰自身没有额外序列化覆盖，恢复重新从活动取得时间；活动期限完整保存链未覆盖。合成可读取内层种类，旧画面的爆冰延迟不推迟新合成物建立。解除或到期不会恢复一个此前完整保存的内层生成器及其原 ID。[冰的生命周期](../code/Lua/decompiled/Board/Model/Item/ItemIce.lua#L10)

## 7. 吞噬、变形与剪刀：动画参与业务的具体方式

### 吞噬

ItemSwallow 保存所需 code、数量、已吞进度，以及重复／逐次喂料配置；进度序列化为 `swallowInfo`。点击批量取料会扫描棋盘，跳过锁格；每帧也根据种类计数检查是否存在可吞材料。TapProtectionTime 当前为 0，不宜仅凭名称宣称有实际防连点时长。

- **拖入材料：**先检查能吞，再增加目标进度和成本、保存目标、删除源，随后发布 SwallowItem 播放飞行。
- **批量点击：**先选出一批来源并通知 View，图标逐个到达后才调用 Swallow；到达顺序由飞行距离影响，不是一个整体同时消费的批次。

Swallow 执行体重查来源和目标对象仍在当前容器，但**没有重新调用 CanSwallow 校验当前需求和容量**。已经移走／替换的对象可被拒绝；同一对象的需求状态变化是否安全，则不能由身份检查保证。

有 Spread 时，未喂满只是使产出不可用，不删除能力；喂满会通知生成能力初始化或恢复次数。重复或逐次喂料按各自配置清零进度。没有 Spread 且喂满时，可触发 Transform。单次消费已保存目标后，还可能改变后续能力状态，不能把“前面调用过保存”视为所有后续字段也已保存。

批量缺少目标 View 时直接返回；遍历途中缺某个来源 View 时也返回，已经安排的飞行动画没有在该方法中统一取消。运行是否造成部分结算仍需验证，不能认作全批次自动回滚。[吞噬结算](../code/Lua/decompiled/Board/Model/Item/ItemSwallow.lua#L150)、[批量表现回调](../code/Lua/decompiled/Board/View/BaseBoardView.lua#L227)

### 变形

ItemTransform 保存目标或权重、时长、开始时间和费用配置，计时保存列为 `transformStartTimer`。存在 Spread 时不自行处理点击；否则点击可扣能量并开始计时，或立即变形。每秒到期调用 Transform，普通路径 Replace 新物；活动还有独立变换层替换分支。

Turnbox 的模型先替换，新 View 创建后直接对新物 SetLocked(true)，动画完成清锁并刷新位置。这个布尔锁没有来源标识，也没有在该局部 Sequence 中配对取消解锁。**较强推断：**若取消不补执行完成回调，可能留下锁；外部 SafeKill／关闭协议缺失，不能断言必现。

**保存缺口须单独保留：**OnTap 开始有时长的变形时直接写 `m_startTimer` 并发事件，方法内没有立即 SaveItemProperty；OnTimeSkip 则明确会保存。不能因为有 `ToSerialization` 就说“开始变形必定已写入存档”。是否由外部补存待验证。[变形开始时点](../code/Lua/decompiled/Board/Model/Item/ItemTransform.lua#L53)

### 剪刀

剪刀次数保存为 `leftCount`。拆分前检查空间、次数和目标可拆分，取前一级种类并打开确认窗。确认后只发布 SplitItem；View 找不到两个旧对象就返回。找到时设置 UI 事件锁，先移除剪刀 View，再播放动画。

到 0.5 秒回调，**先调用 onEnd 清 UI 锁，再调用 DoSplitItem**。DoSplitItem 再次验证对象当前占位，但没有重查最初的全部空间／次数条件，也不验证捕获的目标位置仍是原位置。之后删剪刀和目标，按剩余次数决定是否生成后续剪刀，再找空位生成两个前一级物品。[拆分回调](../code/Lua/decompiled/Board/View/BaseBoardView.lua#L285)

这里有两个独立边界：

1. 取消动画且不执行回调时，业务拆分和解锁都可能未发生；完整取消协议待验证。
2. 两个产物先由 GenerateItem 保存，之后才按原目标一半分配评分及多项成本；DoSplitItem 和所读 View 回调中未见再次保存。数据库刷新不会自动重新读取这些普通字段，是否有其它路径补存待验证，不能说成本分配当场完整持久化。[拆分与成本分配](../code/Lua/decompiled/Board/Model/Item/ItemSplit.lua#L97)

## 8. 补充能力：层数与充能阶段

Sand 是不可移动的包装物，保存原始层数和当前层数。点击寻找扫帚，`m_bInSweeping` 阻止重复开始；OnSweep 减层，未清完保存，清完则震动邻格并替换内物。当前层数写入 `spreadState`，说明组件状态没有统一独立命名空间。具体扫帚动画闭环不在本次完整追踪范围。

Charge 保留 Initializing／Charging 两阶段，配置包含阶段、初始等级、权重和产物。创建时先按权重选阶段，再处理初始化时间；保存 `chargeStartTimer/chargeStage/chargeLevel`，到期转 Charging 并保存。恢复前的构造已可能消耗随机数，即使随后被存档阶段覆盖；“载入不影响随机序列”不能未经验证就成立。[层数保存](../code/Lua/decompiled/Board/Model/Item/ItemSand.lua#L11)、[充能阶段](../code/Lua/decompiled/Board/Model/Item/ItemCharge.lua#L40)

## 9. 正常库存、售出与撤销

正常 StoreItem 先登记 Inventory，再清棋盘占位，不删除 ItemManager 对象；取出则移除库存记录、写格位、更新棋盘引用与位置。因此 ID 和能力数据保留。工具类有“入库动作实际转奖励并移除”的专用分支，不属于普通库存迁移。

售出在有非零价格时先加收益，再清格、OnRemoved、删除 Item 记录，最后发事件。非零价 View 立即移除并播放独立奖励动画；零价删除缩小 0.5 秒后收尾。旧回调会核对当前 View 映射，若已被撤销生成的新 View 替换，只清旧资源。

UndoSellItem 接受旧 Item 对象，按以下顺序执行：

1. 原位空则恢复原位；原位被占而其它地方有空位，则把待恢复物放到空位。
2. 全盘满时，先删除原位占用物，把它的 code、部分成本及可选 Sunshine 关联写进产物缓存。
3. 扣回售出收益，但不检查 Consume 返回值；随后旧物更新位置、重新保存并占格，再创建新的 View。

该方法没有可见单次撤销凭据，也不重新创建一份稳定序列化副本。上层如何限制记录、金额不足、重复调用和跨关闭恢复，入口未保留；不能说玩家一定能重复利用。

**满盘挪物不等于完整保存另一个物品。** 这条 CacheItems 调用没有传原物 ID，也没有保存组件次数、冷却或吞噬进度。缓存虽写入部分成本列，当前 `GetItem` 返回的 cost 只含 freeScore；普通 PopCachedItem 再调用 GenerateItem 创建新 ID。因此原文“挪入缓存”必须与正常库存区分，不能暗示完整状态原样保留。[缓存数据](../code/Lua/decompiled/Board/Model/Board/ItemCacheModel.lua#L72)

## 10. 事件、旧回调与资源清理

| 机制 | 可确认的作用 | 不能据此保证什么 |
| --- | --- | --- |
| PairEvent | 复制监听列表后同步执行，通常按登记顺序 | 不是提交后才运行，也不局部隔离异常 |
| 全局 EventDispatcher | 当前派发中的嵌套事件先缓存，之后 FIFO 处理；监听者以弱键保存，顺序来自 pairs | 不给直接业务调用排队，不保证能力顺序或事务完整 |
| 组件派发 | 对各具体组件调用同名方法，基类提供空钩子 | 不支持靠返回值停止传播或声明依赖顺序 |
| View 添加／删除 | 检查占位冲突、清理重叠 View、维护模型对象映射 | 不保证资源创建失败后回滚逻辑，也不是所有删除都核对当前绑定 |

全局派发未在局部用受保护调用收尾。**较强推断：**监听抛异常不仅可能中断当前业务，还可能使“正在派发”的标记未清，后续事件继续进入缓存。是否由外层统一捕获并重置，材料缺失。[全局派发实现](../code/Lua/decompiled/Common/Event/EventDispatcher.lua#L53)

ItemView.OnDestroy 会解绑事件、取消按对象调度并 Kill 保存的 Tween；位置动画会尝试停止跳跃 Tween，跳跃辅助函数也有 OnKill 入口。但棋盘方法中还有局部 Sequence 和延迟回调，不能假定它们全部归 ItemView 管理。BoardView.OnDestroy 会解绑棋盘事件；主盘 OnDisable 的局部 Complete 不能推广为全部动画的完成保证。

普通业务移除只调用 OnRemoved，并非统一 Destroy。画面 RemoveSelf 是回池还是销毁、回池会不会执行 OnDestroy、SafeKill 是否补完成回调，都缺工厂或桥接实现。既有身份检查、旧 View 比较和局部门禁应保留，但目前没有证据证明关闭、重建、换绑和取消在所有路径上都有统一收尾。[ItemView 销毁清理](../code/Lua/decompiled/Board/View/Item/ItemView.lua#L145)
