# 03 · Seaside Escape 2.6.0：与我方设计的比较和取舍

复核日期：2026-09-26。本篇比较建立在已还原的目标实现上：它把物品、能力和画面分开组织，但业务仍由模型直接修改，部分结果由动画回调完成。**轻量格子、独立物品身份和能力专用数据值得借鉴；操作完成、保存和画面通知的边界需要重新设计。** 以下取舍是分析建议，不是已批准的架构决策。

## 1. 比较的前提

我方当前范围是独立核心棋盘、宿主 Profile、本地规则与保存、售出／删除专用撤销，首期不做订单。参考项目的订单只用于解释评分、产物选择和刷新依赖，不因此增加我方需求。

比较依据为我方 [逻辑表现分离设计](../../../_Plan/02a_逻辑表现分离架构详解.md)、[Function 与 Effect 讨论](../../../_Plan/10_Function与Effect建模讨论.md)，并核对了 [架构取舍](../../../_Plan/02_架构与参考取舍.md)、[Profile 方案](../../../_Plan/03_状态模型与Profile.md) 和 [决策记录](../../../_Plan/09_决策与接续记录.md)。其中 Command 表达意图，Consumer 收集操作，Batch 同步 Apply 后交给表现；AtomicOperation 的命名不代表自动回滚。Function、Effect、State 的最终分工仍有待讨论，必要的业务阶段不能因组件化而消失。

## 2. 概念相似在哪里，区别在哪里

目标侧行为均为**已确认（静态证据）**；与我方概念的对应和取舍属于分析判断。“没有对应”仅限现有材料，没有将命名相近视为设计相同。

| 我方概念 | 目标项目的对应或近似做法 | 对我方的意义 |
| --- | --- | --- |
| Entity | ItemModel 有实例 ID、数据、行为和组件；ID 兼作存档键，运行关联也依赖对象引用 | 身份与类型分开可借；退场、复活和旧引用有效期仍需定义 |
| EntityView | ItemView 绑定模型，BoardView 保存映射，直接持有 Transform 等资源 | 只有部分对应；缺少 View 工厂，不能证明支持实体、View、资源分别存活 |
| Cell／CellEffect | 主盘是轻量槽位；部分活动另有固定在坐标的地格锁 | 首期不必每格建立完整 Entity；确有地格规则时再增加独立数据 |
| Profile | Item、Board、Inventory 等内存表经队列写数据库 | 沿用宿主 Profile；需要借鉴的是完整状态的发布时机，不是 SQL 基建 |
| 逻辑 Function | 能力组件组织行为与专用数据，可直接调用棋盘、钱包和 UI | 能力归属可借，谁能在何时改数据仍需约束 |
| 表现 Function | ItemView 组件与 BoardView 事件处理并存，不与逻辑组件一一对应 | 符合两侧独立拆分的方向，但专用 View 缺失，不能认定其框架完整性 |
| Effect | 包装物、限制组件只覆盖部分语义；拆壳通常重建物品、换 ID | 若要求解除效果后保留原物身份和运行状态，就不能直接照搬包装 code |
| State | 开箱阶段、次数、计时起点、吞噬进度和临时锁混合存在 | 分清业务事实、互斥阶段与演出门禁，保留必要状态 |
| Command | 点击、拖动等方法参数近似操作请求；没有贯通的独立命令队列 | 输入请求可以很薄；全局事件缓存不等于业务命令队列 |
| Consumer | 规则检查分散在输入、棋盘和能力组件，处理方法会直接修改数据 | 执行前校验及其适用条件需要收拢，不能直接作为只读收集者 |
| AtomicOperation | 没有直接对应；Source／Target／New 是执行途中发布的对象引用 | 可保留明确结果，但消息既非不可变副本，也不承担统一 Apply |
| Batch | 多次移除、生成和占位顺序执行，没有统一的玩法提交单元 | 我方即使增加 Batch，也必须明确完成边界和失败策略；数据库事务不能替代它 |

## 3. 哪些思想值得保留

“保留”指采用设计思想，并非复制恢复代码，也不预先承诺完整框架。

| 可借鉴点 | 实际收益 | 采用条件 |
| --- | --- | --- |
| 轻量格位与物品身份分开 | 移动、入库不必重建物品；格子无需完整对象树 | 同一路径维护占位与物品位置，不能任意分别修改；长期坐标记录使用稳定值，避免直接保留池化位置对象 |
| 配置直接描述合成关系 | 可表达不完全规则的合成链，普通合成不必上通用规则引擎 | 检查目标存在、反向关系冲突，特殊道具另行处理 |
| 能力拥有专用阶段和数据 | 生成、吞噬、变形可共用物品结构，避免一个巨大分支 | 明确合法组合和组件间协议；能力组合不自动解决冲突 |
| 多个限制分别否决操作 | 解除一种限制时，其它限制仍可生效 | 目标只统一了移动；我方按真实需要分别定义拖动、合成、激活和入库查询 |
| 明确落点顺序 | 生成位置可解释、可测试；必要的计数和索引减少重复扫描 | 先采用简单顺序，仅为实际查询建立缓存，并保证占位变化同步更新 |
| 普通合成先形成结果，旧画面随后退场 | 核心替换无需等待动画，旧画面仍有数据可用 | 还需把邻格反应、额外产出和保存纳入完成边界；目标已有更早的属性通知，不能照搬其全部发布时点 |

## 4. 哪些做法需要改造

### 时间和随机数据应有明确归属

保存时间起点和配置时长，能避免逐秒存档；但必须先确定库存、隐藏、离线及配置变更的计时策略。“恢复生成次数”与“补发离线产物”应分别定义。

目标的普通固定产出序列按 Type 共享，特殊序列才可能按实例保存；保存剩余序列也不代表保存了全局随机状态。若我方要求每实例固定前缀或独立序列，就要改变归属。没有确定回放需求时，不必预建完整随机回放框架。

### 临时附着效果与拆壳得到新物，应采用不同身份语义

包装 code 适合“壳消失，创建内容物”，不保存完整内层能力历史。冻结后还要保留原冷却、次数和身份，则应保留宿主并增加限制数据，或明确保存嵌套对象；仅将 Cobweb 改名为 Effect 无法满足这一要求。

### 操作完成后，再发布稳定结果和保存数据

目标在产物已建立、费用尚未扣除时通知画面；生成物品时甚至先保存并发属性事件，再登记格位。同步监听抛错可能截断后续修改。全局派发还没有异常后的清理保护，异常可能令“正在派发”标记保留，后续事件持续进入缓存。这里确认的是代码顺序，实际故障是否发生仍待验证。

另有局部保存缺口：拆分先保存输出物，再设置其分摊成本；变形点击路径启动计时但不立即保存；吞噬先保存目标，再改变生成器状态。没有找到这些路径共同适用的补存保证。因此不能只因“有序列化接口”就认为最后状态必定已进入存档。[保存与属性事件](../code/Lua/decompiled/Board/Model/Board/BaseSceneBoardModel.lua#L127)、[拆分赋值时点](../code/Lua/decompiled/Board/Model/Item/ItemSplit.lua#L116)、[全局派发](../code/Lua/decompiled/Common/Event/EventDispatcher.lua#L53)

我方若采用 Command／Apply，应先完整处理规则、费用与连带结果，再交出表现消息和 Profile 数据；同时明确失败出口。增加接口名称并不会自动获得事务或回滚。

### 动画可取消，业务应有自己的完成条件

剪刀和批量吞噬在 Tween 回调中消费材料，与独立核心目标冲突。剪刀回调先解除界面锁，再执行拆分；批量吞噬找不到后续 View 时，前面已安排的动画没有统一撤销。现有身份检查只确认“物品当前位置仍指向它”，不确认它仍在操作开始的位置，也不重查全部业务条件。

可以保留旧／新物品引用供画面使用，或按画面需要传递结果副本；关键是明确旧对象存活期、完成／取消收尾和绑定版本。售出立即撤销的局部回调防护值得借鉴，但不能推广成所有异步句柄都安全。核心操作也不必为了形式统一拆成大量细碎 Operation。

### 限制来源、能力顺序和存档字段需要约束

- 临时 `m_bLocked` 只有一个布尔值，不记录来源，画面结束清锁可能覆盖另一来源；手动产出又未统一查询它。业务限制与演出输入门禁应分开，多来源限制须分别记录或重新计算。
- `pairs` 没有稳定业务优先级，部分查询取第一个组件结果。首期可明确函数顺序或禁止冲突组合，无需先建立复杂规则语言。
- 能力共写一行扁平存档，任意组合可能争用字段。当前 Sand 与 Spread 装配分流，尚不是已确认的存档冲突；扩展时应采用专用数据或校验字段归属。

### 撤销要有完整记录和单次生效规则

目标 Undo 复活调用方保存的旧对象，方法内部不核验单次凭据，也不使用扣款失败返回值。满盘时挪走的占位物进入产物缓存，仅保留 code、部分成本及附加信息，取出时生成新 ID，不保留完整组件状态；部分写入的成本列在取出方法中也未全部还原。[撤销入口](../code/Lua/decompiled/Board/Model/Board/BaseSceneBoardModel.lua#L1148)、[缓存取出数据](../code/Lua/decompiled/Board/Model/Board/ItemCacheModel.lua#L111)

我方只做售出／删除专用撤销，应定义完整记录、有效期限、单次生效、金额和满盘策略。不能将“移入缓存”当成无损入库，更不必沿用其满盘挪物玩法。上层是否已保证原项目这些前提，材料不足。

### 恢复应明确是重建还是复用

现有恢复方法没有清空全部运行索引，库存统计也不总是重算，不能认定同一实例可任意重复加载。若我方选择复用对象，需要完整清理和重建规则；若选择重建，应明确释放旧订阅和异步引用。

目标还会将未知 code 替换为金币、链最高级或清理孤立物。独立验证阶段应先保留可定位的错误信息，正式迁移和补偿另行决定。反编译中的异常变量、缺符号和抽象空方法，本身不作为设计缺陷。

## 5. 三个扩展性推演

以下均为**假设推演**，不是游戏已有功能，也不增加我方正式需求。

### A. 暂时冻结自动生成器，保留原冷却和次数

直接包装为 ice# 不适用：现有冰只保留内层 code，到期通常替换为金币，不能保存原生成器的完整运行历史。

| 改动面 | 最小需要处理的内容 |
| --- | --- |
| 配置与装配 | 新增冻结限制和到期数据；可在创建时固定装配、只切换数据，不必先支持任意热插拔 |
| 权限 | 手动和自动生成查询同一限制，同时明确移动、合成、入库是否受限；仅设置布尔锁会漏路径 |
| 时间 | 明确冻结期间冷却继续还是暂停；暂停需要剩余时间或冻结区间，不能顺带重置次数 |
| 保存 | 使用不冲突的专用字段，恢复原 Spread 后恢复冻结；结束冻结不重建宿主 |
| 表现与清理 | 增加覆盖外观，解除时刷新；入库、销毁和迟到回调识别原宿主与当前绑定 |

可复用产物选择、落点和移动否决。若确需运行时增删能力，还要维护格位层组件索引和清理协议；已有 Add 方法不足以承担它们。缺少专用 View，无法进一步确定资源复用成本。

### B. 一个地格被锁住，格内物品同时带气泡

活动棋盘已经分开地格锁和 Item，可作为局部参照；主盘的障碍物却占用物品槽位，不能在同槽再放第二个气泡物品来表达这件事。

最小改动是增加主盘持久地格数据，使合成、拖动、落点和库存入口都查询地格及物品限制；画面增加固定地格覆盖，独立于气泡。可借活动强制读取底层物品的方式，但必须分清“存在”“可操作”“可放置”，不能将锁格查询返回 nil 当作空位。

生命周期必须明确：移动气泡后，地格锁留在原地；地格解锁不破泡；泡泡到期不解锁地格。保存也是地格状态与气泡各自保存。是否将其建模为 CellEffect 仍是我方待议问题，这个例子只能说明数据需要分开归属。

### C. 物品被消耗时触发邻格效果

现有 OnRemoved 钩子在清格之后、摘 ItemManager 之前执行，没有移除原因。直接在其中递归修改棋盘，会混淆合成消耗、出售和包装替换。

至少需要给移除入口及调用方增加原因，新增能力配置／装配／持久参数，明确合成、吞噬、拆分的触发次序，再交给 View 表现。同次反应还需去重和终止条件，并约定旧物查询何时有效；现有合成两次四邻扫描会访问共同邻格，不能直接当成通用连锁求解。

可以复用空间查询、邻格方向、移除钩子及旧／新结果数据。若未来确有连锁，先实现局部有序计算再提交；首期无需预建无限规则引擎。

## 6. 尚需哪些证据才能定论

下表是**待验证问题**，本次没有运行这些实验。已确认的局部代码缺口与推断的实际后果分开列出；不要求先重新下载并完整反编译游戏。

| 问题 | 已确认的边界／剩余缺口 | 最小验证及其影响 |
| --- | --- | --- |
| 实际权限和生成配置 | 有分支，缺配置实值；包装不必都不可拖 | 补普通、自动、宝箱、泡泡／冰的代表配置，确认真实能力组合和数值 |
| 回池、换绑与旧回调 | 有 OnDestroy 和局部映射检查，缺池及动画桥接 | 移除→立即撤销→旧动画结束；确认订阅、映射及资源清理，决定绑定版本规则 |
| 动画取消和条件过期 | 拆分／批量吞噬依赖回调，复查只覆盖部分身份关系 | 动画中关闭、取消、移动或消耗目标，检查结算、部分完成和输入锁 |
| 产出和通知异常 | 次数、物品、通知、扣款分步执行，派发无异常清理保护 | 监听抛错或扣款失败，检查产物、费用、保存及后续事件是否继续；确定故障出口 |
| 空间不足和特殊产出 | 两条自动落点顺序不同；普通路径与 NotItem 等旁路不同 | 分别测全盘满、邻格满远处空、恢复空位，核对次数、随机游标及非物品奖励 |
| 离线时间与 ID | 局部计时可见，缺顶层调度；分配器初始化不续接已有计数 | 隐藏／后台／重启测试冷却和产量；固定同秒重建及多分配器，检查 ID 冲突 |
| 撤销的上层保证 | 缺记录创建与失效入口；缓存不能完整恢复被挪物 | 补 InfoBar 调用，测金额不足、重复、关闭及满盘，核对被挪物 ID、成本和能力 |
| 重复恢复是否可达 | ResetData 未清全部索引，库存统计可能已存在 | 补外部重建链，在同实例连续加载两份不同数据，检查占位、查询、订阅和统计 |
| 修改后的最后状态何时保存 | 拆分成本、点击变形起点、吞噬后生成器状态缺局部补存 | 在对应操作后直接检查 DBTable，再关闭重开；确认是否存在外部补存及丢失窗口 |
| 落盘及同步保证 | 可见 SQL 排队和同步覆盖，缺原生事务、SaveImmediately 和服务端实现 | 补最小桥接及调用链，跨表写入中断后恢复；分别验收 Profile 完整性、耐久和冲突处理 |
| 无画面核心能复用多少 | 拆分／批量吞噬已有依赖 View 的明确反例，其余还依赖 GM | 用最小替身服务运行普通合成，再对照依赖动画的操作；界定需改造的入口 |

Function＋Effect 的采用方式、Effect 归属以及实体退场管理，仍应由我方具体玩法语义和最小验证决定。本报告没有修改共享规划或登记新的用户决策。
