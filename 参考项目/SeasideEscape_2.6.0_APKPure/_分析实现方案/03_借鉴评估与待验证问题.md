# Seaside Escape 2.6.0：借鉴评估、扩展推演与我方比较

这篇回答“哪些思想可以带走，哪些需要改造，哪些还不能下结论”。它以 [01 的实际结构](01_架构与数据模型.md) 和 [02 的操作流程](02_功能扩展与执行流程.md) 为依据，不重新从我方术语猜测参考项目。

**可以先保留的判断是：轻量格子、物品身份和局部能力数据值得学；动画回调决定业务结果的路径，需要按我们的独立核心目标重新设计。** 这仍是候选取舍，不是最终架构决定。

只关心取舍时，先读第 3–5 节；需要对照 Entity、Function、Effect 等名称时，再查第 2 节。第 6 节是明确的假设推演，第 7 节列出尚未运行的最小验证。项目与路径说明见文末。

## 1. 比较前提与范围

先还原目标项目再阅读我方 [02a](../../../_Plan/02a_逻辑表现分离架构详解.md)、[10](../../../_Plan/10_Function与Effect建模讨论.md)，并核对 [02](../../../_Plan/02_架构与参考取舍.md)、[03](../../../_Plan/03_状态模型与Profile.md) 和 [09](../../../_Plan/09_决策与接续记录.md) 中相关约束。本报告不重复审计外部 A/H/S 工程，也不把其中的推荐全部视为用户已批准方案（[E38](04_证据索引.md#e38)）。

我方当前范围是独立核心棋盘、宿主 Profile、本地规则与保存、售出／删除专用撤销，不做订单。参考项目中订单参与物品评分、生成选择和状态刷新，只用于解释耦合；不建议因此恢复订单需求。

最有价值的比较并不是“它也有 Item/View”。它采用的两个具体取舍是：**格子轻量、物品带身份及能力；业务以直接调用和组件互调实现，异步边界则依流程混合处理。** 前者可减少建模成本，后者为更严格的提交／取消边界提供了反例（[E02–E07/E11–E25](04_证据索引.md#e02)）。

## 2. 用我方术语理解它，但不强行一一对应

表中目标侧事实为“已确认（静态证据）”，映射和启发属于分析判断；“无对应”均限定已读路径。

可以把比较分为三组：第一组问“谁有身份、数据和画面”；第二组问“行为和状态放哪里”；第三组问“一次操作怎样形成并完成”。它们解决的问题不同，不应只因名字相近就合并。

### 身份、画面与保存

| 我方概念 | 目标项目的近似对应 | 相似处和实质差异 | 影响／证据 |
| --- | --- | --- | --- |
| Entity | ItemModel＋ItemManager | 有身份、数据、领域行为及组件；ID 直接是 DB 键，运行关联又用对象引用；没有统一的退场状态／绑定版本号 | 可以共用物品模型，身份和清理规则仍需单独设计（[E05/E06/E22/E27/E28](04_证据索引.md#e05)） |
| EntityView | ItemView＋BoardView.m_modelViewMap | 绑定逻辑对象、持表现组件；可见实现直接使用 GameObject/Transform；缺 View 工厂，无法证明 View 可独立于资源长期存在 | 与我方“Entity、View、资源三段生命”仅部分近似（[E20/E22/E41](04_证据索引.md#e20)） |
| Cell / CellEffect | 主盘为槽位；活动另有 m_tileLock/cloudState | 轻量格子足够表达主盘；活动证明固定地格限制与物品包装确实是两类归属 | 不必每格完整 Entity，也不能将地格锁随物品一起替换（[E03/E04/E18/E33](04_证据索引.md#e03)） |

### 行为、效果与业务阶段

| 我方概念 | 目标项目的近似对应 | 相似处和实质差异 | 影响／证据 |
| --- | --- | --- | --- |
| 逻辑 Function | BaseItemComponent 的子类 | 能力组合、独立专用数据；允许直接调用棋盘／钱包修改，没有 Apply 阶段限制 | 可以借能力归属，需重新约束谁在何时修改数据（[E06/E07/E14/E24](04_证据索引.md#e06)） |

### 一次操作的执行过程

| 我方概念 | 目标项目的近似对应 | 相似处和实质差异 | 影响／证据 |
| --- | --- | --- | --- |
| Command | TapItem/DragItem/OpenItem 等方法参数及输入事件 | 表达操作请求的作用近似；没有贯通核心流程的独立 Command 对象、统一解释队列 | 可保持输入请求很薄，但不把事件缓存当业务 FIFO（[E09–E12/E21](04_证据索引.md#e09)） |
| Consumer | Board 方法＋各能力处理函数 | 规则裁决分布在输入、Board、组件；不是只读收集者 | 我方若采用 Consumer，需要重新收拢执行时校验（[E09/E10/E16](04_证据索引.md#e09)） |

## 3. 可以直接借鉴的思想

这里“直接”指采用最小设计思想，不是复制逆向源码，也不表示已经批准整套方案。

### 让格子保持轻量，让物品拥有身份

物品索引和格位容器分开，物品移动、入库仍可保留身份，格子不必各自拥有完整对象树。代价是必须在同一条操作路径中维护好占位和物品位置，不能允许调用者任意修改两边（[E03–E05/E28](04_证据索引.md#e03)）。

对我们的小棋盘，数组或坐标值配合物品 ID 索引是一个可验证的起点；等实际出现固定在地格上的规则，再判断是否需要 CellData。

### 普通合成关系可以明确写在配置里

目标项目记录合成结果，并派生反向关系，没有把所有规则都简化成“等级加一”。这能表达不完全规则的链，但需要检查目标缺失、反向关系冲突，特殊道具仍要专门处理（[E08/E10](04_证据索引.md#e08)）。

对我们的启发是保留可检查的配置关系。普通合成本身未必需要一个通用规则引擎。

### 能力负责行为，同时保留必要的阶段和数据

生成、吞噬、变形可以附在同一物品上，各自保留次数、进度和阶段。这能共用物品结构，又不把所有字段都塞进一个巨大业务分支。它的前提是明确合法组合和组件间协议；仅有组件集合还不能自动解决冲突（[E07/E14/E24](04_证据索引.md#e07)）。

因此，Function 可以组织行为，生成次数和开箱阶段仍可作为明确数据保存，没有必要只为消除 State 这个名字而重新包装全部字段。

### 让各项限制分别表达“这次操作不允许”

`CanMove` 会接受所有适用限制的否决；解除一个限制，不必连带改掉其它组件。这个思想能避免“一次解锁把其它限制也清掉”。不过，目标只对移动做了这样的汇总，合成和激活等并未统一（[E06](04_证据索引.md#e06)）。

我们可以按实际需要分别查询“能否拖动”“能否作为合成目标”“能否激活”，并记录限制来自哪里，而不是先设计覆盖所有可能行为的权限框架。

### 把落点顺序当成明确的玩法规则

目标有逐格、方环、八邻和同链贴近等搜索方式，同时维护空位和类型计数。它们让生成落点可解释，也减少重复统计；代价是每次占位变化都要更新相关缓存（[E03/E04/E16/E42](04_证据索引.md#e03)）。

对首期棋盘，先选择一种简单且可测试的顺序即可。只有确实需要某种查询时，再添加相应索引。

### 普通合成可以先有结果，再让旧画面退场

目标的普通合成先创建结果物，旧 View 之后继续演出。这让核心替换无需等待动画，也能保留旧数据供画面使用。但它的邻格和额外产出仍在事件之后执行，完整发布边界还需要改造（[E11–E13](04_证据索引.md#e11)）。

可带走的是这个基本时序，并进一步明确：结果包含什么、新旧身份怎样传给画面、旧对象由谁负责收尾。

## 4. 需要满足条件或改造后再用的做法

### 用时间起点恢复冷却

记录起点和配置时长，能免去保存每秒进度，离开后也能按差值判断就绪。它依赖明确的时钟、配置更新和库存／隐藏推进策略；源码不能替我们决定离线是否补产物（[E14/E29](04_证据索引.md#e14)）。

若采用这一思想，应先分别定义“恢复可用次数”和“补发产物”，再通过选定的时钟入口推进。

### 保存预先排好的产出序列

目标会把整数权重展开并洗牌，保存剩余序列，保证一轮分布并让重启后能继续。需要注意，普通序列按物品 Type 共享，不是每个生成器各有一份；全局随机数生成器的状态也没有通用恢复证据（[E30](04_证据索引.md#e30)）。

若我们的需求是每实例固定前缀或独立序列，就要改变数据归属。首期没有确定回放需求时，也不必因此引入完整随机回放框架。

### 用包装代码表示待解锁内容

包装 code 紧凑，拆壳后按配置重新创建也容易。它适合“壳消失，得到一件新物品”；代价是换 ID，而且内层原有冷却、次数等完整历史并未保存（[E07/E18/E19](04_证据索引.md#e07)）。

若我们的语义是给原物临时附加限制，并在解除后保留身份和能力数据，就需要附着数据或明确的嵌套对象，不能只把 Cobweb 改名成 Effect。

### 给画面传递旧物和新物

事件消息携带旧／新模型引用，画面容易找到对象并安排动画。便利的另一面是引用仍可变，旧对象应活多久、迟到回调是否还能使用，都需要管理（[E11/E17/E22](04_证据索引.md#e11)）。

我们可以按表现实际需要，选择暂留旧对象或传递完整结果副本；不必为了形式统一，把每个简单动作拆成几十个 Operation。

### 先更新待保存数据，再集中写入

目标每次操作维护内存中的存档数据，稍后集中排队写库，降低直接 I/O 的频率。但这份内存数据可能暴露操作中间状态，底层事务究竟包住哪些写入也缺少证据（[E26](04_证据索引.md#e26)）。

我方沿用宿主 Profile，重点是完整逻辑完成后何时交出稳定数据，以及怎样确认落盘成功，而不是搬用它的 SQL 基建。

### 旧动画回调执行前，确认自己仍对应当前绑定

售出后立即撤销，会为同一个物品建立新的 View。目标的部分旧回调会核对当前映射，避免把新 View 一起删掉；这解决了一个具体的迟到回调问题，但不能覆盖所有异步句柄（[E22/E28](04_证据索引.md#e22)）。

我们可以在同会话删除、恢复和换绑时记录绑定版本号，让回调识别自己是否已过期，并明确完成／取消时谁清理句柄。

## 5. 不建议原样采用的做法，以及原因

以下是代码结构带来的维护或故障风险。除非有运行复现，否则不把它们称为原游戏已经发生的事故。

### 在业务修改中途同步通知画面

产物已建立、费用尚未扣时进入表现监听，代码路径直接，但同步监听抛错可能截断后续步骤。合成也在通知画面后继续处理部分连带变化（[E11/E16/E17/E21](04_证据索引.md#e11)）。

如果我们采用 Command／Apply，应先完成必要业务，再分发表现。仅增加这些类型，并不会自动获得完整提交或回滚能力。

### 让动画结束决定材料是否消费

剪刀和批量吞噬把消费放在 Tween 回调中，让视觉到达与业务发生一致；代价是缺 View 时不能结算，取消时还可能剩下未完成的消费或输入锁（[E23/E24](04_证据索引.md#e23)）。

这与独立核心棋盘目标有直接冲突。若要求动画可取消，逻辑结果应先完整确定，表现自己完成或取消收尾。

### 多个临时来源共用一个布尔锁

`m_bLocked` 简单地阻止移动或自动产出，但清锁时不知道是谁加的锁；手动产出也不统一查询它。画面还会直接修改这个业务权限字段（[E06/E14/E25](04_证据索引.md#e06)）。

应区分业务限制和“演出中暂不接受输入”。有多个来源时，需要分别记录来源或根据现存限制重新计算，避免某个动画结束时清掉别人的锁。

### 让无序遍历决定有冲突的业务结果

`pairs` 派发简单，但多个能力同时响应时没有稳定业务顺序；`GetMergedType` 还会返回首个提供实现的组件结果。若组合要求先后或唯一结果，就需要额外规则（[E06](04_证据索引.md#e06)）。

首版可以采用明确函数顺序或禁止冲突组合，不必一步到位引入复杂规则语言。

### 默认所有组件都能共享扁平存档字段

现有固定装配下，共用物品一行数据实现简洁。未来若把 Sand 与 Spread 任意组合，它们会争用 `spreadState`，而序列化遍历也没有顺序保证（[E14/E37](04_证据索引.md#e14)）。

可采用独立专用数据结构或受校验的存档结构。当前配置把两者分开，不能把这个未来组合风险写成已存在的 bug。

### 撤销直接复活旧对象，却把有效性检查交给外部

目标 Undo 方法复用旧物，扣回售出收益后恢复；本方法没有单次凭据检查，也未使用扣款失败返回值。全盘满时，还可能将占位物移进缓存。上层是否保证这些前提，材料缺失（[E28/E36](04_证据索引.md#e28)）。

我方只做售出／删除专用撤销，更应明确完整记录、单次生效和空间策略；不能因为目标有满盘挪物分支，就自动采用同一玩法。

### 开发阶段静默替换未知配置

目标有把无效 code 换成金币或清掉孤立物的恢复策略，能避免坏数据阻塞进入游戏，但原始原因和补偿语义缺失（[E34](04_证据索引.md#e34)）。

在我们的独立验证阶段，缺配置应能被定位和诊断。正式版本怎样修复、迁移或补偿，是另一个需要明确讨论的问题。

反编译中的未定义局部名、抽象空方法和缺符号本身不算设计缺陷；真实错误是否可达，还需配置、字节码或运行补证。

## 6. 三个扩展性推演

本节全部为**假设推演，不是该游戏已有功能**，也不新增我方正式需求。列出改动面，是为了检验“组件化”到底省了什么。

### 假设 A：自动生成器暂时冻结，但保留既有冷却／次数

基于 E06/E07/E14/E16/E25。直接把 code 包成 ice# 不能实现：现有 ItemIce 取代物品装配，只保存内层 code，到期通常换金币，不保存原 Spread 运行状态。

| 需要处理的入口 | 可能的最小改动 | 组合冲突 |
| --- | --- | --- |
| 配置与装配 | 在 ItemModelFactory 或明确的动态入口装一个**新增的冻结限制数据／组件**；新增专用到期字段 | 逻辑 Add 不维护已在 Layer 的组件索引；若运行时增删需一起更新索引，不能只 Add |
| 权限 | ItemSpread.Update 和 OnTap/_TrySpread 都查询同一限制；同时审查 CanMove/CanItemMerge/CanItemStore | 只设置 m_bLocked 会漏手动产出，也会与 Turnbox 的清锁互相覆盖 |
| 时间 | 明确冻结期间计时继续还是暂停；继续时保留 Spread 起点，暂停则记录剩余或冻结区间 | “能力暂停”与“冷却暂停”不是同一动作，不可隐式重置次数 |
| 保存 | 在 Item 行增加不冲突字段，或专用能力数据；恢复先还原 Spread，再恢复冻结 | code 不足以记录原物运行历史；不能把冻结结束变成重建新 Spread |
| 表现与释放 | 补工厂／View 覆盖资源，解除只刷新外观；销毁、入库、迟到回调识别宿主 | 专用 View 缺失，因此无法估算其确切复用程度 |

可复用：现有 Spread 产物选择／落点和 CanMove 的否决思想。必须新增：跨意图限制查询及动态生命周期，或者限制为创建时固定组件、只切数据。后者通常更小，不必先支持任意组件热插拔。

### 假设 B：地格有锁，同时物品带气泡

基于 E07/E19/E28/E33。活动 BaseUIBoardModel 已分开 tileLock 和 Item，因此它的层级能表达此假设的一部分；**主盘**却是 MapBlocker/PaperBox 占格模拟解锁，不能同时在同一槽位放第二个气泡 Item。

需要修改主盘 Board/SceneItemLayerModel 的可用格查询及持久地格状态；CanItemMerge/DragItem/Spread 搜索/库存入口统一查询 Cell 与 Item；输入层明确锁格选中行为；View 加固定地格覆盖并与气泡 View 分开。可以参考活动 `GetItem(position,force)` 的“存在”与“可操作”区分，但应避免将“锁住物品返回 nil”误当空格。

关键冲突是生命周期：移动气泡时地格锁留原地；解锁地格不破泡；泡泡到期不应顺便解锁地格。可借 E33 的派生锁矩阵与锁空格计数；是否采用 CellEffect 仍是我方待议问题（规划编号 Q11），不能由这个推演替用户确认。保存增加的是地格状态，不应复制一份随气泡移动的锁（[E38](04_证据索引.md#e38)）。

### 假设 C：物品被消耗时触发邻格效果

基于 E06/E11/E12/E23/E24。现有 OnRemoved 钩子可复用，但它在**清 Layer 后、摘 ItemManager 前**执行，而且没有传入移除原因。直接在该钩子递归修改棋盘，会把合成、出售、包装替换等混为同类消费。

改动面至少包括：BaseBoardModel.RemoveItem／调用者传明确原因；新增能力的配置／工厂注册／持久参数；在合成、吞噬、拆分各路径确定触发次序；View 增表现消费入口。还需明确同次邻格反应去重、旧物查询有效性和终止条件。`_MergeItem` 现有两次四邻扫描可能访问相同位置，不能当成已实现的通用反应队列。

可复用：空间搜索、邻格方向、移除钩子和结果 Source/New。不能原样复用：无理由参数的任意递归事件写入。若我方以后确有连锁，先做局部有序求解再提交；目前仅为判断扩展成本，不建议首版预建无限规则引擎。

## 8. 后续综合时应保留的判断

轻量格子、配置合成关系、局部能力状态和显式落点顺序，足以为首期独立棋盘提供可控的组织方式；没有证据要求一开始就为所有 Cell、效果和操作建立完整框架。另一方面，如果保留我方“动画可以取消，核心结果仍必须成立”的目标，则必须避开已确认的剪刀／批量吞噬回调结算，并把能力写入、结果发布与存档出口放到可检查的顺序中。

这只是局部候选取舍。Function＋Effect 是否采用、Effect 属于 Cell 还是 Item、是否保留运行实体退役，仍应依我方具体玩法语义和最小实验讨论，不在本报告登记成用户决策（[E38](04_证据索引.md#e38)）。
