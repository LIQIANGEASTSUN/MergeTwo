# 02　Merge Mansion：功能与执行流程

> Merge Mansion **26.08.01**｜复核日期 **2026-09-26**｜静态分析，未运行游戏。
> 目标：`参考项目/MergeMansion_26.08.01_APKPure/`；本文位于目标目录的 `_分析实现方案/`。仓库根：`/Users/betta/Company/Projects/MergeTwo`。正文中的源码链接相对本文定位。

配置、状态、棋盘规则和显示代码共同组成一个功能。未单独标为推断或待验证的实现描述，均限于已确认的静态证据。

## 1. 新功能要接入哪些地方

该项目没有把所有功能塞进一种通用组件。能力配置决定规则参数，物品状态记录进度，棋盘方法安排执行，玩家动作补上费用和玩家上下文，显示代码处理结果。

因此，新能力往往不只是“加一个配置”。它可能还要接入状态创建、恢复、时间调度、合成时的数据迁移、操作权限和画面刷新。附件提供了一个可以动态加入对象的扩展点，但所查核心路径没有统一的 Function 注册器，也没有已确认的通用效果叠层、冲突与过期协议。多个字段能同时存在，不证明任意玩法组合都能正确执行。

## 2. 先分清两种“等一段时间”

| 问题 | 冷却后恢复点击额度 | 到时自动产出 |
| --- | --- | --- |
| 等待结束后发生什么 | 物品又有额度可供点击 | 尝试补存储或往棋盘放产物 |
| 主要能力／状态 | `ActivationFeatures / ActivationState`，配合 `StorageState` | `SpawnFeatures / SpawnState`，配合存储数据 |
| 是否直接新增棋盘物品 | 补额度的方法本身不新增物品 | 成功的自动产出路径会新增物品 |

这一区别直接来自方法中的写入行为：[TryToFillActivationStorage](../native/Cpp2IL-ISIL/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Items/MergeItem.txt#L15277) 修改容量与下次时间；[TryToSpawnFromSpawner](../native/Ghidra-C/0x03678CA4.c#L48) 的成功分支会调用 `AddItem`。

物品有两个独立容量字段：[ActivationStorageState](../structure/Cpp2IL-DiffableCs/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Items/MergeItem.cs#L295) 服务手动生成，`SpawnStorageState` 服务自动产出。两者都使用 `StorageState` 类型，不表示共享同一份容量。

### 2.1 点击生成与冷却补充

**归属与数据。** 能力属于物品。`ActivationFeatures` 配置产物、落点、周期、容量、费用、条件和初始是否充满；`ActivationState` 记录周期、使用次数、预计时间、相对进度和暂停信息，`ActivationStorageState` 记录当前量。费用属于玩家钱包，落点由棋盘处理。

**创建与触发。** 恢复代码按物品定义创建或重绑这些状态。点击触发激活动作；时间到达则可以触发 `ActivationStorageFill`，补回可点击额度。显示组件不是这个业务计时器的所有者。

**权限与执行。** 玩家动作检查可见性、能力和能量，棋盘与物品继续检查激活条件、解锁、次数和空间。激活会取用容量、改时间和次数，再生成产物；棋盘与费用能否在失败时共同恢复仍待验证。

**表现与组合。** 手动产出结果交给显示处理器播放动画，冷却界面的完整绑定未追清。物品还可以保留气泡、显隐等状态，权限判断分布在不同入口；不能假定解掉其中一种限制就该恢复所有操作。

**解除、迁移与保存。** 周期耗尽后有衰变等配置，合成时也有专门的状态合并、重置和存储处理。恢复时重新计算时间；入库后的全部保留规则和离线补充上限待验证。

### 2.2 自动产出

**归属与数据。** 这是物品的另一种能力，使用自己的产物选择器、落点策略、周期、容量和衰变配置。`SpawnState` 保存生成周期、已生数量、预计时间、相对进度、暂停截止时间和产出计数，另配 `SpawnStorageState`。[tempFillForSpawnStorage](../structure/Cpp2IL-DiffableCs/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Items/Spawning/SpawnState.cs#L6) 还保存一批补充中尚未装入容量的数量；手动生成也有对应暂存量，所以周期、已用次数、剩余容量和待补数量不能混成一个计数。

**创建与触发。** 状态同样按定义恢复。棋盘时间更新遇到 `SpawnStorageFillOrSpawn` 等事件后，决定补存储还是尝试生成；不要求玩家再点击，也不是从画面的 Update 自行生成。

**权限与执行。** 更新路径读取物品的到期状态，成功时选产物、找位置、更新生成状态、加入物品并增加计数。空间不足时，上游已有“存储未满则尝试补存储”的路径，并通过 `SpawnReaction` 区分无变化、请求生成和补存储，不能把满盘一概写成失败。

若实际进入 `TryToSpawnFromSpawner`，则所见分支先选择产物，再检查候选位置数量。因此“此尝试失败仍可能推进随机”是**较强推断**，还缺具体选择器的随机消耗行为；也不表示每次满盘更新都会进入这个方法。

**表现与组合。** 自动与手动产出共用一个具体表现处理器，但触发逻辑不同。自动与手动能力也有各自的时间状态。下一事件如何处理同刻到期、暂停和其它限制的组合，仍待验证。

**解除、迁移与保存。** 存在周期终止和衰变规则；移动可保留原物，合成显式处理生成状态。满盘时停表还是积累、离线后补几次，以及入库后如何计时，尚不能完整判断。

## 3. 遮挡、宝箱与气泡不是同一种东西

### 3.1 物品遮挡：改变可见程度，也影响操作

**归属与数据。** `ItemVisibility` 是物品字段，不是固定在地格上的锁。它有五个枚举值，表达隐藏、部分可见、可见等状态；没有找到可以任意增加外壳层数的集合。

**创建与触发。** 初始布局可以配置显隐，新物品也可以传入显隐值。邻格发生合成或执行显式解锁时，棋盘调用显隐更新。所见转移包括“隐藏且内部部分可见 → 部分可见”“部分可见／隐藏且内部可见 → 可见”；带 Blocking 的第五个值在这段代码里没有解除。

**权限与执行。** [UpdateVisibility](../native/Ghidra-C/0x035D7CB4.c#L85) 的两阶段行为不同：“隐藏且内部部分可见 → 部分可见”写字段后直接返回；“部分可见／隐藏且内部可见 → 完全可见”才继续处理衰变、激活、自动产出的计时及 `OnCobwebCleared`。两阶段不能统称为重置计时。拖动源要求完全可见，合成目标则使用另一项查询。**较强推断：** 部分可见物品可以不能主动拖出，却仍作为合成目标；这由目标权限调用与提示候选共同支持，但还缺完整接口实现和所有组合的运行真值表。

**表现与组合。** 显示组件读取显隐，选择颜色、fog 等外观；解除时有换外观和尘效。资源缺失，不能进一步确认每个值对应蜘蛛网、灰色箱子或某个透明度。这个枚举可与气泡、生成状态并存，但本身不是任意外壳的独立叠加系统。

**解除、迁移与保存。** 解除先改规则数据，再处理画面；动画未结束时是否开放输入待验证。显隐随原物移动；这与固定地锁的迁移规则不同。合成的特殊继承、入库和全部覆盖资源清理仍需逐条补证。

### 3.2 可开启宝箱：保存倒计时和剩余奖励

**归属与数据。** 宝箱状态属于物品的 `Extra`，保存开始／预计结束时间、相对耗时、剩余奖励、是否已填奖、次数及上下文。它是真实业务数据，不能用“显示一个箱子皮肤”代替；所查结构也没有宝箱状态自己的独立实例编号。

**创建与触发。** 物品定义声明宝箱能力，恢复分支创建 `ChestState`。开始开箱动作检查棋盘、物品状态和可见性，提交后进入开始倒计时路径；另有状态方法写入开始时间。二者之间的接口调用及 UI 发起链未完全接通，因此不宣称已经追完整个开箱按钮流程。

**权限与执行。** 先检查宝箱及开启就绪条件，`IsLootable` 未通过时尝试填奖，再判定取奖状态并找空位；找不到就返回。通过空位检查后才调用 [GetOneLoot](../native/Cpp2IL-ISIL/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Board/MergeBoard.txt#L17854)，再按产物是否允许放入棋盘决定落盘或送入口袋。**口袋分支不是满盘兜底**，而且空位检查前可能已填奖，不能承诺这次未领取就完全没改状态。奖励具体在哪个底层调用中扣除仍待验证，不能仅凭 `TakeItemFromChest` 的名称推定已消费。合成校验涉及宝箱状态，全部拖动、售出和开启中合成规则待验证。

**表现与组合。** 画面根据物品定义和状态呈现，对应结果驱动刷新；完整倒计时与领取动画时序未恢复。宝箱状态可与其它可选状态共存，但这不证明所有开启、气泡和合成组合都合法。

**解除、迁移与保存。** 奖励耗尽可触发移除；合成对宝箱状态有专门处理。时间和剩余奖励需要随实例保存并恢复；入库、重启后的领取一致性及旧配置迁移仍待验证。

### 3.3 气泡：能力还在，外面另加了一层限制

**归属与数据。** 物品的 [BubbleState](../source/AssetRipper/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Items/Bubble/BubbleState.cs#L11) 保存到期、奖励列表和变化类型等信息；旧单个 Bonus 字段已标为过时，不能把奖励限定为一项。棋盘另有同名相关状态管理气泡产生，两者不能混用。生成／构造路径会装入物品气泡，但具体概率配置没有保留。

**触发、权限与执行。** 购买移除气泡和时间到期是不同入口。`RemoveItemFromBubble` 清掉物品的气泡引用，棋盘随后更新时间并产生结果；到期路径则可能移除或替换物品。各操作怎样受气泡限制、购买费用是否与棋盘共同恢复，仍待验证。

**表现与组合。** 显示组件持有气泡标志和资源，收到移除结果后更新。去掉气泡不会直接删掉同一物品的激活或自动产出状态；因此底层能力可以仍然存在。但“去掉气泡后全部操作都可用”没有证据，还要看其它条件。

**解除、迁移与保存。** 气泡状态有保存／恢复线索；移动、合成、入库后是否允许保留及全部特例尚未还原，不能从普通物品移动推导气泡一定可拖动。

### 3.4 消费型附件：可以动态加入，但用途有限

**归属、数据与装配。** `ItemAttachmentsState` 在物品 Extra 中保存附件列表。生成路径确实会创建 `AuxEnergyItemAttachment` 并通过 `AddAttachment` 加入，所以不只是声明了一个空集合。所查接口没有统一的附件实例编号、层数或截止时间协议。

**触发、权限与执行。** 合成或移除可以按参数消费附件；[ConsumeAttachments](../native/Cpp2IL-ISIL/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Items/Attachments/ItemAttachmentsState.txt#L24) 遍历调用附件接口，然后清空列表。它不是拖动、点击和售出权限的统一入口，移动时从原槽移除也不必消费附件。

**表现与组合。** 多附件可以同存，UI 有附件奖励动画线索，消费则由业务路径发起。消费中增删列表、异常后部分消费、防重入及连锁终止如何处理，尚未确认；动画名称也不能证明存在统一的动画完成确认协议。

**解除、迁移与保存。** 消费后清列表，父状态可序列化。具体附件类型如何注册、入库后如何保留、跨版本如何恢复，仍有缺口。

## 4. 权限为什么不能用一个“能不能动”概括

该项目为不同意图分别查询条件。下面是已见入口，不是所有组合的完整规则表。

| 玩家想做什么 | 业务侧主要看什么 |
| --- | --- |
| 拖出一个物品 | 源坐标合法、存在物品、可移动、完全可见。 |
| 把它作为合成目标 | 目标可移动、显隐允许作为目标；普通合成另查双方能力、合成链门槛和匹配规则。 |
| 与目标换位 | 要进入允许的 Swap 分支；部分可见目标可能回退为寻找空位的 Move。 |
| 点击生成 | 可见、支持生成、通过费用校验（含适用的无限能量条件），再检查激活状态和落点。 |
| 售出 | 单独查询 `CanBeSold`，不能拿“可移动”代替。 |

`GetMoveResult` 还对 Artifact 类道具检查正向或反向合成兼容，不能把普通同类合成的判定概括为全部特殊玩法。源与目标的显隐查询不同，也解释了“不能拖出，但允许别人合入”的可能性。多限制共存时，逐项解除是否仍保持其它禁令，尚待验证；查询分散本身不是已发生故障的证据。

## 5. 六条流程：从操作到数据，再到画面

**共同的保存边界：** 各功能保存的是具体业务状态，所查字段及恢复入口不等于实际文件写入。以下六条流程均有这一缺口；“数据生效”指内存变化。

### 5.1 载入棋盘

1. **准备配置与存档模型。** 已见 `BoardInfo / BoardCell` 布局结构，以及玩家、棋盘、物品的可序列化模型。读文件、反序列化和配置解析如何到达恢复入口，仍有缺口。
2. **恢复业务对象。** [GameOnRestoredFromPersistedState](../native/Cpp2IL-ISIL/Metacore.MergeMansion.SharedLogic/GameLogic/Player/PlayerModel.txt#L6466) 依次调用棋盘与物品的 `RestoreInternalState`，补建或重绑状态并计算时间。未知配置、未知状态类型怎样失败，尚未完整确认。
3. **设置显示棋盘。** UI 的 `Init3 → SetMergeBoard` 刷新槽位和坐标。它与上一步之间的启动安排缺失，不能画成已确认的直接调用。
4. **把业务占位补到画面。** `UpdateInner` 比较模型与显示槽，补充添加／移除结果；[CreateItemForUI](../native/Cpp2IL-ISIL/Mansion.Scripts/UnityBoardController.txt#L72120) 从池中取对象，设位置并初始化外观。对账不能保证识别同槽同类物品替换后的全部身份变化。
5. **开放输入。** 全部资源准备完成到允许输入的总入口没有追清；资源失败、背景异步加载和旧画面清理的完整行为待验证。

### 5.2 拖拽，随后移动、交换或合成

1. **拖的是画面，先不改占位。** `Draggable` 的拖动回调修改 Transform，屏幕位置换算成候选业务坐标。部分回调订阅位置缺失。
2. **判断意图并请求执行。** 显示控制器经 [GetMoveResult](../native/Ghidra-C/0x0367930C.c#L52) 等入口，构造移动、交换或合成的玩家动作。可见局部待处理输入和确认状态，但执行器代码缺失，不能推定全局先进先出或统一锁盘。
3. **规则校验后改变棋盘。** 非法坐标、没有源物、不可移动／不可见或不匹配，会进入相应拒绝或其它分支。移动把原对象放到空位，再清来源；无空位则保留原位置。[交换](../native/Cpp2IL-ISIL/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Board/MergeBoard.txt#L25800)先刷新并应用原布局的增益，再读出两物、写回相反槽位，随后按条件处理新布局增益和时间倍率；增益处理并非只在换位后发生。普通合成由策略建立结果物品，写目标槽并清来源槽。**这些占位写入是业务变化的生效点。**
4. **处理合成的附带结果。** 邻格显隐、增益、时间、额外产物和附件还可能继续变化。第一条 `MergeBoardAct` 在关键占位之后产生，但它后面仍有工作，不能把第一条结果的构造时点当作整个大操作已经全部提交。
5. **播放合成并回收旧画面。** 结果经尚缺的监听转发到 `OnBoardAct / ProcessActs`；[ProcessMergeAct](../native/Cpp2IL-ISIL/Mansion.Scripts/UnityBoardController.txt#L49261) 再播放合成与消失动画，旧显示对象等动画收尾后回池。业务物品已被消费，不需要等旧图片消失才产生新物品。

正常拒绝与执行中异常不同。当前能确认顺序写入，不能证明中途出错能撤回全部变化；取消动画也不等于撤销业务。

### 5.3 点击生成物品

1. **界面先判断是否值得发起。** 控制器根据选择、能量和可点击状态，构造 `TryMergeBoardProcessActivationForCoordinate`。这只是交互预判。
2. **动作重新检查资格与费用。** `Execute` 检查棋盘、坐标、物品可见性、生成能力和钱包能量。[能量不足时](../native/Ghidra-C/0x036EE3E8.c#L175)，还会检查无限能量是否适用于该能量类型；不能简单写成余额不足必然拒绝。`commit=false` 的分支与其它动作并不完全相同，不能一概当成统一预演机制。
3. **棋盘处理激活。** 提交分支建立 `GenerationContext`，调用 [ProcessActivationForCoordinate](../native/Cpp2IL-ISIL/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Board/MergeBoard.txt#L11834)，检查激活条件、解锁与空间，选择产物。`Activate` 取用存储量并更新时间、周期和次数。特殊衰变及多产出尚未全部恢复，所以不能把所有“没有产物”都解释为没有副作用。
4. **产物真正进入棋盘。** 多产出迭代器调用 `AddItem` 后构造结果，这时新物品才在业务棋盘出现。附件也可能在此装入。
5. **上层继续处理结果和费用。** 所见代码中，棋盘处理早于普通钱包扣费；中间还有发现与监听处理。因此“已经有结果”不能直接等同“成功生成一件并完成扣费”。监听异常、重入、扣费失败如何补偿，仍待验证。
6. **画面呈现产出。** `ProcessAutoSpawnedOrManualSpawnedAct` 处理生成表现；其中对具备 Persistent 状态的物品还会构造 [ResetPersistentDecayCycles](../native/Cpp2IL-ISIL/Mansion.Scripts/UnityBoardController.txt#L54060) 并出现执行器调用，不能扩大为每次产出必定执行。这个动作实际改什么数据没有完整代码，不能据此断言所有业务依赖动画，也不能断言表现完全没有业务影响。

一个较小的助手 `SpawnToBoard` 能确认“找不到空位返回 Nothing；成功加物品后再给结果”。这能证明该局部失败分支，不能替代上面整条生成与扣费流程的故障保证。

### 5.4 时间到达，或关闭后重新打开

1. **模型推动时间。** `GameTick → RefreshActiveBoard` 检查是否需要更新，创建上下文并调用棋盘 `Update`。声明中的每秒 5 次是模型常量，不是实际每 200 毫秒唤醒或后台运行的证明。
2. **收集下一次事件。** 棋盘遍历物品的 `NextEvent`，放入按时间排序的缓存，同时保存物品引用和坐标。[同刻键处理方法](../native/Cpp2IL-ISIL/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Board/MergeBoard.txt#L38070)可见候选时间数值逐次加 1 的循环，支持“冲突时顺延到空闲时间键”的较强推断；字典查询的泛型符号、时间最小单位及同刻业务优先级仍未完全确认。
3. **按事件类型修改数据。** 点击额度到期只补额度；自动产出事件可以补存储或生成物品；气泡到期则可删除／替换物品。生成成功会改占位和计数；没生成也不能保证随机完全不变。
4. **把变化交给画面。** 结果经监听转发到显示处理器；普通时间规则不是由产出动画推动。结果转发仍有同一处代码缺口。
5. **重启后重建状态。** 恢复入口读取保存的绝对时间和相对进度，重新绑定状态。满盘积累、暂停期间补算、离线次数上限和隐藏棋盘怎样推进，均待验证；不能只凭活跃棋盘入口判定其它棋盘完全不走时间。

### 5.5 解除物品遮挡

1. **由邻格合成或主动解锁触发。** 入口分别是邻格显隐递归更新与 `ProcessUnlockItemForCoordinate`；主动解锁的全部付费条件尚未追全。
2. **先改变限制数据。** 棋盘查邻格或指定位置，调用 `UpdateVisibility` 修改显隐；变为完全可见的路径还调整相关计时并通知清除遮挡，变为部分可见则提前返回。**字段改写就是此处的业务生效点**，并非只换了一张图。
3. **后续操作读取新权限。** 拖动源、合成目标和点击仍分别查询规则，不是看某个显示对象是否可点来决定全部行为。
4. **显示解除效果。** `ProcessBecameVisibleAct` 调用外观切换，另有尘效。动画多久结束、所有资源何时清理、是否要等动画完成才开放输入，未完整确认；取消表现不表示显隐自动回滚。

邻居显隐朝可见状态前进，支持“普通传播会停止”的**较强推断**；缺少全部特殊路径，不能推广为任意邻格连锁都已有防循环和固定排序。

### 5.6 删除或售出，再回收画面与撤销

1. **检查是否允许售出。** `ProcessSellForCoordinate` 查询 `CanBeSold`；一般删除则进入底层移除方法，是否消费附件由参数决定。
2. **业务先离开棋盘。** [DoRemoveItem](../native/Ghidra-C/0x036868CC.c#L15) 读取原物，按需消费附件，再把槽位清成空。占位到此结束，但方法仍可返回原对象，供结果或撤销使用。
3. **售出记录费用与撤销信息。** 上层增加货币，并记录原物引用、棋盘与坐标。这是原对象，不是冻结的历史副本；记录字段中也没有独立保存本次售价。全部费用异常补偿未证实。
4. **旧图片可以继续播完动画。** [RemoveVisualItemAfterAnimation](../native/Cpp2IL-ISIL/Mansion.Scripts/UnityBoardController.txt#L66018) 禁止旧显示对象拖动／选择，挂上完成回调并清显示槽。动画结束后，回调经 `Dismantle` 清动画、效果和部分资源，再回池。
5. **取消和离场另有清理。** 能看到停止旧 Tween、取消与重置拖动，但完整回调、订阅和资源清理未贯通。不能判定已经泄漏，也不能承诺完全无残留。
6. **撤销时放回原业务对象。** [TryToUndoSellItem](../native/Cpp2IL-ISIL/Metacore.MergeMansion.SharedLogic/MasterFunctions.txt#L16992) 检查原位置或另找空位。还可见“读取占位物 → 送入口袋 → 移除该占位物”的分支，之后用 `AddMergeItem` 放回原物；所以不只是简单的原槽恢复。接着重新调用 `SellPrice`，再请求钱包扣款，并非直接读取一笔保存好的原售价。部分选择／跳转指令缺失，占位转入口袋的完整触发条件及扣款失败保证仍待验证；临时记录也不代表重启后可撤销。

这里最值得运行验证的是：售出后立即撤销，旧动画稍后结束，会不会误回收已复用的画面？本地回调只捕获显示对象，没有看到“这还是不是当时那次绑定”的检查，但外部池可能另有保证。因此这是**待验证风险**，不是已复现缺陷。
