## 先看结论

**这个项目先在内存中处理棋盘规则，再把处理结果交给画面。** 例如一次允许执行的普通合成，会先改变两个位置上的物品，再由显示代码播放合成和消失动画。动画并不负责创建这次合成的结果物品。这一局部顺序已确认，但连接业务代码与界面的部分转发代码缺失，不能说整套实现已经完全还原。[E12](04_证据索引.md#e12)、[E15](04_证据索引.md#e15)

它组织物品的方法也比较具体：**配置说明“这种物品能做什么”，物品自己的数据记录“它现在进行到哪一步”。** 生成器的产物、周期和容量属于前者；已经使用几次、下次什么时候恢复、宝箱还剩哪些奖励属于后者。不同能力有各自的数据结构，没有找到一套能统一添加任意功能或限制的通用框架。[E08](04_证据索引.md#e08)、[E09](04_证据索引.md#e09)、[E29](04_证据索引.md#e29)

最值得我方参考的是这两种区分，以及另一条容易混淆的规则：**冷却结束后可以继续点击，和冷却结束后自动产生物品，是两条不同流程。** 对方把它们分开实现。这对我方设计生成器、离线补算和满盘规则都有直接参考价值。[E17](04_证据索引.md#e17)、[E18](04_证据索引.md#e18)

这些是**已确认（静态证据）**。真正如何写入存档、发生异常后如何恢复、满盘时离线产出怎样累计，以及旧动画结束后会不会碰到已复用的显示对象，仍有待验证。本报告没有把这些缺口当成游戏缺陷。[E13](04_证据索引.md#e13)、[E19](04_证据索引.md#e19)、[E25](04_证据索引.md#e25)、[E27](04_证据索引.md#e27)

## 与我方设计有什么关键不同

我方讨论的流程是：先表达操作意图，再收集执行步骤，统一修改状态，最后通知表现。目标项目则主要由具体的棋盘方法直接完成修改，再生成结果描述。[E12](04_证据索引.md#e12)、[E13](04_证据索引.md#e13)、[E33](04_证据索引.md#e33)

这里最容易误读的名称是 `MergeBoardAct`。它大致表示“刚才发生了什么”，而我方的 `AtomicOperation` 表示“接下来执行什么修改”。二者不能只因为都描述一次操作就画等号。前者还保存对象引用，不能直接当成冻结不变的历史记录。[E15](04_证据索引.md#e15)

这说明我方可以借鉴它的数据归属和规则拆分，却不必照搬整套执行方式。具体取舍见 [03_借鉴评估与待验证问题](03_借鉴评估与待验证问题.md)；本次没有敲定我方最终架构。

## 这份材料能证明到哪里

当前目录是 APK 提取后的逆向资料。包内记录注明版本 26.08.01、Unity 6000.3.22f1、IL2CPP ARM64；原安装包、配置值和美术资源没有保留。很多 `.cs` 只有类型和字段，函数里的空块或默认返回值并非游戏原逻辑。本报告还核对了原生中间表示和部分伪 C。[E01](04_证据索引.md#e01)

三类标注的含义是：

- **已确认（静态证据）**：能从所列字段、调用或局部分支中核对；未运行游戏。
- **较强推断**：已有多处线索，但缺少关键一环；正文会说明缺什么。
- **待验证**：当前材料不足以作结论，需要补代码或做最小运行实验。

研究覆盖核心模型、代表功能及六条操作流程，没有通读全项目或恢复全部特殊玩法。工具输出也有函数混入、指令缺失等问题，集中记录在 [E02](04_证据索引.md#e02)。原材料 3,119 项哈希检查全部匹配；只修改本目录的分析文档。
