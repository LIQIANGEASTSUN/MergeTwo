## 1. 棋盘先变化，画面再呈现变化

**已确认（静态证据）：** 棋盘上的物品由 [MergeBoard](../structure/Cpp2IL-DiffableCs/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Board/MergeBoard.cs#L270) 管理，每个物品是一个 `MergeItem` 对象。它们保存规则所需的数据。画面另外使用 `UnityBoardController` 和 `BoardItemHandler`，负责位置、图片、动画和输入。

例如，假设两个符合条件的同类物品合成出一个新物品。**这是解释流程的例子，不代表包内某组真实配置。** 业务代码先把目标位置改成结果物品，再清掉来源位置；之后产生一条“发生了合成”的结果。显示处理器再根据结果播放合成和消失动画。所以画面上旧物品尚未消失时，它在业务棋盘中已经不再占位。

```mermaid
flowchart TD
    A[拖动或点击输入] --> B[玩家动作：校验并请求执行]
    B --> C[棋盘与物品：修改业务数据]
    C --> D[棋盘结果：记录发生了什么]
    D -. 中间转发代码缺失 .-> E[显示控制器：接收并处理结果]
    E --> F[物品画面：更新外观与播放动画]
```

这里的玩家动作 `PlayerAction` 携带请求参数，并执行校验和业务调用；棋盘结果 [MergeBoardAct](../source/AssetRipper/Metacore.MergeMansion.SharedLogic/GameLogic/Merge/MergeBoardAct.cs#L23) 则描述已经发生的变化，包含坐标、物品定义、时间及源／结果物品引用。它是 readonly 结构，但引用指向的对象仍可变化，不能当成冻结的历史快照或等待执行的指令。

显示侧用 `unprocessedActs` 暂存结果，再由 `ProcessActs` 预处理并按结果类型分派，处理后清理列表；预处理的完整语义未还原。[OnBoardAct](../native/Cpp2IL-ISIL/Mansion.Scripts/UnityBoardController.txt#L78303) 与 `AddAct` 是写入这个列表的不同入口，不构成已确认的前后调用链。输入执行器和上游监听转发仍缺完整实现，图中只概括分工。

这里说“业务数据是依据”，只是在比较客户端模型与画面，**并不判断服务器最终由谁裁决**。普通合成的关键占位修改已能确认先于动画，但还不能推广成“所有业务都完全不依赖表现”：产出表现处理器里另有发起业务动作的线索，其实际影响待验证。

## 2. 棋盘中的格子，首先是一个位置

### 数据怎样摆放

**已确认（静态证据）：** 业务棋盘用一维列表 `BoardItems` 保存物品，空位置记为 `null`；业务坐标通过访问器转换成列表下标。画面则另有二维显示槽位。以下只是结构示意，不表示真实布局或坐标方向。

```text
业务棋盘 MergeBoard
  宽度 Width、高度 Height
  物品列表 BoardItems = [物品 A, 空, 物品 B, …]

业务坐标 Coordinate(x, y)
  ├─ 转成列表下标 → 找到当前位置的物品
  └─ 计算显示位置 → 放到画面上的对应位置
```

在所查的棋盘、配置、玩家模型和界面类型中，**没有找到带独立实例编号和行为的运行格子对象**。`BoardCell` 虽然名字里有 Cell，但它是初始布局配置，主要描述放什么物品、初始显隐是什么。它不能证明每个运行格子都是一个 Entity。

空格、范围之外的坐标和被遮挡的物品也要分开：空格没有物品；无效坐标不能按普通格子访问；被遮挡的物品仍存在于棋盘中。某个显隐值带有 `Blocking`，并不意味着这里存在一份固定地块锁数据。

### 坐标和画面怎样对应

[GetIndex](../native/Cpp2IL-ISIL/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Board/MergeBoard.txt#L2238) 的指令使用棋盘宽度和乘加运算；反向方法也有除法、余数的线索。因此 `index = y × Width + x` 是**较强推断**。但关键指令没有完整转换，工具输出还存在不一致，不能当成已确认公式。是否从 0 开始、原点在哪、坐标朝哪个方向增长，仍待验证。

显示控制器读取边界对象、宽高和比例，计算格子显示位置与拖动范围。玩家拖动物品时改变画面位置；[OnDrag](../native/Cpp2IL-ISIL/Mansion.Scripts/Draggable.txt#L382) 与 `OnEndDrag` 都会把屏幕位置换算成业务坐标，并有邻近坐标与安全区域的判断，不能把坐标计算限定在松手之后。没有证据表明合成规则靠两个图片的实时像素距离判断。

**待验证：** 实际棋盘尺寸、洞位、保留位置、多层内容、多格物品，以及格距、锚点和缩放。当前包缺少配置资源，不能凭游戏印象补成“固定 7×9”或某种布局。

### 占位、找空格和邻格搜索

物品对象本身没有在所查字段中重复保存业务坐标，因此移动主要修改棋盘列表。但移动后还会更新坐标增益、时间候选缓存和显示槽位；这不是完全没有同步成本。

落点由 `IPlacement` 一类策略提供。移动到已占用的位置时，[ProcessMove](../native/Ghidra-C/0x03679798.c#L17) 可以寻找替代空格；找不到就返回原坐标，不能把“判定结果为 Move”理解成覆盖目标物品。邻格传播使用 `CrossNeighbours`，合成提示另有可见／部分可见候选缓存。各配置究竟选哪种策略、按什么方向搜索和平局时选哪格，尚未确认。

## 3. 同一种物品，不是同一个物品

假设棋盘上有两件完全相同的工具。**这只是身份关系的说明例子。** 两者可以使用同一个 `ItemId`，因为这个值表示“哪一种物品”；但它们是两个不同的 `MergeItem` 对象，各自保存当前状态。把其中一件移走后，原位置还能放另一件物品，所以坐标也不能永久代表原物。

| 要区分的内容 | 代码中对应什么 | 能说明什么 |
| --- | --- | --- |
| 物品种类 | `ItemId`、配置的 `ConfigKey` | 读取同一类物品的定义；不是每次创建分配的唯一编号 |
| 合成链和等级 | `MergeChainDef`、`LevelNumber` | 说明配置关系；等级相同本身不足以证明能合成 |
| 当前运行物品 | `MergeItem` 对象引用 | 移动可以继续用原对象；普通合成可以创建新对象 |
| 当前所在位置 | 棋盘编号与 `Coordinate` | 找到此刻占用该位置的物品；不能保证以后还是原物 |

以上结构已确认；跨存档后怎样按稳定身份重新找到同一个实例，仍待验证。所查 `MergeItem` 等声明没有独立实例 UUID，不等于整个游戏任何系统都没有实例编号。

### 配置说“能做什么”，状态说“现在做到哪里”

`MergeItem` 是普通业务类，不是挂在场景里的 Unity 组件。物品定义保存它具有什么能力、采用什么策略；可选状态容器 [MergeItemExtra](../structure/Cpp2IL-DiffableCs/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Items/MergeItem.cs#L291) 保存这个实例的进度。显示组件 `BoardItemHandler` 再读取有关数据选择外观。

```mermaid
flowchart LR
    Board[MergeBoard 棋盘] --> Item[MergeItem 当前物品]
    Item --> Def[ItemDefinition 种类配置]
    Def --> Features[Features 能力参数与策略]
    Item --> Extra[MergeItemExtra 可选状态]
    Extra --> State[生成次数、计时、宝箱奖励、气泡等]
    View[BoardItemHandler 显示组件] --> Skin[按物品定义与状态选择外观]
```

这个结构允许同一类物品对象携带多种状态。定义经 `DefinitionDef / ItemDef` 引用配置，`get_Extra` 可在首次需要时创建可选状态容器。创建物品既可以构造新对象，也可以把已有对象放回棋盘；恢复时，[RestoreInternalState](../native/Cpp2IL-ISIL/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Items/MergeItem.txt#L31992) 按能力补建或重新绑定状态。它并不是“每一种生成器或宝箱都必须写一个 Unity 子类”。

普通合成则有明确的状态迁移工作：[Combine](../native/Cpp2IL-ISIL/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Items/Merging/MergeExtensions.txt#L1742) 先合并状态并构造结果物品；之后 [BaseMergeMechanic.Merge](../native/Cpp2IL-ISIL/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Items/Merging/BaseMergeMechanic.txt#L257) 才根据 `ResetTimers` 等配置决定后续处理。`ResetStates` 作用于新结果，不能说它发生在新建之前，也不能说每次合成都必定重置计时。存储处理另有 `Sum / Reset / PreserveRatio` 策略；`FlushStorages` 的调用线索存在，但缺失的比较指令使完整触发条件仍待验证。衰变、手动生成、自动产出、宝箱、Sink、时间容器、次数、经验、Persistent 等状态有各自处理分支，所以新增一种状态后，不能指望它自动得到正确的合成行为。

这里的 `State` 不一定是“开启／关闭”这样的互斥阶段。例如宝箱状态还保存剩余奖励。表现代码里的 Effect 对象又可能管理显示资源；没有足够证据把所有名为 Effect 的类型都归为纯粒子，或都归为统一业务限制系统。

## 4. 字段归属

下表集中说明数据归属；“可保存”只表示模型提供了相应字段，不等于已经完成文件写入。

| 内容与实际类型 | 关键数据、归属和写入者 | 身份与保存／表现关系 |
| --- | --- | --- |
| 棋盘 `MergeBoard` | `BoardItems`、宽高、修改时间、合成次数；由增删移合方法修改 | `BoardIdentifier` 标识棋盘；主要字段有保存标记，显示槽另存。 |
| 格子位置／布局 `Coordinate`、`BoardCell` | 前者定位运行槽位；后者配置初始种类、显隐与布局 | 所查范围没有独立运行 Cell ID；不把布局配置当运行格子。 |
| 物品 `MergeItem` | 定义引用、显隐、创建时间、`extra`；物品、棋盘及扩展方法共同处理 | 对象引用表示当前实例；运行对象也承载可序列化数据。 |
| 能力配置 `ItemDefinition / Features` | 合成、生成、落点、周期等规则和策略 | 配置键标识种类；显示组件缓存当前物品类型。 |
| 物品附加数据 `MergeItemExtra` | 手动／自动生成及各自容量、宝箱、气泡、附件等状态 | 从属于物品；没有已确认的统一附加效果身份协议。 |
| 物品遮挡 `ItemVisibility` | 存于物品，由显隐更新方法修改 | 随原物移动并保存；画面另有显隐缓存。 |
| 棋盘范围的状态与缓存 | 冷却移除／OnFire 时间、棋盘气泡状态；另有坐标增益和时间排序缓存 | 持久事实与临时缓存需要分开；不能全部归为物品 Effect。 |
| 画面 `UnityBoardController / BoardItemHandler / Draggable` | 显示槽、资源、交互标志、拖动位置；由显示代码更新 | 物品画面可回收复用；未见持久 View 身份。 |
| 费用 `Player.Wallet` | 激活动作和售出逻辑处理钱包；界面做预判 | 最终校验不由图片决定；与棋盘修改能否共同恢复待验证。 |
| 撤销 `ProgressState` | 原物引用、棋盘编号、坐标；售出时记下 | 属于临时撤销记录，不是跨重启的历史栈。 |
| 多棋盘 `PlayerModel / CustomMergeBoardsState` | 主／活动棋盘、棋盘集合、当前活跃棋盘编号 | 多处复用 `MergeBoard`；未全面分析活动特殊规则。 |
| 存档结构 | 玩家、棋盘、物品模型中的 `MetaMember` 字段；恢复时重绑配置和运行状态 | 没有找到完整独立文件存档层，不能据标记推断写盘成功。 |

## 5. 有保存标记，不等于已经写入文件

**已确认（静态证据）：** 模型带有 `MetaMember` 等序列化标记，也存在“恢复玩家 → 恢复各棋盘 → 恢复物品”的调用。某字段同时有 `NonSerialized`，不能据此否定另一套 Meta 序列化机制。

**待验证：** 谁读取文件、何时生成快照、何时写盘、写失败怎样恢复，以及未知状态类型和旧版本数据怎样迁移。部分修复代码存在，仍不足以证明完整保障。因此全文所说“已经生效”，若无特别说明，指内存中的业务修改，不表示已经保存到磁盘。

## 6. 时间、随机与性能能判断到什么程度

时间事件由棋盘集中收集到排序字典，条目包含事件类型、物品引用和坐标，物品提供下一次事件；并非每张物品图片各自开一个业务计时器。状态里同时有绝对时间和相对进度。随机使用玩家的 `RandomPCG` 和 `GenerationContext`，后者还持有分布状态；`SpawnFactoryState.currentSpawnIndex` 另存生产序列进度。

这些结构让固定时间、固定随机源的测试**看起来可行（较强推断）**，但还需处理玩家接口、配置、钱包和执行器等依赖。本次没有运行无画面测试，也没有服务端证据，不能据此宣称可确定性重放或证明服务器算法。

时间缓存重建、提示搜索和画面对账都可见扫描与缓冲。一次遍历的工作量随项目数增长，是静态成本判断；一次更新还可能处理多个过期事件，所以不能用“一次线性扫描”代表整体性能。同刻事件顺序、离线补算上限、手机耗时和内存分配仍待验证。

## 7. 资料范围与结论限制

[包内提取记录](../逆向方法与完整性.md#L3)注明包名 `com.everywear.game5`、版本 **26.08.01**，技术形式为 Unity **6000.3.22f1**、IL2CPP ARM64、metadata 39。当前目录没有原始 XAPK、ELF、metadata、配置数值和美术资源，因此版本来自提取记录，不能在此独立重验安装包。

材料包括 AssetRipper C# 836 文件、Cpp2IL 结构 849 文件、原生／ISIL 1,310 类型文件。13,384 条方法记录中，12,054 条有非空指令，1,330 条只有签名；选定的 112 个 Ghidra 方法有 109 个输出、3 个失败。历史初筛将其中 39 个留作候选，62 个标为越界、8 个标为异常膨胀。数量不等于已读懂的函数数，候选也不等于可靠实现。

两套 `.cs` 的方法体均为占位，适合核对类型与字段，不能把 `return default` 当作游戏行为。ISIL 有未翻译指令和失效跳转；同文件的反汇编文本也可能与 ISIL 不一致。具体例子包括：坐标 getter 的两种输出不一致，`BoardItems` 被 AssetRipper 显示为 public、被 Cpp2IL 显示为 private；移动判定、自动产出和激活的部分伪 C 越进相邻方法。分析只采纳能互相核对的局部行为，不用混入的尾部补全流程。
