## 2. 真正值得取走的三个细节

### 优先参考：合成后的状态逐项决定去向

**已确认（静态证据）：** 对方把计时重置和容量处理分开。`Combine` 构造结果后，[BaseMergeMechanic.Merge](../native/Cpp2IL-ISIL/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Items/Merging/BaseMergeMechanic.txt#L257) 按 `ResetTimers` 决定是否重置；容量有 [Sum／Reset／PreserveRatio](../structure/Cpp2IL-DiffableCs/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Items/Merging/StorageActionType.cs#L4) 三种策略。具体计算、截断方式与 `FlushStorages` 的完整条件尚未全部确认，不能仅凭枚举名称补出公式。

**对我方的价值：** [01 的 C12](../../../_Plan/01_需求与历史差异.md#L59) 和 [09 的 Q03](../../../_Plan/09_决策与接续记录.md) 已指出合成生成器的继承问题，但还没有具体选择。应分别决定轮次／已用次数、冷却、固定产出游标、物品附加效果的去向，不用一个“全部重置／全部复制”开关代替所有规则。尤其要防止合成反复领取固定前缀。先用具体前后状态样例确定产品规则，再决定是否需要可配置策略；这不要求引入新的框架。

### 有对应玩法时参考：点击额度与自动产出容量独立

**已确认（静态证据）：** [MergeItemExtra](../structure/Cpp2IL-DiffableCs/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Items/MergeItem.cs#L295) 分别保存 `ActivationStorageState` 与 `SpawnStorageState`；同为 `StorageState` 类型，不代表同一份容量。周期、已用次数、剩余容量和本批尚未补入的数量也分开，后者可见 [tempFillForSpawnStorage](../structure/Cpp2IL-DiffableCs/Metacore.MergeMansion.SharedLogic/GameLogic/Player/Items/Spawning/SpawnState.cs#L17)。补点击额度和向棋盘生成物品是不同事件。

**对我方的价值：** [05](../../../_Plan/05_生成器与时间.md) 已区分手动与被动生成，但当前需求以轮次／次数为主，并未要求完整的双容量玩法。只有后续确实出现“容量逐步补充”“同一物品兼具两种产出”或“满盘暂存产能”时，再采用相应数据。不能把对方复杂生成器的字段都变成我方首期需求；计时工具可以共用，到期后修改什么状态仍分别定义。

### 补充规则样例：解除限制是否同时影响计时

**已确认（静态证据）：** [UpdateVisibility](../native/Ghidra-C/0x035D7CB4.c#L85) 在隐藏转部分可见时提前返回，转为完全可见时才继续处理相关计时。不能把所有“解锁”当成同一事件。

**对我方的价值：** [04](../../../_Plan/04_棋盘交互与合成.md) 已有深浅锁权限，[10](../../../_Plan/10_Function与Effect建模讨论.md) 已有效果解除协议，但还应把“带锁生成器何时开始计时、深转浅是否改变期限、完全解除是否重置”写成具体样例。借鉴的是分阶段定义副作用的方法；对方锁随物品走，我方还涉及固定地锁，不能直接套其行为。确切规则仍待确认。

产物选择和落点也是对方已有的策略边界。我方确实出现第二种算法时再抽接口；单一规则保持直接方法即可，不照搬全部 Features 类型。以上都可进入现有 Rules／Operation，不必另建一套执行机制。

## 3. 不建议沿用的做法

下列建议针对我方需求；其中的潜在风险没有被本次运行复现，反编译缺口也不算原游戏缺陷。

**不要把不断补中央分支称为零成本扩展。** 对方新能力可能要同时改 Extra、恢复、时间、合成和显示分派。这在能力集合稳定时可以可控；若持续增加可插拔玩法，修改面会扩大。我方可以保留简单中央编排，但应明确新增能力要接哪些位置，再判断哪里值得抽 Function。

**不要默认坐标或显示对象引用永远指向原物。** 原位置可以换物，池对象可以重新绑定；本地回收回调没有看到绑定校验。原外部框架可能有保证，实际错误待验证。我方需要显式说明如何识别旧回调的目标，而不是把一项看不到的约定当成安全前提。

**不要把结果通知同时当执行指令和历史存档。** `MergeBoardAct` 在关键写入之后产生，而且包含对象引用。它适合短期传递“刚才发生了什么”；用于持久重放、撤销或待执行操作，则还需要快照和版本含义。我方应区分这些职责，不能靠名称合并。

**不要未经验证就复制表现侧发起业务的路径。** 产出表现处理器会构造并间接派发特定动作，但动作实现不全，可能涉及业务，也可能只是辅助同步。在我方独立核心目标下，应先查清无画面时是否仍需执行，再决定它归哪里；不能直接断言原游戏靠动画推进所有业务。

**不要把连续修改当成失败时自动恢复。** 已见棋盘与钱包顺序变化，外层执行器是否提供补偿未知。直接方法需要定义故障边界，Command／Batch 同样需要；叫 `AtomicOperation` 也不会自动撤回之前写过的数据。

## 4. 与我方概念如何对应

同名不代表同职责，没同名也不代表缺能力。下表用“主要由谁承担”比较，不强行建立一一映射。目标结构是静态事实；对我方是否值得采用，仍是候选判断。

| 我方概念 | 对方最接近的实现 | 对我方有什么含义 |
| --- | --- | --- |
| Entity | `MergeItem` 保存物品事实，`MergeBoard` 保存棋盘；没有在所查范围找到通用实体管理与统一能力生命周期 | 独立实例身份是否必要，应通过撤销、恢复和迟到回调验证，不能只因对方有物品类就证明我方框架。 |
| EntityView | 控制器、`BoardItemHandler`、拖动组件和对象池共同承担 | 是一对多关系；我方显式管理绑定和资源可以使责任更清楚，也增加管理成本。 |
| 逻辑 Function | 配置、策略、物品方法、状态和棋盘分支共同承担 | 配置本身不是可加载行为实例；Function 可以使用状态，不必把每个字段都拆成一个 Function。 |
| 表现 Function | 结果处理方法、显示组件和效果组件 | 无需与逻辑能力一一对应；一段表现可以处理多个业务结果。 |
| Command | 各种 `PlayerAction` 带操作参数，也执行校验和修改 | 有近似之处，但完整队列和预演含义未知，不能等同我方整个 Command Runtime。 |
| Consumer／Batch | 没有已确认的对应框架；业务方法直接安排修改，结果集合随后收集结果 | `collectedActs` 不是一批等待 Apply 的指令；我方是否需要 Batch，应看跨对象修改与统一表现的实际需求。 |
| AtomicOperation | 局部棋盘方法直接写数据，`MergeBoardAct` 描述写入后的结果 | 没有直接对应；双方都需说明“原子”具体保证什么，不能把结果通知当待执行操作。 |
| Effect | 气泡、附件或棋盘增益承担某些相近用途，另有只与表现有关的效果对象 | 没有已确认的统一协议；先验证动态限制、叠加确有需求，再决定抽象范围。 |
| State | 生成、存储、宝箱等具体状态 | 表示当前业务事实，不一定是互斥阶段；例如剩余奖励天然需要保存，多状态共存也很正常。 |

## 5. 三个扩展例子：检验模型，而不是补写游戏功能

以下均为**假设推演，不是该游戏已有功能**。目的是看增加一种规则究竟要改哪里，不能作为该游戏已经支持这些玩法的证据。

### 假设 A：自动生成器被临时冻结，但仍允许移动

可以复用自动产出状态、时间调度和周期策略。已有 `pausedUntil` 字段，但其完整含义与补算关系尚未还原，不能直接当成现成冻结系统。

1. **先定义冻结什么，再加数据。** 配置要写清只暂停自动产出，还是也禁止点击。若既有暂停字段不能安全复用，就需在 `Extra` 增加可保存的冻结状态。两次冻结来自不同来源时，不能让后解除的一次误清全部限制。
2. **接入真正生成的入口。** `NextEvent`、自动产出方法和恢复方法都要知道冻结，约定解冻时顺延截止时间还是补算。只禁 UI 点击挡不住自动生成；只挡最后的 `AddItem`，还可能已经消耗次数或随机。
3. **明确移动与合成的继承。** 移动时状态随原物；合成时在 `Combine / ResetStates / FlushStorages` 中明确继承、清除或拒绝，不能让默认空值替玩法做决定。
4. **分别更新权限和画面。** 自动生成、点击、拖动各查自己的规则；显示组件加冻结标志和结果刷新。解气泡不能顺便解冻，旧动画也不能给新物重新加上旧标志。
5. **保存并验证组合。** 需要补序列化成员或类型注册、旧数据迁移和离线规则；用两个限制逐项解除的场景验证。

**候选判断：** 这类功能的修改面不小。先用它检验“带来源的限制集合”是否必要，不能仅凭一个暂停字段就说扩展已解决。

### 假设 B：地格固定上锁，格上的物品又带气泡

可复用棋盘坐标、现有气泡状态及结果到画面的通路。但物品显隐随物品走，不能代替留在原地的锁。

1. **地锁归棋盘或轻量 Cell。** 增加坐标到地锁的记录，并接初始布局和恢复。即使格上没有物品，锁也必须能存在；不一定因此需要完整 Cell Entity。
2. **区分坐标合法与允许占用。** 移动、交换、生成落点、合成源目标和解锁都要查询相应地锁规则。直接把锁格判成无效坐标，可能连读取和显示已有物品也一并禁止。
3. **独立解除两种限制。** 解气泡只改物品状态，解地锁只改棋盘记录；物品移动不搬走地锁。地锁无需进入物品合成的状态继承逻辑，但合成许可要检查它。
4. **地格覆盖层独立显示。** 它不应挂在会随物品回池的显示对象下面，空格也要能显示；还需规定与气泡的遮挡顺序及点击命中。
5. **按位置保存地锁。** 保存棋盘与坐标，并处理布局版本变化。只有棋盘重排等需求要求追踪“同一块地”时，才进一步判断独立 Cell ID 的价值。

**候选判断：** 这个例子能检验轻量 Cell 是否足够；目标当前结构不能零修改支持，但也没有理由直接升级成完整格子实体框架。

### 假设 C：物品被消耗时，给邻格一份奖励

已有附件消费接口可以作为入口，也有邻格遍历工具。但所见 `IItemAttachment.Consume` 参数主要是玩家、棋盘编号和物品种类编号，缺少原坐标；同类物品共享种类编号，不能据它反查唯一来源。

1. **增加附件及装配入口。** 可新增附件实现、配置创建处和多态保存注册，保存尚未消费的状态。
2. **在物品离开前保留来源。** 扩展消费上下文，传入原坐标、消费原因和结果收集信息。棋盘清空后再反查来源不可靠。
3. **规定哪些行为算消费。** 合成、售出、删除和移动未必都触发；原移动路径就能不消费附件。还要明确先移除再搜索邻格，还是先搜索再移除。
4. **给连锁规定顺序和终止。** 奖励可能再触发生成或消费，需要明确排队、去重、落点与上限，避免回调中改同一附件列表。原接口本身不证明已有这些保证。
5. **把显示和撤销也接完整。** 结果应携带稳定来源，画面只呈现附件标志与邻格奖励；业务消费不能等动画完成才成立。撤销是否连奖励一起恢复必须单独规定。

**候选判断：** 附件是可用的局部扩展点，但需要补消费上下文和事件边界；不能直接等同通用连锁效果系统。

## 6. 未确认边界与继续研究的条件

**当前无需继续补齐以下全部证据。** 这些缺口保留为结论边界，不作为下一轮默认任务。只有我方已确定要采用某一具体机制，而这些未知直接影响选择时，才值得回头查对应代码；不为完整还原原游戏重建整个工程。**本次没有执行下列运行实验。**

### 优先在我方实现中验证的四个问题

这些主题已进入我方 [08 的验证清单](../../../_Plan/08_实现顺序与验证.md)，应优先验证自己的契约，不必先证明原游戏如何处理。

**提交中途失败，能恢复到什么状态？** 原项目缺少 `IActionsExecutor`、`PlayerActionCore` 和监听器完整实现，队列、补偿与重试保证未知。我方可固定随机源，在状态写入和快照发布处注入失败，核对物品、次数、余额及故障结果，保证不继续执行残缺状态上的新命令，也不自动重复生成或扣费。若未来确需验证原项目同一问题，再补上述入口并在钱包／监听处理中测试；服务器裁决仍需另找服务端证据。

**旧动画会不会碰到新物品？** 原项目需要补外部对象池与 Tween 的取消约定才能定论。我方直接测试售出后立即撤销、合成中切棋盘、停止动画后在同槽放同类新物：旧回调不改变新绑定，同一资源至多回池一次，业务不等动画完成；同时覆盖原位被占、钱包不足及售价条件变化，撤销使用原实际收入。

**解除一个限制，会不会放开其它限制？** 原项目需要真实配置和完整权限实现；部分可见→完全可见与隐藏→部分可见应分开测试。我方按实际允许的锁、气泡和暂停组合逐个解除，分别检查拖出、作为目标、点击和售出，以及第 2 节提出的计时变化；剩余限制应继续起作用。是否需要汇总多个拒绝原因，可据这些用例决定。

**内存中的成功能否可靠保存？** 目标只留下标记和恢复链，快照、文件写入与错误恢复缺失。我方则应在宿主 Profile 下验证生成／售出后强退、写盘失败再打开、旧字段缺失：占位、次数、钱包要按既定保存语义一致恢复，撤销的会话边界要明确。
