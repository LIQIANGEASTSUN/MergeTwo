## 实际执行的方法

1. **AssetRipper 1.3.14.0**：先实际运行指定程序的 `--help`。单独加载主 APK 时日志显示 `Unknown` 脚本后端，导出的示例是 `Dummy class`。随后将主 APK 内容和 ARM64 分包的 `libil2cpp.so` 合成临时 Android 目录，用该程序 `--headless` 服务的 `/LoadFolder` 和 `/Export/UnityProject` 执行完整导出。日志显示识别 `IL2Cpp`、metadata v39、映射 216,494 个方法定义，最终脚本导出成功。结果在临时目录经过筛选后原样复制到本目录。AssetRipper 对少量 MonoBehaviour 序列化布局报不匹配；这限制了资源中字段值的可信度，不改变下述“脚本方法体是占位”的判断。
2. **仓库内 Il2CppDumper**：对同一 `libil2cpp.so` 和 metadata 实际运行，失败于 `System.NotSupportedException: ERROR: Metadata file supplied is not a supported version[39].`。该工具没有提供可用的 `dump.cs` 或地址脚本，因此本目录没有把它当作代码来源。
3. **Cpp2IL 2022.1.0-pre-release.21**：在临时目录执行官方 ARM64 程序，以这两个输入和 Unity `6000.3.22f1` 生成 `diffable-cs` 与 `isil`。日志显示解析 v39，映射 216,494 个方法定义并完成两个输出。`diffable-cs` 提供类型结构；`isil` 提供该工具关联的 ARM64 指令和中间表示。两类文件均未改写、裁剪或合并。
4. **Ghidra 12.1.2**：对剥离符号的 ARM64 ELF 尝试完整分析；日志大量重复 `ERROR Function body does not fully contain the call site area (LSDACallSiteTable)` 和 `ERROR Failed to disassemble at 055ec248 (GccExceptionAnalyzer)` 等错误，长时间无进展后中止该轮，改用 `-noanalysis` 针对核心方法地址独立反编译。Ghidra 导入基址为 `0x100000`，所以使用 `Ghidra 地址 = Cpp2IL RVA + 0x100000`。第一轮选取 97 个方法，随后补充 15 个棋盘判定、移动、生成、消耗和库存相关方法。独立伪 C 结果和每个目标的状态记录在 `native/Ghidra-C/`。这是工具生成的原生伪代码，不是原始 C#。

所有解包、外部工具运行和全量临时输出都在系统临时目录完成。结果目录不包含 APK、ELF、metadata、Unity 工程、图片、音频、模型、动画或配置资源；Finder 生成的 `.DS_Store` 也已清除。原安装包保持不变。

## 代码范围与完整性边界

- 保留棋盘、坐标、摆放、合成物、生成/消耗/泡泡/箱子/锁定/解锁、库存/口袋、玩家动作、玩家与进度状态、存档迁移、配置类型、合成任务、活动棋盘、棋盘界面交互，以及理解这些流程所需的直接基类、接口和枚举。文件内非二合成员保留原样。
- 范围来自类型名、路径、C# 字段/方法签名、ISIL 具名调用和基类引用的联合检查。没有只靠文件名一个条件。`代码索引.json` 逐文件记录用途分类和原样复制的 SHA-256。
- C# 文件的 `{ }`、`return false`、`return 0`、`return default(...)` 等均为逆向工具的占位代码。**本次没有恢复原始 C# 方法体**。原始行为线索在 `native/` 的反汇编、ISIL 与部分 Ghidra 伪 C 中。
- 自动原生分析可能错认函数边界或漏掉间接调用。方法地址由 Cpp2IL 给出，Ghidra 的 RVA 对齐经关键方法抽样核对，但没有逐个验证全部 13,384 个保留方法。不可把每一行原生输出直接视作已证明的对应方法实现。
- 没有运行游戏做动态跟踪；服务器侧代码、被裁剪的客户端代码、运行时下载的逻辑和加密内容不在此包内，无法从这份 XAPK 证明完整性。对配置值只用来定位类型，没有把配置资源留在最终目录。
