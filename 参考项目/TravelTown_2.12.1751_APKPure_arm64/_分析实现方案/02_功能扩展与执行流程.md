## 1. 先分清“能做”“允许做”和“已经做成”

一个生成器可以同时处于以下状态：它有生成能力、还有剩余次数，但被箱子盖住，所以本次点击不能生成。即使允许点击，如果棋盘没有空位，也不应把这次尝试当成成功。

这套实现把这些问题分开放在不同位置：

| 问题 | 由哪些数据或规则回答 |
| --- | --- |
| 这件物品会不会生成？ | 生成组件及其配置 |
| 现在可不可以操作？ | 锁、箱子、冷却等限制，以及相应系统的资格检查 |
| 有多少额度、什么时候恢复？ | 周期组件中的次数、容量、剩余时间和阶段 |
| 本次是否真的产出了？ | 生成执行返回值、已使用的交互标志和产出结果 |

这解释了为什么一次点击会经过多个系统，而不是“生成器组件自己把所有事做完”。工厂负责添加数据，共享系统分工执行，View 另行显示结果。[E10](04_证据索引.md#e10)、[E23–E28](04_证据索引.md#e23)

## 2. 从进入棋盘到退出：六条实际流程

阅读下面的编号步骤时，需要区分两种顺序：**单个方法内部的顺序已经核对；多个系统在最终棋盘中的完整排序尚未恢复。**涉及系统协作的地方会单独标出，不把推演写成已运行成功的链。

保存和动画还有两个共用边界：六条新路径均未接通完整本地保存入口，不能宣称操作已落盘；已读业务写入早于结果分发，但动画结束、取消及资源失败后的清理仍缺部分实现。详见 [01 保存边界](01_架构与数据模型.md#persistence) 与本篇[失败和中断](#consistency)。[E05](04_证据索引.md#e05)、[E19–E21](04_证据索引.md#e19)、[E38–E39](04_证据索引.md#e38)

### 流程 1：载入棋盘——先恢复一件物品，再给它建立画面

**先理解目的：**玩家重新进入时，要恢复的是同一件物品的业务进度，而不只是放回一个相同图标。

1. **准备种类配置和保存记录。**配置决定应该有合成、生成、时间锁等哪些数据；记录提供这一件物品的实例编号、位置及已发生的进度。对应类型是 MergeItem、ItemPayloadBase、MergeBoardItemState。
2. **按配置建立实体。**工厂的 CreateEntity／CreateBoardItemEntity 创建运行对象，并添加相应组件。
3. **把进度填回组件。**UpdateComponentsFromState 调用各状态恢复器，恢复身份、锁、次数、时间和产物队列。时间恢复前还有 CalculateCyclesDelay／CalculateUnlockTimeLeft 等修正。
4. **建立屏幕上的物品。**PopulateBoard／PopulateCells／CreateItems 和 AddBoardItem 负责格子、物品 View、布局绑定、表现行为及覆盖资源。

这些是已经定位的恢复和显示环节；**待验证：**新棋盘顶层加载者怎样组织它们、何时把完整模型交给其它模块、何时设置初始化完成和开放输入。不能简单写成“创建完 View 就一定允许操作”。未知物品配置、损坏记录、资源加载失败时的处理也未闭合。[E10–E13](04_证据索引.md#e10)、[E19–E20](04_证据索引.md#e19)、[E27](04_证据索引.md#e27)、[E30](04_证据索引.md#e30)

### 流程 2：拖拽与合成——画面拖到一起后，业务层才决定结果

玩家把 A 拖向 B，并不等于 A 已经完成业务移动。界面先根据布局确定起点、终点，再交给规则系统判断移动、合成、换位或拒绝。

1. **输入进入控制器。**BoardItemDragEnded 计算起止格子，调用 MoveItem；控制器把它包装成 MoveAction，启动一轮规则。
2. **多个系统处理位置和规则。**MoveSystem 有写入位置并登记“已移动”的代码；移动锁系统检查源物和目标的固定状态；合成验证器检查合成能力、箱子、种类及合成链；SwapSystem 负责换位相关处理。**较强推断：**它们共同形成上述分支；完整执行顺序及中间位置如何被修正，仍需最终注册和过滤条件补证。
3. **进入已确认的合成方法。**PerformMerge 按合成链找新种类，创建新实体，记录合成标记，加入新物，然后依次给两件旧物加 Dead 标记，最后记录合成和创建结果。
4. **清理旧物并表现结果。**KillSystem 将标记退出的物品从实体集合移除。规则执行结束后，View 创建新物的画面、更新格子并调用动画处理；旧 View 的删除通过后续回调完成。

**数据何时生效：**在第 2、3 步中每次写入位置、添加实体、设置标记时就已修改内存。结果通知和动画发生得更晚。合成并不是等两件物品“飞到一起”后才由动画回调创建新物。[E14–E19](04_证据索引.md#e14)

**待验证：**加入新物到清理旧物之间，新旧实体可暂时共存。其它系统怎样排除 Dead，拒绝分支怎样恢复位置，以及中途异常怎样恢复，不能仅由这一段成功方法证明。

### 流程 3：点击产出——先找到空位，再把这次交互记为成功

此处的主体是 Producer 点击生成链。它把“有资格尝试”“真的产出了”“应当扣费”分开处理。

1. **检查是否可以尝试。**InteractionSystem 检查相应权限和能否支付费用。不满足时记录拒绝；满足时登记 PendingInteraction，即“待处理的一次交互”。此时并不等于已经扣费。
2. **先找放产物的地方。**ProducerSystem 的点击分支寻找附近空位；没有空位就记录 BoardIsFull，不进入本次 TryProduce。
3. **有空位才实际生成。**TryProduceItem 从产物队列取一项，创建并加入新实体，减少可产出次数，记录产出结果。返回成功后，将本次交互标记为 Used，即“已经使用”。
4. **费用系统检查成功标志。**InteractionCostSystem 跳过未使用的交互；对已使用的交互，根据配置消费资源或物品。
5. **界面显示产物。**规则执行后的结果交给公共 View 流程，建立新产物的画面。

上述单方法行为已确认。**较强推断：**正常满盘点击不会在该 Producer 分支推进产物队列或标记交互成功，费用系统也有跳过未成功交互的机制；完整“不产出就不扣费”仍需确认系统顺序，以及是否另有能力使用了同一次交互。[E23–E25](04_证据索引.md#e23)、[E27](04_证据索引.md#e27)

可直接对照：[生成分支的原生实现](../native_arm64/TravelTown.MergeBoard/025768_ProducerSystem.s#L304)、[费用系统的成功标志检查](../native_arm64/TravelTown.MergeBoard/025743_InteractionCostSystem.s#L164)。

**待验证：**如果已取出产物，但后续创建、加入实体或扣费发生异常，有没有把队列位置、次数和余额一同恢复？本次未找到通用补偿证据。正常拒绝和中途出错是两种不同问题。

### 流程 4：时间推进——冷却好了，不一定已经生成了物品

需要先区分两个动作：

- **恢复额度或结束冷却：**改变生成器的数据，使它具备再次产出的条件。
- **实际产出：**选择产物、找到位置、创建新的物品实体。

周期系统负责前一类变化，自动产出系统负责后一类变化。不能把一个“冷却结束”结果当成“棋盘已经多出一件物品”。Spawner 有明确的定时创建分支；Producer 除点击外还有就绪分支，但 ReadyToProduce 是谁在所有情况下设置的，尚未查清，所以也不能断言它永远只靠手动点击。[E24](04_证据索引.md#e24)、[E26–E28](04_证据索引.md#e26)

时间具体这样进入规则：

1. **在线时累计经过时间。**IntervalTicker 在 Update 中累计时间，达到调度间隔后调用 ProcessTimeInterval，并更新棋盘上次同步时间。它不是给每件物品各建一个独立计时器。
2. **把时间作为输入。**控制器生成 IntervalTick，像处理点击一样执行一轮规则；暂停时会跳过。
3. **推进周期和额度。**TimeCycleSystem 的 ProcessDelay／ProcessCycles 更新剩余秒数、阶段和计数，必要时记录冷却变化。
4. **自动产出系统响应时间输入。**Spawner 的 HandleSpawnByTick 选择可用位置，再经 GetItemToSpawn／SpawnItem 创建产物并扣次数。落点选项 Anywhere 会参与这一过程。
5. **重开时处理经过的时间。**计时器启动时会用当前服务时间减去棋盘上次同步时间，推入时间差；载入恢复本身也有剩余时长修正和“已由载入修改”的标志。

第 5 步是离线恢复最需要谨慎的地方：**已确认存在两处时间处理，但尚未端到端证明它们不会重复计算。**周期代码会识别载入修正标志并跳过相应首轮处理，这是防重复的线索；最终效果还依赖装配和调用顺序。[E06](04_证据索引.md#e06)、[E26](04_证据索引.md#e26)、[E28–E30](04_证据索引.md#e28)

**待验证：**满盘时自动产出积压多少、时间是否继续、一次长离线最多补多少、后台与失焦如何处理，以及暂停时未执行的时间是否保留。不能据现有代码补出一套确定的离线产品规则。

### 流程 5：解除箱子或普通锁——先改限制事实，再播放解除效果

箱子覆盖和普通锁是两份数据。即使外观相似，代码也分别解除，不使用一个“全部解锁”操作替代。

1. **确定谁该被解除。**UnboxingSystem 可响应合成、消费、资源或需求相关入口；涉及邻物时，通过布局查询相邻的带箱物品。不同拆箱方式的计数和阈值不能凭名字合并。
2. **修改对应的数据。**UnboxItem 将 Boxed 改为 false 并写回；UnlockEntities 则单独将 Locked 改为 false。
3. **记录已经发生的变化。**拆箱增加临时标记和拆箱结果，普通解锁生成自己的结果。
4. **后续规则重新读取权限，View 呈现解除。**一个限制取消后，其它仍存在的锁、箱子或限制继续参与相应判断。

**数据何时生效：**第 2 步写回时，而不是解除动画结束时。已读方法没有在动画取消后重新加锁的代码。**待验证：**具体覆盖物怎样退场、动画期间怎样处理点击命中、取消后如何释放资源，仍缺表现后端。[E22–E23](04_证据索引.md#e22)、[E31–E32](04_证据索引.md#e31)、[E19–E21](04_证据索引.md#e19)

### 流程 6：售出、删除与撤销——逻辑退出、画面退场和恢复身份分开处理

以售出为例，它有专门的撤销逻辑，不能推广为“所有操作都支持撤销”。

1. **售出规则让物品退出。**SellItemSystem 检查资格，通过后标记 Dead 并记录售出结果；KillSystem 再将它从运行集合移除。合成消耗旧物也使用类似的标记清理机制。
2. **画面处理退场。**HandleBoardResult 获取删除对象，调用动画处理，并在协程后续传出删除回调。回调最终可调用 DeleteItems。
3. **解除 View 绑定。**已见释放链会清理表现行为、必要时取消拖拽，并从容器移除绑定。对象池回收与全部订阅、动画清理是否完成，尚缺部分实现。
4. **玩家撤销售出。**撤销模型保留旧 Entity；UndoSellItemSystem 复制其组件字典到一个新 Entity，查找附近空位，写回位置，去掉 Dead，再加入棋盘。无空位有失败结果。

**身份与位置：**撤销建立新的运行对象，复制原组件中的身份数据；它寻找附近空位，不保证原格恢复。复制字典也不等于把其中所有对象都复制一遍：若组件中引用产物队列等可变对象，新旧实体可能仍指向同一份对象。[E04](04_证据索引.md#e04)、[E36–E37](04_证据索引.md#e36)

**待验证：**原对象是否还会被计时或旧回调修改，决定这种共享是否有实际风险。旧动画回调会不会误操作已换绑的 View、售出和撤销怎样结算资源、重开后是否还能撤销，也未形成完整证据。删除回调存在，不足以证明它在动画取消时一定执行。[E19–E21](04_证据索引.md#e19)

## 3. 理解流程后，查阅每种功能怎样组成

下面保留原分析模板要求的十个维度，方便横向比较。阅读主线到这里已经完成；这些表用于回答“数据在哪里、谁创建、怎样限制、如何恢复”等具体问题。


### 3.1 点击生成器：生成能力、次数与费用分别管理

依据：[E10](04_证据索引.md#e10)、[E23–E25](04_证据索引.md#e23)、[E27](04_证据索引.md#e27)、[E34](04_证据索引.md#e34)。

| 维度 | 还原结果与边界 |
| --- | --- |
| 归属 | 生成组件（ProducerComponent）附在物品上；每件产物会创建新的实体。 |
| 数据 | 生成组件保存产物队列、随机种子、能力配置和就绪标志；周期组件保存额度与累计；交互组件保存费用和消耗项。 |
| 创建与装配 | 种类配置有 Produce 能力时，工厂添加生成和周期组件。 |
| 触发 | 待交互标记触发点击分支；每轮还会检查 ReadyToProduce 就绪分支。**待验证：**ReadyToProduce 的全部设置来源。 |
| 规则权限 | 交互系统检查操作资格和支付能力，生成系统检查组件与空位；普通锁、箱子、冷却阻挡参与限制，其余排除条件待验证。 |
| 执行 | 生成系统建产物、减次数、记录结果，成功后标记交互已使用；费用系统据此消费。详见流程 3。 |
| 表现 | 公共结果处理器与容器创建产物 View；飞行动画、费用文字和资源失败分支待验证。 |
| 组合与冲突 | **较强推断：**扣费依赖系统顺序；同一物品同时配置点击生成和自动产出时，周期数据怎样共用或覆盖待验证。 |
| 解除与迁移 | 消耗额度、增加累计，另有寿命上限判断；耗尽后的变身／删除、合成继承与入库暂停未闭合。 |
| 保存与恢复 | 从记录中的种子、队列位置和周期数据重建产物队列；就绪标志是否跨会话保留待验证。 |

### 3.2 自动产出：周期负责额度，生成系统负责创建

依据：[E24](04_证据索引.md#e24)、[E26–E30](04_证据索引.md#e26)、[E34](04_证据索引.md#e34)。

| 维度 | 还原结果与边界 |
| --- | --- |
| 归属 | 自动产出与周期数据都在物品上；棋盘级计时器统一提供经过的时间。 |
| 数据 | 自动产出组件保存队列、种子、能力配置和落点选项；周期组件保存容量、剩余时长、次数与阶段。 |
| 创建与装配 | 种类配置有 Spawn 能力时装配；实际多少秒产出一次，取决于缺失的配置。 |
| 触发 | 自动产出系统分别处理点击与时间输入；周期系统推进额度，自动产出系统创建物品。 |
| 规则权限 | 已见筛选会排除带普通移动限制的物品；Anywhere 选项影响落点；其它条件及满盘是否暂停计时待验证。 |
| 执行 | 找到落点、选择产物、创建新物后扣次数并记录结果。关键方法与时间推进见流程 4。 |
| 表现 | 产物经公共结果机制显示，不等飞行动画结束才加入业务容器；阶段视觉和后台策略待验证。 |
| 组合与冲突 | 容量、周期阶段和限制分别存储；**较强推断：**同一轮里推进时间和生成的先后会影响结果；冷却结束通知本身不是产物。 |
| 解除与迁移 | 生成减额度、加累计，周期转段重置部分计数；满盘积压上限和入库规则待验证。 |
| 保存与恢复 | 截止点、剩余时间和队列进度共同恢复；载入修正标志与计时器如何避免重复补时，见流程 4。 |

冷却、实际产出与 Producer 就绪分支的区别，见流程 4。

### 3.3 普通锁与箱子：两份可以分别解除的数据

依据：[E16](04_证据索引.md#e16)、[E20](04_证据索引.md#e20)、[E22](04_证据索引.md#e22)、[E31–E32](04_证据索引.md#e31)。

| 维度 | 还原结果与边界 |
| --- | --- |
| 归属 | 箱子组件和普通锁组件都附在物品上；本条拆箱链不代表独立地格锁或可开出奖励的宝箱种类。 |
| 数据 | 箱子记录是否覆盖、当前／总交互次数、拆箱方式和资源；普通锁记录是否锁定。 |
| 创建与装配 | 普通物品工厂添加这两类数据；初始格可提供配置，恢复器从共享锁记录分别回填。 |
| 触发 | 拆箱有消费、合成、资源、需求入口，邻接经布局查询；普通 Lock 由 UnlockingSystem 另行解除。 |
| 规则权限 | 普通锁和箱子都参与移动限制；在已读验证器中，箱子未解除时不能通过合成检查，普通锁与同种合成的关系见下文。 |
| 执行 | 拆箱先将 Boxed 改为 false；普通解锁单独将 Locked 改为 false；随后分别记录结果。 |
| 表现 | 锁适配器读取业务限制，容器另建覆盖显示对象；箱子、网罩、灰化资源及输入命中刷新待验证。 |
| 组合与冲突 | 解除 Box 不清 Lock，反之亦然；实际合法组合与动画期间输入仍需验证。 |
| 解除与迁移 | 解除保留组件、改布尔；**较强推断：**移动不把限制迁到地块。合成新物的继承规则未知。 |
| 保存与恢复 | Box／Lock 各自回填，不是仅存物种 Id；解除中重开是否重复播放动画待验证。 |

**为什么“不能拖动”不等于“不能被合成”？**可以设想 A 被固定在原格，玩家不能把 A 拖走，但可以把匹配的 B 拖到 A 上合成。这是两个不同权限：前者检查 A 能否主动移动，后者检查 A 能否接收合成。

源码中的局部规则支持这个区别：拖动查询会汇总普通锁、箱子和固定位置标记；合成验证器则会先处理箱子限制，而同种合成成功可以早于普通移动锁检查返回。移动锁系统遇到固定目标时，也会先询问是否能合成，再决定是否阻止这次移动。对应入口是 FixedPosition、CanMergeSame 和 ItemMovementLockSystem。[E15–E16](04_证据索引.md#e15)、[E22](04_证据索引.md#e22)

**较强推断：**普通锁定物可以被设计为固定的同种合成目标。但完整输入、系统注册和实际配置还缺证据，不能写成“本版本所有带锁物品都允许这样合成”；带箱物品也不能套用这个例子。

**“逻辑已解锁，覆盖物仍退场”：**组件写入先于 View 消费，允许表现落后；动画时长、命中和取消后的释放仍待验证，见流程 5。

### 3.4 时间锁：计时状态和阻挡标记配合工作

依据：[E10](04_证据索引.md#e10)、[E30](04_证据索引.md#e30)、[E33–E34](04_证据索引.md#e33)。

| 维度 | 还原结果与边界 |
| --- | --- |
| 归属 | 时间锁数据和阻挡标记附在物品上，并有组信息；未见每个限制单独的实例编号。 |
| 数据 | 记录剩余／总时长、是否正在解锁、是否允许解锁、所属组、来源、载入修正和使用标志等。 |
| 创建与装配 | 工厂根据时间锁配置创建数据；系统在运行中添加或移除阻挡标记。 |
| 触发 | 点击可进入开始解锁处理，时间输入推进剩余时长；全部触发前提未还原。 |
| 规则权限 | 区分能否开始、是否正在解锁及同组状态；各操作怎样读取时间锁阻挡标记仍待验证，不能当作普通移动锁。 |
| 执行 | 修改时间锁状态并更新阻挡标记；能力组件可以保留。 |
| 表现 | 公共 View 与表现行为负责呈现；时间锁专用图标、进度条及动画处理链待验证。 |
| 组合与冲突 | 有组集合／组内查询；优先级、同时点击、重复开始及实际组配置待验证。 |
| 解除与迁移 | 可以移除阻挡标记，已使用标志还参与合成限制；入库或合成后组状态怎样变化仍待验证。 |
| 保存与恢复 | 有解锁剩余时间修正；完整保存字段以及配置改变后的恢复行为待验证。 |

### 3.5 补充功能的覆盖等级

**有限次数生成器：已确认（静态证据），但只确认局部。**周期组件记录累计产出，并有查询是否达到总次数上限的方法 ExceededLifetimeLimit。达到上限后是删除、替换还是等待，还取决于其它系统和配置，不能从这一个查询方法推断。[E27–E28](04_证据索引.md#e27)、[E34](04_证据索引.md#e34)

**售出／撤销：关键生命周期链已确认（静态证据）。**见流程 6，它是专门模块，不是通用 Undo 框架。[E36–E37](04_证据索引.md#e36)

**旧气泡与等级锁：仅补充，不混入新系统。**旧 LockedComponent 包含 Bubbled、LevelLock 及网络／飞行动画等锁；旧 Merge 确实调用 TryDropBubble。没有完成新 ECS 的气泡付费、过期和退款链，等级锁也未形成端到端证据。不能因为共用了保存记录和适配字段，就推定新 ECS 已执行同样规则。[E35](04_证据索引.md#e35)

充能、消耗、工具生成的工厂装配已见，但本次未追到全部执行与恢复链；选择箱、复制／升级工具的产品规则不在这里凭类名展开。半透明、变灰、蜘蛛网的具体美术映射因为资源和部分表现实现缺失而待验证。

## 4. 失败、连续输入和动画中断分别怎样看

这套实现有拒绝分支和阶段标记，但没有证据证明所有异常都能恢复到操作前。尤其要区分“检查时拒绝”和“写到一半失败”。[E05–E06](04_证据索引.md#e05)、[E17–E18](04_证据索引.md#e17)、[E24–E25](04_证据索引.md#e24)

| 情况 | 已见机制 | 仍然不能据此承诺什么 |
| --- | --- | --- |
| 无空位或付不起费用 | 找空位失败、支付资格拒绝、交互成功标志 | 同一交互带多项能力时，也完全不会扣错或多生成 |
| 快速连续点击 | 控制器同步执行每轮规则，View 有选择和双击入口 | 所有输入都进入一个先进先出的队列 |
| 结果处理器又发起新操作 | 执行结束后可调用扩展处理器 | 上层一定会阻止嵌套执行；本体未见完整重入排队协议 |
| 某个系统中途异常 | 多步直接修改组件和集合 | 已生效的步骤一定自动撤销 |
| 动画取消或资源失败 | 核心数据已修改，有局部释放入口 | 所有残留画面和输入状态一定能恢复正确 |
| 关闭后旧回调才到达 | 闭包仍可持有待删除对象和 View | 回调一定会检查当前绑定是不是旧的那一件 |
| 一个变化触发其它功能 | 系统列表、临时标记和结果列表支持协作 | 已有统一防重复、终止连锁或循环次数上限 |

这些是证据边界和需要验证的条件，不是已发现的游戏故障。

## 5. 再补三点：随机进度、性能、可测试性

### 5.1 生成结果需要恢复到“队列的哪一步”

产物队列不只保存可产出种类，还保存随机种子和当前位置。已读 Producer 恢复路径以保存的 Seed 加 TotalNumberOfCycles，并结合 ItemIndex 重建队列，再加入配置中的组合或权重项。取项工具还可能在队列耗尽时重新填充并更新组件。[E27](04_证据索引.md#e27)

这解释了保存为什么要记录生成进度：只恢复物品种类，会遗漏“下一次应该从哪里继续取”。但真实概率表、服务端随机算法和配置变更后的重放结果均缺证据；不能保证同一种子在任何版本配置下都会产生同样结果。

### 5.2 ECS 在这里不自动等于某种性能结论

已见实体集合遍历、组件字典查询，以及每轮创建的输入、结果、临时集合和迭代器；最近空位和邻接也会遍历布局。它可以是小棋盘上容易理解的直接实现，但是否需要优化，应测实际规模、耗时和分配量。本次没有这些测量，也不混用旧路径的距离缓存来评价新路径。[E03–E09](04_证据索引.md#e03)

### 5.3 怎样才能验证上述规则

**较强推断：**如果补齐系统顺序，提供纯数据布局、可控配置、替代钱包、固定时钟和固定队列状态，就能用稳定输入验证生成、满盘、冷却和恢复。当前材料不是可运行工程，本次未实施这些测试。具体的最小验证方法集中在 [03 待验证清单](03_借鉴评估与待验证问题.md#questions)。
