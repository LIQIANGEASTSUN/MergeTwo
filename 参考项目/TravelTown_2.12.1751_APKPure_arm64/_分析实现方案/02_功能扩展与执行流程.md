## 1. 先分清“能做”“允许做”和“已经做成”

一个生成器可以同时处于以下状态：它有生成能力、还有剩余次数，但被箱子盖住，所以本次点击不能生成。即使允许点击，如果棋盘没有空位，也不应把这次尝试当成成功。

这套实现把这些问题分开放在不同位置：

| 问题 | 由哪些数据或规则回答 |
| --- | --- |
| 这件物品会不会生成？ | 生成组件及其配置 |
| 现在可不可以操作？ | 锁、箱子、冷却等限制，以及相应系统的资格检查 |
| 有多少额度、什么时候恢复？ | 周期组件中的次数、容量、剩余时间和阶段 |
| 本次是否真的产出了？ | 生成执行返回值、已使用的交互标志和产出结果 |

这解释了为什么一次点击会经过多个系统，而不是“生成器组件自己把所有事做完”。工厂负责添加数据，共享系统分工执行，View 另行显示结果。

## 2. 从进入棋盘到退出：六条实际流程

**单个方法内部的顺序已经核对；多个系统在最终棋盘中的完整排序尚未恢复。**以下将直接可见的写入和需要系统协作的推断分别说明。

六条新路径共用两项边界：完整本地保存入口尚未接通；业务写入早于结果分发，但动画结束、取消和资源失败后的完整清理仍待验证。每条流程中的“生效”指内存数据生效。

### 流程 1：载入棋盘——先恢复一件物品，再给它建立画面

重新进入棋盘时，配置决定物品的能力，保存记录恢复这件物品的进度，View 根据恢复后的实体建立画面。

1. **准备种类配置和保存记录。**配置决定应该有合成、生成、时间锁等哪些数据；记录提供这一件物品的实例编号、位置及已发生的进度。对应类型是 MergeItem、ItemPayloadBase、MergeBoardItemState。
2. **按配置建立实体。**工厂的 CreateEntity／CreateBoardItemEntity 创建运行对象，并添加相应组件。
3. **把进度填回组件。**UpdateComponentsFromState 调用各状态恢复器，恢复身份、锁、次数、时间和产物队列。时间恢复前还有 CalculateCyclesDelay／CalculateUnlockTimeLeft 等修正。
4. **建立屏幕上的物品。**PopulateBoard／PopulateCells／CreateItems 和 AddBoardItem 负责格子、物品 View、布局绑定、表现行为及覆盖资源。

这些是已经定位的恢复和显示环节；**待验证：**新棋盘顶层加载者怎样组织它们、何时把完整模型交给其它模块、何时设置初始化完成和开放输入。不能简单写成“创建完 View 就一定允许操作”。未知物品配置、损坏记录、资源加载失败时的处理也未闭合。（[记录恢复入口](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025903_MergeBoardItemsEntityFactory.s:211)）

### 流程 2：拖拽与合成——画面拖到一起后，业务层才决定结果

玩家把 A 拖向 B，并不等于 A 已经完成业务移动。界面先根据布局确定起点、终点，再交给规则系统判断移动、合成、换位或拒绝。

1. **输入进入控制器。**BoardItemDragEnded 计算起止格子，调用 MoveItem；控制器把它包装成 MoveAction，启动一轮规则。
2. **不同系统分别执行权限、移动和组合规则。**MoveSystem 按起点找到物品，写入终点并登记“已移动”；移动锁系统检查源、目标的固定状态，并询问组合验证器；合成验证器检查能力、箱子、种类和合成链；SwapSystem 根据移动标记处理换位。这是职责划分，不能把列举顺序当成实际执行顺序。
3. **进入已确认的合成方法。**PerformMerge 按合成链找新种类，创建新实体，记录合成标记，加入新物，然后依次给两件旧物加 Dead 标记，最后记录合成和创建结果。
4. **清理旧物并表现结果。**KillSystem 将标记退出的物品从实体集合移除。规则执行结束后，View 创建新物的画面、更新格子并调用动画处理；旧 View 的删除通过后续回调完成。

**数据何时生效：**在第 2、3 步中每次写入位置、添加实体、设置标记时就已修改内存。结果通知和动画发生得更晚。合成并不是等两件物品“飞到一起”后才由动画回调创建新物。（[合成写入](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025760_MergeSystem.s:451)）

**阻止移动不是位置回滚。**BlockMovement 添加临时 MoveBlock 标记，并记录物品与原位置；该方法没有把位置写回。因而不能还原成“先移动，发现被锁再搬回去”。实际门禁与移动系统的先后、对阻挡及 Dead 的排除条件，仍待最终注册和委托映射补证。合成先加新物再清旧物的中间状态，以及异常恢复也受这些条件影响。（[阻挡方法](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025912_MergeBoardEntitiesExtensions.s:306)）

### 流程 3：点击产出——先找到空位，再把这次交互记为成功

此处的主体是 Producer 点击生成链。它把“有资格尝试”“真的产出了”“应当扣费”分开处理。

1. **检查是否可以尝试。**InteractionSystem 检查相应权限和能否支付费用。不满足时记录拒绝；满足时登记 PendingInteraction，即“待处理的一次交互”。此时并不等于已经扣费。
2. **先找放产物的地方。**ProducerSystem 的点击分支寻找附近空位；没有空位就记录 BoardIsFull，不进入本次 TryProduce。
3. **有空位才实际生成。**TryProduceItem 从产物队列取一项，创建并加入新实体，减少可产出次数，记录产出结果。返回成功后，将本次交互标记为 Used，即“已经使用”。
4. **费用系统检查成功标志。**InteractionCostSystem 跳过未使用的交互；对已使用的交互，根据配置消费资源或物品。
5. **界面显示产物。**规则执行后的结果交给公共 View 流程，建立新产物的画面。

上述单方法行为已确认。**较强推断：**正常满盘点击不会在该 Producer 分支推进产物队列或标记交互成功，费用系统也有跳过未成功交互的机制；完整“不产出就不扣费”仍需确认系统顺序，以及是否另有能力使用了同一次交互。

方法依据：[生成分支的原生实现](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025768_ProducerSystem.s:304)、[费用系统的成功标志检查](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025743_InteractionCostSystem.s:164)。

**待验证：**如果已取出产物，但后续创建、加入实体或扣费发生异常，有没有把队列位置、次数和余额一同恢复？本次未找到通用补偿证据。正常拒绝和中途出错是两种不同问题。

#### 喂料满足条件后，也可以进入生成分支

Producer 并非只有手动点击入口。FeedingCombinationFeedSystem 把喂入物的记录加入目标数据，并将被喂入的实体标记退出；CheckForFedProducers 再检查已收集物品能否组成配置要求的组合。找到至少一个可用组合，就把目标的 ReadyToProduce 设为 true；没有组合则设为 false。（[喂料与就绪判断](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025738_FeedingCombinationFeedSystem.s:241)）

ProducerSystem 每轮先处理点击，再检查就绪物品。ProduceItemIfReady 找到空位且生成成功后，会清除 ReadyToProduce；找不到空位时不清除，并结束这次就绪遍历。取产物工具也会读取喂料记录。因此，**喂料满足组合是已确认的就绪来源，ReadyToProduce 不能直接解释成“冷却结束”。**（[就绪生成与清标记](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025768_ProducerSystem.s:480)）

**较强推断：**只要后续一轮仍满足筛选条件，就可以再尝试就绪生成，无需该轮再次点击。是否在喂料的同一轮立刻产出、恢复后何时重算，以及是否还有其它就绪来源，仍取决于系统顺序和完整写入链。喂料有专门状态恢复器，但尚未闭合跨会话流程。

#### 这些能力的数据如何组合和恢复

ProducerComponent 属于生成器物品，保存能力配置、产物队列、种子和就绪标志；TimeCycleComponent 保存额度和周期，InteractionComponent 保存费用与消耗条件。普通锁、箱子和冷却阻挡参与交互资格；其他查询排除条件仍未全部还原。工厂仅在对应能力存在且启用时装配，喂料也是显式配置分支。

**同一物品并不会自动获得两套独立周期。**工厂先为 Produce、再为 Spawn 尝试写入同一个 TimeCycleComponent 类型；TryAddComponent 在能力启用后直接调用 SetComponent，没有“已有周期则跳过”的检查。结合每类组件只有一个槽，**较强推断**后写入的 Spawn 周期会覆盖前者，而不是各自计时。实际配置是否允许这种组合、两种产出是否有意共用周期，仍待验证。（[两次周期装配](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025903_MergeBoardItemsEntityFactory.s:671)、[启用检查与写入](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025903_MergeBoardItemsEntityFactory.s:4198)）

恢复 Producer 时，代码以保存的 Seed 加 TotalNumberOfCycles，并结合 ItemIndex 重建产物队列，再填入配置的组合／权重项。队列耗尽还可能补充内容并写回组件。保存不能只记录种类，还要记录“序列走到哪一步”；真实权重、服务端算法和配置变更后的重放一致性仍未知。（[队列恢复](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025846_ProducerComponentStateUpdater.s:47)）

产物的显示沿用公共 View 容器；飞行动画、费用文字、资源失败和就绪标志的持久化尚未闭合。生成器合成时哪些进度继承、入库后是否暂停，也不能由普通创建流程推出。

### 流程 4：时间推进——冷却好了，不一定已经生成了物品

需要先区分两个动作：

- **恢复额度或结束冷却：**改变生成器的数据，使它具备再次产出的条件。
- **实际产出：**选择产物、找到位置、创建新的物品实体。

周期系统更新额度和阶段；Spawner 的定时分支负责真正创建物品，Producer 的喂料就绪则是另一种触发。三者不能统称为“等一段时间自动生成”。

#### 周期数据分别记什么

可用额度可以理解为“已经充好的使用次数”。恢复额度只是增加这种次数，真正创建物品还要找到空位并执行生成。

| 数据 | 含义与变化 |
| --- | --- |
| ItemsToProduce | 当前可用额度；成功产出时递减，周期处理可以补充 |
| ItemsProducedPerSubCycle | 已产出的计数，参与子周期位置和整轮切换的计算；不能当作剩余次数 |
| TotalSpawnedItemsInLifetime | 累计产出数，用于寿命上限判断 |
| Capacity、ItemsPerSubCycle、SubCycles | 最大额度、每次补充量及子周期配置 |
| CycleDelayLeft、SubCycleDelayLeft | 整轮等待与子周期等待的剩余时间 |
| State | 当前处于冷却还是容量阶段；原枚举为 Cooldown、CycleCooldown、Capacity、FullCapacity |

成功产出的扣次数工具，在额度大于零时减少可用额度，并增加已产出计数和寿命累计。ProcessCycles 结合产出计数计算子周期进度；ProcessCycle 按配置补额度并受容量约束，进入新轮时重置相应计数、增加轮数。因此它不是简单地把“经过秒数除以间隔”当作产物件数。（[周期字段](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/metadata_blocks/TravelTown.MergeBoard/TypeDef_026019.txt:1)、[次数更新](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025725_SpawningItemsUtils.s:371)）

达到寿命上限时，ProcessTime 把可用额度归零、阶段设为 Cooldown。TimeCycleSystem 随后按“没有额度、冷却被阻挡或已达寿命上限”添加 CooldownBlock，否则移除该标记。这一步限制继续产出，**本身没有删除实体**。（[周期处理与阻挡](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025781_TimeCycleSystem.s:267)）

#### 时间怎样进入系统，自动产物落在哪里

1. **棋盘统一提供时间输入。**IntervalTicker 在 Update 中累计经过时间，达到调度间隔后调用 ProcessTimeInterval，控制器包装成 IntervalTick；每件物品保存自己的周期数据，不各自建立独立计时器。
2. **周期系统推进等待和额度。**ProcessDelay／ProcessCycles 消化经过时间、转换阶段，并记录相应结果。它与产出系统的最终先后仍待系统装配补证。
3. **Spawner 处理产出。**它先有点击处理，再在存在 IntervalTick 时扫描自动产出物品。HandleSpawnByTick 要求可用额度至少为一；已见筛选还会排除普通移动限制，完整过滤条件未全部恢复。
4. **按落点配置找位置。**Anywhere 开启时，在布局允许的全部空位中找靠近生成器的位置；关闭时只在相邻格中排除已占位，再选一个候选。这里的相邻由几何布局接口决定，不能擅自改写成固定上下左右顺序。
5. **找到位置才取产物。**调用 GetItemToSpawn，再由 SpawnItem 建实体、扣额度、记录结果。若没有合适空位，或取项返回空，本分支提前返回；无空位时尚未取产物，也未扣额度。

**每次定时分支扫描，对每个参与的实体最多调用一次 SpawnItem。**HandleSpawnByTick 没有循环补出全部积压物品。例如，可用额度为三且有三个空位，也不代表这次定时扫描会连续创建三件（说明性例子）。传入长时间差同样不等于一次补出所有离线产物；周期补额度与分次创建是两层行为。满盘时该产出分支不花掉额度，但不能由此推断周期计时也暂停。（[自动产出扫描](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025773_SpawnerSystem.s:5)、[落点与单次产出](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025773_SpawnerSystem.s:459)）

SpawnerComponent 保存自己的种子、队列、能力和 Anywhere 选项，工厂根据启用的 Spawn 配置装配。具体多少秒恢复、容量多大，仍缺实际配置；产物经公共结果机制显示。合成后的进度迁移、入库和后台行为没有闭合证据。

#### 重开与暂停，不是同一件事

载入时，CalculateCyclesDelay 根据记录中的绝对截止时间重算剩余等待：存在截止字段时先清剩余值，再为尚未到期的截止点填入时间差。这只是校正等待时间。恢复器回填次数并设置 ModifiedByStateLoad；周期系统遇到该标记时清除它，跳过本次时间处理。另一方面，IntervalTicker.Start 会把服务时间与棋盘上次同步时间的差值推给控制器。（[载入时间修正](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/ghidra_pseudoc/0x6A9787C.c:8)、[跳过载入后的首次周期处理](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025781_TimeCycleSystem.s:377)）

**待验证：**上述两处补时是否配合正确，取决于载入、计时器和系统的调用顺序；有防重复标记不等于已证明重复载入、长离线和满盘腾空都正确。应比较一次大时间差与多次小时间差的额度、队列和实际产物。

暂停还存在一个具体边界：控制器 IsPaused 时直接跳过 Tick；IntervalTicker.Update 则在调用前清空累计时间、返回后更新时间戳。**较强推断（有条件）：**若宿主只暂停控制器而让计时器继续 Update，这条调用链不会自行保留被跳过的时间。宿主是否同时停用计时器、失焦或后台怎样处理仍未知，不能据此认定游戏实际丢时。（[计时器调用次序](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025678_IntervalTicker.s:130)）

### 流程 5：解除箱子或普通锁——先改限制事实，再播放解除效果

箱子覆盖和普通锁是两份数据。即使外观相似，代码也分别解除，不使用一个“全部解锁”操作替代。

1. **确定谁该被解除。**UnboxingSystem 可响应合成、消费、资源或需求相关入口；涉及邻物时，通过布局查询相邻的带箱物品。不同拆箱方式的计数和阈值不能凭名字合并。
2. **修改对应的数据。**UnboxItem 将 Boxed 改为 false 并写回；UnlockEntities 则单独将 Locked 改为 false。
3. **记录已经发生的变化。**拆箱增加临时标记和拆箱结果，普通解锁生成自己的结果。
4. **后续规则重新读取权限，View 呈现解除。**一个限制取消后，其它仍存在的锁、箱子或限制继续参与相应判断。

**数据何时生效：**第 2 步写回时，而不是解除动画结束时。已读方法没有在动画取消后重新加锁的代码。**待验证：**具体覆盖物怎样退场、动画期间怎样处理点击命中、取消后如何释放资源，仍缺表现后端。

箱子和普通锁都附在物品上。BoxComponent 保存覆盖布尔值、当前／总交互次数、拆箱方式和资源；LockComponent 保存普通锁布尔值。普通工厂装配这两份数据，初始格可提供配置，恢复器从共享锁记录分别回填；解除时保留组件、只改对应事实。它们不等于独立地格锁，也不等于可领奖励的宝箱物种。（[拆箱写入](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025757_ItemUnboxingSystem.s:2160)、[普通解锁写入](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025758_ItemUnlockingSystem.s:55)）

**为什么“不能拖动”不等于“不能被合成”？**可以设想 A 被固定在原格，玩家不能把 A 拖走，但可以把匹配的 B 拖到 A 上合成。这是两个不同权限：前者检查 A 能否主动移动，后者检查 A 能否接收合成。

源码中的局部规则支持这个区别：拖动查询会汇总普通锁、箱子和固定位置标记；对工厂正常装配、两边都有 Box 组件的物品，合成验证器要求双方 Boxed 均为 false；而同种合成成功可以早于普通移动锁检查返回。移动锁系统遇到固定目标时，会询问一组组合验证器（其中包括合成验证器）；所有验证器都不接受时，才登记移动阻挡。不能把这组判断缩成只检查合成。同种合成还要求双方具备相应合成类型、配置 Id 相同且存在下一阶；特殊配方路径另查普通移动锁。这分别由 FixedPosition、CanMergeSame 和 ItemMovementLockSystem 实现。（[合成资格分支](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/ghidra_pseudoc/0x6A87644.c:79)、[固定目标的组合验证](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025753_ItemMovementLockSystem.s:139)）

**较强推断：**普通锁定物可以被设计为固定的同种合成目标。但完整输入、系统注册和实际配置还缺证据，不能写成“本版本所有带锁物品都允许这样合成”；带箱物品也不能套用这个例子。

锁适配器从业务组件派生拖动限制，覆盖显示由 View 另行创建；具体是木箱、网罩、灰色还是半透明，需要资源才能判断。获准移动时限制仍属于原物品；合成新物是否继承、解除过程中重开是否重播、同时带多种限制时的完整输入规则，仍待验证。

#### 时间锁还需要计时进度和组规则

时间锁是另一套物品数据，不能从普通 Lock 的布尔值推出。TimeLockComponent 记录是否正在解锁、能否开始、剩余／总时间、组、来源、载入修正和使用标志；它没有为每个限制另建独立实例编号。

工厂按时间锁配置装配。点击可以进入 StartUnlocking，时间输入经 ProcessTime 推进；UpdateTimeLockBlockComponent 按状态添加或移除阻挡标记，原能力仍可保留。该系统有组集合和组内查询，Used 标志还参与合成限制。（[时间锁阻挡的动态增删](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025787_TimeLockSystem.s:616)）

**待验证：**所有开始前提、同组优先级、重复点击、各操作对 TimeLockBlock 的读取、合成和入库后的组状态均未闭合。恢复有剩余时间修正，但完整保存字段及配置改变后的处理仍不明确；专用图标、进度和动画缺表现链。不能把“能动态增删一个阻挡标记”扩大成任意效果的多来源叠加能力。

### 流程 6：售出、删除与撤销——逻辑退出、画面退场和恢复身份分开处理

以售出为例，它有专门的撤销逻辑，不能推广为“所有操作都支持撤销”。

1. **售出规则让物品退出。**SellItemSystem 检查资格，通过后标记 Dead 并记录售出结果；KillSystem 再将它从运行集合移除。合成消耗旧物也使用类似的标记清理机制。
2. **画面处理退场。**HandleBoardResult 获取删除对象，调用动画处理，并在协程后续传出删除回调。回调最终可调用 DeleteItems。
3. **解除 View 绑定。**已见释放链会清理表现行为、必要时取消拖拽，并从容器移除绑定。对象池回收与全部订阅、动画清理是否完成，尚缺部分实现。
4. **玩家撤销售出。**撤销模型保留旧 Entity；UndoSellItemSystem 复制其组件字典到一个新 Entity，查找附近空位，写回位置，去掉 Dead，再加入棋盘。无空位有失败结果。

**身份与位置：**撤销建立新的运行对象，复制原组件中的身份数据；它寻找附近空位，不保证原格恢复。复制字典也不等于把其中所有对象都复制一遍：若组件中引用产物队列等可变对象，新旧实体可能仍指向同一份对象。（[专用撤销](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoardSellItemCapability/033594_UndoSellItemSystem.s:5)、[实体复制构造](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.ECSInstance/033678_Entity.s:86)）

**待验证：**原对象是否还会被计时或旧回调修改，决定这种共享是否有实际风险。旧动画回调会不会误操作已换绑的 View、售出和撤销怎样结算资源、撤销记录何时失效、如何防止重复撤销、重开后是否还能撤销，也未形成完整证据。删除回调存在，不足以证明它在动画取消时一定执行。

#### 有限使用次数：耗尽后有明确的退出分支

另有 ExpendableComponent，保存 Uses、MaxUses、耗尽产物／变换配置、每次交互是否附带产出、计时器等。这与 TimeCycle 的“寿命累计到上限后停止产出”是两套机制。

ProcessExpendableItem 在符合本次处理条件时将 Uses 减一并写回；降到零或以下时调用 RemoveEntity，记录 ExpendableItemRemovedResult 和 ItemExpiredResult，再走公共退出与表现流程。对被判定为生成类的实体，它还要求本轮存在以该实体为来源的新生物品，不能仅因尝试了交互就减使用次数。其它实体要求本轮有 PendingInteraction，处理时会将交互标为 Used。已有计时器且次数已耗尽的分支会提前返回，不能忽略这个前提。（[有限次数与退出](/Users/betta/Company/Projects/MergeTwo/参考项目/TravelTown_2.12.1751_APKPure_arm64/native_arm64/TravelTown.MergeBoard/025730_ExpendableSystem.s:288)）

Uses 仍大于零且配置 SpawnOnEachInteraction 时，还会进入附加产出服务。**待验证：**配置中的变身、原地替换、耗尽奖励如何完整衔接、怎样恢复，以及它与 TimeCycle 寿命限制是否组合；字段和服务入口存在不能证明每一种终结方式已经贯通。

## 4. 失败、连续输入和动画中断分别怎样看

这套实现有拒绝分支和阶段标记，但没有证据证明所有异常都能恢复到操作前。尤其要区分“检查时拒绝”和“写到一半失败”。

| 情况 | 已见机制 | 仍然不能据此承诺什么 |
| --- | --- | --- |
| 无空位或付不起费用 | 找空位失败、支付资格拒绝、交互成功标志 | 同一交互带多项能力时，也完全不会扣错或多生成 |
| 快速连续点击 | 控制器同步执行每轮规则，View 有选择和双击入口 | 所有输入都进入一个先进先出的队列 |
| 结果处理器又发起新操作 | 执行结束后可调用扩展处理器 | 上层一定会阻止嵌套执行；本体未见完整重入排队协议 |
| 某个系统中途异常 | 多步直接修改组件和集合 | 已生效的步骤一定自动撤销 |
| 动画取消或资源失败 | 核心数据已修改，有局部释放入口 | 所有残留画面和输入状态一定能恢复正确 |
| 关闭后旧回调才到达 | 闭包仍可持有待删除对象和 View | 回调一定会检查当前绑定是不是旧的那一件 |
| 一个变化触发其它功能 | 系统列表、临时标记和结果列表支持协作 | 已有统一防重复、终止连锁或循环次数上限 |

这些是证据边界和需要验证的条件，不是已发现的游戏故障。
