## 1. 先看三处真正影响设计的差异

### 1.1 行为怎样组织：物品 Function 与共享 System

你的设计让 Entity 管理业务身份、数据和逻辑能力，并讨论用逻辑 Function 组织行为。Travel Town 新路径则把物品的数据放在组件里，把行为集中到共享 System：每件生成器有自己的次数和队列，处理生成的规则由系统共用。

对照一次点击就能看出差别：参考项目的交互资格、创建产物、扣费、周期推进分别在不同系统里。因此，“一个逻辑 Function 对应一个 System”并不成立；一项功能可能横跨几个系统。

**本报告建议：**先借鉴“每件物品保存自己的状态，规则职责明确”的划分，再决定是否需要 ECS 框架。如果首期只有少量能力，专用处理模块也能表达这些职责；采用 ECS 会额外带来系统顺序、组件查询、保存和表现装配的管理成本。

### 1.2 数据何时生效：统一 Apply 与系统直接写入

**ECS 和 Command／Operation 并不是二选一。**ECS 规定数据和规则怎样组织；Command／Operation 规定请求怎样求解、修改何时生效。你的原架构允许内部使用 ECS，也允许 Function 委托共享规则模块。真正需要比较的是这里两种具体写入方式：

| 参考项目已确认的新路径 | 你的原架构执行契约，拟用于新二合 |
| --- | --- |
| 输入交给系统 → 系统直接改数据 → 记录已发生的结果 → 表现消费结果 | Command 表达意图 → Consumer 收集 Operation → Batch 同步 Apply → 再分发表现 |

参考项目的结果是“事情已经做完的记录”。你的 Operation 持有准备好的数据，在 Apply 内执行修改。它们都可以告诉表现层要显示什么，但产生和生效的时点不同。参考项目网络追踪中的 Operation 只是通知载荷，也不能当作你方案中的本地提交操作。

**本报告建议：**是否保留统一提交层，要看它是否确实帮助你把位置、费用、次数和随机进度一起检查、一起生效。不要仅因参考项目较直接就删除这层，也不要认为名字叫 AtomicOperation 或 Batch 就已经具备失败回滚。两边都需要明确中途失败怎么办。

### 1.3 能力、进度、阶段与附加限制怎样分工

参考项目的生成能力、剩余次数、周期阶段、箱子和普通锁各有位置。这可以用一个具体问题理解：**解开生成器的箱子后，要保留什么？**应保留它的生成能力、当前次数、周期进度，以及任何仍然存在的其它限制。拆箱方法只修改箱子数据，就表达了这种区别。

**本报告建议：**先把这些业务语义分清，再决定是否使用 Function、State 或 Effect 包装。该项目没有给出“所有状态都改成 Effect”的证据；同类型组件只有一个槽，也没有自动解决同类限制的多来源、层数和分别到期。

比较范围仍按你当前计划：先做独立核心棋盘，使用宿主 Profile，先完成本地规则和保存，首期只做售出／删除专用撤销，不做订单。以下建议不扩展这个范围。（[已确认范围](/Users/betta/Company/Projects/MergeTwo/_Plan/09_决策与接续记录.md:7)）

## 2. 与你的概念逐项对应

| 你的概念 | 参考项目的近似对应 | 应怎样理解这个对应 |
| --- | --- | --- |
| Entity | 运行实体与身份、位置、能力组件 | 都承载物品数据；参考实体主要是组件容器，行为在共享系统。 |
| EntityView | 物品 View 及实体到 View 的绑定容器 | 都负责显示和局部生命周期；参考项目用 Entity 对象引用做绑定键，未确认绑定版本防护。 |
| 逻辑 Function | 系统、组件查询、规则工具和验证器共同承担 | 是一对多或多对多关系；例如生成横跨交互、生成、费用和周期系统。 |
| 表现 Function | View 内可组合的表现行为，以及动画、覆盖物处理 | 表现可独立组合；不要求与业务组件一一对应。部分实现被裁剪。 |
| Command | 移动、点击、初始化和时间输入 | 都表达意图；参考控制器直接执行一轮规则，外层是否排队待验证。 |
| CommandConsumer | 响应输入的多个共享系统 | 都可能共同处理操作；参考系统直接写数据，不是先统一收集只读求解结果。 |
| AtomicOperation／Batch | 尚无已证实的等价本地提交层 | 执行结果是事后记录，网络操作是发送载荷，不能硬作对应。 |
| Effect | 箱子、普通锁、时间锁阻挡等，在部分语义上相近 | 可以暂时限制仍然存在的能力；未证实通用效果身份、来源叠加和统一保存机制。 |
| State | 周期阶段、解锁进度、次数和布尔事实 | 既有互斥阶段，也有独立业务数值；并非所有 State 都是一种状态机。 |
| Profile／保存 | 保存记录、状态恢复器，以及旧路径保存系统 | 都需要配置与进度分开；参考新路径到本地保存的完整连接仍缺证据。 |
| 专用撤销 | 售出撤销模块 | 都可限定业务范围；参考实现复制旧组件并找附近空位，不保证回原格；经济补偿和旧回调隔离仍待验证。 |

表中“对应”是分析映射，不表示两边接口、时序或保证相同。

## 3. 哪些思想可以直接借鉴

“直接借鉴”指采用一个清楚的设计原则，不是复制整套逆向代码。下面列出各自解决的问题和最小采用成本。

| 借鉴点与解决的问题 | 对你的最小用法与代价 |
| --- | --- |
| 把物品种类、实例身份、位置和运行对象分开，避免移动或恢复时认错物品 | 先把四者写进数据契约；索引和 View 绑定必须说明用哪一种身份 |
| 格子保持轻量、物品独立保存，不因每格有画面对象就建立完整格子实体 | 普通棋盘可使用格子编号和占位查询；若地格真有独立进度，再增加 CellData |
| 能力与限制分开，使暂停操作时不丢失能力和进度 | 用限制控制能否生成，不用删除生成 Function 来模拟封锁；仍需处理多来源限制 |
| 按操作区分权限，避免“不能拖动”被误解为“什么都不能做” | 明确能否拖动、作合成目标、生成和售出；需要覆盖源、目标和换位的组合验证 |
| 用明确结果通知表现，使逻辑成功与动画结束分开 | 结果应带足实例、起点和终点信息；若只带可变 Entity 引用，延迟播放可能读到后续状态 |
| 保存生成进度，使重开后从正确的位置继续 | 不只存种类，也存必要的次数、随机队列和时间进度；代价是配置版本及离线补时测试 |

这些思想不要求你先把现有设计改造成完整 ECS。

## 4. 哪些需要条件或改造，哪些不适合照搬

### 4.1 有对应需求时再采用

| 参考做法 → 解决的问题 | 采用条件和改造成本 |
| --- | --- |
| 组件组合与共享系统 → 多种物品共用规则，减少物品子类 | 能力数量和组合需求值得承担调度成本时采用；必须明确系统顺序、临时标记、保存和表现入口 |
| 自由几何布局 → 不规则棋盘也能找邻格和落点 | 你若需要自由布局，应把坐标、邻接和等距选择转成纯数据；表现只读取布局，需验证缩放和重排后的规则稳定性 |
| 同一结果交给多个处理者 → 界面和其它模块响应同一次变化 | 可先接 Graphic 与 Profile；内存更新、表现分发、磁盘保存是否成功应分别记录，不必提前增加网络系统 |
| 售出专用撤销 → 用较小范围支持恢复 | 明确是否必须原格、没空位怎么办、货币如何退回、有效期和实例身份；组件复制策略也要明确 |
| 载入时间修正 → 重开时补上经过的时间 | 要能说清“已计算到哪个时刻”；先验证不重复补时，再决定是否需要载入与计时器两处修正 |

以上结构存在有静态证据；能否适合你的项目是本报告的条件性建议。

### 4.2 对你的独立核心目标，不建议沿用

**让规则读取可变化的界面坐标。**原实现找最近格会用 RectTransform；在有画面的游戏内这样做可能方便，但与你要求无画面运行的核心冲突。建议将规则坐标作为数据提供。依赖已确认，是否曾导致真实错误未证实。

**复制旧棋盘系统的整套界面依赖。**旧 BoardSystem 同时依赖界面、动画参数及宿主服务，直接搬入会把外围一并带入。它可以是原产品的历史选择；你这里只需提取有用规则。结构已确认，维护成本是静态判断。

**把浅复制当作完整撤销快照。**新建一个组件字典，只是重新放入同一批值；其中引用的队列可能仍共享。如果旧对象完全不再修改，可能可控；如果还会收到计时或回调，就必须验证。你的撤销可考虑专用记录，明确哪些数据复制、哪些重建。复制方式已确认，实际串扰仍待验证。

**把成功标记当作事务保证。**Used 和 Dead 有明确用途，但它们不证明创建、扣费、随机推进中途失败后能全部撤销。你若保留统一 Apply，仍要设计失败前检查、故障隔离或从可信状态重建的出口。原项目的异常策略缺证据，不能据此判定有故障。

**用一个 IsLocked 决定所有操作。**这是从参考项目的权限差异得到的建议，**不是说它犯了这个错误**。拖动、合成源、合成目标、点击和售出需要各自的语义，可以共享底层锁数据，但不宜共用一个未经区分的总开关。

## 5. 用三个假设检验：加一种玩法，到底要改哪里

以下都是**假设推演，不是该游戏已有功能**，也不增加你的首期需求。目的在于把“组件方便扩展”具体化为修改范围。

### 5.1 生成器暂时被冻结，但仍能移动

先约定冻结只禁止实际产出。冷却是否继续，是另一条产品规则，不能由“冻结组件”这个名称替你决定。

| 要改的地方 | 为什么需要改、能复用什么 |
| --- | --- |
| 配置和物品数据 | 增加冻结的来源、期限等事实；不能直接使用会阻止移动的普通移动锁 |
| 工厂与规则注册 | 让工厂添加数据，增加处理到期的系统；明确解冻与自动生成谁先执行 |
| 所有生成入口 | 点击生成、Producer 就绪分支、Spawner 点击及定时分支都要检查；只挡点击会漏掉其它入口 |
| 时间规则 | 冷却继续时只阻止创建；冷却暂停时还要修改周期推进，不能通过删掉周期数据丢弃进度 |
| 保存与恢复 | 保存期限和来源，规定载入与离线计算顺序；两次冻结不能因一次解除而全部消失 |
| 表现 | 添加冻结显示和解除结果，只移除冻结，不影响箱子、普通锁或时间锁 |

可复用组件容器、工厂、系统注册、结果与 View 机制；但最终系统顺序和部分表现入口仍缺证据。**推演评价：**至少跨越上述六处，不能概括成“加一个 Component 就完成”。

### 5.2 地格有固定的锁，格内物品还有随身气泡

这一次有两份独立状态：地格锁留在原位置，气泡跟着物品。新路径已见的 Box／Lock 属于物品，不能直接拿来表示“物品移走后仍锁着的地格”。

需要给格子编号增加地格状态及保存记录，不必因此把每格变成完整 Entity。移动、换位、合成和生成落点都要同时查询地格与物品的限制；空位搜索也必须区分“没有物品”和“可以放置”。画面上，地格锁由 CellView 管，气泡由 ItemView 管，分别解除和清理。

**推演中的缺口：**新路径完整气泡链未找到，旧字段不足以证明付费解除、到期替换和保存都可复用。气泡到期后能否在锁格留下物品、合成后是否继承限制，也需要新增规则及相应工厂、期限处理、恢复和表现入口。

### 5.3 物品被消耗时，对邻格触发一次效果

先明确“消耗”指什么：是合成消耗、交互消耗，还是连售出也算？Dead 只表示物品将退出，不能直接代表所有消耗原因。

这项能力可参考现有拆箱中的消费触发、邻格查询和临时标记。新规则需要在旧物清理前保存消耗原因、原位置和实例身份，再由响应系统查询邻物、修改邻物数据并生成表现结果。工厂和配置需要能给物品添加这项能力，系统注册也必须保证所需数据尚未被清理。

如果效果又消耗邻物，就产生连锁。必须决定只响应最初一批，还是继续扩散；若继续，要规定去重和次数上限。现有临时标记可以辅助实现，不能证明已经有通用的连锁终止机制。

临时触发信息可以只活在本轮，但邻物被改变后的状态需要保存。表现结果应携带原位置，不能等源物退场动画结束才触发业务，否则取消动画会改变规则。需要补结果处理和保存连接；新棋盘完整保存入口未定位，是推演中的实际缺口。

## 6. 暂不能判断的部分与最小验证

“最小验证”是后续建议，均未执行。首先需要明确系统顺序，并提供可控配置、纯数据布局、替代钱包、固定时钟与队列状态。优先级表示对方案判断的影响，不是原游戏故障严重级别；服务端权威和纠正策略因缺服务端资料仍无法判断。

| 编号／优先级 | 问题与现有依据 | 最小补证／验收方式 |
| --- | --- | --- |
| Q01／高 | 哪套实现对应实际棋盘？ | 补安装器／实例化调用链及配置选择；记录同版本棋盘实例真实类型 |
| Q02／高 | Move、Lock、Merge、Swap、Cost、Kill 顺序及系统装饰器（包装系统执行的代码）如何影响结果？ | 补齐最终系统类型与顺序、移动阻挡／Dead 的查询过滤，并检查装饰器是否改变调用条件 |
| Q03／高 | 新棋盘一次变化何时被保存？ | 补保存数据转换器、PostTick 保存处理器、生命周期保存入口；区分内存发布、写 API 返回、真正持久化 |
| Q04／高 | 删除→撤销→池复用，旧动画回调能否误删新绑定？ | 补动画调度／池实现；延迟旧回调，恢复并换绑后再释放回调，检查新实例仍有效 |
| Q05／高 | 锁定物可作同种目标的完整规则是什么？ | 分别测试 Locked、Boxed、FixedPosition 及其组合，覆盖源／目标／不匹配交换；输入与模型两层都测 |
| Q06／高 | 单一生成分支满盘会提前返回；多能力组合是否仍零扣费、零随机推进？ | 固定 seed/index、钱包和容量；满盘点击前后逐字段比较；再验证一空位及 Produce／Spawn 同时启用，核对共享周期与同一交互的消费 |
| Q07／高 | 定时分支每物每轮最多一件；补额度、满盘积压、暂停和重开组合后怎样表现？ | 相同起点对比大 interval/小 interval、载入一次/两次、满盘后逐格腾空、只暂停控制器／同时停计时器；比较额度、队列、时间戳与产物 |
| Q08／中 | 已确认喂料设置就绪、生产成功清除；同轮触发、满盘重试和恢复是否正确？ | 补喂料→Producer 顺序与其余就绪写入者；测试凑齐组合、满盘后腾空、生成失败和关闭重开 |
| Q09／中 | 规则修改到一半失败时，如何恢复？ | 在工厂创建、AddEntity、减次数、ConsumeResource 处注入失败；查宿主重建／补偿而非假定回滚 |
| Q10／中 | 浅复制撤销数据在旧对象仍被引用时是否安全？ | 列出队列、能力数据和临时组件中共享的对象；售出后让计时／旧回调到达，再撤销，检查状态与经济 |
| Q11／中 | 资源缺失、隐藏、关闭时 View 是否正确释放并重新同步？ | 补 VisualAdapter、动画 View、blocker loader、池 Deactivate；取消不同阶段并重开，检查重复 View／监听 |
| Q12／中 | 逻辑落点会不会随表现 Transform 改变？ | 保持业务状态不变，改变缩放／重排／加载状态后查询最近格与邻格；决定纯数据布局的稳定规则 |
| Q13／中 | 未知配置、缺失字段、旧存档及耗尽物品的记录怎样恢复？ | 补序列化与版本迁移入口；最小样本含未知 item id、缺实例编号、旧周期字段、已耗尽 Expendable，确认拒绝／修复／退出策略 |
| Q14／低 | 组件扫描与临时分配是否值得优化？ | 在可运行同版本工程测典型棋盘规模、一次点击和一次长时间推进的分配／耗时；无数据前不建复杂索引 |
