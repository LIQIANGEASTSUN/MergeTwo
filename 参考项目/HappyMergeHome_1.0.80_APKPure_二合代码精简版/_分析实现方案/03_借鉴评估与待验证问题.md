# 03　Happy Merge Home：借鉴评估与待验证问题

版本：1.0.80（目录标识）｜复核日期：2026-09-26｜静态分析，未运行游戏。

这个项目说明：小棋盘可以采用简单的数据结构，但数据迁移、组合限制和延后回调仍需要明确规则。值得借鉴的主要是具体处理办法，而不是把现有执行链整体搬进独立核心。

比较以我们的当前范围为准：先验证独立核心棋盘，沿用宿主 Profile，本地规则与保存先行，首期只做出售／删除专用撤销，不做订单。依据是现有 _Plan 中的架构、Function／Effect、状态与 Profile 讨论及决策记录；Command 执行方案和 Function＋Effect 组合仍属于候选建议，不是本报告新增的决策。

## 1. 可以直接借鉴的思想

**格子先承担位置与占位。** 一维列表和少量运行信息足以表达小矩形棋盘。首期若仍是一格一物，可以保留轻量 Cell；出现独立地形或多格物品后再扩充，不必提前给每格建立完整实体生命周期。

**种类、位置和具体实例分开。** 同种物品共用配置，位置随移动改变。我们还需明确定义实例身份和 View 绑定身份，使旧回调不能只凭位置操作后来出现的物品。参考包的 UniqueId 使用协议未恢复，不能直接充当现成方案。

**冷却恢复、自动生产与开启等待分别处理。** 三者分别改变可用次数、产物或等待阶段。即使共用时钟，也应让保存的数据和到期结果各自清楚，避免用一个倒计时隐含所有行为。

**预先定义放不下的产物如何处理。** 参考实现保存已经选定的产物，并用配置限制缓存量。若我们需要自动生产，可以采用这种明确积压规则的思想；落点范围、缓存量、离线库存与缓存的关系仍须按自己的玩法决定。

**解除限制有明确的业务生效点。** 箱罩先改 State，再播放解除动画，使规则结果不必等待演出。动画期间是否接受新输入则独立定义，不能让显示资源是否存在决定解锁是否成功。

**撤销只覆盖确有需求的操作。** 专门保存出售恢复信息符合我们的首期范围。最低要求仍包括完整恢复字段、身份、原位置被占用时的去向及经济对账；参考实现只能提供场景，不能替我们保证快照完整。

## 2. 需要条件或改造后借鉴

**配置决定能力。** 适合能力种类少、变化稳定的棋盘。新增独立触发、持续数据或组合限制后，公共配置和大分支的修改面会扩大，再判断哪些行为值得拆成逻辑 Function。Unity 的显示组件不能直接作为领域能力模块。

**依次尝试拖放处理器。** 可以组织特殊道具与默认操作，但应显式登记优先级，并区分“未处理、拒绝、完成”。参考代码的布尔值不足以表达统一成功结果，完整注册顺序也未恢复。

**用参考时间重算到期。** 适合重开恢复，可减少反复保存倒计时；前提是时钟回拨、库存上限、配置变更和暂停语义明确。参考实现虽有 PauseCd / ResumeCd，各类计时的读取方式却不同，不能直接照搬为通用冻结。若我们采用只读求解，还要把查询中的到期修改移到明确入口。

**复用显示对象。** 对象池能减少重复创建，但需要一并定义动画取消、事件解绑与旧回调失效。可以试验“绑定代次”：每次重新绑定递增版本，回调执行前确认版本仍匹配。这是我方保护方案，不是参考项目已证实具备的能力。

**在容器间移动完整记录。** 可以保留原物品的次数和时间，减少逐字段复制。参考入库先加背包再清棋盘，取出再恢复计时；采用时需保证容量、落点、暂停和失败恢复共同成立，不能只复制其中一个追加方法。

**保留少量明确扩展入口。** 活动子类覆写方法比全部改基类容易定位，但参考基类仍有活动分支。可学习有限扩展点，不必为首期引入活动体系，也不能认为用了继承就已经隔离依赖。

对于 63 格、规则稳定的场景，直接函数和轻量数据仍是合理候选；当前没有性能实测，不能由此保证更大规模适用，也没有必要仅为模仿架构增加全量能力树。

## 3. 不建议原样沿用的做法

**让显示回调决定业务变化。** 气泡回调替换物品，部分动画回调修改可保存字段，会把界面关闭、取消和复用纳入业务正确性的条件。独立核心更适合由逻辑入口确定变化；确需等待表现确认的少数业务，应单独规定协议。

**让查询悄悄改数据。** 次数查询恢复冷却，时间查询补库存或修正时标，在直接调用中可能方便，却不适合作为只读 Consumer。应显式更新到期状态，或把这些变化列入本次待执行结果，区别于失败输入造成的非法写入。

**多步修改中夹杂通知。** 清来源、改目标、改邻格分步发生，若监听者立即发起新操作，就可能观察到中间状态。参考材料尚未证明实际发生重入；对我们而言，完整校验和对外通知的时点应明确。Batch 可以组织顺序，AtomicOperation 的名称并不提供自动回滚。

**用一个状态值承载越来越多独立限制。** 单 State 适合互斥阶段，但不自然表达地格锁、物品气泡和临时禁止生产同时存在。必要的业务 State 应保留，只有真正独立、可叠加的限制才考虑 Effect；不能反过来要求所有状态都变成效果。

**把商业活动分支带进首期核心。** 参考游戏的基础棋盘、管理器和 View 都有活动依赖，修改一个行为可能触及多个位置。这是其产品范围带来的维护成本；我们的首期无需提前承担。

**靠多处手工补齐撤销字段。** 字段少时可控，生成器和附加状态增加后容易遗漏。专用撤销应定义恢复哪些业务事实、哪些身份，以及哪些时间继续流逝，不把全部显示临时状态一并复制。

这些评价针对适用性与维护成本。反编译异常、缺失函数和未恢复的安全措施，本身都不能算作原游戏已发生的 Bug。

## 4. 与我们的设计概念逐项比较

| 我方概念 | 参考项目最近的对应 | 需要区别的地方 |
| --- | --- | --- |
| Entity：业务物品 | StorageMergeItem，加 Manager 与 Board 中的规则 | 数据和行为由多个对象承担，没有已证实的统一实例生命周期 |
| EntityView：显示绑定 | MergeBoardItem，配合 Grid 与 MergeBoard | View 持有可写记录，部分回调参与业务，职责超出资源绑定 |
| 逻辑 Function：组织行为 | 配置判断、Manager 方法、Procedure、活动 Model | 未证实每物品能力的独立装配／移除／恢复；Procedure 主要分派交互 |
| 表现 Function：组织显示行为 | View 内的 Refresh、Play、协程和动画序列 | 多种表现集中于 View，未见独立注册体系；两侧 Function 本就不要求一一对应 |
| Command：表达操作意图 | Pointer 事件、ProcedureHandle 最接近输入入口 | 已查路径直接调用并修改，未证实 Command 对象及 FIFO 消费协议 |
| Consumer：计算变化 | Procedure 和 Manager 的判断与执行片段 | 查询和写入混合，不能直接作为只读收集器 |
| AtomicOperation / Batch：应用变化 | SetBoardItem、RemoveBoardItem 等局部写动作 | 未找到统一变化列表和完整批次 Apply；我方候选流程是先收集全部、同步 Apply，再分发表现，基础机制同样不自动回滚 |
| Effect / State：附加影响与当前事实 | State、UnlockState、暂停、气泡等附加字段 | 互斥阶段与特殊字段混用；PlayEffect 等纯视觉方法不是业务效果系统 |
| Cell：格子 | 持久化列表槽位＋运行 Grid | 轻量位置记录，Grid 引用物品 View，未证实独立 GUID 或自有 View 生命周期 |
| Profile：保存与恢复 | DragonU3DSDK.Storage 记录和变化通知 | 可保存结构已知，实际写盘及服务端协议未恢复，不能直接等同于宿主 Profile |

“未证实”限于保留类型、方法索引，以及从输入、生产、合成、记录修改到相关回调的已查路径；不代表全包其他模块没有类似机制。

## 5. 三个扩展假设揭示的修改成本

以下是**假设推演，不是该游戏已有功能，也不是新增需求**。

### 自动生成器临时冻结，解除后继续计时

可以复用时间输出配置、参考时间、库存、缓存和 View 刷新。首先要规定“停止积累”还是“继续积累但禁止落物”；单加冰图标无法回答这个问题。

若复用 IsPause / PauseCDTime，必须补齐所有相关时间查询和生产入口的兼容性。当前已找到暂停调用，却未证明时间库存与缓存释放会统一受控；不兼容时应使用独立冻结数据并定义保存方式。

修改面至少包括 RefreshAllProduct、TimeProductItem、OperateItem 的时间分支和 FreeTimeProductItem。停止积累还需修正参考时间或保存冻结起止信息，解除后受库存、缓存上限约束；View 更新覆盖和提示，合成、删除、撤销规定继承或清理方式。

把 State 直接改为 6 会连带改变拖动、合成和扫描权限，而且未必阻止点击时间分支，不能只表示“冻结自动生产”。最小验证应覆盖扫描、点击、附近无空位、重开和撤销。

### 地格有锁，格内物品同时带气泡

可复用 boardId＋index、物品列表和气泡显示，但必须在 StorageMergeBoard 或等价轻量 Cell 数据中增加按坐标保存的地格事实，初始化和版本迁移都要补默认值。

IsGridUnlock、拖放处理器和两种找位方法都要读取地格锁；交换或入库移动物品时，地格信息必须留在原坐标。RefreshGrid 分别更新地格覆盖和物品气泡，不能轮流覆盖同一个 State。

现有找位方法对 State=10 的过滤不同，新增地格层时应统一放置条件。解除地格锁也只能解除其自身限制，泡泡仍然存在。这个需求可能需要独立格子数据，但不自动要求完整 Cell Entity。

### 消耗物品时，对十字方向邻格产生影响

可复用十字遍历和合成、删除入口，但要先定义“消耗”是否包含出售、有限生成器耗尽及气泡替换。应在这些业务入口收集影响，不能笼统挂到既用于创建又用于替换的 SetBoardItem。

配置需要触发参数，存档仅保存必须跨次保留的次数或阶段，View 播放邻格效果。若出售撤销也恢复邻格副作用，专用快照范围就要扩大。

现有邻箱连锁依靠状态改变终止，不是通用连锁协议。订阅改物事件后再改物，可能递归触发同类事件；新增可循环规则时，需要本次去重、触发次数约束或无环配置，并明确超限如何处理。

## 6. 尚不能判断的部分与最小验证方式

以下补证目标按对方案取舍的影响排序，不代表线上缺陷的严重程度。

| 优先级与问题 | 最小补证或验证 | 会影响什么判断 |
| --- | --- | --- |
| 优先：费用与产物是否共同完成 | 补齐 OperateItem 的费用调用，验证资源不足、无空位、目标失效及 ProductOneItem 中途失败 | 能否借鉴其经济一致性处理 |
| 优先：通知能否插入新操作 | 确认 SetBoardItem 事件分发方式、监听顺序；观察清来源后、写目标前的棋盘 | 是否需要额外防重入和统一完成点 |
| 优先：旧回调是否失效 | 启动回调后移动／删除物品，再关闭界面或复用 View；核对动画取消是否仍触发回调 | View 复用和业务身份保护 |
| 优先：何时真正写盘 | 补齐存储服务与序列化入口，取得保存、关闭重开及失败样本 | Profile 接入与恢复可靠性 |
| 随后：拖放权限与动画门禁 | 确认处理器注册顺序；分别试验网锁作来源／目标、道具解网、破罩中输入和受限生成器点击 | 分散检查的最终规则 |
| 随后：交换与边缘找位 | 核对缺失的函数边界或原指令；试验物品互换、空格交换、边角搜索与 3×3 多空位 | 两侧占位、真实选位顺序和 State=10 处理 |
| 随后：撤销恢复完整性 | 普通物品、计时生成器和附加状态分别出售后撤销，再占用原位置；检查字段、身份、金币、重复点击和关闭后的凭据 | 专用快照需要覆盖多少数据 |
| 随后：暂停与离线结算 | 补一份相关配置，比较入库前后、后台、关闭重开；检查时钟倒退、暂停时的库存及缓存上限 | 补库存、冻结时间与补产物能否区分 |
| 随后：容器迁移完整性 | 追踪取出目标的选择；试验目标被占、背包满和迁移中途失败 | 记录是否可能同时占两处或丢失 |
| 按需：资源与未知配置 | 补一个 Prefab、灰色材质及资源失败路径；核对 RefreshGrid 缺配置删除的调用环境 | 透明度、锚点、命中与迁移容错 |
| 按需：随机和外部服务 | 补产出选择函数、随机状态保存及相关服务协议 | 能否重现产出，以及客户端与服务器的职责 |

部分问题需要补充未保留的配置、原生指令或可运行样本，当前伪代码无法单独给出答案。
