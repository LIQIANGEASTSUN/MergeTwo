# 01　Happy Merge Home：架构与数据模型

版本：1.0.80（目录标识）｜复核日期：2026-09-26｜静态分析，未运行游戏。

## 分析范围与结论边界

本项目把物品记录、格子位置和显示对象分开存放，但规则仍分散在管理器、棋盘界面和显示回调中。它采用轻量数据结构承载多种玩法，主要靠配置与处理分支扩展；目前不能把它视为已经与 Unity 界面隔离的逻辑核心。

本次覆盖主棋盘的创建、坐标与找位、拖放合成、手动与时间生产、箱体和网锁解除、气泡、入库取出、回收及出售撤销。活动仅用于确认核心依赖，未逐个审计。

材料是从安装包恢复的结构稿和原生伪代码，包含 342 份 C# 结构文件、840 份类型块、10788 条方法索引及 10754 份伪代码。C# 空方法不能证明原游戏没有行为；部分伪代码存在截断、类型失真或函数边界异常。当前索引中的截断方法为 227 个，历史提取说明写过 277 个，差异原因未确认。配置值、完整资源、部分外部服务和原始指令未保留，版本也未由原包元数据独立核实。

文中按以下含义区分结论：

- **已确认（静态证据）**：类型字段、可读分支或调用顺序能够相互核对。
- **较强推断**：已有直接线索，但缺少配置、调用关系或运行验证。
- **待验证**：当前材料不足以判断；不把它写成游戏缺陷。

不少方法有热更新分支。本报告还原的是保留的普通原生路径，不能代表所有线上热更新行为。“未找到”限于保留类型、方法索引及本次追踪路径；它不是对全游戏的否定。

## 1. 数据、位置和画面由谁负责

屏幕上的一件物品，对应三类信息：**它是什么、它在哪里、它怎样显示**。下表中的字段与类型关系均为已确认（静态证据）。

| 负责什么 | 实际类型与主要字段 | 归属与用途 |
| --- | --- | --- |
| 多个棋盘 | StorageGame.MergeBoards | 按棋盘编号保存 StorageMergeBoard |
| 棋盘与容器 | StorageMergeBoard：width、height、items、bags、rewards | 保存尺寸，以及棋盘、背包和奖励队列中的物品；部分棋盘另有冰相关列表 |
| 物品业务记录 | StorageMergeItem：Id、State、UnlockState、次数、时间、ProductItems、UniqueId 等 | 同一种记录承载普通物品、生成器和受限物品 |
| 格子运行信息 | MergeBoard.Grid：xIndex、yIndex、index、id、state、cd、isAnim、board | 位置与显示缓存；其中 board 引用格内物品的显示对象 |
| 种类与合成链 | TableMergeItem：id、type、in_line、level、next_level | id 识别物品种类，in_line 识别合成链，next_level 指定普通合成结果 |
| 棋盘交互与执行 | MergeBoard：Rect、gridSize、Grid[]、拖动索引、动画集合、处理器列表 | 接收输入，执行部分规则，组织显示和动画 |
| 共用业务方法 | MergeManager | 查询、改写记录，处理生产、时间和容器操作 |
| 物品显示对象 | MergeBoardItem：_id、_state、_index、storageMergeItem、tableMergeItem、覆盖资源、Animator | 显示图标、箱罩、网、泡泡和动画；也持有可写业务记录 |
| 出售恢复信息 | MergeClickTips：sellItem、selectedGridIndex、sellColdTime | 界面对象暂存待恢复记录、原位置和出售时间；未证实为持久化撤销栈 |

**较强推断**：已追踪流程主要以 StorageMergeItem 为业务依据。GetBoardItem 从存储列表取记录，OnRefresh 也重读记录再更新格子和画面，因此 Grid 和 View 中重复保存的种类、状态、位置更像运行副本。这里不包含钱包或服务器的最终权威判断。

显示与业务并未彻底分离：MergeBoard 直接执行合成与生产，MergeManager 部分方法访问界面和活动，气泡回调会替换物品，RefreshGrid 的缺配置分支还会删除物品。将它改造成独立核心，需要调整写入入口，不能只搬走数据类。

## 2. 棋盘是一张按位置排列的物品列表

**已确认（静态证据）**：Items 的第几个元素就是第几个棋盘位置。空位也保存一条 StorageMergeItem，只是 Id=-1。已查主棋盘没有另一套独立 Cell 存档；运行 Grid 也未见独立实例编号或完整业务生命周期。

因此，这里的格子可以理解为“位置和占位”，物品数据则随记录存在于棋盘或容器中。箱体、网和气泡在主路径中主要记在物品上，不是固定于坐标的独立地形。限制随记录保存，不代表带限制的物品都允许移动或入库。

新建棋盘的一个明确分支是 7 列、9 行：先填空记录，再按初始格配置写入物品种类和状态。已有棋盘读取保存的宽高；不能把所有活动盘都推定为 7×9。实际初始配置值未保留。

位置从 0 编号，按行递增，横向向右、纵向向上：

~~~text
index = y × width + x

3 列、2 行的说明示例（不是本包真实布局）：
y=1    3 | 4 | 5
y=0    0 | 1 | 2
       x=0  1   2
~~~

Id=-1 只表示没有物品，格子本身仍存在。超出有效范围的位置在输入换算中返回 -1；State=10 又被部分找位和操作分支特殊处理，不能与普通空位混为一谈。IsOutOffBoard 会按棋盘编号查询活动范围，但不足以证明通用的空洞、稀疏地形或临时占位模型。已查结构也未显示通用多格物品、同格多层内容的占位协议。

## 3. 种类、位置和实例身份不能混用

两个相同物品可以拥有同一个种类编号，却占据不同位置。交换之后位置改变，种类不变；合成后种类改变，承载记录的内存对象却可能不变。

项目中有四种不同信息：

- **种类编号 Id**：对应 TableMergeItem.id，不是每件物品唯一的编号。
- **位置 boardId＋index**：多数棋盘读写使用的定位方式。
- **对象引用**：记录和显示对象各有引用，都可能复用。
- **UniqueId 字段**：确实存在，但尚未恢复出创建、合成、撤销、换绑共用的身份规则。全文检索只找到其访问器定义，不能排除直接字段访问、内联、反射或热更新使用。

以下记录处理方式已确认：

| 操作 | 实际处理 |
| --- | --- |
| SetNewBoardItem | 可以复用原位置记录，改种类、状态并重置生产数据；New 不保证创建新实例身份 |
| 按种类调用 SetBoardItem | 可以原地改写记录 |
| 传入整条记录的 SetBoardItem | 可以替换列表中的记录引用 |
| RemoveBoardItem(out) | 交出旧记录，用 Id=-1、State=1 的空记录替换占位 |
| AddBagItem / UseBgItem | 入包保存原记录引用；取出把记录移回棋盘，另处理计时恢复 |

重置也不只是“所有字段清零”。ResetStorageMergeBoardStatus 会清生产计数、缓存、若干时标、库存、暂停标记、轮次、折扣及部分附加字典；配置有 original_count 时，又会按“输出量－初始量”设置已用次数。没有证据证明它重建了全部附加状态或重新分配 UniqueId。

这意味着合成、耗尽替换、入库和撤销各自需要明确数据迁移规则，不能由方法名或对象引用自动推定。

## 4. 能力、当前阶段和外观如何关联

**已确认（静态证据）**：配置规定物品能生产什么、冷却多久、下一等级是什么；记录保存已经使用的次数、可用库存、时间及限制。能力可以仍在配置中，当前状态却不允许某种操作。

主路径采用“同一种记录＋配置判断＋执行分支”，并非每种物品各有一个领域子类。限制主要使用单个 State 整数，再配合 UnlockState、气泡参数、暂停和强化等字段；显示组件数量多，也不能据此称为 ECS 或可自由装配的能力系统。

| 数据值 | 已确认含义 | 适用界限 |
| --- | --- | --- |
| State=0 | IsLockWeb 识别的网锁 | 保存在物品记录，不等于独立地格锁 |
| State=-1 | 箱体遮挡状态之一 | 不等于配置 type=2 的箱子物品 |
| State=1、3 | IsOpen / IsUnlock 接受的开放、计时阶段 | 状态 3 本身不证明会自动生产 |
| State=2、6 | 枚举对应气泡、冰块 | 单值阶段，不是可直接相加的限制标志 |
| State=4、5 | 枚举对应 slabstone、mine | 本次未贯通其玩法流程，不能套用普通物品规则 |
| State=10 | IsBox 接受，一般找空位排除，部分操作拒绝 | 命名枚举未列出，具体业务含义待验证 |

一个 State 不能同时等于网锁和气泡。UnlockState 可以保存箱罩解除后的阶段，例如拆罩后仍为网锁；这支持特定的前后阶段，不等于任意限制叠加。

外观由同一批事实派生。普通棋盘的 State=-1 或 0 会选择 ui_grey 材质；View 另有箱、网、气泡等资源。箱罩解除先修改记录，再播放破罩动画。实际透明度、素材层次、输入遮挡与资源加载失败行为仍待验证，不能只凭字段名称补出画面效果。

## 5. 坐标换算与空位搜索

### 从位置编号得到格子中心

IndexToPos 的可读计算为：

~~~text
y = index / width 的整数商
x = index - y × width
gridSize = (Rect.width / width, Rect.height / height)

localX = Rect.x + (x + 0.5) × gridSize.x
localY = Rect.y + (y + 0.5) × gridSize.y
localZ = 0
~~~

InitGrids 从最上行向下创建，但编号规则不变。IndexToPosition 随后调用 Transform 相关函数，**较强推断**用于转为世界位置；具体 API 未恢复。

反向 PosToIndex 在伪代码中以浮点转整数，再检查宽高、z 和活动范围。不能直接改写成负数也向下取整的 floor。实际锚点、缩放、素材内边距和视觉间距未确认。拖动还读取 Transform 实时位置寻找目标，因此输入并非只依赖逻辑坐标。

### 三种搜索服务不同用途

**一般放置：从起点向外扩圈。** FindEmptyGridView 接受的空位条件是 Id=-1 且 State≠10。默认先检查起点；ignoreSelf=true 时先找周围，周围失败后仍可能回退到空的起点。因此该参数不是“绝不使用起点”。

在远离边界的第一圈，首轮候选顺序可还原为北、东北、东、东南、南、西南、西、西北，部分角点会重复检查。伪代码中一些边界条件异常，不能把它概括为所有越界坐标都已正确跳过；边缘结果仍需验证。

**时间自动生产：检查附近 3×3。** GetSudokuEmptIndex 按列再按行检查 Id=-1，本段未见 State=10 过滤。**较强推断**：每列找到首个空位后继续检查后面的列，返回最后一个有空位的列中的首个空位，而非整个区域的第一个空位。依据是循环只结束当前列；尚缺原指令或运行样本交叉确认。

**邻箱解除：检查十字方向。** TryOpenBoxes 遍历横向三格、纵向三格，中心重复，不查对角；满足解锁条件后可以递归向邻箱扩展。

按静态循环估计，单次 3×3 搜索候选数固定，全盘扫描为 O(W×H)，扩圈搜索保守按搜索半径 R 估为 O(R²)。反编译边界尚有疑点，不能保证每格只访问一次，也没有性能实测。棋盘还维护提示候选和动画集合，物品修改会标记计数待更新，完整缓存失效规则未追完。

## 6. 内存记录变化与真正保存

**已确认（静态证据）**：记录字段带 JSON 保存标记，StorageList 声明变化与同步接口，set_State 写字段并增加外部计数。将这个计数理解为变化通知是**较强推断**，存储服务实现没有完整恢复。

因此，“业务生效”仅表示内存状态已经改变。字段可序列化不等于已经写盘，更不证明断电恢复、文件原子性或服务端权威。未知配置和版本迁移也未恢复完整；RefreshGrid 在配置缺失时删除物品的局部分支，需要结合调用环境判断。

规则依赖 Unity 对象、界面位置、全局管理器、钱包和活动模块。客户端本地计算产物的路径可见，但目前没有证据证明核心已经提供可替换的时钟、随机、存储接口或无画面运行测试。
