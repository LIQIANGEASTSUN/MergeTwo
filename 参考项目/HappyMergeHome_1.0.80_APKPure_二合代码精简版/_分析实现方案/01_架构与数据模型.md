# 棋盘、物品和画面之间是什么关系

版本：1.0.80（目录标识）｜分析日期：2026-09-25｜仅静态分析，未运行游戏。

## 先分清“物品的数据”和“物品的画面”

屏幕上看到一个物品，程序里并不只有一个对象。这个项目至少分别保存了**物品是什么、它占哪个位置、它怎样显示**。理解这三件事，比先记住类名更重要。

| 负责什么 | 项目中的名称 | 可以怎样理解 |
| --- | --- | --- |
| 保存物品的种类、状态、次数和时间 | StorageMergeItem | 一件物品的业务记录 |
| 保存棋盘尺寸，以及棋盘、背包、奖励中的物品 | StorageMergeBoard | 棋盘和容器中的物品清单 |
| 记录某格的坐标、当前物品与动画标志 | MergeBoard.Grid | 棋盘界面使用的轻量格子记录 |
| 显示图标、箱体遮挡、泡泡和动画 | MergeBoardItem | 屏幕上那件物品的显示对象，也就是View |
| 接收点击、拖动并执行操作 | MergeBoard | 棋盘交互控制器 |
| 查询或修改记录、计算生产等规则 | MergeManager | 多处共用的业务方法 |

这些类型和字段是**已确认（静态证据）**。全部棋盘又由StorageGame中的字典按棋盘编号组织。（[E02](04_证据索引.md#E02)、[E05](04_证据索引.md#E05)）

问题在于：这几部分虽然分开存放，却没有严格分开职责。棋盘交互控制器直接执行部分规则；显示对象也拿着物品记录，部分回调还能改业务数据。因此它不能原样当成一个脱离Unity界面即可运行的逻辑核心。（[E09](04_证据索引.md#E09)、[E12](04_证据索引.md#E12)、[E27](04_证据索引.md#E27)）

~~~mermaid
flowchart TD
  Config["配置表<br/>规定物品种类、合成结果和产出规则"]
  Record["业务记录<br/>StorageMergeBoard / StorageMergeItem"]
  Manager["共用业务方法<br/>MergeManager"]
  Board["点击、拖动与规则执行<br/>MergeBoard"]
  Grid["格子运行记录<br/>Grid"]
  View["图标、遮挡与动画<br/>MergeBoardItem"]
  Config --> Manager
  Config --> View
  Board --> Manager
  Manager <--> Record
  Board --> Grid --> View
  View -->|"持有引用；部分回调写入"| Record
  Manager -->|"通知刷新；部分直接访问界面"| Board
~~~

图中的箭头表示引用或调用，并不表示一次操作能整体成功、整体回滚。

**较强推断**：在已追踪的核心流程中，业务判断主要以StorageMergeItem为依据。读取物品的方法从存储列表取记录，收到刷新通知时也先重读记录，再更新格子和画面；格子与View里的种类、状态和位置因此更像运行时副本。钱包和服务器的最终权威、实际写盘过程仍待验证。（[E09](04_证据索引.md#E09)、[E11](04_证据索引.md#E11)、[E20](04_证据索引.md#E20)、[E33](04_证据索引.md#E33)）

## 格子有多“重”？物品放在哪里？

**已确认（静态证据）**：棋盘用一张按位置排列的列表保存物品。第几个列表元素，就是第几个棋盘位置。空位也有一条记录，只是物品种类写成-1。已查主棋盘没有单独保存一套完整的Cell实体。（[E02](04_证据索引.md#E02)、[E06](04_证据索引.md#E06)）

运行中的Grid另记坐标、位置编号、动画标志，以及格内物品的显示对象。它没有已证实的独立实例编号或完整业务生命周期。这就是本报告所说的“轻量格子”：先把它理解为**位置和显示缓存**，不必理解成拥有一整套行为的物品。（[E05](04_证据索引.md#E05)）

新建棋盘的一个明确分支是7列、9行。已有棋盘则从存档读尺寸，活动棋盘不能全部按7×9推定。新建时先填空记录，再按初始格配置写入物品种类和状态；配置的实际数值没有保留下来。（[E06](04_证据索引.md#E06)）

位置编号按行递增：

~~~text
index = y × width + x

例如3列、2行（仅作说明，不是本包真实布局）：
y=1    3 | 4 | 5
y=0    0 | 1 | 2
       x=0  1   2
~~~

横向向右、纵向向上。这里指棋盘自身矩形内的坐标，不是屏幕坐标。完整换算和落点搜索见后面的[实现细节](#坐标细节)。（[E07](04_证据索引.md#E07)）

## 两个相同物品，为什么仍要区分身份？

以两件同种物品为例：它们的**种类编号可以相同**，但占据不同位置；交换后，位置变了，种类不变。这个例子说明“是什么”“在哪里”和“是哪一件”是三个不同问题，不是新增游戏规则。

项目中能定位到四种不同的信息：

- **种类编号**：StorageMergeItem.Id对应配置表的id；它不是每件物品唯一的编号。
- **位置**：多数读写使用“棋盘编号＋格子编号”，也就是boardId和index。
- **内存对象**：业务记录和显示对象各自有对象引用，而且都可能被复用。
- **UniqueId字段**：确实存在，但它是否在创建、合成、撤销和显示换绑中形成完整的实例身份规则，尚未证实。（[E02](04_证据索引.md#E02)、[E09](04_证据索引.md#E09)、[E37](04_证据索引.md#E37)）

复用带来一个实际区别：名叫SetNewBoardItem的“放入新物品”方法，可能只是改写原位置上的旧记录，并重置生产字段。另一个SetBoardItem重载则可以替换整条记录。所以不能用“对象引用没变”来断言仍是原来那件业务物品。（[E09](04_证据索引.md#E09)、[E10](04_证据索引.md#E10)）

| 操作入口 | 对记录的处理 |
| --- | --- |
| SetNewBoardItem、按种类编号调用的SetBoardItem | 可以改写已有记录 |
| 传入整条StorageMergeItem的SetBoardItem | 可以替换列表中的记录引用 |
| RemoveBoardItem(out) | 交出旧记录，并用空记录替换棋盘位置 |
| AddBagItem | 把传入的记录引用加入背包；完整摘板和容量校验流程尚未贯通 |

以上处理可由静态代码确认。（[E09](04_证据索引.md#E09)、[E10](04_证据索引.md#E10)、[E30](04_证据索引.md#E30)、[E32](04_证据索引.md#E32)） 合成和交换的先后顺序另见[拖动与合成流程](02_功能扩展与执行流程.md#流程2)。

## “有这个能力”和“现在允许使用”是两回事

物品配置可以规定它会产出什么、冷却多久、下一等级是什么。物品当前记录则保存剩余次数、时间和限制状态。**配置仍让它具备生产能力，当前状态却可能禁止这次生产。** 项目主要通过配置检查和过程分支组合这些条件，而不是为每种物品建立独立的领域子类。（[E03](04_证据索引.md#E03)、[E19](04_证据索引.md#E19)）

限制也没有全部做成独立效果对象。它使用一个State整数表示某些阶段，再配合UnlockState、泡泡参数、时间、暂停和强化等字段。一个State不能同时等于“网锁”和“泡泡”；UnlockState可以记录箱体遮挡解除后的状态，但这不等于已经支持任意多个限制叠加。（[E02](04_证据索引.md#E02)、[E04](04_证据索引.md#E04)、[E25](04_证据索引.md#E25)）

| 数据值 | 可以确认的含义 | 需要保留的界限 |
| --- | --- | --- |
| Id=-1 | 该位置没有物品内容 | 格子本身仍存在 |
| State=0 | 被IsLockWeb识别为网锁 | 主路径保存在物品记录中，不是独立地块锁 |
| State=-1 | 箱体遮挡状态之一 | 不等同于配置type=2的“箱子物品” |
| State=1或3 | IsOpen接受的open/time阶段 | 状态3不自动代表会自动生产 |
| State=2或6 | 泡泡/冰块状态 | 不是可以直接相加组合的位标志 |
| State=10 | 开箱判断接受；一般找空位排除；部分操作拒绝 | 枚举没有名称，具体业务含义待验证 |

这些对应关系有静态证据。（[E04](04_证据索引.md#E04)、[E14](04_证据索引.md#E14)、[E17](04_证据索引.md#E17)） 限制放在物品记录里，也不意味着任何带限制物品都允许移动或入库。项目尚未显示通用的多格占位、同格多层物品结构；显示对象有多个覆盖资源引用，也不能据此认定规则允许任意组合。

外观会读取这些状态。例如，普通棋盘对部分受限状态选择灰色材质。箱体解除时先改记录、随后播放破罩动画，详细过程见[解锁与气泡](02_功能扩展与执行流程.md#流程5)。实际透明度、素材和输入遮挡范围因缺资源而待验证。（[E25](04_证据索引.md#E25)、[E26](04_证据索引.md#E26)）

## 数据改了，是否就已经保存？

**还不能这样认定。** 当前能确认的是：物品字段带有JSON保存标记，列表有变化通知接口；修改State时，原生代码会写字段并增加外部计数。把这个计数理解为“记录发生了变化”是**较强推断**，负责处理它的存储服务没有完整恢复。（[E02](04_证据索引.md#E02)、[E33](04_证据索引.md#E33)）

因此，后文说“业务生效”或“提交”，只表示内存中的业务数据已经改了。什么时候写入文件、写到一半如何恢复、是否发往服务器，都是另外的问题。未知配置如何迁移也没有定论；刷新画面的一个局部分支甚至会在配置缺失时删除物品，需要核实具体上下文。（[E28](04_证据索引.md#E28)）

如果要把它改造成我们的独立核心，难点不仅是复制这些字段。原有执行链还依赖Unity对象、画面位置、全局管理器、活动模块和钱包。抽取部分规则来测试是可行方向，但当前材料没有证明它已具备可替换的时钟、随机数和存储接口。（[E05](04_证据索引.md#E05)、[E09](04_证据索引.md#E09)、[E12](04_证据索引.md#E12)、[E19](04_证据索引.md#E19)、[E22](04_证据索引.md#E22)、[E34](04_证据索引.md#E34)、[E37](04_证据索引.md#E37)）

## 实现细节：坐标与找空位

本节用于核对算法，可以在需要时再读。

### 格子怎样落到画面上

IndexToPos把位置编号转为格子中心，公式为：

~~~text
y = index / width 的整数商
x = index - y × width
gridSize = (Rect.width / width, Rect.height / height)

localX = Rect.x + (x + 0.5) × gridSize.x
localY = Rect.y + (y + 0.5) × gridSize.y
localZ = 0
~~~

InitGrids虽然从最上行向下创建，但仍使用同一编号公式。IndexToPosition之后还有一次Transform相关外部调用，**较强推断**是转换为世界坐标，具体API未恢复。反向的PosToIndex在伪C中使用浮点转整数，并检查边界、z和活动区域；不能擅自改写成负数也向下取整的floor算法。（[E06](04_证据索引.md#E06)、[E07](04_证据索引.md#E07)、[E08](04_证据索引.md#E08)）

真实锚点、缩放、素材内边距和视觉格间距待验证。拖动过程还使用Transform实时位置来找目标，因此输入并非完全只依赖逻辑坐标。（[E12](04_证据索引.md#E12)）

### 不同功能找空位的方式不同

**一般放置——向外一圈圈找。** FindEmptyGridView在允许时先检查起点，再向外搜索；候选要求Id=-1且State不是10。非边界位置第一圈通常依次是北、东北、东、东南、南、西南、西、西北，越界位置会跳过。（[E17](04_证据索引.md#E17)）

**时间自动生产——只看周围3×3。** GetSudokuEmptIndex按列再按行检查。**较强推断**：每列找到首个空位后只退出内层循环，后续列可能覆盖先前结果，所以可能选中最后一个有空位的列；本段也未见排除State=10。这个反直觉细节需要原指令或小棋盘样本复核。（[E18](04_证据索引.md#E18)）

**解除邻近箱体——只看十字方向。** TryOpenBoxes检查横向三格与纵向三格，中心会重复，不检查对角；满足条件后还会继续解锁邻箱。（[E25](04_证据索引.md#E25)）

项目另外保存了提示候选和动画对象集合，修改物品时会标记物品计数需要更新。完整缓存更新规则没有追完。（[E05](04_证据索引.md#E05)、[E09](04_证据索引.md#E09)） 按静态算法估计，一般找空位或全盘扫描约为O(W×H)，局部3×3检查的候选数量固定；没有运行性能数据。
