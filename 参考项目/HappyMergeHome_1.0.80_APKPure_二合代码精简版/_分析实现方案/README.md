# Happy Merge Home 的二合棋盘是怎样实现的

版本：1.0.80（目录标识）｜分析日期：2026-09-25｜仅静态分析，未运行游戏。

## 先了解三个结论

**它把“物品数据”和“屏幕上的物品”分开存放，但没有把规则与画面完全分开。** 要保存的种类、状态、次数和时间放在数据记录中；棋盘界面负责接收拖动、点击，同时也执行部分规则。物品的显示对象还持有数据引用，有些显示回调（事先登记、稍后执行的函数）会直接修改物品。这些都是**已确认（静态证据）**。（[E02](04_证据索引.md#E02)、[E05](04_证据索引.md#E05)、[E09](04_证据索引.md#E09)、[E27](04_证据索引.md#E27)）

**它用较简单的数据结构承载多种玩法。** 棋盘主要是一张按位置排列的物品列表，每个格子只有少量运行信息。物品是否能生产、怎样生产，通常由配置和处理分支决定。没有在已追踪路径中找到完整的“给每件物品动态装上或卸下能力模块”的机制。（[E02](04_证据索引.md#E02)、[E05](04_证据索引.md#E05)、[E19](04_证据索引.md#E19)、[E37](04_证据索引.md#E37)）

**它值得借鉴的是具体处理办法，不能直接当作我们的独立核心。** 例如，它区分“冷却结束后可以再点”和“到时间自动产生物品”；附近没有空位时，可以先记住已选出的产物；出售也有专用撤销路径。另一方面，真实写盘、扣费是否完整、旧动画回调是否安全，仍有关键证据缺口。（[E21](04_证据索引.md#E21)、[E23](04_证据索引.md#E23)、[E31](04_证据索引.md#E31)、[E33](04_证据索引.md#E33)）

## 这些结论能确定到什么程度

本次阅读的是从游戏安装包恢复的类型结构和原生伪代码，不是完整的原始C#工程。材料缺少配置值、媒体资源和部分外部函数；一些方法的反编译结果也不完整。（[E01](04_证据索引.md#E01)）

文中统一区分：

- **已确认（静态证据）**：能在当前文件中定位到字段、调用或可读分支。
- **较强推断**：已有较明确的依据，但还缺调用顺序、配置或运行验证等关键一环。
- **待验证**：现有资料不能回答，报告列出需要补查的位置。

因此，“记录里有这个字段”不等于游戏已经完整使用了它；“没找到”也只限于本次检索范围。特别是实际扣费、磁盘保存、线上热更和服务器校验，不能靠类名推定。（[E01](04_证据索引.md#E01)、[E37](04_证据索引.md#E37)）

本次覆盖主棋盘的创建、坐标、拖动与普通合成、手动和时间生产、箱体遮挡、气泡回调、回收及出售撤销。活动只用于解释核心依赖，并未逐个审计。关于我们自己的方案，仍以独立核心棋盘、宿主Profile、本地规则与保存、专用出售/删除撤销、不做订单为边界；这里的建议不构成新决策。（[E36](04_证据索引.md#E36)）
