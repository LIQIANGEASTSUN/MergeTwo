# 35 个活动配置 getter 的 Ghidra 控制流修正

本次从已保留的 37 个“Ghidra 未产生伪 C”的方法中，额外恢复 35 个 `SummerWatermelonModel.get_PackageConfig` / `get_ProductAttenuationConfig` 的**原生伪 C**。这些方法有相同的 ARM 结构：方法起点后的 `0xDC` 处是一条无条件 `b`，跳到共享配置读取函数。原 Ghidra 局部分析把目标函数并进 getter，造成异常庞大的函数边界并反编译失败。

修正过程逐个从原生指令验证：尾部是 `b`，唯一控制流目标等于反汇编算出的目标地址；然后在 Ghidra 对这一条指令设置 `CALL_RETURN` 控制流覆盖，并把 getter 函数体限制为其自身的 `0xFC` 字节，再导出伪 C。此覆盖仅改变**分析工具的解释**，没有修改 `libil2cpp.so` 或安装包。方法索引记录 `native_flow_override_instruction_rva`、`native_flow_override_target_rva` 与 `native_flow_override=CALL_RETURN`。原先的 [ARM 汇编区间](failed_method_arm_disassembly_index.csv)仍保留，可核对原始机器指令。

例如 `0x2FF9798` 的原始 `b` 位于 `0x2FF9874`，目标为 `0x36FD420`；对应 [重导伪 C](code/Ghidra_native_pseudocode/2ff9798.c) 与 [ARM 反汇编](code/ARM_disassembly_when_pseudocode_failed/2ff9798.asm)。该伪 C 有可读的包装逻辑和对共享函数的调用，但 Ghidra 推断出的类型、返回值和函数名可能不准确。它**不是原始 C#，也不是自动生成 C# 占位方法的补全**。

另有 277 个方法的伪 C 含 `halt_baddata` 截断标记，仍标为 `pseudocode_partial_bad_instruction`。例如 `MergeBoard.RefreshBaseOrder` 在调用公共路径后，ARM 区间出现无法解码的尾部字节；现有证据不足以把被调函数统一设为“不返回”或补造后续逻辑。因此保留原输出和逐方法质量标记，不将其算作完整恢复。
