# Merge Studio 4.5.0：哪些值得借鉴，哪些需要重新设计

Merge Studio 最有参考价值的是一些具体做法：让格子保存自己的锁定信息、分别判断拖动和合成权限、区分“补次数”和“自动产物”。它也展示了另一种取舍：把交互、业务修改和画面更新集中到控制器，调用直接，但不利于我们把核心棋盘独立出来测试。

以下比较建立在 [项目的数据模型](01_架构与数据模型.md) 和 [实际操作流程](02_功能扩展与执行流程.md) 上。**源码事实、借鉴评价和假设推演是不同层次**；前者可以核对静态证据，后两者是基于我方目标的分析，不是已批准的最终方案。

## 1. 比较前提

我们已确定的范围是：先做独立核心棋盘，沿用最终宿主的 Profile（玩家存档结构），本地规则与保存先行，首期只支持售出／删除专用撤销，不做订单。

“先收集操作意图，再统一修改数据，最后更新画面”，以及 Function／Effect 如何组合，仍是设计文档中的讨论方案。本文用它们来比较职责边界，不把这些建议自动登记为用户决策。[我方范围与讨论依据，MS40](04_证据索引.md#ms40)

## 2. 用一次点击理解两种设计的差别

以“点击生成器，花费能量并生成一件物品”为例：

| 要解决的问题 | Merge Studio 的已见做法 | 我们正在讨论的做法 |
| --- | --- | --- |
| 谁接收意图 | Unity 输入进入物品控制器，再调用类型分支或发送事件 | Command 只表达“玩家想生成” |
| 谁判断和修改 | 控制器直接检查并扣容量／能量；产出接收者再选物、放置 | Consumer 先读取状态、收集要做的修改，再由 Batch 同步 Apply |
| 谁更新画面 | 控制器还负责创建对象、设置交互状态、启动动画 | EntityView 和表现 Function 根据业务结果更新画面 |
| 谁保存 | 可见保存事件和向宿主的转发，快照及落盘时点尚不完整 | 保存也纳入提交后的设计讨论，具体快照方案尚未批准 |

左列实现依据见 [点击产出](02_功能扩展与执行流程.md#43-点击产出) 和 [保存边界](01_架构与数据模型.md#5-保存请求到哪里为止)；右列是 [我方讨论方案，MS40](04_证据索引.md#ms40)。两列比较的是职责安排，不代表右列已经实现，也不证明左列发生过扣费丢物。

**核心差异在于谁负责完整的一次业务修改。** Merge Studio 的 `ItemEntity` 保存记录，但容量修改、限制解除等行为分散在配置和控制器中；`ItemController` 既接近我们说的 View，也承担部分逻辑。因此不能只把类名改成 Entity／EntityView，就得到独立逻辑层。[字段与行为归属，MS04／MS13／MS22](04_证据索引.md#ms04)

其 Box、Lock、Bubble 模块可以对应部分表现职责；配置子类和规则方法可以对应部分逻辑职责。但没有证据表明这些对象已经组成我方讨论的 Function 集合，也没有证明两侧一一对应。固定的限制标记、宝箱阶段和容量事实，也不能统称为 Effect 后就省掉状态管理。[扩展方式，MS20](04_证据索引.md#ms20)、[限制与阶段，MS19／MS24／MS28](04_证据索引.md#ms19)

所有概念的逐项映射保留在文末 [概念对照表](#查阅资料概念对照表)。其中 AtomicOperation 即使采用，也不自动提供事务回滚；“统一提交”仍需要定义拒绝和失败时如何保持数据一致。

## 3. 借鉴评价

### 3.1 可直接借鉴的设计思想

**格子可以保持轻量。** `CellEntity` 保存坐标和地格锁，`CellController` 负责对应场景对象，解决了地格状态的归属问题。对规则小棋盘，我们可以先让 Cell 保存必要事实，按真实需求决定是否需要完整实体能力。代价是位置记录与场景引用仍需同步，这套结构也不自动支持多格机关。[已确认的结构，MS02–MS03／MS06](04_证据索引.md#ms03)

**按操作分别问“能不能做”。** 该项目用不同查询处理拖动、主动合成和被动接收合成，能表达主动与被动权限不同的情况。我们至少可以分开 `CanDrag`、`CanMergeAsSource`、`CanMergeAsTarget`，同时保持统一调用习惯，防止规则散落后互相矛盾。辅助函数已确认；Jelly 最终能否作为目标仍是较强推断。[MS16／MS19](04_证据索引.md#ms19)

**次数、截止时间和阶段各有用途。** 项目分别保存容量、期限与宝箱阶段，便于区分“还有几次”“什么时候到期”“正在开启还是已就绪”。我们即使采用 Effect，也仍需要这些业务事实；其成本是必须另外定义时间基准、迁移和离线补算，字段本身不解决恢复问题。[已确认，MS04／MS24–MS28](04_证据索引.md#ms24)

**冷却补次数和自动产物应分别验收。** 该项目将两者分支处理，避免到期后的两种行为混淆。我们可以先写两个清晰的验收流程，再决定内部是否共享容量或求解函数；共享数据后，权限和满盘策略依然需要各自定义。[已确认，MS25–MS26](04_证据索引.md#ms25)

**解除一种限制时，要保留其它限制。** `Unbox` 在 Jelly 仍存在时不恢复普通拖动，解决了 Box＋Jelly 的具体组合。我们可以直接借用这个最小验证用例。它只是一个已实现的特例，还不足以证明通用效果系统正确，也不要求我们先做通用 Buff 框架。[已确认，MS29](04_证据索引.md#ms29)

### 3.2 需要条件或改造后借鉴

**配置子类适合区分行为，但要先隔离引擎依赖。** `BoardItemData` 子类与配置适配器组织了不同生成器和宝箱，减少参数与规则混放。不过现有配置带 Sprite，行为还接收 Controller。若借入独立核心，需要提取只读规则配置，并让逻辑策略脱离 Unity 对象。[结构已确认，MS05／MS20／MS38](04_证据索引.md#ms20)

**可以借外观模块的划分，回收规则需要自己补全。** 模块工厂和对象池有助于复用箱子、锁、气泡及物品对象；创建路径有证据，回池后的解绑、动画取消和旧回调失效则不完整。我们需要明确资源归谁释放，并验证对象重新绑定后不会收到上一次使用留下的回调。[创建已确认，回收保证待验证，MS13–MS14／MS37](04_证据索引.md#ms37)

**查询索引应在有需要时再加。** `ItemChainManager` 的增删调用表明它维护合成链辅助索引，可以减少相关查询的全盘扫描。但每次占位变更都多一份同步责任，当前小棋盘未必因此更快。我们可先扫描，实际出现热点后再加能从棋盘重建的索引，不把缓存当成唯一事实来源。[已确认增删调用，MS09](04_证据索引.md#ms09)

**主盘与活动盘的复用值得看，分支结构不必照搬。** 同一 `BoardController` 处理两类棋盘，复用了交互和产出代码；代价是活动标志、两类数据及全局服务进入核心分支。它是否支持完全隔离的多个棋盘实例尚未证明。我们当前先完成独立核心，没有必要预先引入整套主／活动双结构。[复用已确认，MS11／MS22／MS39](04_证据索引.md#ms39)

**售出专用撤销符合我们的范围，但语义要重新写清。** 独立撤销事件可以解决少量可恢复操作，不必记录全部历史。参考实现可确认重建入口，却不保证回原格，退款、记录寿命和身份恢复也待验证。我们可以借其范围控制，不能直接把未审完的恢复流程当作完成范例。[MS35](04_证据索引.md#ms35)

### 3.3 不建议沿用的可见做法

以下评价以我方“独立核心棋盘”的目标为前提，不等同于认定原游戏存在玩家可见缺陷。

**控制器同时修改业务与画面。** 这样一个对象就能完成交互、扣费和刷新，调用方便；但规则依赖场景对象，脱离 Unity 运行和测试的成本高。对我们的目标，业务结果应先明确，再交给表现层消费。[可见写入与资源调用，MS11／MS22／MS29–MS30](04_证据索引.md#ms22)

**一次操作由多个调用点逐步写入。** 这种做法容易复用现有小方法，但坐标、占位、次数和费用分别更新后，要依靠外部条件或补偿保证完整性。我们更适合先求出完整结果再统一提交，并区分正常拒绝与内部故障。逐步写入是事实；部分失败是否留下错误状态，目前只是风险推断。[MS09–MS11／MS22–MS23](04_证据索引.md#ms23)

**解除限制时直接恢复普通交互状态。** 局部写 `Movable.DEFAULT` 简单直接，适合组合严格受控的情况；新增限制后，则可能要在多个解除入口补判断。我们宜从剩余业务事实查询权限，减少 View 自行决定许可的机会。该建议基于维护成本，不把缺少组合证据当成现有缺陷。[MS29–MS30](04_证据索引.md#ms30)

**运行数据混合业务与动画信息。** `ItemRuntimeData` 同时保存期限、价格、Tween、Animator 和输入锁，减少了跨对象传参，却让保存边界、池复用重置及测试隔离更难理解。我们可以分开领域运行事实与表现临时数据，不能仅凭“是否可序列化”划界。[字段已确认，MS04](04_证据索引.md#ms04)

### 3.4 暂不能判断的关键取舍

合成是否等待动画、结果是否沿用旧物身份、保存何时真正完成、回收是否彻底取消旧回调，以及离线和随机的完整保证，都缺关键证据。它们暂不列为优点或缺点；具体补证入口见 [第 5 节](#5-待验证清单与最小补证)。

## 4. 三个扩展性推演

以下是**假设推演，不是该游戏已有功能，也不是我方新增需求**。目的在于观察：现有结构遇到一个新规则时，要改动多少地方。

### 假设 A：自动生成器暂时冻结，解除后保留原次数

已有生成器配置、容量和期限可以复用，不需要把物品换成另一种类来模拟冻结。但“暂时不能产出”必须进入多个操作入口，增加一个外观模块并不能完成业务规则。[已有基础，MS04／MS20／MS25–MS27](04_证据索引.md#ms25)

- **配置与状态：** 增加冻结许可、持续时间和必要的截止时间记录，定义旧存档默认值；不要覆盖宝箱或容量阶段，也不能只依赖恢复规则不明的 RuntimeData。
- **装配与触发：** 增加明确的施加／解除入口。现有材料没有可确认的通用业务能力注册入口，不能假定调用模块工厂就能动态注册冻结。
- **权限与时间：** 先补全 `ProcessItemSpawn`、`PreventRecharge`，决定冻结暂停产出、补容量还是两者；分别调整点击、自动、拖动、合成、售出等受影响的查询。还要规定冻结与产出同刻到期的顺序，以及离线期间怎样补算。
- **表现与回收：** 可用新模块或图标显示冻结；载入时重新绑定，回池时清理。不能让旧截止时间无意积累成解冻瞬间的大量补产，除非产品规则明确如此。

这个推演说明：配置子类可复用，临时限制仍要跨入口协调，不能把改动量理解成“一次动态注册”。

### 假设 B：地格仍锁着，上面的物品又带气泡

`CellEntity.IsLocked` 和 `ItemEntity.IsBubbled` 可以分别保存两种事实，但普通 `SetItemOnBoard` 会拒绝锁格。因此，字段能同时存在，不等于当前创建过程允许这种玩法。[已有结构与限制，MS03–MS04／MS11](04_证据索引.md#ms11)

首先要选择：锁区只保存待展开的内容描述，还是允许一个活跃物品对象存在。前者要在地格描述中补充气泡期限；后者要修改初始化、特殊放置、空位查询与点击命中，不能只跳过一次格子检查。

随后要调整 `SetCloudItems`／`GetFromCloud`、气泡计时入口、存档迁移和外观层级，规定锁区内是否计时、到期如何转换、云和气泡怎样先后消失。`RemoveBubble` 恢复权限时也要考虑格子仍锁着。气泡模块和时间字段可以复用；工厂与载入方法体不全，实际改动规模仍待补证。[云区与气泡，MS31／MS33](04_证据索引.md#ms31)

### 假设 C：物品被消耗时，解除一个邻格覆盖

可以复用四邻格判断和 `Unbox`，但现有 `ProcessUnbox` 只为活动规则返回候选，不是通用的“物品被消耗”事件。[已有局部能力，MS29／MS32](04_证据索引.md#ms32)

需要先规定合成、普通删除、售出和耗尽中哪些算消耗，并找到各自真正修改业务记录的位置。合成提交还缺可信方法体；也不能用 Unity 的 `OnDestroy` 代替业务消耗，否则隐藏或回池可能误触发。

配置要定义触发来源和效果，存档只记录必要的一次性进度。执行时保留旧坐标，求出邻格变化后与主消耗一起提交，再播放邻格解除表现。还需明确重复命中、连锁上限、重入和撤销范围；当前资料没有证明完整的去重与传播协议。这也可能扩大我们首期撤销的语义，若采用须另作需求裁定。[删除与生命周期，MS34／MS37](04_证据索引.md#ms34)

## 5. 待验证清单与最小补证

最影响判断的三个问题是：**合成在动画前还是动画后修改数据；一次产出的扣除与放置是否完整完成；保存与对象回收是否真正结束。** 它们分别决定我们能否借用提交顺序、失败处理和生命周期做法。

其它问题包括多限制解除、自动产出的满盘／离线结算、售出撤销语义、布局与随机配置。它们已有明确查找入口；缺失方法体不能算作原项目的设计缺陷，也不需要以重新下载整个 APK 为本次整理的前提。
