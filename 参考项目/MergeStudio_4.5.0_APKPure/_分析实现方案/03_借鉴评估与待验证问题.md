# 03｜Merge Studio 4.5.0：借鉴评估与待验证问题

**最值得借鉴的是具体规则的划分：格子锁与物品限制分开，主动拖动与接收合成分开，容量恢复与自动产出分开。** 对我们希望独立验证的核心棋盘，控制器同时处理业务和画面的组织方式则需要改造。

本篇基于 2026-09-26 的静态复核。实现事实来自前两篇重建的模型和流程；下面的概念映射、取舍及假设扩展是分析建议，不是原项目的架构声明，也不代表已经批准我方最终方案。

## 1. 与我方设计的对应关系

我们的已确认范围是：先验证独立核心棋盘，沿用最终宿主的 Profile，本地规则与保存先行，首期只做售出／删除专用撤销，不做订单。

本次对照了共享设计文档中的执行契约、Function／Effect 讨论和决策记录。Command → Consumer → Batch 同步 Apply → 表现，以及独立快照、Function＋Effect 等具体适配仍在讨论。不能把文档中的推荐自动视为用户决策；本次也未修改这些设计文档或实现玩法代码。

| 我方概念 | Merge Studio 的近似对应 | 实质差异 |
| --- | --- | --- |
| Entity | ItemEntity、运行数据、配置行为和部分 Controller 职责 | 业务职责分散；ItemEntity 主要是可写记录，保留字段中无稳定实例 ID |
| EntityView | ItemController、CellController、外观模块、对象池 | 有绑定与资源管理，但 ItemController 还扣容量、改限制和进度 |
| 逻辑 Function | 配置虚方法、配置子类及 Controller 的规则方法 | 有策略扩展，未定位每实例动态 Function 集合和统一生命周期 |
| 表现 Function | Box／Lock／Bubble、粒子及动画模块 | 有模块划分，未确认有序 Function 协议，也不与逻辑能力一一对应 |
| Command | Unity 输入和 Move／Merge／SpawnerSpawn 等事件 | 有意图与结果消息混用的迹象；统一排队、重入和重复处理语义待验证 |
| Consumer／Batch | OnEvent 接收者和直接调用 | 已见路径直接修改数据，未定位统一只读求解后批量写入的流程 |
| AtomicOperation | 未定位对应的操作对象协议 | 已见逐次写入；全局一致性保障不完整。我方采用这个名字也不会自动获得回滚 |
| Effect | Item 的固定限制字段、Cell 的地格锁 | 有附加影响语义，未定位独立效果实例、层数、来源和冲突汇总 |
| State | 宝箱阶段、容量阶段、数值、期限及运行锁 | 分别描述业务阶段、当前事实、调度和表现协调，不能合并成一种状态 |
| Profile | 可序列化对象图及向宿主发送的保存请求 | 有持久记录，稳定快照、完整提交和落盘成功仍未确认 |

以点击生成为例，参考项目先在控制器中扣容量和能量，产出接收者再选物、创建并放置。我们讨论的方案希望先求出本次完整变化，再同步修改业务数据，最后交给表现。差异在于谁负责完整的一次业务操作，不能仅靠把 ItemController 改名为 EntityView 来解决。

上述“未定位”限于本次检查的类型、方法和调用索引，以及已读的核心原生路径，不等于断言未恢复代码中完全没有相应机制。

## 2. 可以直接借鉴的设计思想

### 格子先保存必要事实

CellEntity 保存坐标、地格锁和待展开内容，CellController 对应画面，解决了位置状态的归属。对小棋盘，我们可以先采用轻量格子，只在需要独立行为或生命周期时再扩展实体能力。

代价是数据位置与画面引用仍需同步；这种结构也不自动支持多格机关。值得借的是清晰归属，而非复制全部双位置表。

### 权限按操作提问

`IsMovable`、非活动判定与 `PreventMerge` 分别服务不同操作，能表达主动和被动权限不同的情况。我们可以分开 `CanDrag`、`CanMergeAsSource`、`CanMergeAsTarget`，同时让各入口采用一致的查询方式。

这能避免一个“锁定”标记禁止一切，但查询分开后仍须协调规则，不能让同一事实在各处得到矛盾结论。Jelly 最终作为目标的完整规则尚未确认，不应直接照搬成我方产品规则。

### 容量、期限和阶段分别保存

参考项目用数值表示剩余容量，用期限表示何时到期，用阶段表示等待、开启和就绪。CurrentCapacity 是浮点数，也提醒我们不要默认把容量和点击次数等同。

即使采用 Effect，这些业务事实也仍然需要表达。最低限度是分清数值、时间和阶段，再定义时间基准、容器迁移及恢复；仅增加字段不会自动解决离线结算。

### 自动产出和补容量分别定义结果

自动生成器也可以补容量，因此两者应按行为区分，不能只按物品类型互斥分类。我们可以分别验收“等待后容量增加”和“等待后棋盘出现产物”，再决定是否共享内部计算。

代价在满盘、暂停和冻结等边界：一种行为被阻止时，另一种是否继续必须单独规定；不能用一个通用“冷却结束”事件替所有规则作决定。

### 解除一种限制后保留另一种

`Unbox` 在 Jelly 仍存在时不恢复普通拖动，提供了一个明确的组合用例。我们可以直接采用“Box＋Jelly，解除 Box 后仍不能拖动”作为局部验证。

这是一个已实现的特例，不是通用效果系统正确性的证明。先保证已有组合，不需要为此预建无限扩展的 Buff 框架。

## 3. 需要条件或改造后借鉴

| 候选做法 | 解决的问题与已有依据 | 代价、条件及对我们的用途 |
| --- | --- | --- |
| 用配置子类区分行为 | BoardItemData 子类和适配器组织生成器、宝箱参数与虚规则 | 现有配置含 Sprite，行为接收 Controller；若进入独立核心，应分离只读规则配置和引擎资源，不因子类存在就认定已完成分层 |
| 拆分外观模块并复用对象 | Box、Lock、Bubble 模块及池创建路径支持资源复用 | 回收和旧回调保证缺失；可借模块边界，但须明确绑定、释放及回池重置责任 |
| 增加合成链查询索引 | SetItem／Clear 同步增删 ItemChainManager 项，便于按链查询 | 每次占位变化多一份同步责任，未实测比扫描更快；当前小棋盘可先扫描，有热点再增加可重建的索引 |
| 多种棋盘共用控制器 | 主盘／活动盘复用了部分交互和产出 | 活动标志、不同数据根和经济服务进入核心分支，多实例隔离未证明；我们先完成独立核心，不预先复制双结构 |
| 采用售出专用撤销 | 独立 UndoItemSell 事件与重建入口控制了恢复范围 | 原格、退款、记录寿命和身份语义未完整确认；可借范围控制，具体规则仍需按我方需求定义 |

## 4. 不建议沿用的做法及其适用边界

以下评价以“独立核心棋盘”为前提，不等同于认定原游戏存在玩家可见故障。

**控制器同时修改业务与画面。** 交互、扣费、刷新放在同一对象中，调用直接，适合围绕 Unity 场景组织的实现；代价是规则依赖具体对象，测试和复用成本较高。对我们，业务结果宜先明确，再交给表现消费。

**一次业务由多处逐步写入。** 移动依次改坐标和占位，点击将扣除与落地分开，渐进式合成还会在动画前更新进度。这些都是可见事实，但是否产生部分失败取决于外部保障。我们更适合先求出完整结果，规定正常拒绝、内部故障和保存时点；同步 Apply 也不意味着自动事务回滚。

**解除入口直接恢复普通交互状态。** `RemoveJelly`、`RemoveBubble` 的局部 DEFAULT 写入简单直接，在合法组合严格受控时可以工作。随着限制增多，维护者可能要逐个入口补条件。对我们，更稳妥的候选是依据剩余业务事实查询权限，让外观解除不自行决定业务许可。这里评价的是维护成本，现有组合是否会出错仍待验证。

**运行数据混合业务调度和表现对象。** ItemRuntimeData 把时间、价格、Tween、Animator 与锁放在一起，减少传参，却让保存范围、池重置和依赖隔离难以理解。我们可以区分需要恢复的领域运行事实与可重新派生的表现数据，不能只按可序列化标记切分。

完整合成提交、保存成功、回收安全、离线和随机保证目前都缺关键证据，暂不将它们评价为原项目的优点或缺点。

## 5. 三个扩展性推演

以下均为**假设推演，不是 Merge Studio 已有功能，也不是我方新增需求**。它们用于说明现有结构遇到新规则时，哪些部分可复用、哪些地方需要协调。

### 自动生成器暂时冻结，解除后保留容量

可以复用生成器类型、容量和期限，不必通过更换物品种类模拟冻结。需要增加冻结参数、必要的截止时间记录、旧档默认值，以及施加和解除入口。现有外观模块工厂不能代替尚未确认的业务能力注册机制。

关键是先定义冻结暂停产出、补容量还是两者，再协调 `ProcessItemSpawn`、`PreventRecharge`、点击及其它受影响权限。自动更新先尝试产出再检查补容量，因此只给某个计时分支加冻结判断可能不够。还要规定冻结和产出同刻到期的先后、离线如何补算，避免解除后意外集中补产。

外观可以使用新模块或图标，但加载时须重建绑定，回池时须清理。冻结状态不能覆盖宝箱阶段，也不宜只放入保存规则不明的临时数据。实际改动涉及配置、状态、权限、调度、恢复和表现，不是一次动态注册就能完成。

### 地格仍锁着，上面的物品又带气泡

Cell 锁和 Item 气泡有独立字段，但普通 `SetItemOnBoard` 会拒绝锁格。虽然存在 skipCellCheck，仍不能推断查询、输入和计时都会支持该组合。

首先要决定锁区只保存待展开内容，还是允许活跃物品存在。前者需要保存待展开气泡及其期限；后者需要核对特殊放置、空位查询、命中和权限，不能只绕过一次检查。

随后要调整 `SetCloudItems`／`GetFromCloud`、气泡期限处理、迁移和外观层级，规定锁区内是否计时、到期如何转换、解锁与爆泡如何衔接。`RemoveBubble` 恢复权限时也要考虑地格仍锁着。模块和时间字段可复用，工厂与载入缺体使完整改动量仍待验证。

### 物品被消耗时解除邻格覆盖

可以复用四邻接判断和 Unbox；现有活动 `ProcessUnbox` 只返回候选，不能当成通用的“物品被消耗”事件。

需要定义合成、删除、售出和耗尽中哪些算消耗，并在真正修改业务记录的位置触发。合成最终提交缺体，不能用 Unity OnDestroy 代替，否则隐藏或回池可能被误当成业务消耗。

配置须表达触发来源和效果，存档只保留必要的一次性进度。执行时保存旧坐标，求出邻格变化并和主消耗一起提交，再播放表现；同时定义重复命中、连锁上限、重入和撤销边界。这里的邻格副作用可能扩大售出／删除撤销语义，若采用需另行裁定，而不是顺手加入首期范围。

## 6. 仍会影响判断的问题

本次复核已经确认部分合成进度在动画前写入，但完整消费与结果建立仍未知。优先需要确认的是完整提交时点、产出失败语义，以及保存和回收的完成边界。下表保留具体问题和最小验证方式，不把缺失方法当作原游戏的缺陷。

| 优先级 | 问题 | 已知边界与最小验证 |
| --- | --- | --- |
| 高 | 合成何时消费旧物、建立结果并保存？ | 已知 CurrentTaskIndex 可提前变化。需补 MergeTweenAction 的异步执行体、可信的 MergeItemsOnBoard 和 GetFromMerge，区分 MergeStart／Merge，并确认结果身份、覆盖与期限继承 |
| 高 | 载入／合成／放置动画取消后，是否释放输入锁并留下完整棋盘？ | 关键异步执行体缺失。最小场景是动画中隐藏、关闭或回池后重开，同时检查占位、业务进度及 SpawnLock／MergeTargetLock，而不只看动画是否消失 |
| 高 | 点击生成能否完整提交，失败是否保留原费用和容量？ | 需确认 SpawnerSpawn 的生产与分发连接。验证缺产物配置、最后一空格被占、放置返回失败时的容量、能量和占位，区分正常拒绝与内部故障 |
| 高 | 保存读取哪个时点，什么时候可以确认落盘？ | SceneController 转发已确认；需补 MasterController.SaveBoard、SaveWorker 的复制和写入边界，对比内存重建与结束进程后的恢复，并观察保存失败 |
| 高 | 解除一个限制后，剩余限制是否仍有效？ | 需确认 BoardChangeState 和合法配置组合。对 Box＋Jelly、Bubble＋其它限制分别检查拖动、合成源／目标、点击和补容量，不能只验证图标变化 |
| 中 | 自动产出在满邻位、拖动、暂停和离线时如何结算？ | 接收者按尝试数扣容量，上游 ProcessItemSpawn 缺体。验证无邻位、一个邻位、时钟回拨、重复重进，以及多个生成器竞争；分别观察产物数、容量和调度时间 |
| 中 | 回池重绑后是否仍收到旧回调或监听？ | 取消接口存在，使用和释放缺体。需确认 DestroyItem／OnDisable／OnDestroy、模块归还及异步取消，构造旧动画或资源回调迟到的新绑定场景 |
| 中 | 售出撤销的身份、退款、位置和寿命是什么？ | 已知传记录重建且不保证原格。验证售出后花费、满盘、关闭、再次售出和重复撤销，确认记录复制、旧回调失效及恢复失败语义 |
| 中 | 实际布局、邻格与候选顺序是什么？ | 索引公式已确认，配置实例和比较器缺失。最小补充是目标版本 BoardData／初始位置及排序规则，验证边角、锁区和远距离挤位，不用其它版本截图补值 |
| 较低 | 随机结果和配置版本变化怎样恢复？ | 概率字段、教程及非概率入口可见。需确认抽样方法、种子／版本数据、缺配置及序列化处理；样本可检查异常，不能单凭小样本证明算法 |

这些未知不妨碍采用轻量格子、分操作权限、容量与时间分离等局部思想。它们限制的是对完整执行保证的判断；最终架构仍应由我方范围和可验证的行为决定。
