# Merge Studio 4.5.0：一次操作怎样改变棋盘

这篇从玩家的操作出发，解释点击、拖动、等待和拆箱分别改了什么数据。最值得先记住的区别是：**冷却结束可能只是恢复生成次数，也可能直接生成物品；拆掉物品外壳与打开独立宝箱，也是两种流程。**

下文“已确认”均指静态代码证据，没有运行游戏验证。流程缺少关键方法体时，会明确写出能够追到哪里。数据对象的职责见 [棋盘与物品模型](01_架构与数据模型.md)，精确来源见 [证据索引](04_证据索引.md)。

## 1. 不同物品的行为放在哪里

**已确认（静态证据）**：配置类既保存参数，也定义部分行为。普通生成器、自动生成器和宝箱使用不同的 `BoardItemData` 子类；`ItemController` 再按类型执行分支，修改 `ItemEntity` 中的次数、阶段和限制标记。扩展一种物品时，可能同时涉及配置子类和控制器中的判断。[配置与行为继承，MS05／MS20](04_证据索引.md#ms20)

以创建物品为例，控制器初始化后还会调用配置的虚方法 `Initialize`，把控制器交给配置行为。这说明它的配置对象并非纯数据。合成规则也有虚方法：原生代码中默认 `IsMergeable` 返回 true，而导出的 C# 文件写着占位 false；规则判断必须以能恢复的方法体为依据。[创建与初始化，MS13](04_证据索引.md#ms13)、[合成规则，MS17](04_证据索引.md#ms17)

箱子、锁、气泡的外观由模块工厂管理。工厂按类型保存 Prefab，并提供获取和销毁接口；但注册方法体缺失，不能由此认为“任意业务能力都能动态添加或移除”。生成扣费还有功能处理器参与，能够影响容量扣除，但其注册顺序和停止处理规则尚不明确。[模块工厂，MS14](04_证据索引.md#ms14)、[生成扣费，MS22](04_证据索引.md#ms22)

## 2. 先分清几种容易混淆的功能

| 玩家看到的事情 | 代码中实际改变什么 | 说明 |
| --- | --- | --- |
| 点击生成器产出 | 消耗次数／能量，选择产物，再尝试放上棋盘 | 扣除和放置由不同方法负责，见 §4.3 |
| 生成器冷却完成 | 补充容量，或调整容量阶段 | 这个分支本身不生成棋盘物品，见 §4.4 |
| 自动生成器到期 | 尝试在可用邻格创建物品，再扣容量 | 可放数量受邻格限制，见 §4.4 |
| 宝箱开启后可领取 | 独立宝箱物品从等待进入计时，再到可领取阶段 | `ChestState` 保存阶段；开启入口还没有完整恢复 |
| 拆掉物品外壳 | 清除原物品的 `IsBoxed`，恢复图标并移除箱子模块 | 原物品仍在；若还有 Jelly，就继续保留其拖动限制 |
| 解锁云区／地格 | 清除格子的锁，再根据配置建立其中内容 | 锁属于格子，里面生成的物品仍可能带自己的限制 |

这些区别有静态证据支持；各自缺失的调用环节见下文。[生成与时间，MS21–MS28](04_证据索引.md#ms21)、[外壳与地格，MS29–MS31](04_证据索引.md#ms29)

`IsBoxed` 表示现有物品的外壳，`BoardItemChestSpawner` 表示独立宝箱物品，`CellEntity.IsItemBoxed` 则描述锁区尚未展开的内容。不能因为画面上都像“箱子”，就把它们建成同一种对象。Jelly 也暂用代码原名：材料缺少美术资源，无法确认它是否表现为蜘蛛网、半透明或变灰。[格子与物品字段，MS03–MS04](04_证据索引.md#ms03)、[宝箱，MS28](04_证据索引.md#ms28)

## 3. 权限不是一个总开关

**“不能拖动”并不自动等于“不能接收另一件物品来合成”。** 代码分别检查拖动、合成来源和合成目标；同一种限制，在不同操作中的作用可能不同。

| 要做的操作 | 已确认的局部判断 | 还不能推出什么 |
| --- | --- | --- |
| 拖动 Jelly／Box 物品 | `IsMovable` 返回 false，初始化时设为 `Movable.LOCKED` | 所有输入分支并未完整恢复 |
| 把受限物品主动拖去合成 | 合成检查拒绝带 Jelly、Bubble 或 Box 的来源 | 这不代表三者作为目标时规则相同 |
| 向 Box 物品合成 | 棋盘明确检查目标 `IsBoxed` 并拒绝 | 不是仅靠外观挡住点击 |
| 向 Jelly 物品合成 | 辅助函数将 Jelly 与 Bubble／Box 区分；`PreventMerge` 不检查上述拖动锁 | **较强推断**：支持“不能主动拖，但可作为目标”的可能性；完整目标筛选和配置规则仍缺失 |
| 拖动／换位 Bubble 物品 | `IsMovable` 不因 Bubble 单独返回 false | 不能据此声称所有气泡物品都能拖动 |
| 售出或入库 | 有各自的配置许可接口 | 完整条件待验证，不能从“可拖动”推导 |

证据：[输入与合成检查，MS15–MS16](04_证据索引.md#ms16)、[权限辅助函数，MS19](04_证据索引.md#ms19)。普通换位的可见分支还会检查目标 `IsMovable`，但全部类型、教程和候选筛选的组合没有恢复完整。

这里有两套容易看混的状态：`Movable.Status.LOCKED` 控制拖动状态；`InteractionStatus` 表示交互状态。合成的 `PreventMerge` 检查后者是否禁止点击，以及运行中的合成目标锁 `MergeTargetLock`。它们不是同一个变量。[初始化，MS13](04_证据索引.md#ms13)、[权限公式，MS19](04_证据索引.md#ms19)

**多限制组合的实际例子**是 Box＋Jelly：`Unbox` 只去掉 Box，Jelly 仍在时不会恢复普通拖动状态。相比之下，`RemoveJelly`、`RemoveBubble` 的局部代码会直接设为 DEFAULT。后两者是否会恢复不该有的操作，取决于这种组合能否出现，以及后续是否重新检查权限，不能直接判为缺陷。[拆箱，MS29](04_证据索引.md#ms29)、[解除 Jelly／Bubble，MS30](04_证据索引.md#ms30)

**较强推断**：已读流程主要靠各入口分别判断和处理特例，尚未找到一个完整的“根据所有剩余限制计算权限”的统一入口。但中央刷新方法 `BoardChangeState` 的方法体缺失，它可能承担部分工作。生成器配置也可以与 Box 标记共存；拆箱没有重新装配生成能力，手动、自动、充能各自是否受限仍要分别查证。

## 4. 六条执行链及明确断点

### 4.1 载入棋盘

**能确认的是读取存档和创建运行对象的两段代码；把它们连接起来的异步载入过程尚不完整。**

1. **读取记录。** `BoardController.Load` 检查存档键，读取字符串，按需解压后反序列化为棋盘数据。缺少存档时如何建立默认盘、坏数据如何修复，没有完整证据。[MS12](04_证据索引.md#ms12)
2. **建立棋盘和物品。** 有 `LoadBoard(BoardData, bool)` 和 `ItemEntityFactory.GetFromLoadBoard` 入口，但前者的异步状态机执行体、后者的方法体缺失。因此，清旧棋盘、建立格子、处理旧配置 ID 的顺序仍待验证。[MS12／MS14](04_证据索引.md#ms14)
3. **创建可视对象。** 通用 `SpawnItem` 路径从对象池取出对象，取得 `ItemController`，调用控制器初始化和配置的虚 `Initialize`。初始化根据 `IsMovable` 设置交互状态，根据 `IsBoxed` 开关图标，并处理锁／气泡等表现。[MS13](04_证据索引.md#ms13)
4. **开放输入。** 这一步还不能定位。缺少完整载入状态机，无法确定 `_isInitialized`、输入开放与首次保存之间的顺序，也无法确认资源创建失败如何收尾。[MS12／MS37](04_证据索引.md#ms37)

第 3 步是已确认的通用创建路径；它是否由载入过程对每个格子逐一调用，属于**较强推断**。

### 4.2 拖拽、移动、换位与合成

开始拖动时，输入管理器先处理上一件仍在拖动的物品：存在旧对象就调用其 `DragEnded`，再记录新对象。随后控制器更新排序、选择和预合成反馈。松手时，`DragStopped` 清除拖动锁、调整缩放，并依据碰撞候选、匹配规则和限制判断选择分支；拒绝或部分教程分支会让物品回位。[输入与候选检查，MS15–MS16](04_证据索引.md#ms15)

三个主要分支的可见顺序如下。表中箭头表示同步调用先后；没有补全缺失的异步代码。

| 分支 | 已确认的调用顺序 | 需要注意的边界 |
| --- | --- | --- |
| 移到空格 | `MoveItemOnBoard` 改原物坐标 → 清旧格并请求保存 → `SetItemOnBoard` 写新格 → 启动放置协程 | 新格的运行、持久占位都先于该放置动画写入；保存实际读取哪个时点仍未知 |
| 挤走目标 | `SwapItemsOnBoard` 顺序清理和放置两件物品 | 距离大于 1 时，被挤物使用另一个候选空格的首项，不保证回到来源格；排序规则与失败恢复待验证 |
| 启动合成 | `MergeIt` 设置两物的运行锁、停止局部动画 → 调用 `MergeTweenAction` | 只能确认异步入口前已加锁，不能确定何时消费旧物、生成结果或保存 |

依据：[占位写入，MS09–MS11](04_证据索引.md#ms09)、[合成入口与缺口，MS18](04_证据索引.md#ms18)。普通拖动处理和运行锁不等于已证明存在按先后排队执行的命令系统。

**合成结果的种类可以单独确认。** `BoardData.GetMergedItemData` 按 `SetID` 找合成链：未到末级就取下一等级，链末可以使用 `ItemSpawnedByLastLevel`；找不到配置时有返回空值的路径。[MS17](04_证据索引.md#ms17)

**合成提交的时点仍待验证。** 合成事件接收者确实调用 `MergeItemsOnBoard`，但发出事件的具体位置缺失，提交方法的反编译边界也严重失真。无法判断业务是否等待动画、旧物是否复用、结果继承哪些状态。需要恢复的方法和地址集中在 [待验证清单](03_借鉴评估与待验证问题.md#5-待验证清单与最小补证)。

### 4.3 点击产出

这个流程最需要关注的是：**检查空间、扣次数／能量、选择产物和放置物品分散在不同方法中。**

1. **确认这次点击要生成。** `ProcessItemClick` 检查当前选中位置等条件，同坐标时进入 `ProcessDoubleClick`。函数名虽含“双击”，但真实时间阈值未确认；不能理解成任意一次点击都会产出。
2. **先看空间和生成资格。** `ProcessDoubleClick` 取得可用格。普通生成分支会在满盘时先拒绝；宝箱等特殊类型不能直接套用。`ProcessSpawn` 接着检查能量、容量阶段等条件，正常能量不足或 `NO_CAPACITY` 时返回 false。
3. **扣次数和费用。** `ProcessSpawn` 先通过 `ChangeCurrentCapacity` 减容量，再修改用户或活动能量。此时这些业务数据已经改变，而方法本身尚未选出最终产物；无限能量和功能处理器还会影响具体扣法。[点击与扣除，MS21–MS22](04_证据索引.md#ms21)
4. **选择产物。** `SpawnerSpawn` 的事件接收者使用随机／教程路径选择产物，再取得配置并调用 `GetSpawn` 工厂。空产物会直接返回。第 3 步与本步是否属于同一条完整事件链是**较强推断**：事件生产端的泛型类型没有完全恢复。[产出接收者，MS23](04_证据索引.md#ms23)
5. **把产物放上棋盘。** 接收者调用 `SpawnItem`，再调用带保存标志的 `SetItemOnBoard`。后者检查锁格和占用，成功路径先写运行及持久占位，再启动放置动画；这个调用点没有处理其 bool 返回值。[放置顺序，MS11](04_证据索引.md#ms11)

**较强推断的风险**：若第 3、4 步确属同一链，选物为空或后续放置失败可能发生在扣费之后。尚缺事件分发保证和补偿处理的证据，所以这是需要验证的一致性问题，不能写成已复现的游戏缺陷。

### 4.4 时间推进、自动产出与离线

`UpdateSpawners` 读取当前毫秒值，按物品类型和期限更新。可以确认使用了时间戳，但真实时钟来源、更新频率没有完整审计。[时间推进，MS25](04_证据索引.md#ms25)

**普通生成器：到期补次数。** 先检查 `PreventRecharge`，再比较下一次更新时间，执行容量加一或整理容量阶段；这个分支不直接生成物品。状态变更会调用控制器刷新，但完整图标／倒计时刷新方法缺失。覆盖状态是否阻止补容量，仍需恢复 `PreventRecharge`。[容量与阶段，MS24–MS25](04_证据索引.md#ms24)

**独立宝箱：计时后变为可领取。** 非初始化地进入 CHARGING 时，`SetChestState` 设置“当前毫秒＋ChargeTime×1000”的期限；到期更新将阶段改为 CHARGED。`ProcessChest` 在已就绪且能量足够时扣容量／能量。开启入口怎样启动计时、完整动画如何衔接尚不清楚；缺少配置实例，也不能给出实际几秒开启。[宝箱，MS28](04_证据索引.md#ms28)

**自动生成器：到期尝试放物品。** 可见更新分支会检查棋盘是否等待、物品是否正被拖动等条件，再调用 `ProcessItemSpawn`。该方法体缺失；另一个已恢复的自动产出接收者会取“请求数量”和“可用邻格数量”的较小值，循环创建并放置，最后按循环数量扣容量并请求保存，且有播放／不播放动画的分支。[自动产出，MS25–MS26](04_证据索引.md#ms26)

这里扣的是**尝试次数，不是已确认的放置成功数**。没有邻格时循环为零，但生产端代码不全，不能保证计时状态也完全不变。多个自动生成器同时到期时谁先执行，也待验证。

**离线恢复：看到了补算入口，尚不能确认完整结算。** 暂停事件处理会取得经过时长并设置 elapsed；`ProcessOfflineCapacity` 检查是否允许补充，再按周期份额和余数更新容量／时间。自动物品另有 `AutoOfflineCount` 和 `CreateOfflineAutoItems` 无动画创建路径。精确补产数、满盘剩余数量如何保留、重进是否重复补算、时钟回拨和离线上限均未确认；这不证明游戏在后台持续运行。[离线处理，MS27](04_证据索引.md#ms27)

随机产物的配置有 Probability，另有教程选择和宝箱 NonProbabilistic 参数；权重归一化、抽样算法、随机种子、远端配置及服务端校验待验证。[随机与配置，MS38](04_证据索引.md#ms38)

### 4.5 解除限制与外观

**拆 Box 会先改变业务标记，再清理箱子外观。** `Unbox` 的顺序是：清除 `IsBoxed` → 请求保存 → 若没有 Jelly 则恢复普通拖动状态 → 显示物品图标 → 检查锁 → 销毁箱子模块 → 按参数播放粒子。原物品没有因此换种类，Jelly 限制也得到保留。[拆箱，MS29](04_证据索引.md#ms29)

另外两种解除的局部顺序不同：`RemoveJelly` 先把拖动状态设为 DEFAULT，再清除 `IsJelly`，然后移除锁模块并处理粒子／缩放；`RemoveBubble` 先清除物品气泡标记，随后恢复拖动状态、移除气泡模块并播放爆破反馈。它们如何考虑其它剩余限制，见 §3；解除后的最终保存还要追上层事件。[解除 Jelly／Bubble，MS30](04_证据索引.md#ms30)

这些调用顺序说明标记变化与外观清理有先后，**不证明画面中一定隔了一帧，也不证明期间能被其它事件观察**。可直接查阅 [Unbox 源码](../code/Ghidra/ghidra_expanded_pseudocode.c) L5065–5138、[RemoveJelly／RemoveBubble 源码](../code/Ghidra/ghidra_flow_pseudocode.c) L5307–5747。

地格解锁是另一条流程：`SetCloudItems` 匹配锁定状态和解锁等级，先修改格子等级并清锁，再读配置、调用 `GetFromCloud`，异步创建其中的物品。逻辑解锁已经发生，但资源消失、创建失败恢复、最终保存的完整顺序仍缺后续状态机。[云区与地格，MS31](04_证据索引.md#ms31)

还有一个容易误读的入口：`ProcessUnbox` 只返回满足活动等级、Box 标记和四邻格条件的候选，本身不执行 `Unbox`，且要求 `EventEntity`。因此它不能作为“主棋盘每次合成都拆邻箱”的完整证据。[相邻拆箱候选，MS32](04_证据索引.md#ms32)

### 4.6 删除、回收与撤销

**普通删除的可见顺序是先处理运行对象，再清理持久记录，最后按标志保存。**

1. `DestroyItem(Coordinate, ...)` 先调用 `DestroyItemGameObject`。后者移除生成器更新列表中的条目，调用物品控制器的 `DestroyItem(false)`，再清运行槽位。
2. 随后 `DestroyItemEntity` 删除合成链查询项，将位置中的 Item 置空，并清除格子中描述锁内物品的字段。
3. 最后按参数请求保存。控制器的 `DestroyItem` 方法体缺失，所以第 1 步不等于已证明对象同步回池、动画全部取消、订阅全部解除。[删除顺序，MS34](04_证据索引.md#ms34)

**售出使用单独路径。** `DestroyItemGameObjectViaSell` 调用 `DestroyItem(true)`，外围还保留售出运行数据。其封装与普通删除不同，不能把上述顺序套用于所有售出情况。

**撤销售出会重新选择可用位置。** `UndoItemSell` 事件携带物品记录和配置，进入 `SpawnAtRandomPosition`：无可用格时返回空；有位置时修改传入记录的坐标，创建控制器并保存放置。它不保证回到原格，选择索引的外部函数也未恢复，不能确认“均匀随机”。[售出与撤销，MS35](04_证据索引.md#ms35)

**待验证**：取消和回收方法多数只剩签名。虽然存在对象销毁时取得取消令牌的 API，但其传递和使用不明，不能证明旧回调在对象回池后必然失效。撤销记录的寿命、退款、共享引用还是复制、关闭后能否撤销，也尚未确认。当前只能说明售出专用撤销，不能扩展为通用历史回放。[生命周期，MS37](04_证据索引.md#ms37)

## 5. 这些流程共同说明了什么

控制器在多个路径中直接修改业务数据，再调用动画或外观模块；局部运行锁负责阻止部分重叠操作。这是已确认的调用方式。至于事件是否同步嵌套、接收顺序是否固定、重复事件是否只生效一次、连锁何时停止，目前资料不足以给出全局保证。[事件与输入，MS02／MS15](04_证据索引.md#ms15)、[功能处理器，MS22](04_证据索引.md#ms22)

保存还要单独看：这里的“请求保存”不等于已经写入文件，也不证明读取的是不可变快照。完整边界见 [保存请求到哪里为止](01_架构与数据模型.md#5-保存请求到哪里为止)。对我方设计的影响见 [借鉴评估](03_借鉴评估与待验证问题.md)；下一步最小补证见 [待验证清单](03_借鉴评估与待验证问题.md#5-待验证清单与最小补证)。

### A.4 补充能力的研究边界

`BoardItemPerishableSpawner`、`BoardItemProgressive`、`BoardItemPickBox` 及充能相关类型／分支已经定位；`ProcessDoubleClick` 对不同产出类型分别调用重载，并有选择箱界面路径。它们支持“继承＋中央分支”的扩展判断，但本次没有审计完每类的耗尽、奖励、版本恢复与生命周期，不提供这些功能的完整规则说明。[MS13、MS20–MS21]
