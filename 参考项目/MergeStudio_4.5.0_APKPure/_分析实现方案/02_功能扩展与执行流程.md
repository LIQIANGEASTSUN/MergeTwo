# 02｜Merge Studio 4.5.0：功能扩展与执行流程

**一次操作通常由控制器分步完成：判断条件、修改记录、发送事件、创建对象并播放动画。** 这些步骤有局部顺序，但完整合成、保存和回收仍缺关键方法体，不能把局部顺序当成全局一致性保证。

以下依据 2026-09-26 的静态复核。明确标注的推断和待验证事项之外，“已确认”均表示能从类型、字段偏移及可信原生方法相互核对，没有运行验证。

## 1. 功能由配置继承和控制器分支共同组织

普通与自动生成器分别是 `BoardItemDefaultSpawner`、`BoardItemAutoSpawner`，都继承 `BoardItemSpawnerData`；独立宝箱 `BoardItemChestSpawner` 沿另一分支继承 `BoardItemData`。配置既保存参数，也有 `Initialize`、合成许可等虚方法。初始化会把控制器交给配置行为，控制器自身又按配置类型分支。

这属于“配置子类定义部分行为＋控制器集中处理部分行为”的混合方式。新增一种物品可能需要配置子类、适配器、数据工厂和控制器分支一起修改，不能推断为每件物品都能任意增删 Function。

外观另有 Box、Lock、Bubble 等 `ItemControllerModuleBase` 模块。模块工厂按类型保存 Prefab，提供获取与销毁接口；注册和完整回收实现缺失。它可以支持外观拆分，但模块多不等于 ECS，也不证明存在统一的业务效果生命周期。生成过程另有功能处理器影响容量扣除，其注册、处理顺序和终止规则尚未恢复完整。

以下功能需要分开理解：

| 功能 | 归属与主要数据 | 业务含义 |
| --- | --- | --- |
| 点击生成 | Item；容量、生成器阶段、产出池，费用来自用户或活动能量 | 点击通过检查后消耗资源，再建立产物 |
| 补容量 | 同一 Item；容量、充能期限及运行调度时间 | 恢复产出能力，这一步本身不建立棋盘物品 |
| 自动产出 | 自动生成器 Item；共享容量和调度字段，还有离线计数 | 尝试向邻格放物；该类型也有补容量分支 |
| 宝箱生成器 | 独立 Item；宝箱阶段、容量、开启期限 | 从等待开启进入计时，再到可领取 |
| Box 外壳、Jelly、Bubble | Item 上的固定标记，部分带等级或期限 | 限制现存物品；不因覆盖存在就换成另一种物品 |
| 地格／云区锁 | Cell 的锁、解锁等级和待展开内容 | 固定在位置上，解锁后可以创建仍带物品限制的内容 |

`IsBoxed` 是现存物品的外壳，`BoardItemChestSpawner` 是独立宝箱物品，`CellEntity.IsItemBoxed` 是锁区待展开内容的描述。三者不是同一个“箱子状态”。缺少美术资源，Jelly 保留代码原名，不能认定它就是蜘蛛网、半透明或变灰效果。

## 2. 权限按操作分别判断

已恢复辅助函数的局部规则如下。表中逻辑只是这些函数自身，不代表每个输入入口都必然调用它们。

| 方法 | 已确认的条件 |
| --- | --- |
| `IsInactiveItem` | Jelly、Bubble、Box 任一存在 |
| `IsInActiveAndNonMergeableItem` | Bubble 或 Box；未包含 Jelly |
| `IsJellyOrBoxedItem` | Jelly 或 Box |
| `IsOnlyJelly` | 有 Jelly 且没有 Box；这里未检查 Bubble |
| `IsMovable` | 没有 Jelly 且没有 Box；这里未检查 Bubble |
| `PreventMerge` | `InteractionStatus` 为 NONCLICKABLE／TUTORIAL_NONCLICKABLE，或运行数据的 `MergeTargetLock` 已置位 |

`Movable.Status.LOCKED` 与 `InteractionStatus` 是两套状态，不能混为一个锁。初始化会把不可移动物品设为拖动锁定；合成的 `PreventMerge` 则检查交互状态及合成目标锁。

拖放校验还会检查来源是否为非活动物品、是否同链同级、是否存在合成结果，以及双方是否阻止合成。棋盘的合成检查明确拒绝 Box 目标，普通换位也检查目标 `IsMovable`。

**较强推断：Jelly 可能支持“不能主动拖动，但可以作为合成目标”。** 依据是主动来源被拒绝，辅助函数又把 Jelly 与 Bubble／Box 分开；缺少完整候选筛选和子类规则，尚不能写成所有 Jelly 物品的最终规则。同样，Bubble 没有单独出现在 `IsMovable` 中，也不能证明所有气泡物品都可拖动或换位。售出、入库有各自的配置许可接口，完整条件未审完。

组合限制不是一个统一开关：`Unbox` 保留尚未解除的 Jelly 拖动限制；`RemoveJelly`、`RemoveBubble` 的局部路径则直接恢复 DEFAULT。后两者是否会放开不该开放的权限，取决于组合能否出现和后续刷新。中央方法 `BoardChangeState` 缺少方法体，因此目前只能确认分散判断与特例处理，不能断言全局完全没有统一汇总。

## 3. 载入与创建：记录如何变成可交互对象

### 可确认的两段流程

1. `BoardController.Load` 检查存档键，从 DataSaveWrapper 取字符串，走压缩或非压缩路径，再进行 JSON 反序列化。
2. 通用 `SpawnItem` 从池取得对象，拿到 ItemController，调用控制器 `Initialize`，再调用配置的虚 `Initialize`，随后处理相应粒子和动画。

连接这两段的 `LoadBoard` 异步执行体，以及 `ItemEntityFactory.GetFromLoadBoard` 方法体缺失。因此“载入逐格调用通用创建”是**较强推断**；清旧盘、建立格子、处理旧配置、开放输入和首次保存的完整顺序仍待验证。默认盘、坏档修复和资源失败处理也不能按常见做法补全。

### 初始化中的实际分支

新创建标志会把 `SpawnerState` 设为 `NON_INITIALIZED`，随后还要经过配置初始化，不能把“新物品”直接解释成“满容量”。生成器阶段包括 NO_CAPACITY、SMALL_CAPACITY、BIG_CAPACITY、NON_INITIALIZED，分别对应无容量、小容量、大容量及尚未初始化；它们与具体数值共同描述状态。

`InitializeMovableStatusAndUI` 根据 `IsMovable` 设置拖动状态，根据 `IsBoxed` 开关物品图标。其缩放／气泡初始化分支先处理 Jelly，再以 `else` 处理 Bubble，说明这段代码有优先顺序，不能解释成任意覆盖模块都会独立叠加。Box、Lock、Bubble 的初始标记如何由数据工厂装配，以及池对象是否完整重置，仍缺方法体。

## 4. 拖拽、移动、换位与合成

开始拖动前，输入管理器先处理上一个拖动物品：存在旧对象就调用其 `DragEnded`，再记录新对象。物品控制器随后更新选择、排序和预合成反馈。松手时，`DragStopped` 清拖动锁、调整缩放，从碰撞候选中筛选落点，并结合合成／移动规则分支；部分失败和教程分支会让物品回位。

这能证明有局部输入协调，不能证明输入按命令队列依次执行。事件是否同步嵌套、订阅顺序、去重、防重入和连锁终止规则仍未完整恢复。

### 移到空格

已确认的 `MoveItemOnBoard` 顺序为：

```text
改原 ItemEntity 的坐标
  → ClearCell 清旧位置，saveBoard=true
  → SetItemOnBoard 放到新位置，saveBoard=false
```

普通放置检查目标是否锁定或已占用，成功后先写运行位置和持久位置、更新链索引，再处理表现和保存。存在显式的 `skipCellCheck` 参数；这只能说明有特殊放置入口，不能证明跳过检查后其它规则都允许。

放置动画也有条件：在运行对象有效且 `merged=false` 的可见分支中，设置 SpawnLock 并启动 `ItemSetAnimationRoutine`。因此“占位先于这段放置协程”成立，但不能推广为所有合成分支，也不能说此前没有画面变化——`SpawnItem` 已可能启动表现。协程结束、取消时如何解锁，尚未恢复。

移动在清旧格时就发出保存请求，而新格稍后才写入；实际保存取得哪个时点的数据未知。这是需要核实的一致性边界，不是已经证实保存了半个移动。

### 换位或挤走目标

`SwapItemsOnBoard` 依次修改坐标、清位置、放置两件物品。坐标欧氏距离大于 1 时，被挤物采用可用位置候选的首项；距离不大于 1 的分支使用原来源位置。

距离较远时也不保证被挤物离开原来源格：来源格已被清空，可以进入候选，首项仍可能是它。排序比较器没有恢复，不能写成固定回原格、必去第三格或一定取最近格。放置时先处理被挤物，saveBoard=false；再处理拖动物，saveBoard=true，成功路径末尾请求保存。两次放置的返回值在这里没有被检查，异常恢复和最终落盘仍需确认。

### 合成前已有部分业务写入，完整提交仍未追通

`BoardData.GetMergedItemData` 按 SetID 查合成链：通常取下一等级，链末可用 `ItemSpawnedByLastLevel`，缺配置时有返回空值的路径。合成许可还受配置子类的虚规则影响。

`MergeIt` 的可见顺序并非只有动画锁：**在渐进式物品的类型分支中，会先根据配置更新目标 ItemEntity 的 `CurrentTaskIndex`，然后才设置来源 SpawnLock、双方 MergeTargetLock，处理局部动画并调用 `MergeTweenAction`。** 这个字段是物品进度，所以不能断言“合成动画前绝不修改业务数据”；也不能据此断言所有合成都在动画前完成提交。

另一个容易误判的点是事件名称：动画前可见包含来源、目标、结果配置的泛型发布，但 `BoardEvent.MergeStart` 和 `Merge` 都有这三类字段，缺泛型类型信息时不能仅靠载荷认定是哪一个事件。已确认的 `OnEvent(Merge)` 会调用 `MergeItemsOnBoard`，然而合成动画状态机缺失，提交函数边界也失真。

因此，旧物消费、结果新建还是复用、覆盖与期限继承、占位最终一致、保存及动画失败补偿，仍属于**待验证**。目前能确认的是部分进度提前写入及运行锁先行，不能绘出完整合成提交链。

## 5. 点击生成：检查、扣除和产物落地

### 容量不是固定的整数次数

`CurrentCapacity` 是 float。普通 `ProcessSpawn` 通过 `EnergyMultiplierHandler.GetCapacityReduceAmount` 决定扣除量，功能处理器还可能影响是否扣容量；能量扣除另受 `UsesEnergy`、无限能量及用户／活动分支影响。没有配置实例，不能写成每次点击固定扣一容量、一能量。

`ChangeCurrentCapacity` 把容量限制在 0 到 BigCapacity 之间。由正值降到零时，会调用 `CalculateNextChargingTime` 计算充能期限，再整理容量阶段，并按参数请求保存。阶段设置会反调控制器 `BoardChangeState`，其完整权限、图标和时钟刷新仍待验证。

### 普通生成分支的实际步骤

| 步骤 | 已确认的调用与数据变化 | 拒绝或缺口 |
| --- | --- | --- |
| 识别操作 | `ProcessItemClick` 检查选中位置和坐标，同坐标进入 `ProcessDoubleClick` | 方法名不能证明真实双击时间阈值，也不是任意一次点击都会产出 |
| 检查空间 | `ProcessDoubleClick` 查询可用格，再进入对应类型的 ProcessSpawn 重载 | 普通分支满盘会先拒绝；宝箱等特殊分支不能直接套用 |
| 检查与扣除 | 普通 `ProcessSpawn` 检查能量和容量阶段；通过后先减容量，再扣用户或活动能量 | 能量不足、NO_CAPACITY 等正常拒绝返回 false；此方法尚未选定最终产物 |
| 选择产物 | `OnEvent(SpawnerSpawn)` 走随机／教程选择，取得配置，调用 `GetSpawn` 工厂 | 空产物直接返回；扣除端到该事件的完整泛型发布连接仍是较强推断 |
| 创建和放置 | 接收者调用 `SpawnItem`，再调带保存标志的 `SetItemOnBoard` | 此调用点未处理放置的 bool 返回值；放置自身仍会检查锁格和占用 |

**较强推断的风险：** 若扣除与产出接收者确属同一完整事件链，选物为空或放置失败可能发生在扣除之后。缺少总线分发和补偿实现，不能把它写成已复现的扣费丢物。

产物配置有 `Probability`、`IsLocked`、`Reward`，还有教程选择和宝箱的 `NonProbabilistic` 参数。`SpawnerConfigAdaptor` 保存的是“当前生效配置”引用，不足以证明它专指活动配置或来自远端。概率归一化、抽样算法、种子保存、远端启用和服务器校验均待验证。

## 6. 时间推进：补容量、自动产出、宝箱和离线

`UpdateSpawners` 使用当前毫秒值。物品记录的 `ChargingFinishAtTick` 表示充能期限；运行数据的 `NextSpawnerUpdateMs/UpdateStepMs` 用于更新调度。它们不是可以互换的一个“冷却时间”。实际时钟来源、调用频率和防回拨规则尚未完整确认。

### 普通生成器：到期补容量

普通分支先检查 `PreventRecharge`，再比较下一更新时间；到期后推进该时间，并执行容量加一，或在已满时整理阶段。下一时间为零时先初始化为当前时间加更新间隔。这个分支本身不建立棋盘物品。

`CalculateNextChargingTime` 还会读取容量配置、ChargeTime 和当前时间，写物品记录的充能期限。由于部分常量与分支含义未恢复，不给出未经确认的统一公式。`PreventRecharge` 方法体缺失，Box、Jelly 等限制是否暂停补容量也仍待验证。

### 自动生成器：先尝试产出，随后才可能补容量

在调度时间已初始化、棋盘未等待自动生成、物品未处于拖动态时，更新代码的常规分支按以下顺序执行：

```text
调用 ProcessItemSpawn 尝试产出
  ├─ 返回 true：把下次更新时间设为当前时间＋间隔，然后返回
  └─ 返回 false：再比较下次更新时间
                  ├─ 未到期：返回
                  └─ 已到期：推进时间，检查 PreventRecharge，尝试补容量
```

另外有一个受外部标志控制的分支，会重复调用 `ProcessItemSpawn` 直到返回 false，再进入后续处理；标志的业务含义未确认，不能解释成普通玩家都具备的机制。

`ProcessItemSpawn` 本体缺失，它内部可能还有时间、容量和限制判断。因此不能断言自动产出完全不受冷却，也不能把 `NextSpawnerUpdateMs` 当成唯一产出周期。能确认的区别是：**自动产出与容量恢复是两种行为，但可以共存在同一种生成器中。**

自动产出事件的接收端已恢复：取“请求数量”和“可用邻格数”的较小值，循环创建、放置，最后按循环次数扣容量并请求保存；存在播放／不播放动画的分支。扣除依据是尝试次数，不是核对过的成功放置数。没有邻格时循环为零，但不能因此保证上游时间也没有变化。多个生成器的执行先后和同一空位竞争仍待验证。

### 独立宝箱：开启计时后才可领取

`ChestState` 是 WAITING、CHARGING、CHARGED 三个阶段。非初始化地进入新的 CHARGING 时，`SetChestState` 设置“当前毫秒＋ChargeTime×1000”的期限并调整充能计数；到期更新切到 CHARGED。新进入就绪状态的路径把期限设为 -1，该分支还调用控制器整理开启外观。

领取使用 `ProcessSpawn(BoardItemChestSpawner, int)` 重载，要求 CHARGED 且能量条件允许，然后按容量扣除量处理容量和能量。容量的具体扣法不能直接套用普通生成器的 ChangeCurrentCapacity 路径。

配置含 Capacity、产出池、OpenSprite 和 SpineSkin，说明开启阶段和外观有专门支持。但开启入口、完整动画、合成／入库许可、领空后销毁及恢复初始化细节未追通；缺配置实例也无法给出实际开启秒数。宝箱阶段与 IsBoxed、Jelly、Bubble 分开存放，不代表任意交叉组合都合法。

### 暂停恢复与离线补算

这次复核进一步连通了暂停恢复路径：`ApplicationPause` 的恢复分支计算经过时间，经 `SetMillisecondsPassed` 记录后，调用 `ProcessPausedSpawnerCapacity`。后者扫描运行位置，对有效的生成器调用 `ProcessOfflineCapacity`，传入经过时长和 `isFromPause=true`。

`ProcessOfflineCapacity` 先检查是否阻止补充，再按周期的份额和余数处理容量及下次更新时间。自动产物另有 `AutoOfflineCount` 和 `CreateOfflineAutoItems` 的无动画创建入口；事件数量的恢复仍不完整。

因此，可以确认恢复前台时会尝试补容量，但尚不能确认全部离线补产规则。满盘剩余数量是否保留、离线上限、时钟回拨、隐藏期间处理、重进两次是否重复结算，以及最终保存点都待验证。这些入口也不证明游戏在后台持续运行。

容量和阶段存在 ItemEntity 中，入库／商店另有剩余充能时间；移动同一记录会保留这些字段。各生成器耗尽、合成继承、入库暂停和动态卸载的完整规则尚缺方法体，不能统一推定为保留或清零。

## 7. 限制解除：业务标记与外观分别怎样改变

### Box、Jelly 和 Bubble

| 解除入口 | 已确认的主要顺序 | 组合、保存及表现边界 |
| --- | --- | --- |
| `Unbox` | 清 IsBoxed → 请求保存 → 没有 Jelly 时恢复 DEFAULT → 显示图标 → 检查锁 → 销毁箱子模块 → 按参数播放粒子 | 就地修改原物品，不换种类、不重装生成能力；明确保留 Jelly 的拖动限制 |
| `RemoveJelly` | 设 DEFAULT → 清 IsJelly → 移除锁模块 → 处理排序、粒子和缩放 | 调用来源、解锁成本及最终保存未追全；其它剩余限制是否重新检查待验证 |
| `RemoveBubble` | 清气泡标记 → 恢复拖动状态、清气泡模块并处理爆破等反馈；还清 ShopRemainingChargingTick | 说明解除涉及商店剩余时间数据，不是只删外观；完整迁移、保存和剩余限制处理待验证 |

这些顺序不证明业务标记变化与画面清理之间一定隔了一帧，也不证明外部事件能在中间插入。外观可以从业务标记派生，但输入状态和模块仍需各入口维护。

Box 还有 UnboxLevel，Jelly 的解锁费用／图像有配置线索；Bubble 保存绝对期限与生成触发信息。`CheckBubbleTime` 包含运行 BubbleLock、教程／状态条件和期限检查。可确认存在到期检查，但到期替换成什么、选中或隐藏时是否暂停、过期重开如何恢复尚不完整。期限保留在原物品记录中，不等于跨入库、替换和销毁都会自动正确传递。

### 地格／云区解锁

`SetCloudItems(level)` 匹配锁定状态与解锁等级，先修改 Cell 的等级并清 `IsLocked`，再准备其中内容、查配置、调用 `GetFromCloud` 并异步创建物品。地格锁在内容创建前已改变；后续云资源消失、创建失败恢复和最终保存的完整顺序缺少异步执行体。

Cell 的待展开内容可描述受限或带箱子的物品，但所有描述字段如何映射到 Item 标记仍需工厂确认。解锁地格不等于给现有物品解除所有限制。

活动棋盘另有 `ProcessUnbox`、`ProcessLevelUnbox`：根据活动等级、Box 标记及四邻接等条件返回候选列表。它们要求 EventEntity，并不直接执行 Unbox，不能作为“主棋盘每次合成都自动拆邻箱”的证据。

## 8. 删除、回收与售出撤销

### 普通删除的清理受参数影响

`DestroyItem(Coordinate, saveBoard, resetInfo)` 先处理运行对象，再清持久记录，最后按标志请求保存：

1. `DestroyItemGameObject` 对有效物品移除 `_spawnerList` 条目，并调用物品控制器的 `DestroyItem(false)`。
2. **只有 `resetInfo=true` 时**，该函数才处理匹配的选中状态并将运行位置的 Item 置空。不能说所有删除调用都会在这里清运行槽；`false` 路径是否由其它步骤完成，需要调用者确认。
3. `DestroyItemEntity` 删除链查询项、清持久位置的 Item，并清 `LockedItemSetID/LockedItemLevel`，不等于清除格子的全部锁和覆盖描述。
4. 按 saveBoard 请求保存。

ItemController 的 DestroyItem 本体缺失，因此调用它不等于已经同步回池、取消所有动画和解除所有监听。异常辅助函数附近的失真代码也不能作为合法恢复路径。

### 售出与撤销是专门流程

`DestroyItemGameObjectViaSell` 使用 `DestroyItem(true)`，外围保留售出运行数据，不能直接套用普通删除的每一步。

`UndoItemSell` 事件携带 ItemEntity 和配置，进入 `SpawnAtRandomPosition`。没有可用格时返回空；有格时修改传入记录的坐标，创建控制器并保存放置。恢复位置不保证是原格；选择候选下标的外部函数未恢复，不能由方法名认定均匀随机。

记录是共享引用还是复制、撤销期限、退款、售出后花费、关闭重开、第二次售出和重复撤销的规则均待验证。目前只能说明存在售出专用撤销，不能推导出通用历史回放。

### 生命周期仍缺关键保证

BaseSubscriber 有 OnDestroy 和销毁取消令牌接口，ItemController 有 OnDisable、OnDestroy、DestroyItem；但这些关键实现以及若干异步执行体仅剩签名。不能说它完全没有取消设施，也不能证明对象回池重绑后旧回调必然失效。模块归还、订阅释放、动画取消及运行锁复位都需完整路径支持。

`BoardItemPerishableSpawner`、`BoardItemProgressive`、`BoardItemPickBox` 和充能相关类型也已定位。点击分支有对应重载和选择箱界面，渐进式合成提前修改进度已确认；各类耗尽、奖励、恢复与生命周期未完整审计，不据此补出一套完整规则。
