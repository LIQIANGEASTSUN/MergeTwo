# 03｜哪些值得借鉴，哪些需要改造

> Gossip Harbor 3.99.0（版本号308）｜复核日期：2026-09-26｜静态分析，未运行游戏。

## 1. 与我们的设计相比，差异在哪里

这个样本在数据归属上比较清楚：位置、物品身份、能力进度各有所属。执行边界却更分散：组件直接改状态，一次操作分步保存、通知，部分业务由动画回调继续完成。**数据分层值得参考，不能因此一并接受它的操作时序。**

我们的范围仍是独立核心棋盘、沿用最终宿主Profile、本地规则与保存先行、首期仅售出／删除专用撤销、不做订单。以下是候选建议，不确定最终架构，也不增加玩法需求；Function、Effect、State怎样组合仍待选择。

| 我们的概念 | 本项目最接近的部分 | 主要差别 |
| --- | --- | --- |
| Entity：业务身份与数据 | ItemModel；区域障碍也有独立对象 | 格子没有完整Entity；模型仍访问显示和GM服务 |
| EntityView：表现绑定 | ItemView与棋盘的模型—画面映射 | 部分动画还继续写业务，旧绑定回调保护不统一 |
| 逻辑Function：组织行为 | 生成、吞入、转换等能力组件 | 自己持有并修改状态，没有统一限制在Apply阶段写入 |
| 表现Function：组织显示与交互 | 能力画面组件、ItemView和BoardView方法 | 两侧不一一对应，跨物品动画由棋盘画面协调 |
| Command：表达请求 | 多数入口直接调用模型方法 | 未见通用请求队列；ItemCommand仅为局部活动能力 |
| AtomicOperation／Batch：执行已决定的变化 | 删除、替换、占位等直接调用 | 没有统一的完整变化收集阶段；我们自己的Batch也不自动提供失败回滚 |
| Effect：可附着的玩法影响 | 包装物、加速字段只能作局部类比 | 包装解除会换身份；未确认通用效果集合；画面Effect主要是特效 |
| State：运行事实与阶段 | 开箱阶段、次数、吞入进度、配置阶段 | 各有业务含义，不能因为引入Effect就全部取消 |
| Profile：宿主保存体系 | 多张业务表与同步模块 | 可参考保存内容，不能当作宿主Profile的现成适配 |

Command与Function也不互相替代：前者表达请求和执行边界，后者组织行为。拖拽跟手等局部反馈可以直接由画面处理，真正落子才需要进入业务入口。

## 2. 可以直接借鉴的思想

“直接借鉴”指采用思路，不指复制恢复代码。

**位置与物品身份分开。** 它解决了移动、入仓后进度应继续属于同一物品的问题；代价是两份位置关系必须由可靠入口共同维护。对当前小矩形棋盘，轻量格子加独立物品已经有样本依据，不必先给每格建立完整Entity。坐标换算和显示尺寸是否进一步移出逻辑层，可按实际布局需求决定。

**能力保留必要状态。** 能力负责行为，阶段、次数、时间记录事实，避免因冷却反复拆建能力。采用时要补齐状态保存和恢复，不能只注册行为。我们的Function可以组织行为，State保留事实，Effect处理确有独立附着、叠加和解除需求的影响。

**区分主动源和被动目标。** 蛛网说明单一“可操作”开关不够。值得借鉴的是权限语义，而不是分散的检查位置：界面和业务可以使用同一查询，业务入口仍应复核当前对象、目标与条件。

**保存计时依据。** 开始时刻和阶段时长支持恢复时重算，避免把每秒显示值作为唯一状态。代价是必须定义后台、时钟校正、配置改变及恢复顺序；保存期限本身不承诺离线产量。

**区分完整物品与创建资格。** 仓库或缓存究竟保留身份和进度，还是只保留以后生成什么，应由产品规则决定。使用一个Code不能同时表达这两种含义；异常引用回退为新物时，也应明确是否允许丢失旧进度。

## 3. 需要条件或改造后采用的设计

**包装物适合内物尚未运行的场景。** 初始地图中的待解锁物可以只存创建描述，节省内物的运行和保存；代价是解除后换编号、重新初始化。已有生成器临时被锁、还需保留次数与冷却时，包装替换就不够，应另有保持身份的限制数据。

**有限池适合约束一轮分布。** 它减少一轮总量的不确定性，却不保证固定顺序。采用前先决定池属于实例、类型还是棋盘，再明确配置切换和失败重试怎样影响它。类型共享与实例递减是不同选择，35／2／5只是样本数值。

**模型消息可以解耦显示，但必须说明完成边界。** 消息携带必要的前后对象和结果，便于画面独立组织节奏；若发消息后规则还在继续，监听者就不能把它当作完整提交。我们若统一Apply，应先完成本次连带变化，再发布足以解释结果的数据，不能仅要求画面重新读取当前模型来猜所有中间过程。

**显示对象复用要有明确绑定生命周期。** 回池节省创建成本，也增加取消旧动画、资源加载和订阅的成本。可验证一个最小约定：每次绑定有独立标记，迟到回调只操作标记一致的绑定。还要核对复用时能力画面集合是否匹配，不能只重置图标或判断类型相同。

**显式存档字段可作遗漏检查，恢复入口还要隔离副作用。** 逐项保存比序列化整个运行对象更清楚，但新增能力必须同时修改保存与恢复。吞入恢复会先抽新需求的例子说明，“创建默认实例再覆盖旧字段”可能提前改变共享数据。我们仍应接宿主Profile，区分新建与恢复，确认完整快照发布和实际落盘的边界。

**小棋盘可先用简单扫描。** 遍历和少量缓存容易理解；筛选、排序、临时分配也有成本。63格的做法不能外推到大盘，但当前没有证据要求立即引入ECS或到期队列，应先测实际更新频率与规模。

## 4. 不建议照搬到独立核心中的做法

**让动画决定业务是否完成。** 批量吞入、区域障碍便于对齐视觉节奏，却增加无画面运行和取消恢复的难度。候选改法是先确定业务结果，再由画面展示；期间是否锁玩家输入是另一项交互决策，不能用输入锁代替业务提交。

**让多个界面共写业务保护开关。** 气泡的单一标志无法表达是谁申请保护、谁还有未完成操作。多来源互相覆盖目前是风险推断；若确需延缓到期，应有明确的申请与释放规则。仅延迟退场画面时，不必同时改变业务到期。

**把部分完成当成可安全重试。** 普通生成先改池与次数，再扣费建物；特殊分支又有不同成本语义，bool返回还可能表示“产出成功但不能继续”。我们应区分前置拒绝、完整成功和中途异常，确保表现失败不触发第二次扣费或产出。

**依赖组件遍历顺序处理组合规则。** 广播容易扩展，却没有天然的先后、终止和对象有效性保证。只有确实要组合的能力才需要明确优先级、是否继续和旧对象检查，不必为无限假想玩法预建框架。

**把界面检查当作唯一防线。** 开箱、售出等以后可能被宿主、时间更新或测试直接调用。界面可提前提示，业务入口仍需核对资格与身份，包括延迟确认返回时再次检查。

**撤销失败时强行删除其它物品。** 这满足了恢复旧物，却改变了另一件物品；样本还在扣款前腾位。我们的专用撤销应明确凭据、空位、退款回收和失效条件，无需复制这个兜底或扩展成通用历史栈。

## 5. 仍需验证的问题及最小验证方式

以下均未执行运行实验。已确认的分支不再当作未知；需要验证的是缺失依赖、分支可达条件和实际影响。

### 一次操作与保存是否会只完成一部分

- **消息与中间状态。** 补事件总线实现，确认同步、嵌套和异常传播；在合成通知及交换位置通知处观察数据，判断监听者能否读到未完成状态。
- **扣费与生成异常。** 补钱包和存储实现，分别让普通产出的扣费、建物失败，核对池、次数、费用、物品和占位；活动提前返回分支另测，不能套用同一成本预期。
- **存档不一致和旧数据。** 确认底层保存队列及原子性，构造未知类型、缺失引用和跨表不一致，检查局部清理或重建是否造成价值丢失。缓存回退新建与保留旧实例应分别验证。
- **服务端裁决。** 当前只见客户端计算、上传和冲突恢复，需要协议或服务端实现才能判断它最终校验哪些规则。

### 关闭、取消和复用会留下什么

- **批量吞入。** 分别在无画面、飞行中取消、源物被移动或替换时执行，确认是否重复消费、漏消费或补做；输入锁不能代替这些检查。
- **区域障碍。** 满进度而动画未完成时关闭界面，对比当前会话与重载后的锁状态。非自定义物品奖励分支还需确认是否被实际配置使用，以及m_reward是否由缺失代码补入。
- **气泡。** 交叉测试选中、广告、确认窗口、自然到期和物品替换，确认保护是否提前释放，迟到确认是否操作了旧位置上的其它对象。
- **画面回收。** 让旧资源加载在同类型View重新绑定后才返回，检查取消、订阅和绑定标记；另构造重复跳跃和缺失合成View，验证已获字节码确认的两处保护缺口能否在实际流程触发。
- **撤销。** 测试快速撤销、满盘、原格被占和金币不足，核对删了谁、扣了多少，以及旧退场回调有没有误删新画面；同时决定恢复后的时间应自然流逝还是冻结。

### 时间、恢复与能力组合是否完整接通

- **离线和库存。** 测试短恢复、长恢复、入仓跨期限、满盘重开，以及自动生成器周围堵住后的手动点击，确认恢复次数、产量和落点各自的规则。
- **吞入恢复。** 同一存档反复重载，比较共享需求序列及下一件新吞入物的目标，确认初始化抽取是否改变后续分布，并检查1秒保护重置的影响。
- **加速与组件组合。** 补齐加速扫描的调用／注册证据；用真实配置查找同时响应同一事件的多个能力，验证宿主替换后是否继续执行。人为构造冲突不能直接当作线上问题。

## 6. 用三个假设检验扩展成本

以下均为**假设推演，不是该游戏已有功能**，也不增加我们的玩法需求。

### 6.1 自动生成器临时被冻结

先决定冻结只阻止产出，还是连次数恢复也暂停。前者可以继续计时；后者必须记录暂停时刻或调整期限，简单停止Update会使解冻后按旧时间补算。

可复用ItemSpread、物品身份和倒计时显示；需要增加冻结数据，补工厂装配、ItemManager保存和恢复，接入手动、自动两个生成入口。若同时限制移动或合成，还要接对应棋盘查询，表现侧添加冻结外观。

包装替换或拆建能力可能丢进度；同型组件单槽也不能直接表示两个冻结来源。最小实验是保持同一编号，冻结、保存、重开、逐一解除，再核对次数、时间和两个产出入口。

### 6.2 土地有锁，物品同时带气泡

土地锁留在位置，气泡属于物品；买开气泡、到期变金币或物品移动，不应顺手改变土地锁。继续套包装前缀不能自动表达这层归属。

可复用坐标、占位查询、气泡时间与资源；新增按坐标保存的限制数据、恢复入口和资格查询，覆盖画面挂在格子位置。活动矩形障碍只能参考，不能视为现成CellEffect。

可先用轻量格子数据验证，无需立刻把每格建为完整Entity。分别先解除地锁、先解除气泡，结果应一致，且解除一种后仍尊重另一种限制。

### 6.3 物品被消耗时影响邻格

先定义消耗原因：合成、售出、使用、替换和入仓不能混为一类，清除占位也不等于销毁物品。

可复用四邻遍历与合成／替换入口，但应在规则处理时记录消费原因和目标。若影响是可附着能力，还要补工厂、状态保存／恢复及表现。ReplaceItem内部也会删除旧物，不能把所有删除都无条件触发相同连锁。

多个反应可能争用落点或再次命中同一物品。可以为这条实际规则建立明确顺序、同次去重和结束条件，先确定结果再通知画面。验证两相邻触发物、同一目标两次命中、替换后再删除；现有四邻冲击不能证明任意组合已经安全。
