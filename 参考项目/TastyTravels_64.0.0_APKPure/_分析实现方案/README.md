# Tasty Travels 64.0.0：它怎样实现二合棋盘

这组文档先解释 Tasty Travels 自己的实现，再讨论哪些做法适合我们的设计。**结论来自本地逆向材料的静态分析，没有运行游戏验证。** 已确认的代码行为、由此作出的推断，以及仍缺证据的问题分别标明。

## 先了解三个关键结论

**第一，格子、物品和画面各有自己的职责。** 格子主要记录“这里放了哪个物品”；物品记录“我是谁、属于哪种物品、现在有哪些能力和限制”；显示对象负责把这些数据画出来。格子没有像物品一样的一整套身份和能力系统。这种分工是本项目最清楚、也最容易单独借鉴的部分。[E02](04_证据索引.md#e02)、[E06](04_证据索引.md#e06)、[E08](04_证据索引.md#e08)、[E15](04_证据索引.md#e15)

**第二，普通合成先改变棋盘数据，再播放动画。** 两个旧物品退出棋盘，新物品先创建出来，随后画面才演出合成。因此，动画完成不是这次合成成立的条件。不过，修改过程中已经可能发出事件通知，而且部分解锁条件还会读取界面状态。它有逻辑与表现的分工，但还没有形成完全独立的纯逻辑核心。[E07](04_证据索引.md#e07)、[E12](04_证据索引.md#e12)、[E14](04_证据索引.md#e14)、[E17](04_证据索引.md#e17)

**第三，组件化解决了能力的组织问题，却不会自动保证整次操作都成功或都撤回。** 例如点击生成会先扣费、推进次数，再检查具体产物能否放进某个格子。这个先后顺序有代码证据；它是否会在正常配置下造成损失，仍需实验。评价时必须把“看到的顺序”和“可能产生的故障”分开。[E19](04_证据索引.md#e19)

## 阅读正文需要的几个术语

| 术语 | 在本报告中的意思 |
| --- | --- |
| 业务数据／逻辑 | 决定格子占用、物品数量、费用、冷却和规则资格的数据与操作。 |
| 表现／View | 物品的图片、动画、遮挡和显示绑定。画面上仍在播放，不代表物品仍参与业务。 |
| 能力组件 | 挂在物品上的功能对象，例如点击生成、自动产出、气泡。这里不是指 Unity 的显示组件。 |
| 实例 ID／种类 ID | 前者区分“哪一个物品”，后者区分“哪一种物品”。两个同种物品仍是两个实例。 |
| 存档记录（DTO） | 用于保存或传输的数据记录。把运行对象转成记录，不等于记录已经写入磁盘。 |
| 事件／回调 | 通知其它代码某件事发生了。同步通知可能在当前操作尚未结束时执行；动画或广告回调则可能晚到。 |

## 这些结论可以相信到什么程度

**已确认（静态证据）**表示字段、分支或调用顺序可以在保留材料中核对。这里的行为结论限定为包内原实现；运行时热补丁系统 IFix 是否替换了它，仍需额外材料。**较强推断**表示证据支持该解释，但还缺调用接线、配置条件或运行实验。**待验证**表示缺口尚未补齐。“没有找到”只描述本次查找范围，不等于游戏没有该功能。

材料包括 563 个 C# 类型结构文件、497 个原生伪 C 文件、10,346 条原生方法记录。索引标记 10,344 条反编译成功、2 条失败，另有 226 条无地址签名。C# 文件主要告诉我们“有哪些字段和方法”，不能当成完整源码；伪 C 也可能失真。例如点击生成器恢复方法需要以 ARM 指令核对，不能照抄其伪 C 的提前返回。[E01](04_证据索引.md#e01)、[E20](04_证据索引.md#e20)

本次覆盖了核心棋盘、合成、生成器、时间、邻接解锁、售出撤销、装配与保存、显示回收；宝箱、气泡和活动只覆盖代表分支或依赖入口。未全审所有技能、奖励、活动、服务器及异步资源回调。目录缺少原配置表、Prefab（预制显示资源）、图集、原安装包和热补丁，因此具体地图尺寸、掉率及美术效果不能独立确认。历史材料的冲突见[E34](04_证据索引.md#e34)。
