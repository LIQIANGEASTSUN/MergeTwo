# Tasty Travels：哪些值得借鉴，哪些需要改造

Tasty Travels 可以帮助我们简化格子和能力的组织，但它的直接调用方式并未解决我们关心的提交、持久保存和回调失效问题。以下评价基于前两篇的实际实现；**建议与假设均不是已经批准的架构决定。**

## 1. 比较之前，先明确我们要解决什么

我方目前已确认的范围是：先验证独立核心棋盘，沿用宿主已有的 Profile 存档，本地规则与保存先行；首期只做售出／删除专用撤销，不做订单。Command／Operation 如何接入、是否建立纯核心程序集、是否独立保存效果集合，仍有推荐和待决部分。

本篇所说的“统一提交”，是先决定整次操作要怎样改变数据，再把这些改变应用出去；它并不自动保证异常时全部撤回，也不等于数据库事务。这个区别在比较我方 AtomicOperation 时尤其重要。

## 2. 哪些可以借鉴，哪些需要改造

### 2.1 轻量格子：可以直接借鉴

格子只记录占用物、格类型和区域，足以支持稠密小棋盘的直接定位。我们可以先采用轻量 Cell，不必让每格都拥有与物品相同的两侧 Function。只有地块确实需要独立移动、生命周期或多格占用时，再升级模型。云覆盖与物品限制分开保存的思路也可保留。

### 2.2 身份与显示生命周期：借鉴分工，补齐回调保护

实例 ID 回答“哪一个”，种类 ID 回答“哪一种”；移动保留原身份和进度，普通合成创建新身份。业务退出和画面回收又是两个时点，合成结果不必等待动画结束。

Tasty 用显示状态机管理拖动、生成和合成冲突，以对象池复用显示对象，并集中解绑、退订和清理。这些做法可以借鉴；代价是新增显示状态必须定义退出和取消规则。**我们还需区分业务资格与视觉互斥，并用绑定版本识别旧回调。** 实例 ID、显示对象仍然存在，都不足以保证动画或广告回调仍属于当前绑定；资源缺失、关闭重开和同 ID 撤销也要覆盖。

### 2.3 有状态能力组件：适合组合，新增能力仍有接入成本

次数、冷却和随机序列应随能力保存；禁止使用不必删除这些数据。Function 可以组织行为，必要的业务 State 仍有价值。查询可用性、显式启用和是否计时应分别定义，不能只用一个“禁用”概念概括。

登记表、配置验证和对象池减少了物品子类，但增加一种类型往往还要接入类型编号、组件位图、存档、点击分派与显示，并负责解绑回池。同类型一份的约束也不会自动支持多来源限制。首期能力较少时可固定装配；确有动态需求，再补完整增删协议。点击的显式优先分支也可先保留，出现真实冲突后再考虑策略化，不能把“已登记”当成“已接入所有入口”。

### 2.4 按动作判断权限：可以借鉴，限制叠加需另定

合成源和目标使用不同条件，解除 locked 又保留 frozen，说明“能否主动拖出”“能否作为合成目标”“能否传播解锁”是不同问题。我们不宜用一个总的 CanInteract 包办，也不能直接把 Tasty 的 frozen 等同我方浅锁。

锁、生成器进度、显示阶段、视觉特效与邻接加速各有不同职责；Effect 这个名字不能把它们合成一套机制。我们应区分玩法效果、操作修改和视觉特效，保留记录事实和阶段的 State。若同一种限制可来自多处，还要增加来源与解除规则；现有布尔标志不会自动汇总它们。

### 2.5 直接业务方法：规则易读，消费与通知顺序需要改造

Board 的方法把普通操作写得直观，但数据修改中穿插通知，还调用外部钱包与奖励。点击生成尤其是先消费、后找格；空格预检并不保证找格成功，当前入口也没有按本次产物种类选格。**这些顺序已确认，正常配置是否会造成损失仍待验证。** 不能直接照搬，再把正确性寄托在未证明的配置条件上。

若采用我们的 Command／Operation 方案，可以保留清晰的规则函数，但先确定费用、次数、随机位置和落点，再在规定位置应用修改；整次修改完成后发布完整变化。同步监听者可能观察半次交换或未完成后处理的合成；有害重入尚未复现。若仍保留中途事件，就必须限制监听者能做什么。

直接调用、小状态机或不用 ECS 本身也不是缺点：规则固定、监听者受控的小棋盘可能更适合简单实现，前提是成功、失败和保存的含义清楚。

### 2.6 环境接口：保留真实边界，移除界面对业务资格的决定

Env 有助于让相同模型接入不同环境，但 Tasty 仍有静态全局对象和规则直读界面的依赖。例如 `CanUnlock` 读取 `BoardViewManager.IsLevelDirty`，无画面运行仍要提供这个条件。

我们应优先隔离时钟、配置、随机、钱包和存档；确需等待的业务事实由逻辑或宿主输入提供，纯动画阶段不直接决定持久权限。给每个内部类添加接口，不能代替这项职责调整。

### 2.7 时间推进：保留机制差异，再选择时间表示

点击型到期补次数，自动型还会尝试落物；库存又采用只推进组件的入口。我们需要明确“到期可用”与“到期产出”，并按机制决定满盘、冻结、库存、离线和容量上限，不能都简化成 Ready 后 Spawn。

累计进度加上最后活动时间可以恢复生成器，不必先把所有机制改成绝对截止时间。需要比较的是长时间差、暂停、倍率到期、产出顺序和秒／毫秒转换的影响；用相同场景比较累计进度与截止时间，再确定我方政策。邻接多来源取最大倍率是 Tasty 的已确认规则，不自动成为我们的选择。

### 2.8 单次售出撤销：范围合适，恢复凭据需适配宿主

保留原物品到单槽，能保住身份和能力进度，无需建立通用操作历史，与我方首期范围接近。Tasty 的窗口受离开棋盘和重新选择物品影响；售出物不由常规世界循环计时，也未进入 Merge 存档。它的原格替位政策还可能只保留被移物的种类，不能直接照搬。

我们仍需决定撤销时限、计时、售价扣回、原格占用和跨关闭恢复。若沿用宿主 Profile，可考虑保存完整实例数据作为恢复凭据，避免仅依赖原对象引用；恢复时同步更新显示绑定版本。这是适配建议，不是已经确定的实现。

## 3. 对照我们的 Entity、Function 和操作流程

这是**职责对照**，不是要求替换成同名类。尤其不能把 Tasty 的一次 Board 方法调用直接等同我方 AtomicOperation。

| 我方概念 | Tasty 中近似承担职责的部分 | 关键差别 |
| --- | --- | --- |
| 业务实体 Entity | Item 持身份、数据与能力；Board／World 是容器，格子较轻量 | Item 仍有 Unity 坐标类型和环境依赖，未证明是纯核心。 |
| 显示绑定 EntityView | MBItemView、Holder 和显示控制器共同承担 | MBItemView 自身是 MonoBehaviour，不等于独立普通 C# 包装对象。 |
| 逻辑 Function | 能力组件、Board 方法、Utility、奖励处理器 | 未定位统一控制器覆盖全部逻辑，修改也未限制在统一 Apply。 |
| 表现 Function | Content／Charge／Animation／Effect 及显示状态 | 与逻辑能力不一一对应，显示组件和状态机共同工作。 |
| 意图 Command | 输入函数和操作分类枚举 | 未定位统一先进先出命令队列；局部输入限制不是排队。 |
| 求解 Consumer | Board／Utility 中分散的校验与计算 | 未证实存在完整只读求解阶段，准备过程中也可能改缓存。 |
| 修改 AtomicOperation／Batch | Board.Merge 等最接近一次业务单位 | 有中间通知和外部副作用；两者都不能仅凭名称保证事务或自动撤销。 |
| Effect／State | 限制标志、能力进度、专用效果和显示阶段并存 | 未见通用多来源效果集合及统一权限汇总，不能据此删除所有 State。 |
| 存档适配 ProfileAdapter | ArchiveMan、IUserDataHolder、Merge 记录 | 原项目协议不同于宿主 Profile；文件写入和钱包一致性仍缺证据。 |
| 退出与绑定版本 Retiring／Generation | 分阶段业务销毁、旧 View 延后回收、局部广告校验 | 未定位统一绑定版本；同 ID 撤销后仍需隔离旧回调。 |

“绑定版本”的用途可以用一个**说明性例子**理解：一段动画结束前，显示对象已被回收并绑定给另一个物品。仅知道显示对象还存在，不足以允许旧回调清理它；回调还需要判断自己是否属于当前这次绑定。Tasty 已有部分引用／宿主检查，但统一机制尚未得到证实。

## 4. 如果增加新能力，现有结构需要改哪里

以下三个场景都是**假设推演，不是该游戏已有功能，也不新增我方首期需求**。它们用来检验“组件可以组合”到底能省哪些工作。

### H1. 自动生成器同时受到两份有期限的冻结

生成行为和普通冻结检查可以复用；问题在于一份冻结到期时，不能直接清 `mIsFrozen`，因为另一份可能仍有效。

| 需要处理的部分 | 修改点与原因 |
| --- | --- |
| 数据与装配 | 在 Item 下增加来源和期限记录，或新增组件并修改 Table／ItemComponentType／Validate；同时解决每类型一份的限制。 |
| 到期触发 | 棋盘只更新 active 物品，冻结后自身倒计时可能也停止；需额外检查受限物的期限，或提供世界层时间入口。 |
| 产出规则 | 明确冻结期间停充能、只禁落物，还是结束后补进度；不能直接套用 OnUpdateInactive。 |
| 存档与迁移 | 保存来源、期限及版本，定义合成和售出撤销是否继承；未知组件处理不能悄悄丢掉仍有效的限制。 |
| 显示与清理 | Content／Charge／View 显示剩余时间和来源数；只解除已到期的一份，关闭时清计时显示和旧回调。 |

最小验证：两份不同期限冻结叠加，先到期一份时仍受限，第二份也能准时结束。现有 active 扫描不能直接保证这一点。

### H2. 地格有锁，物品本身又有气泡

地格限制与气泡属于不同对象，可以复用各自结构；但目前没有证据证明各操作入口都已组合这两种资格，显示优先分支也可能只展示一层。

| 需要处理的部分 | 修改点与原因 |
| --- | --- |
| 数据与配置 | 决定复用 Grid／Area 还是新增持久地格锁；不要又复制成 Item.locked，留下两份可写事实。 |
| 权限与空间 | 逐一明确移动、合成、使用、售出和找格规则，即 GetMoveState／GetMergeState／UseItem／SellItem／FindEmpty 系列。 |
| 解除与继承 | 解地锁不解除气泡，搬物品不带走地锁；合成时另定气泡阻止或继承规则。 |
| 存档与撤销 | 地锁跟格子保存，气泡跟物品保存；恢复物品不能覆盖期间地格的变化。 |
| 显示与取消 | Holder／Content 支持两层遮挡及输入优先级，解除一层不清另一层；原 Prefab 缺失，需补资源验证。 |

最小验证：地锁解除后，气泡仍按自身规则限制合成；另一种情况下搬走物品，地锁仍留在原地。

### H3. 消费一个物品后影响邻格，并继续连锁

可以复用消费奖励处理器 `_DisposeBonusProcess／DisposeBonusHandler` 和生成、合成后处理。需要先选定语义：当前合成在创建新结果后才处理旧物消费奖励，所以邻格效果会看到新结果。

| 需要处理的部分 | 修改点与原因 |
| --- | --- |
| 配置与触发 | 扩展处理器，或新增组件和登记；明确哪些消费原因 ItemDeadType 会触发，不能默认售出也算。 |
| 状态数据 | 若有次数、来源或已触发标记，要加组件存档；一次性效果也需要同次去重信息。 |
| 连锁执行 | 用待处理集合确定顺序、去重和终止，避免事件里无限递归；明确新合成物是否受同次连锁影响。 |
| 保存与失败 | 完成整次连锁后再发布快照；循环配置如何拒绝、失败如何收场需要补协议，现有路径未证明能回滚。 |
| 动画与销毁 | 提前复制显示所需数据；旧组件即将释放，晚到动画不能再读取其可变状态。 |

最小验证：相邻两物互相触发时，每个本次最多被消费一次，连锁能够结束；取消所有动画后，业务结果与正常播放相同。

## 5. 尚待验证的问题

以下保留真正影响方案判断的缺口。静态代码能够确认的部分已归入正文；实验尚未执行。

### V01：实际配置和资源是否与当前分支匹配——待验证

原表、Prefab 和热补丁未保留，历史记录的 7×9 等数值不能独立复算。最小补充是目标 BoardBasic、代表生成器表、相应资源绑定及 IFix 清单。这决定地图、显示及“晚查落点仍不会失败”等配置前提是否成立。

### V02：点击失败会不会消耗资源却没有产物——风险为较强推断

先消费、后找格已确认，正常配置能否进入失败分支未知。构造只剩非默认格空位、或无费用生成器满盘使用的情况，记录余额、次数、随机位置、返回码和产物；同时核对外围入口与配置是否排除这些状态。这决定求解与提交顺序是否需要改。

### V03：中途通知会不会让其它系统看到不完整状态——风险为较强推断

给移动／离开事件添加只读观察者，记录物品与格的相互关系；再受控地尝试嵌套操作，检查会被拒绝、排队还是直接执行。这影响事件扩展和稳定快照的发布时点，不能仅凭存在事件认定已发生故障。

### V04：保存何时真正成功——待验证

已定位汇总与上传，尚未贯通文件写入。沿 `_SaveArchiveData／UploadHelper` 补到文件 API，再做一次终止进程后重开，区分内存里有记录与磁盘里已保存。这决定宿主 Profile 适配应以什么作为成功信号。

### V05：一次补很长时间与逐秒推进是否一致——待验证

用同一初态比较两种推进方式，覆盖满盘、腾出一格、冻结、库存、隐藏、倍率到期和时钟倒退；恢复分支还要覆盖约 12.43 天的数值上限。充能上限、落物和时间分段都可能影响结果；实验用于确定时间政策及可复现性。

### V06：旧回调会不会影响重新绑定后的物品——待验证

已有显示清理和局部广告检查，未定位统一绑定版本。测试动画中关闭重开、显示对象回池换绑、售出后同 ID 撤销、广告迟到，观察是否误改新物或释放新 View。这决定回调保护需要覆盖哪些生命周期。

### V07：售出与独立删除的边界是否还有遗漏——待验证

离开棋盘和选中现存物品的清槽、常规循环不推进售出物、Merge 不保存售出槽均已确认。还需核对独立删除按钮是否复用此逻辑，以及外部调用／热补丁是否增加处理；运行检查清槽后的资源释放、余额不足和原格被占的恢复结果。这影响我方撤销范围与恢复凭据。

### V08：旧档、未知类型和坏坐标怎样处理——待验证

存在组件位图和配置版本，不代表兼容政策完整。补查 Deserialize 的版本替换分支，再构造未知种类、未知组件位和重复坐标，观察拒绝、修复与再次保存结果。这决定首版存档格式及遇错时是否停止加载。

### V09：解锁动画被打断时是否清理完整——待验证

DelayUnlockState 的创建和设置可定位，完整方法体缺失。补它的进入、离开与更新时间方法，或做最小解锁中断录制和日志，确认逻辑已解锁但遮挡仍在时的输入与资源释放。

### V10：哪些加速结构实际生效——待验证

通用时间工具原样返回输入，邻接倍率另行应用。邻接多来源取最大倍率已确认；还需核对热补丁、实际配置及来源移动／到期后的缓存刷新，才能判断哪些结构在当前版本实际使用。这影响是否借用其效果表示。

### V11：客户端计算与服务器校验怎样分工——待验证

客户端本地求解和外部钱包／保存接口可见，服务端实现不可见。只有确有接入需求时才补协议及服务端校验材料。不能由客户端有算法断言服务器不具权威，我方本地先行也不等于复刻它的网络协议。
