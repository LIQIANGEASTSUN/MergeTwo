# Tasty Travels：哪些值得借鉴，哪些需要改造

本篇讨论对我们有什么用。依据是前两篇还原的实现，**建议和假设都不是已经批准的架构决定**。分析对象为 Tasty Travels 64.0.0，仅做静态分析；事实、推断和待验证问题的定义见 [总览](README.md)。

## 1. 比较之前，先明确我们要解决什么

我方目前已确认的范围是：先验证独立核心棋盘，沿用宿主已有的 Profile 存档，本地规则与保存先行；首期只做售出／删除专用撤销，不做订单。Command／Operation 如何接入、是否建立纯核心程序集、是否独立保存效果集合，仍有推荐和待决部分。[E35](04_证据索引.md#e35)

Tasty 对我们最有价值的启发有两方面：**格子和能力可以做得简单；但一次操作的修改边界、保存和旧回调仍需要明确规则。** 下面分别说明可以借用什么，以及采用它要承担什么条件。评价依据见 [实际模型](01_架构与数据模型.md) 和 [完整流程](02_功能扩展与执行流程.md)。

本篇所说的“统一提交”，是先决定整次操作要怎样改变数据，再把这些改变应用出去；它并不自动保证异常时全部撤回，也不等于数据库事务。这个区别在比较我方 AtomicOperation 时尤其重要。[E12](04_证据索引.md#e12)、[E13](04_证据索引.md#e13)、[E19](04_证据索引.md#e19)、[E35](04_证据索引.md#e35)

## 2. 可以直接借鉴的设计思想

这里的“直接借鉴”指采用思想，不是复制反编译代码。

### 2.1 格子可以只保存必要信息

Tasty 的格子记录占用物、格类型和区域，就能支持稠密小棋盘的直接定位。**对我们，可先采用轻量 Cell，不必让每个格子都拥有和物品一样的两侧 Function。** 只有当某类地块真的需要独立移动、生命周期或多格占用时，再考虑升级模型。[E02](04_证据索引.md#e02)、[E03](04_证据索引.md#e03)、[E04](04_证据索引.md#e04)、[E05](04_证据索引.md#e05)

### 2.2 “哪个物品”与“哪种物品”分开

Item.id 保持实例身份，tid 表示种类；移动生成器可以继续保留原进度，合成则建立新身份。我们也需要这一区别。不过实例 ID 只能说明是谁，不能独自证明一条晚到的回调仍属于它当前这次显示绑定。**实例 ID、配置 ID 和运行绑定版本应视为不同问题。**[E06](04_证据索引.md#e06)、[E07](04_证据索引.md#e07)、[E12](04_证据索引.md#e12)

### 2.3 禁止使用能力，不必删除它的进度

能力组件保存次数、冷却和随机序列，禁用状态与组件是否存在分开。对我们，这意味着 Function 可以组织行为，必要的业务 State 仍有保存价值；不应仅为上锁就删除生成器并丢掉进度。适用条件是明确谁能修改这些数据，同时注意 Tasty 同类型只有一份组件的限制。[E09](04_证据索引.md#e09)、[E20](04_证据索引.md#e20)、[E27](04_证据索引.md#e27)

### 2.4 按具体动作判断权限

Tasty 的合成源与目标条件不同，解除锁也保留冻结。因此，“不能主动拖出”与“不能被合成进去”应分别查询，而不是一个总的 CanInteract 包办。我们可以借鉴这种意图区分，但不能直接把它的 frozen 等同我方浅锁；各动作语义仍由我们的规则决定。[E11](04_证据索引.md#e11)、[E17](04_证据索引.md#e17)

### 2.5 业务退出与画面收尾分开

合成结果不等待动画完成，旧物品的画面可以继续收尾。对我们，可分别定义“已不参与棋盘规则”和“显示资源已释放”两个时点。采用这种分工后，仍要处理动画取消、资源缺失和旧回调，不能把这些工作省略。[E07](04_证据索引.md#e07)、[E14](04_证据索引.md#e14)、[E15](04_证据索引.md#e15)

### 2.6 补充次数与主动生成分开

点击生成器冷却后补次数，自动生成器还要主动找格落物。两者在满盘和离线时的含义不同。我们也应分别定义时间事件：到期是恢复可用次数，还是要求立即产出，不能都简化成“Ready 后 Spawn”。容量上限和离线补发政策随机制确定。[E20](04_证据索引.md#e20)、[E21](04_证据索引.md#e21)

## 3. 有价值，但需要条件或改造

### 3.1 组件登记表：省下子类，增加了装配责任

Table＋配置验证＋对象池能减少“每种物品一套子类”，也支持动态能力。代价是新增类型常常要同时修改编号、组件位图、配置、存档、点击分派和显示，并保证解绑与回池完整。**若首期能力很少，可以先固定装配；确有动态需求再补完整登记与移除协议。**[E08](04_证据索引.md#e08)、[E09](04_证据索引.md#e09)

### 3.2 直接业务方法：容易追踪，但要管住副作用

Board.Merge 等方法把普通操作写得很直观。问题在于修改之间夹着事件，还连接钱包、奖励和界面条件。我们可以保留清楚的规则函数；若采用 Command／Operation 方案，再让这些函数先求出完整结果，把数据修改和通知放到规定的提交位置。这样借用的是规则组织方式，而不是照搬全部调用关系。[E12](04_证据索引.md#e12)、[E19](04_证据索引.md#e19)、[E21](04_证据索引.md#e21)、[E30](04_证据索引.md#e30)

### 3.3 环境接口：只隔离真正的外部依赖

Env 让同一模型接入不同棋盘环境，有复用价值；但静态全局对象和直接读取 View 又削弱了替换能力。对我们，优先隔离时钟、配置、随机、钱包、存档等真实边界即可。每个内部类都加接口，并不能解决仍然直读界面的规则。[E26](04_证据索引.md#e26)、[E31](04_证据索引.md#e31)

### 3.4 单次售出撤销：范围合适，恢复语义要另定

保留原物品到一个暂存槽，就不必建立所有操作的历史，组件进度也自然保留。这与我们首期专用撤销的范围接近。需要另定的是：能撤销多久、期间是否计时、售价如何扣回、原格被占怎么办，以及重开后还保不保留。若采用宿主 Profile，可以考虑保存完整实例数据作为恢复凭据，而不是依赖原对象引用；恢复时还要更新显示绑定版本。[E30](04_证据索引.md#e30)、[E35](04_证据索引.md#e35)

### 3.5 累计时间：可保存，但长时间间隔要验证

组件累计进度，世界保存上次活动时间，这套方式可以恢复不同阶段的生成器。代价是长时间差、暂停、容量、倍率到期和产出顺序会互相影响，秒与毫秒转换还有精度问题。我们不必先把一切改成绝对截止时间；可用同一组机制对比“累计进度”和“截止时间”，再决定时间政策。[E20](04_证据索引.md#e20)、[E25](04_证据索引.md#e25)、[E28](04_证据索引.md#e28)

### 3.6 显示状态机与对象池：集中清理很有用

显示状态机管理拖动、生成和合成冲突，对象池减少重复创建，ClearData 和 Cleanup 集中解绑、退订与回收。代价是每种新增状态都需要退出和取消规则，而且这里的显示阶段还会影响输入。我们可以保留小型显示状态机，同时把业务资格与视觉互斥分清，统一检查晚到回调是否仍有效。[E14](04_证据索引.md#e14)、[E15](04_证据索引.md#e15)

## 4. 不建议照搬的做法，以及具体原因

### 4.1 用界面状态决定业务资格

`CanUnlock` 读取 `BoardViewManager.IsLevelDirty`，这是**已确认的依赖**。隐藏界面或做无画面测试时，业务仍要提供这个界面条件。对我们，确实需要等待的业务事实应由逻辑或宿主输入提供；纯动画阶段不应直接决定持久权限。[E17](04_证据索引.md#e17)

### 4.2 消费后才确认具体产物能放哪里

点击生成的顺序已确认，但损失尚未复现。粗空位数不等于指定产物的可用格，因此这套实现可能依赖配置保证“晚查也不会失败”。对我们，候选结果应一并确定费用、次数、随机位置和落点，提交前共同检查。是否能复用原顺序，必须先证明这些配置条件始终成立。[E19](04_证据索引.md#e19)

### 4.3 操作做到一半就把对象交给监听者

交换和合成中途发通知是事实；有害重入则是风险推断。监听者可能看到半次交换，或两个旧物已消费而后处理未结束的棋盘。若我们需要稳定快照或允许扩展订阅，应在整次修改完成后发布完整变化；如果仍采用中途事件，则必须明确监听者能做什么。[E07](04_证据索引.md#e07)、[E12](04_证据索引.md#e12)、[E13](04_证据索引.md#e13)

### 4.4 每加一种点击能力都增加固定分支

固定顺序在能力少时清楚可控；能力变多、同一物品有多种用途时，维护者需要知道隐藏的优先关系。首期仍可保留显式分派，等真实冲突出现再考虑策略化；不能因有登记表，就认为新能力已经接入所有入口。[E18](04_证据索引.md#e18)

### 4.5 把所有 Effect 都解释成同一种玩法效果

这是阅读和建模时的**概念误用风险**，不是对原项目命名的全面否定。MBItemEffect 负责视觉，气泡有业务寿命，SpeedEffect 的字段又不保证通用速度路径实际生效。我们应区分玩法效果、操作修改和视觉特效，同时保留记录事实及阶段的 State。[E16](04_证据索引.md#e16)、[E23](04_证据索引.md#e23)、[E24](04_证据索引.md#e24)

以上问题不表示直接调用、小状态机或不用 ECS 就是缺点。小棋盘、固定规则、受控监听者可以让简单实现更划算；但保存成功的含义和回调有效性仍需明确。

## 5. 对照我们的 Entity、Function 和操作流程

这是**职责对照**，不是要求替换成同名类。尤其不能把 Tasty 的一次 Board 方法调用直接等同我方 AtomicOperation。

| 我方概念 | Tasty 中近似承担职责的部分 | 关键差别 |
| --- | --- | --- |
| 业务实体 Entity | Item 持身份、数据与能力；Board／World 是容器，格子较轻量 | Item 仍有 Unity 坐标类型和环境依赖，未证明是纯核心。[E02](04_证据索引.md#e02)、[E06](04_证据索引.md#e06)、[E31](04_证据索引.md#e31) |
| 显示绑定 EntityView | MBItemView、Holder 和显示控制器共同承担 | MBItemView 自身是 MonoBehaviour，不等于独立普通 C# 包装对象。[E15](04_证据索引.md#e15) |
| 逻辑 Function | 能力组件、Board 方法、Utility、奖励处理器 | 未定位统一控制器覆盖全部逻辑，修改也未限制在统一 Apply。[E08](04_证据索引.md#e08)—[E12](04_证据索引.md#e12)、[E18](04_证据索引.md#e18) |
| 表现 Function | Content／Charge／Animation／Effect 及显示状态 | 与逻辑能力不一一对应，显示组件和状态机共同工作。[E14](04_证据索引.md#e14)—[E16](04_证据索引.md#e16) |
| 意图 Command | 输入函数和操作分类枚举 | 未定位统一先进先出命令队列；局部输入限制不是排队。[E18](04_证据索引.md#e18)、[E31](04_证据索引.md#e31) |
| 求解 Consumer | Board／Utility 中分散的校验与计算 | 未证实存在完整只读求解阶段，准备过程中也可能改缓存。[E11](04_证据索引.md#e11)、[E19](04_证据索引.md#e19) |
| 修改 AtomicOperation／Batch | Board.Merge 等最接近一次业务单位 | 有中间通知和外部副作用；两者都不能仅凭名称保证事务或自动撤销。[E12](04_证据索引.md#e12)—[E13](04_证据索引.md#e13)、[E19](04_证据索引.md#e19)、[E35](04_证据索引.md#e35) |
| Effect／State | 限制标志、能力进度、专用效果和显示阶段并存 | 未见通用多来源效果集合及统一权限汇总，不能据此删除所有 State。[E09](04_证据索引.md#e09)、[E17](04_证据索引.md#e17)、[E23](04_证据索引.md#e23)—[E24](04_证据索引.md#e24) |
| 存档适配 ProfileAdapter | ArchiveMan、IUserDataHolder、Merge 记录 | 原项目协议不同于宿主 Profile；文件写入和钱包一致性仍缺证据。[E27](04_证据索引.md#e27)—[E29](04_证据索引.md#e29) |
| 退出与绑定版本 Retiring／Generation | 分阶段业务销毁、旧 View 延后回收、局部广告校验 | 未定位统一绑定版本；同 ID 撤销后仍需隔离旧回调。[E07](04_证据索引.md#e07)、[E14](04_证据索引.md#e14)—[E15](04_证据索引.md#e15)、[E30](04_证据索引.md#e30)、[E32](04_证据索引.md#e32) |

“绑定版本”的用途可以用一个**说明性例子**理解：一段动画结束前，显示对象已被回收并绑定给另一个物品。仅知道显示对象还存在，不足以允许旧回调清理它；回调还需要判断自己是否属于当前这次绑定。Tasty 已有部分引用／宿主检查，但统一机制尚未得到证实。[E15](04_证据索引.md#e15)、[E32](04_证据索引.md#e32)

## 6. 如果增加新能力，现有结构需要改哪里

以下三个场景都是**假设推演，不是该游戏已有功能，也不新增我方首期需求**。它们用来检验“组件可以组合”到底能省哪些工作。

### H1. 自动生成器同时受到两份有期限的冻结

生成行为和普通冻结检查可以复用；问题在于一份冻结到期时，不能直接清 `mIsFrozen`，因为另一份可能仍有效。[E11](04_证据索引.md#e11)、[E21](04_证据索引.md#e21)、[E25](04_证据索引.md#e25)

| 需要处理的部分 | 修改点与原因 |
| --- | --- |
| 数据与装配 | 在 Item 下增加来源和期限记录，或新增组件并修改 Table／ItemComponentType／Validate；同时解决每类型一份的限制。 |
| 到期触发 | 棋盘只更新 active 物品，冻结后自身倒计时可能也停止；需额外检查受限物的期限，或提供世界层时间入口。 |
| 产出规则 | 明确冻结期间停充能、只禁落物，还是结束后补进度；不能直接套用 OnUpdateInactive。 |
| 存档与迁移 | 保存来源、期限及版本，定义合成和售出撤销是否继承；未知组件处理不能悄悄丢掉仍有效的限制。 |
| 显示与清理 | Content／Charge／View 显示剩余时间和来源数；只解除已到期的一份，关闭时清计时显示和旧回调。 |

最小验证：两份不同期限冻结叠加，先到期一份时仍受限，第二份也能准时结束。现有 active 扫描不能直接保证这一点。

### H2. 地格有锁，物品本身又有气泡

地格限制与气泡属于不同对象，可以复用各自结构；但目前没有证据证明各操作入口都已组合这两种资格，显示优先分支也可能只展示一层。[E02](04_证据索引.md#e02)、[E05](04_证据索引.md#e05)、[E11](04_证据索引.md#e11)、[E16](04_证据索引.md#e16)、[E23](04_证据索引.md#e23)

| 需要处理的部分 | 修改点与原因 |
| --- | --- |
| 数据与配置 | 决定复用 Grid／Area 还是新增持久地格锁；不要又复制成 Item.locked，留下两份可写事实。 |
| 权限与空间 | 逐一明确移动、合成、使用、售出和找格规则，即 GetMoveState／GetMergeState／UseItem／SellItem／FindEmpty 系列。 |
| 解除与继承 | 解地锁不解除气泡，搬物品不带走地锁；合成时另定气泡阻止或继承规则。 |
| 存档与撤销 | 地锁跟格子保存，气泡跟物品保存；恢复物品不能覆盖期间地格的变化。 |
| 显示与取消 | Holder／Content 支持两层遮挡及输入优先级，解除一层不清另一层；原 Prefab 缺失，需补资源验证。 |

最小验证：地锁解除后，气泡仍按自身规则限制合成；另一种情况下搬走物品，地锁仍留在原地。

### H3. 消费一个物品后影响邻格，并继续连锁

可以复用消费奖励处理器 `_DisposeBonusProcess／DisposeBonusHandler` 和生成、合成后处理。需要先选定语义：当前合成在创建新结果后才处理旧物消费奖励，所以邻格效果会看到新结果。[E07](04_证据索引.md#e07)、[E12](04_证据索引.md#e12)、[E13](04_证据索引.md#e13)

| 需要处理的部分 | 修改点与原因 |
| --- | --- |
| 配置与触发 | 扩展处理器，或新增组件和登记；明确哪些消费原因 ItemDeadType 会触发，不能默认售出也算。 |
| 状态数据 | 若有次数、来源或已触发标记，要加组件存档；一次性效果也需要同次去重信息。 |
| 连锁执行 | 用待处理集合确定顺序、去重和终止，避免事件里无限递归；明确新合成物是否受同次连锁影响。 |
| 保存与失败 | 完成整次连锁后再发布快照；循环配置如何拒绝、失败如何收场需要补协议，现有路径未证明能回滚。 |
| 动画与销毁 | 提前复制显示所需数据；旧组件即将释放，晚到动画不能再读取其可变状态。 |

最小验证：相邻两物互相触发时，每个本次最多被消费一次，连锁能够结束；取消所有动画后，业务结果与正常播放相同。

## 7. 哪些问题还不能下结论，怎样最小化补证

这些编号用于后续追踪。每项说明缺什么、最小验证方法和它影响哪项选择，无需把整包重新反编译才能开始。

<a id="v01"></a>

### V01：实际配置和资源是否与当前分支匹配——待验证

原表、Prefab 和热补丁未保留，历史记录的 7×9 等数值不能独立复算。最小补充是目标 BoardBasic、代表生成器表、相应资源绑定及 IFix 清单。这决定地图、显示及“晚查落点仍不会失败”等配置前提是否成立。[E01](04_证据索引.md#e01)、[E34](04_证据索引.md#e34)

<a id="v02"></a>

### V02：点击失败会不会消耗资源却没有产物——风险为较强推断

先消费、后精确找格已确认，正常配置能否进入失败分支未知。构造有空格但均不接纳产物的棋盘，记录余额、次数、随机位置、返回码和产物；同时核对生产配置是否禁止该状态。这决定求解与提交顺序是否需要改。[E19](04_证据索引.md#e19)

<a id="v03"></a>

### V03：中途通知会不会让其它系统看到不完整状态——风险为较强推断

给移动／离开事件添加只读观察者，记录物品与格的相互关系；再受控地尝试嵌套操作，检查会被拒绝、排队还是直接执行。这影响事件扩展和稳定快照的发布时点，不能仅凭存在事件认定已发生故障。[E07](04_证据索引.md#e07)、[E12](04_证据索引.md#e12)、[E13](04_证据索引.md#e13)

<a id="v04"></a>

### V04：保存何时真正成功——待验证

已定位汇总与上传，尚未贯通文件写入。沿 `_SaveArchiveData／UploadHelper` 补到文件 API，再做一次终止进程后重开，区分内存里有记录与磁盘里已保存。这决定宿主 Profile 适配应以什么作为成功信号。[E29](04_证据索引.md#e29)

<a id="v05"></a>

### V05：一次补很长时间与逐秒推进是否一致——待验证

用同一初态比较两种推进方式，覆盖满盘、腾出一格、冻结、隐藏、倍率到期和时钟倒退。充能上限、落物和时间分段都可能影响结果；实验用于确定时间政策及可复现性。[E20](04_证据索引.md#e20)、[E21](04_证据索引.md#e21)、[E22](04_证据索引.md#e22)、[E23](04_证据索引.md#e23)、[E24](04_证据索引.md#e24)、[E25](04_证据索引.md#e25)

<a id="v06"></a>

### V06：旧回调会不会影响重新绑定后的物品——待验证

已有显示清理和局部广告检查，未定位统一绑定版本。测试动画中关闭重开、显示对象回池换绑、售出后同 ID 撤销、广告迟到，观察是否误改新物或释放新 View。这决定回调保护需要覆盖哪些生命周期。[E14](04_证据索引.md#e14)、[E15](04_证据索引.md#e15)、[E32](04_证据索引.md#e32)

<a id="v07"></a>

### V07：售出撤销的窗口和边界到底是什么——待验证

售出暂存物未出现在 Merge 存档字段中，所有清槽入口也未追完。继续查 `SetSoldItem` 调用者和独立删除按钮，并测试关闭、选中新物、余额花完和原格被占的情况。这关系到撤销持续多久、是否计时以及如何恢复。[E28](04_证据索引.md#e28)、[E29](04_证据索引.md#e29)、[E30](04_证据索引.md#e30)

<a id="v08"></a>

### V08：旧档、未知类型和坏坐标怎样处理——待验证

存在组件位图和配置版本，不代表兼容政策完整。补查 Deserialize 的版本替换分支，再构造未知种类、未知组件位和重复坐标，观察拒绝、修复与再次保存结果。这决定首版存档格式及遇错时是否停止加载。[E27](04_证据索引.md#e27)、[E28](04_证据索引.md#e28)

<a id="v09"></a>

### V09：解锁动画被打断时是否清理完整——待验证

DelayUnlockState 的创建和设置可定位，完整方法体缺失。补它的进入、离开与更新时间方法，或做最小解锁中断录制和日志，确认逻辑已解锁但遮挡仍在时的输入与资源释放。[E17](04_证据索引.md#e17)

<a id="v10"></a>

### V10：哪些加速结构实际生效——待验证

通用时间工具原样返回输入，邻接倍率另行应用。需要核对热补丁、实际配置和邻接多来源倍率合并，才能区分活跃机制与遗留结构；这影响是否借用其效果表示。[E24](04_证据索引.md#e24)

<a id="v11"></a>

### V11：客户端计算与服务器校验怎样分工——待验证

客户端本地求解和外部钱包／保存接口可见，服务端实现不可见。只有确有接入需求时才补协议及服务端校验材料。不能由客户端有算法断言服务器不具权威，我方本地先行也不等于复刻它的网络协议。[E19](04_证据索引.md#e19)、[E29](04_证据索引.md#e29)、[E30](04_证据索引.md#e30)、[E31](04_证据索引.md#e31)

历史材料的合成顺序和地图数值冲突集中在[E34](04_证据索引.md#e34)；点击恢复伪 C 的失真见[E20](04_证据索引.md#e20)；加速效果的真实路径见 [效果与状态](02_功能扩展与执行流程.md#effect-state)。
