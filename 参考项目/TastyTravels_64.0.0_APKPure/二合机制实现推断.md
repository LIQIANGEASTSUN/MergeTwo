# 二合机制实现推断（Tasty & Travels 64.0.0）

本文是对本目录内 IL2CPP metadata、ARM 原生指令及 Ghidra 伪 C 的**人工分析**，不是原始 C#，也不是本项目拟采用的玩法方案。以下说的“默认路径”是安装包里能读到的本地实现；IFix 热修复分支可替换该路径。C# `scripts/` 中的空方法和固定返回值是工具占位，不能作为逻辑证据。RVA 可在 `native_method_index.csv` 中查到，并用 `native_disassembly.s` 复核。

## 常规两物合成：高可信默认路径

1. `Board.CanMerge(src, dst)` 的普通分支调用 `ItemUtility.GetMergeState(src, dst)`，只把 `MergeState.CanMerge == 0` 视为可合成。参见 `Board.c` RVA `0x20d8e2c` 和 `ItemUtility.c` RVA `0x2154ab0`。
2. `GetMergeState` 检查源与目标不是同一实例，气泡/冻结情况、目标格限制、技能状态，以及双方是否有合成组件；还检查死亡、激活、锁定和云状态。实际的 `MergeState` 枚举里 `HasBubble` 和 `TeslaInUse` 都是数值 `1`，不能仅凭返回数值判定是哪一种拒绝原因。参见 `scripts/asmdef_fat_runtime/FAT/Merge/MergeState.cs`。
3. `ItemMergeComponent.OnPostAttach` 将 `mNext` 设置为 `ItemUtility.GetNextItem(item.tid)`。普通 `PeekMergeResult(srcTid, dstTid, ...)` 在两者 tid 相同且满足技能条件时返回 `mNext`，否则返回 `0`。`GetNextItem` 从物品配置/序列读取后继类型。参见 `ItemMergeComponent.c` RVA `0x211f430`、`0x211f4e4`，以及 `ItemUtility.c` RVA `0x2157970`。两侧技能类型同为 `8` 时存在特殊分支；其业务名称和意图尚不能仅由此确定。
4. `Board.Merge` 调用目标物品合成组件的 `PeekMergeResult`。结果 tid 大于 `0` 才继续：取目标坐标，依次 `_DisposeItem` 两个旧物品、执行对应消耗后处理，在目标格 `_SpawnItem` 生成结果，执行生成奖励处理、`Item.ProcessPostMerge`、相邻解锁检查，最后触发 `onItemMerge(src, dst, result)` 事件。参见 `Board.c` RVA `0x20d8eac`；事件签名见 `Board.cs`。

由此可推断，普通升级链主要由 **tid 到后继 tid 的配置关系** 驱动；棋盘控制实例的销毁与新建，组件和奖励处理器补充特殊效果。具体哪些物品能互合、每条链的内容及奖励数值需要配置值验证。

## 移动、生成与解锁

- `Board.GetMoveState` 返回 `MoveState`（可移动、目标不可移动、格子不允许、物品不允许、未知）；`Board.MoveItem` 仅在 `CanMove` 时移动，并对被占用且可移动的目标执行交换路径。参见 `Board.c` RVA `0x20d9788`、`0x20d9a78` 和 `scripts/asmdef_fat_runtime/FAT/Merge/MoveState.cs`。拖拽落在物品上是否触发合成由上层动作分类选择，不等同于所有 `MoveItem` 都会合成。
- `Board.TrySpawnItem` 查找空格、换算行列、调用 `_SpawnItem`，再调用 `_SpawnBonusProcess` 与生成事件。点击产出器、自动产出器、宝箱也会查找可用格、消耗下一物品类型、生成实例并记录产出原因；其可用性、消耗次数/能量和冷却由各组件控制。参见 `Board.c` RVA `0x20d2888`、`0x20d3924`、`0x20d5a54`、`0x20d6034`。
- 合成后的 `_TriggerUnlockAround` 逐一检查上、下、左、右四邻格。`_UnlockItem` 先调用 `ItemUtility.CanUnlock`，再更新 `Item.SetState`；满足 `Item.CanUnlockAround` 时继续递归检查邻格。因此邻接解锁可能连锁传播，但哪些物品满足条件仍依赖配置与状态。参见 `Board.c` RVA `0x20d1bbc`、`0x20dc760`。

## 状态保存

`Item.Serialize` 写入物品 ID、tid、状态、坐标、组件位标记，并调用各组件序列化；`Deserialize` 执行对应恢复。`MergeWorld.Serialize/Deserialize` 处理 `fat.gamekitdata.Merge`，其中有 `Items`、背包、奖励列表、云、随机参数、配置版本及其他系统状态。参见 `Item.c` RVA `0x2107de4`、`0x210828c`；`MergeWorld.c` RVA `0x2137b80`、`0x213a9e8`；协议字段见 `scripts/asmdef_conf_fat/fat/gamekitdata/MergeItem.cs`、`Merge.cs`。这说明棋盘物品及产出器状态有明确的持久化数据结构；存档触发时机和服务端校验方式尚未确认。

## 解析仍可推进的部分与边界

- **可继续解析**：用 `native_method_index.csv` 把伪 C 中 `func_0x...` 映射回类/方法；给重点函数补 IL2CPP 类型与字段偏移；逐项复核 ARM 指令；追踪 `_CheckDragBehaviour`、组件产出表、奖励处理器以及存档调用者。这样可以形成更接近原始控制流的人工注释或结构化流程图，但不能把它称作原始 C#。
- **需谨慎**：现有 Ghidra 导出使用 `-noanalysis`，少数方法被误标成 `void` 或得到错误局部变量类型。例如 `ItemMergeComponent.PeekMergeResult` 的 metadata 签名为 `int`，相关伪 C 的一个重载却被推成 `void`；判断返回值须以签名、调用方和指令交叉核对。
- **未能确定**：包内配置值加密；IFix 热修复可覆盖默认路径；服务端/动态下载代码未知。因此无法仅凭本包确定完整升级链、产出概率、经济数值、活动特殊规则在实际运行时的最终取值，也不能保证本地默认路径始终执行。

**结论**：可以较高把握推断其二合实现为“拖拽动作分类 → 棋盘判定 → 配置与组件决定结果 → 销毁两物并在目标格生成新物 → 奖励/解锁/事件 → 状态序列化”的结构；具体配置和所有运行时覆盖仍需后续证据。

## 进一步核对：拖拽落点如何选动作

`MergeHelper._FillAffectedArea` 为指针附近四个候选格建立记录并排序，`CheckDragBehaviour` 遍历有效候选格、取格内物品，跳过与被拖动物品相同的实例。它的默认路径按顺序尝试以下判定：`Board.CanMerge` → `ItemUtility.CanConsume` → `CanMix` → `CanFeed` → 条件允许时 `CanStack` → `CanUseForTarget`。这说明“拖到另一个物品上”可能触发多种行为，不能把所有重叠当作二合。证据：`MergeHelper.c` RVA `0x1e17ba8`、`0x1e181b8`；`ItemComponentType.Skill = 11`，见 `ItemComponentType.cs`。

`MBBoardDrag.EndDrag` 根据 `MergeHelper.MergeAction` 分流，可直接确认：

| 动作值 | 名称 | 默认路径中的关键执行调用 |
| --- | --- | --- |
| 1 | `Merge` | `Board.Merge` |
| 2 | `Consume` | `Board.UseClickItemSourceWithConsume` |
| 3 | `Mix` | `Board.MixSourceConsume`，成功后可能调用 `Board.MixSourceProduce` |
| 4 | `Inventory` | `BoardViewManager._TryPutInInventory` |
| 5 | `Feed` | `ItemUtility.FeedItem` |
| 6 | `Skill` | 技能类型分支及相关 UI/物品使用流程；具体子类行为还需逐项核对 |
| 7 | `Stack` | `ItemUtility.StackToTarget` |
| 8 | `Custom` | 自定义事件分发 |

证据：`MBBoardDrag.c` RVA `0x1de9cb0`，枚举见 `MergeHelper.cs`；函数名用 `native_method_index.csv` 对匿名调用地址交叉映射。候选格的精确屏幕半径仍含 UI 常量和缩放，需要进一步核对；不在此把它等同于固定棋盘格半径。

## 进一步核对：产出来源和随机序列

`ItemSourceComponentBase.ConsumeNextOutput(out ItemSourceType, bool)` 的默认路径按不同来源选结果。结合 `ItemSourceType.cs` 和类字段，可辨认固定物品、固定类别、顺序列表、受约束随机列表及权重随机等分支。`ItemClickSourceComponent.ConsumeNextItem` 还关联能量加成、产出次数/充能、输出上限和产出预计算；`Board.UseClickItemSourceWithConsume` 在输出前检查可用格并在输出后调用生成奖励处理。证据：`ItemSourceComponentBase.c` RVA `0x2114444`；`ItemClickSourceComponent.c` RVA `0x2113c00`；`Board.c` RVA `0x20d3924`。

`ItemOutputRandomList` 维护随机列表、种子和下一个下标。`PeekNext` 在列表耗尽时生成新种子并重新生成列表，`TakeNext` 使下标前进；`SetParam(seed, outputedCount)` 能重建该状态。协议 `ComClickSource`、`ComAutoSource` 与 `RandomOutputParam` 都含 `RandomSeed` 和 `RandomNextIdx`；`MergeWorld.Serialize` 调用相应 getter，`Deserialize` 调用 `ItemOutputRandomList.SetParam`。因此**默认路径的随机产出是带进度的序列，而非每次读取存档后从零开始**。具体抽样权重、固定次数约束和实际种子值仍取决于加密配置。证据：`ItemOutputRandomList.c` RVA `0x2142ab4`、`0x214345c`、`0x214359c`、`0x213c448`，以及 `native_direct_calls.csv` 中 `MergeWorld.Serialize/Deserialize` 的直接调用。

## 进一步核对：合成后的组件状态和额外奖励

`Item.ProcessPostMerge` 遍历新结果物品的组件并触发每个组件的 `OnPostMerge(src,dst)`，所以合成不只改变 tid。`ItemClickSourceComponent.OnPostMerge` 的默认路径在源与目标非冻结且具点击产出组件时，读取双方 `itemCount + itemInRechargeCount`，将新组件的 `mItemCount` 至少提高到双方总和；`ItemAutoSourceComponent.OnPostMerge` 则以双方 `itemCount` 之和更新新组件的 `mItemCount` 下限。两者都还调用组件基类后处理。证据：`Item.c` RVA `0x2108c0c`；`ItemClickSourceComponent.c` RVA `0x2115c50`；`ItemAutoSourceComponent.c` RVA `0x210ca9c`；字段偏移在 Il2CppDumper 原始类型转储中核对：点击组件 `mItemCount +0x54`、自动组件 `mItemCount +0x40`；该完整转储因含大量无关类型已移除。这解释了升级产出器时，旧产出器状态可能部分转移到新物品；转移的完整业务规则仍需逐组件核对。

`Board.Merge` 在生成结果后依次调用 `Item.ProcessPostMerge`、合成奖励处理器、四邻解锁与 `onItemMerge`。`ConfigMergeBonusHandler` 的默认路径读取结果 tid 对应的 `ObjMergeItem.MergeBonus` 列表并处理其中条目；还有气泡、冻结、保底、分数等独立奖励处理器。生成奖励另按 `SpawnBonusContext.reason` 分发：基础物品生成奖励处理器的默认路径只处理 `ClickSource(2)` 与 `DieOutput(8)`，并先尝试 `TryProcessPity`，否则执行模拟产出。证据：`Board.c` RVA `0x20d8eac`；`ConfigMergeBonusHandler.c` RVA `0x212d87c`；`BaseItemSpawnBonusHandler.c` RVA `0x2145ec4`；`ItemSpawnReason.cs`。这里只能确认处理器结构与条件，不能给出奖励内容或概率。

## 进一步核对：持久化边界

`MainMergeMan` 的 `FillData/SetData` 通过 `MergeWorld.Serialize/Deserialize` 保存和恢复主棋盘；多个活动棋盘也复用同一套世界序列化入口。物品协议 `MergeItem` 保存实例身份、类型、状态、位置及组件数据；点击源额外保存充能、输出、冷却、随机种子/下标和加成计数，自动源保存输出次数、时间及随机状态。证据：`native_direct_calls.csv` 中 `MainMergeMan → MergeWorld` 的调用，以及 `ComClickSource.cs`、`ComAutoSource.cs`、`MergeItem.cs`。可确认**保存入口和字段结构**；实际写盘时机、服务端权威性及迁移逻辑未在本节确定。

## 人工重述的默认合成流程（非原始代码）

```text
动作 = CheckDragBehaviour(落点, 被拖物品)
如果动作 == Merge:
    如果 GetMergeState(源, 目标) != CanMerge: 结束
    结果tid = 目标.MergeComponent.PeekMergeResult(源.MergeComponent)
    如果 结果tid <= 0: 结束
    位置 = 目标.coord
    销毁源与目标实例，并执行消耗后处理
    新物品 = 在位置生成(结果tid, reason=Merge)
    执行生成奖励处理、新物品全部组件的 OnPostMerge、合成奖励处理器
    检查新物品上下左右的邻接解锁
    发送 onItemMerge(源, 目标, 新物品)
```

此流程对 `Board.Merge` 的主成功路径做了人工重述，省略了异常、日志、委托细节和 IFix 替换路径；不应拿它替代保存的原生反汇编或伪 C。

## 配置核验补充（只记录线索，不保存配置表）

后续从此前临时拆包区的 `assets/lua/gen/*.bytes` 验证了配置格式，未把任何密文或完整明文配置放进本结果目录。原生代码 `ProtoFileUtility.Decrypt`（RVA `0x24337c8`）调用 `CenturyGame.Framework.ConfigData.ConfigHelper.GetDecryptTable`（RVA `0x2c8fd54`）：识别 `$CGF$10` 头，使用 `Constant.kUserLengthLength1`（静态初始化 RVA `0x2434120`，16 字节材料位于 metadata 偏移 `0xBC4230`）派生密钥，再以小端 32 位字和 XXTEA 处理内容。对应转换/解密函数 RVA 为 `0x2c72544`、`0x2c72674`、`0x2c72740`。密钥派生中使用 16 字节材料的十六进制小写文本，去掉分隔符后取前 16 字节；以表尾明文长度约束和 protobuf 字段边界核对了该过程。**这些是安装包中的解密实现和人工复核结果，不是游戏玩法源代码。**

以不落盘的方式核验名称含 `Merge` 的 50 个配置表，50 个都通过解密后的长度与 protobuf 字段遍历；其中 `ObjMergeItemConf` 为 6,052 个 map 条目，`MergeItemCategoryConf` 为 1,350 个，`MergeBoardConf` 为 67 个，`MergeItemSeriesConf` 为 9 个。`MergeItemCategory.Progress` 是有序物品 ID 列表：1,350 个条目均有该字段，长度为 1–15，非空列表平均约 4.26 个 ID。作为可复核的小例子，类别 `25_0` 的 `Progress` 是从 `12000107` 到 `12000121` 的 15 个连续 ID；这与 `ItemUtility.GetNextItem` 按当前位置取下一个 ID 的默认逻辑相吻合。**这说明升级关系由配置驱动；不能仅凭例子推断所有链都连续编号。**

`MergeBoardConf` 的主棋盘 `Id=1` 有 7 列、每列 9 个格位，配置中的列数/行数也分别是 7/9。它说明本包主棋盘基础尺寸为 **7×9**；运行时云、锁定、活动覆盖及配置更新可能改变实际可用格。`MergeItemSeriesConf` 明文 SHA-256 为 `182152483436005514d48d7b9064997582dccee837d2abcadec314b3daf526fc`（仅作复核标识；不保存明文资源）。

此核验消除了“升级链表完全不可读”的旧限制，但不代表活动热更新、服务端配置或 IFix 覆盖已经纳入。原始类/方法实现的真实性界限与前文一致。
